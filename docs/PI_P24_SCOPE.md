# P2.4 scope — every site that still assumes one runtime per session

Produced by a 55-agent audit of six surfaces (API session, auth/credential,
proxy, lifecycle, SDK, DB/tests): 49 candidate sites, 28 confirmed, 21
dismissed. Each was independently verified against the code before landing
here; the dismissed ones were claims that did not survive that check.

**Read this before calling P2.4 done.** The storage split — `session_environments`
as its own table, one environment per session, the credential decision — landed
in P1.7. What did NOT land is every CONSUMER that still assumes a session has
exactly one runtime. That is the "wide, mechanical, unglamorous refactor" the
architecture doc predicted, and it is still ahead of us.

## The findings in full

### 1. [design-needed] `apps/api/src/billing/services/compute-invariant-sweep.ts:103`

**reconcileOrphanComputeSessions / selectOpenComputeInvariantCandidates — the billing invariant sweep joins session_sandboxes, app_runtimes and project_monitor_boxes, but NOT session_environments**

An environment's compute window is opened at session-environment.ts:355 with sandboxId = environmentId (a fresh randomUUID) and NO workloadType, so compute-metering.ts:177 defaults it to 'session'. In the sweep, isApp/isMonitor are false, so runtimeStatus = row.sbStatus and externalId = row.sessionExternalId — both NULL, because environmentId has no session_sandboxes row. decideComputeClose (compute-close-policy.ts:90) hits `!sandboxStatus || !hasProviderTarget` on the very first DB-only rule and returns 'sandbox-row-missing'. maintenance.ts:261 runs this every 5 min (DEFAULT_MAINTENANCE_INTERVAL_MS), so every pi environment's meter is closed within ~5 minutes of opening while the box runs for hours. This is the exact failure the monitor-box join was added to prevent — the comment at lines 72-76 spells it out ("without it every open monitor window reads as sandbox-row-missing and this sweep would close the meter on a healthy, running box on its very first pass") — and the environment has the identical shape. Net effect: a pi session's compute is billed for minutes instead of hours, and during the window before the sweep closes it, countBillingInvariantViolations (line 322: workloadType NOT IN ('app','monitor') AND sessionSandboxes.status IS NULL) counts every live environment as a violation and maintenance.ts:503 logs BILLING INVARIANT VIOLATED.

*Verification:* CONFIRMED — every link verified in code, and both "already copes" hypotheses are refuted.

CHAIN (all four cited line numbers are exact):
1. session-environment.ts:355 (provision) and :269 (resume) both call startComputeSession({sandboxId: environmentId}) where environmentId = randomUUID(), with NO workloadType.
2. compute-metering.ts:177 `workloadType: opts.workloadType ?? 'session'` -> 'session'. Stronger than the claim: the CHECK at packages/db/src/schema/kortix.ts:3701 only allows ('session','app','monitor'), so 'environment' is not even representable — not a caller oversight.
3. Sweep lines 150-174: isApp/isMonitor false -> runtimeStatus = row.sbStatus, externalId = row.sessionExternalId.
4. compute-close-policy.ts:90 `if (!input.sandboxStatus || !input.hasProviderTarget) return db_('sandbox-row-missing')` is the FIRST DB-only rule, no grace, fires on pass one. maintenance.ts runs reconcileOrphanComputeSessions every 5 min (const n = 5*60*1000).

WHY IT DOES NOT COPE:
- "Resolves by session id, worker row is the right answer": NO. The join at compute-invariant-sweep.ts:103 is sessionSandboxes.sandboxId = sandboxComputeSessions.sandboxId — keyed on sandboxId, NOT sessionId. The compute row's sessionId column is never joined, so the worker's session_sandboxes row is structurally unreachable for the environment's compute row.
- "Tracked separately": NO. grep over apps/api/src/billing/ finds ZERO references to sessionEnvironments/session_environments. Schema comment (kortix.ts:2020) says session_environments is "A separate table, not a second row in session_sandboxes", and session_sandboxes.session_id is UNIQUE — the single row per session is the WORKER. No session_sandboxes row can have sandbox_id = environmentId (a fresh randomUUID).
- Path is live: apps/api/src/projects/routes/session-environment.ts:165 calls ensureSessionEnvironment.
- countBillingInvariantViolations (line 322-323) arm `workloadType NOT IN ('app','monitor') AND sessionSandboxes.status IS NULL` matches every live environment -> BILLING INVARIANT VIOLATED logged.

TWO POINTS BEYOND THE CLAIM:
- Worse than "minutes instead of hours": ensureSessionEnvironment:182 early-returns on an 'active' env row without calling startComputeSession, so once the sweep closes the meter it NEVER reopens for that box's remaining running life (only a stop->resume reopens it), while autoStopInterval:60 refreshed by use keeps a worked-on box alive for hours.
- Nothing stamps lastAliveAt for environments (stampers exist only in projects/reaping/sandbox-state-sync.ts for session boxes and projects/lib/monitor-box.ts for monitor boxes), so the billed window is additionally clamped to startedAt + livenessGraceMs.

Introduced by commit ecb7308f "feat(pi): meter the session environment against its parent session", whose own inline comment concedes the premise: "it has no session_sandboxes row, which is what every billing join keys on".

EFFORT = design-needed, not a one-line join: (a) workload_type CHECK must be extended to 'environment' via a Drizzle-generated migration; (b) the sweep needs a fourth leftJoin on session_environments plus isEnvironment branches in all five ternaries (status/updatedAt/metadata/provider/externalId), noting session_environments uses the same session_sandbox_status enum so 'active' maps directly rather than through nonSessionRuntimeBillingStatus; (c) both countBillingInvariantViolations and countStaleLivenessWindows need matching arms; (d) crucially, a join alone only trades 'sandbox-row-missing' for 'beyond-liveness-ceiling' once past the grace — an observer must stamp lastAliveAt for environments the way monitor-box.ts does for monitor boxes (the `monitor_observed` counter exists precisely for that failure mode).

### 2. [mechanical] `apps/api/src/projects/reaping/stop-box.ts:163`

**stopExpiredBox → applyStoppedState — the idle/deadline reaper's stop path never touches the environment**

stopSessionEnvironment is called from exactly one place, stop.ts:129 (the manual user Stop). The dominant stop path — deadline_expired via box-reaper.ts:631 → stopExpiredBox, and provider_reconcile via box-reaper.ts:661 — stops only the worker box and writes only session_sandboxes. After a pi session's worker is reaped for idleness the environment box keeps running, billed to nobody (see finding 1), until Daytona's own autoStopInterval: 60 (session-environment.ts:340) powers it off up to 60 minutes later — and nothing writes 'stopped' to the session_environments row, so it still claims 'active' over a dead box.

*Verification:* Real, and it breaks precisely because of the second sandbox. applyStoppedState (sandbox-state-sync.ts:222), the single stop writer both reaper paths use, is keyed entirely on the worker: it writes session_sandboxes by write.sandboxId, project_sessions by write.sessionId, and pauses compute by write.sandboxId. The environment lives in session_environments and its compute row is keyed by metadata.environmentId (a separate randomUUID minted in provisionEnvironment), so neither the box stop nor the meter close reaches it. A repo-wide grep for sessionEnvironments confirms the only writer of status='stopped' is stopSessionEnvironment, whose callers are stop.ts:129 and the explicit POST /environment/stop route (routes/session-environment.ts:232) — the claim's "exactly one place" is off by that second, also-manual, call site; the substance holds. The provider webhook can't cover it either: reconcileSandboxStoppedByExternalId keys on session_sandboxes.externalId and an environment has no row there. autoStopInterval:60 is minutes (daytonaLifecycle, providers/daytona.ts:157), against a 15-minute worker idle window, so the env outlives its reaped worker by up to ~60 minutes of running compute that the liveness clamp stops billing after startedAt+60min grace (nothing calls markComputeSessionAlive for an env row). The stale 'active' row is the sharper break, not cosmetic: ensureSessionEnvironment returns at line 182 on status==='active' && externalId BEFORE claimEnvironmentWork, and that claim only re-takes 'error'/'stopped'/stale-'provisioning'. So once Daytona powers the box off behind an 'active' row, no path can resume it — the worker's attach loop (lazy-env.ts:152) re-ensures every 2s, gets 'active' forever, and dies on the 180s budget for every compute tool call. It does not self-heal: orphan-boxes.ts:132 puts active/provisioning env rows in the keepSet (pinning the box out of that sweep), and orphan-environments.ts only clears it at a 24h horizon off lastUsedAt, which is stamped solely at provision/resume — never on a plain ensure, contrary to the comment at orphan-boxes.ts:133.

### 3. [mechanical] `apps/api/src/platform/services/session-environment.ts:182`

**ensureSessionEnvironment — short-circuits on status 'active' with no liveness check, and no path ever reconciles that status**

`if (existing?.status === 'active' && existing.externalId) return withPreview(existing)` trusts the row. The only writers of 'stopped' are stopSessionEnvironment (line 422, manual Stop only) and markEnvironmentError; reconcileSandboxStoppedByExternalId (sandbox-state-sync.ts:366-375) selects from session_sandboxes only, so it never matches an environment's externalId. The box's own autoStopInterval: 60 (line 340) therefore stops it while the row still reads 'active'. claimEnvironmentWork (line 236) re-claims only 'error', 'stopped', or a stale 'provisioning' row — never 'active' — so no ensure ever resumes it. The worker's next compute tool call gets 200 + status 'active' with a preview URL that connection-refuses (or previewUrl null after the catch at line 103), polls until its 180 s budget expires, and the session is permanently unable to run bash/read/write with no recovery path short of a manual DB edit. The orphan-box reaper comment at orphan-boxes.ts:83-86 documents this exact wedge and only removed one of its causes.

*Verification:* REAL. The environment is tracked in its own table (session_environments), and that is exactly why nothing reconciles it — the "tracked separately" hypothesis makes it worse, not better.

Verified chain:
1. ensureSessionEnvironment (session-environment.ts:182) returns on `status === 'active' && externalId` with no provider probe, and without refreshing lastUsedAt.
2. claimEnvironmentWork (line 236) re-claims only 'error' | 'stopped' | stale 'provisioning'; an 'active' row is never re-claimed, so runEnvironmentWork's resume branch is unreachable while the row reads active.
3. Grepped every writer of the table: 'stopped' is written ONLY by stopSessionEnvironment (line 422), reachable only from the stop route and session-lifecycle/stop.ts:129 (explicit session stop). markEnvironmentError writes 'error' only from the provision/resume path.
4. reconcileSandboxStoppedByExternalId (sandbox-state-sync.ts:361) selects .from(sessionSandboxes).where(eq(sessionSandboxes.externalId, …)); applyStoppedState writes only session_sandboxes + project_sessions. The Daytona webhook (sandbox-webhooks.ts:102) goes through it. DaytonaProvider has no db writes at all, so an environment box has no session_sandboxes row (asserted by three separate comments) and no reconcile can match its externalId.
5. Trigger is real and self-documented: daytona.ts:145 says autoStopInterval (minutes) is "BACKSTOP only: Daytona's idle signal is 'no inbound requests' … it must sit well above the longest real turn or it kills working boxes" — platform default 720. session-environment.ts:340 overrides it to 60 on the stated theory that "a stopped box resumes on the next ensure", which is precisely what step 1 prevents.
6. Failure shape confirmed worker-side (apps/kortix-worker/src/lazy-env.ts:152-193): it breaks the ensure loop on active+preview_url then health-polls {edge}/kortix/health to a shared 180s deadline. A live preview URL to a stopped box burns the budget and throws "environment daemon never became ready"; if getPreviewLink throws (catch at line 103, previewUrl null) the loop never breaks and throws "environment status: active". Every later tool call re-attaches from scratch and gets the identical answer. bash/read/write are dead for the session.
7. orphan-boxes.ts:83-86 and session-environment.test.ts:151-153 both describe this wedge in the past tense; the keepSet fix removed only the reaper as a cause, leaving the 60-minute provider timer.

ONE CORRECTION to the claim: "no recovery path short of a manual DB edit" is overstated. reaping/orphan-environments.ts (unmentioned in the claim), scheduled from maintenance.ts:319 and enabled unless KORTIX_ENVIRONMENT_REAP_ENABLED=false, calls deleteSessionEnvironment 24h after lastUsedAt, dropping the row so the next ensure provisions fresh. Because the short-circuit never refreshes lastUsedAt, that clock runs from provision rather than from the stop. So the wedge self-heals up to 24h later — still fatal for the session in progress, and the same staleness means a continuously-used environment can be reaped out from under a live session at the 24h mark.

Fix is design-needed, not mechanical: options trade off against each other (probe provider status inside ensure on the hot path, have the worker's failed attach mark the row, add an environment lookup to the webhook/reconcile path, or raise autoStopInterval to the platform backstop), and lastUsedAt should be touched on the active path either way.

### 4. [mechanical] `apps/api/src/projects/session-lifecycle/actions.ts:95`

**deleteSession — deletes the session_environments row while a detached provision may be mid provider.create**

deleteSessionEnvironment reads the row (session-environment.ts:440-446); on a row still 'provisioning' externalId is null, so it skips the provider delete and just runs `db.delete(sessionEnvironments)` at line 461. The detached provisionEnvironment started by ensureSessionEnvironment (line 195) is still inside provider.create; it then opens a compute meter (line 355) and runs the UPDATE at lines 364-378, which now matches 0 rows. The Daytona box exists with NO row in any table: deleteSessionEnvironment can never find it, and the orphan-boxes keepSet (orphan-boxes.ts:122-140) reads session_environments, so it only catches the box after ORPHAN_BOX_GRACE_MS (1 h) and then merely STOPS it, never deletes it. One deleted-mid-provision pi session leaks a permanently undeleted Daytona box plus an open compute row.

*Verification:* REAL, with one correction. The environment IS tracked separately (session_environments) and deleteSession does call deleteSessionEnvironment, so the "resolves by session id / worker row is the right answer" cope does not apply — the break is a genuine TOCTOU on the environment row.

Concrete interleaving (all verified in the current tree; note the file was split since the claim was written — teardown is now apps/api/src/platform/services/session-environment-teardown.ts, deleteSessionEnvironment at :78, readRow :79, the `if (row.externalId)` provider-delete gate :83, `db.delete(sessionEnvironments)` :100, re-exported from session-environment.ts:392-395):
1. ensureSessionEnvironment (session-environment.ts:171) inserts the row `provisioning` with externalId NULL and fires `void runEnvironmentWork(...)` at :188.
2. deleteSession (session-lifecycle/actions.ts:95) awaits deleteSessionEnvironment. The row still reads `provisioning`/externalId NULL, so the provider delete is skipped and the row is dropped.
3. provisionEnvironment (session-environment.ts:298) finishes provider.create at :322-341 and runs the UPDATE at :357-371 — an unconditional `.update(...).where(eq(sessionId))` with NO `.returning()` and no compensation. It matches 0 rows. The Daytona box now exists with no row in any table.

Nothing can ever delete it. reapOrphanEnvironments (reaping/orphan-environments.ts) is driven by session_environments rows, so the deleted row makes it invisible. reapOrphanProviderBoxes (reaping/orphan-boxes.ts:169) is STOP-only by design, and daytona.ts listManagedRunningSandboxes lists `states: [SandboxState.STARTED]` — once stopped (autoStopInterval 60), the box drops out of that sweep permanently. daytonaLifecycle() sets autoDeleteInterval = KORTIX_SANDBOX_AUTODELETE_MINUTES = optInt(-1), i.e. never auto-delete (config.ts:630); autoArchive 720 just moves it to cold storage. managedSandboxLabels() carries no session id, so nothing can re-associate it.

Decisive corroboration: the WORKER box path already fixes this exact interleaving and the environment path does not. session-sandbox.ts:951-988 does a conditional finish — `.where(and(eq(sandboxId), ne(status,'archived'))).returning()`, and on an empty result logs "was deleted mid-provision" and calls provider.remove(). session-sandbox.test.ts:1-12 documents the scenario verbatim. provisionEnvironment is the same detached-provision shape with none of that guard. The same hole exists on the resume branch (runEnvironmentWork :272-275).

The window is WIDER than the claim states: provisionEnvironment awaits ensureSandboxImage inside the same Promise.all before provider.create, so a `provisioning` row can sit for minutes before the box even exists.

CORRECTION to the claim: the compute row does NOT stay open. reconcileOrphanComputeSessions (billing/services/compute-invariant-sweep.ts:131) sweeps every open row; the environment row defaults to workloadType 'session' (compute-metering.ts:179) with sandboxId = environmentId and no session_sandboxes row, so decideComputeClose returns 'sandbox-row-missing' (compute-close-policy.ts:88) and pauseComputeSession closes it on the next maintenance pass (maintenance.ts:263). billableWindowEnd also clamps the bill to lastAliveAt + grace. So the billing half is bounded to roughly one sweep interval, not permanent. (Separately worth noting: that same join closes an environment's compute window even in the happy path — environment metering is effectively defeated by the invariant sweep.)

Net: one deleted-mid-provision pi session leaks a Daytona box that no code path in the repo can ever delete. The billing half of the claim is overstated.

### 5. [design-needed] `apps/api/src/platform/services/sandbox-egress-pin.ts:83`

**pinSandboxEgressIp() - first-write-wins, keyed on session_sandboxes.sandboxId, never cleared**

Line 92 returns early when a pin already exists, and nothing anywhere clears EGRESS_IP_KEY (the constant has exactly three references: definition, this write, the read at :122). The environment has no session_sandboxes row of its own (session-environment.ts:335), so its IP can only land in the worker's slot, once. Failure: the environment box errors, the row goes to 'error', the next ensure re-claims it (session-environment.ts:236) and provisionEnvironment calls provider.create() for a BRAND NEW Daytona box (session-environment.ts:329) with a new egress IP. The stale pin cannot be overwritten, so every /broker and /relay call from the live environment - the only box where bash and the egress shim run - returns 403 sandbox_egress_mismatch for the remaining life of the session. Every network-boundary secret is dead, and the only recovery is flipping the global KORTIX_SANDBOX_EGRESS_PIN_ENFORCED kill switch for all tenants.

*Verification:* CONFIRMED, with a correction to the stated trigger. Mechanism verified: (1) the pin is write-once and never cleared — `egress_ip` has one definition, one write (sandbox-egress-pin.ts:95) and one read (:122) repo-wide, and all 45 `update(sessionSandboxes)` sites merge metadata (jsonb ||, mergeMetadata, spread), including prepareInPlaceRestartMetadata (readiness-clocks.ts:58) which deletes only runtime-wake keys, so even a session restart preserves it. (2) There is exactly one pin slot per session: session_sandboxes.sandboxId === sessionId (session-sandbox.ts:425-430, unique on sessionId) and auth sets c.set('sandboxId', patResult.sessionId) (middleware/auth.ts:285,611). (3) The environment box holds the session's own service key as KORTIX_TOKEN (session-environment.ts:110-124,336), so its boot-timeline relay authenticates AS the session, passes the scope join at boot-timeline.ts:73-90, and pins into the worker's row. (4) The worker never pins: only the sandbox-agent-server daemon posts /platform/boot-timeline, and the pi worker image is node:22-alpine + three scripts (build-context.ts:585-598) with no daemon — grepping `boot-timeline` outside apps/api and kortix-sandbox-agent-server yields only apps/web audit tables. So the environment box is the ONLY pinner and the pin is the FIRST environment's IP. (5) The environment is also the only caller of the gated routes: startEgressShim() runs unconditionally at daemon boot (kortix-sandbox-agent-server/src/main.ts:191) with config.token = KORTIX_TOKEN and hits /secrets/{id}/relay and /secrets/{id}/broker, both gated (secret-broker.ts:74-93, secret-relay.ts:367-385) with KORTIX_SANDBOX_EGRESS_PIN_ENFORCED defaulting to true (optBoolTrue, config.ts:71-75).

CORRECTION to the claim's trigger: on error, markEnvironmentError keeps externalId, so the next ensure RESUMES the same box (session-environment.ts:254) rather than calling provider.create(). provisionEnvironment is only reached when externalId is null. The clean, ordinary path to a new box is the reaper: sessionEnvironments.lastUsedAt is written ONLY at provision (:368) and resume (:274) — nothing touches it during use, because worker↔environment RPC goes over the provider edge and bypasses the control plane by design (kortix-worker/src/lazy-env.ts:1-10). reapOrphanEnvironments (wired at projects/maintenance.ts:319) deletes the row of a LIVE, non-deleted session once lastUsedAt is >24h old (orphan-environments.ts:81-82) via deleteSessionEnvironment → db.delete(sessionEnvironments) (session-environment-teardown.ts:100). session_sandboxes and its pin survive untouched. The next compute tool call inserts a fresh row → provisionEnvironment → a brand-new Daytona box with a new egress IP (the module header itself measures 67.213.121.131 vs 67.213.113.135 for two boxes). Its boot-timeline relay hits line 92 and is discarded, so every /broker and /relay call from the only box running bash and the shim returns 403 sandbox_egress_mismatch for the rest of the session, recoverable only via the global KORTIX_SANDBOX_EGRESS_PIN_ENFORCED=false kill switch. The claim's own path is also reachable but narrower: if provider.create() succeeds and startComputeSession (:348) throws before the externalId update at :357, the orphan box boots and pins while the row keeps externalId null, so the next ensure does provision a genuinely new box.

design-needed: the fix cannot be last-write-wins — the whole point of the boot-time first-write-wins pin is that a later caller must not be able to move it. It needs an ownership decision (pin keyed per environment box rather than per session, or an explicit authoritative clear when the environment row is deleted/re-provisioned, or teaching the verify path that the session may legitimately have a second egress identity).

### 6. [design-needed] `apps/api/src/middleware/session-sandbox-credential.ts:15`

**isSessionSandboxCredential() - true for ANY holder of the session PAT, and both boxes hold it**

The environment is provisioned with KORTIX_TOKEN = the session's own service key (session-environment.ts:343, read by sessionServiceKey at :117-131), and auth.ts:72 sets sandboxId = sessionId for a session-scoped PAT. So sessionId === sandboxId holds for the environment too and this returns true. Every route that means 'only the session's own single sandbox may do this' now admits two boxes and cannot tell them apart.
