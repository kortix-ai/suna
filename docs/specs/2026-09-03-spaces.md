## 1. Problem

A Kortix project is one repo, one agent roster, one flat session list. People
run many unrelated efforts inside one project (a client, a campaign, a
research thread) and today they cannot group sessions under a named effort,
give that effort standing instructions and reference files the agent always
sees, attach scheduled work to it, or share it with specific members/groups
while the rest of the project stays untouched. ChatGPT/Claude "Projects" solve
this inside one workspace. We call the equivalent a **space**.

## 2. Definition

A space is a **named container inside a project**: it groups sessions,
gives the agent standing context, owns scheduled work, and is an IAM object
granted to members/groups exactly like an agent. The manifest is the source of
truth; the database holds only the session join and the grants.

| What                          | Where                                                               |
| ----------------------------- | ------------------------------------------------------------------- |
| Identity, name, description   | `kortix.yaml` → `spaces.<slug>`                                |
| Instructions (inline text)    | `kortix.yaml` → `spaces.<slug>.instructions`                   |
| Context (repo paths)          | `kortix.yaml` → `spaces.<slug>.context[]`                      |
| Default agent                 | `kortix.yaml` → `spaces.<slug>.agent`                          |
| Session visibility mode       | `kortix.yaml` → `spaces.<slug>.sessions` (`private`\|`shared`) |
| Scheduled work                | `kortix.yaml` → `triggers[].space: <slug>`                     |
| Sessions in it                | `kortix.project_sessions.space` (text, nullable)               |
| Who may use it                | `kortix.role_assignments` object grants, `object_type='space'` |
| Unscoped default for members  | `kortix.object_policies` row `space = closed`                  |

Decisions (approved):

- `instructions` is **inline** markdown, delivered to the sandbox by env and
  rendered by the daemon into an OpenCode `instructions` file (§7).
- `context` entries are repo-relative paths. Text files are handed to OpenCode
  `instructions` (inlined natively); directories are listed for the agent to
  read. UI uploads commit to `.kortix/spaces/<slug>/`.
- `agent` is a **default, not a binding**; a space grant does **not**
  imply the agent grant (the person needs both; the grant dialog offers both).
- Scheduled work = `triggers[].space` back-reference; the scheduler is
  unchanged.
- No `enabled` flag (delete the block instead), no nesting, no moving a
  session between spaces, no per-space memory, no feature flag.
- Create/edit/delete need `project.customize.write` (the manifest-editing
  leaf, manager tier).
- Session visibility: `sessions: private` (default) keeps the ordinary model
  (a session is its creator's unless shared); `sessions: shared` makes every
  session in the space readable by everyone granted the space. The
  space page's share control flips it.

**Naming note.** The unmerged `crafts-store-ui` branch renamed its marketplace
"crafts" to "spaces". It is not on `main`; this spec owns the word on
`main`, and that branch must be renamed back if it is ever merged.

## 3. Manifest (`packages/manifest-schema`) — DONE (foundation commit)

```yaml
spaces:
  marketing:
    name: Marketing              # optional, defaults to slug
    description: Campaign work.  # optional
    instructions: |              # optional inline markdown
      Always write in British English.
    context:                     # optional repo-relative paths (file, or dir/)
      - docs/brand.md
      - .kortix/spaces/marketing/
    agent: writer                # optional; must name a declared agent
    sessions: private            # optional; private (default) | shared

triggers:
  - slug: weekly
    type: cron
    cron: "0 0 9 * * 1"
    prompt: Draft the weekly update.
    space: marketing        # optional; must name a declared space
```

Rules (`index.v2.ts`; tests `__tests__/spaces.v2.test.ts`; JSON schemas
regenerated in `apps/web/public/schema/`): slug matches `SLUG_RE`; block is a
table; unknown keys are errors; `agent` must be a key of `agents:`; `sessions`
∈ {`private`,`shared`}; `name`/`description`/`instructions` strings;
`context[]` entries non-empty, not absolute, no `..`; `triggers[].space`
must name a declared space. v1 manifests ignore `spaces`.

Exports: `SpaceBlockV2`, `SpaceSessionsModeV2`,
`SPACE_SESSIONS_MODES_V2`, `validateSpacesV2`,

## 5. Authorization — identical to agents

The IAM engine is generic over `object_type`; `objectUsable` /
`filterAccessibleObjects` / `loadObjectGrants` need no change.

| File | Change |
| --- | --- |
| `apps/api/src/iam/catalog.ts` | `ObjectType` `+ 'space'`. |
| `apps/api/src/iam/resource-grants.ts` | `RESOURCE_GRANT_TYPES`, `CREATABLE_RESOURCE_GRANT_TYPES` `+ 'space'`; `hasAnyResourceGrants` also loads `space`. |
| `apps/api/src/projects/git/types.ts`, `git/config.ts` | `ProjectConfigSummary.spaces: Array<{slug,name,description,agent,sessions,context,has_instructions}>` from the manifest. |
| `apps/api/src/projects/lib/project-resources.ts` | `ProjectResources.spaces`; `projectHasResource(config,'space',slug)`; `filterConfigResourcesForUser` narrows `config.spaces`. |
| `apps/api/src/projects/routes/resource-grants.ts` | GET returns `resources.spaces: [{id,name,description}]`; POST accepts `resource_type:'space'` (error text `resource_type must be agent or space`); orphan check covers it. |

Semantics (unchanged engine): **manager tier** (owner/admin/project
manager/service account/super-admin) sees every space; **member tier**
sees only spaces with a grant row naming them or one of their groups —
zero rows ⇒ zero spaces. Grants come from the two existing generic
surfaces: `POST /projects/:id/resource-grants` and `POST /iam/assignments
{roleKey:'agent-user', scope:{type:'project',id}, object:{type:'space',id:<slug>}}`.
Deleting a space leaves grant rows orphaned (flagged `orphaned:true`).

Enforcement points (new code, all server-side):

1. **Session create** (`routes/project-sessions.ts` + `lib/sessions.ts
   createProjectSession`): `space` in body ⇒ must be declared (`400
   SPACE_NOT_DECLARED`) and accessible via
   `filterAccessibleObjects(actor, pid, 'space', [slug])` (`403
   space_not_accessible`, body `{error, code, accessible_spaces}`).
   When the body names no `agent_name`, the space's `agent` is the
   requested agent; the ordinary agent gate then runs on it.
2. **Session inventory** (`lib/session-inventory.ts` `selectSessionRowsForViewer`
   + `lib/session-list.ts`): a row with `space` set and not in the
   viewer's accessible set is dropped in both scopes. With
   `sessions: shared`, a row in an accessible space is `canAccess: true`
   for the viewer regardless of its own visibility (lifecycle rights
   unchanged). The inventory reads the manifest's space map once
   (`loadProjectSpaces`) only when some row carries a space. New
   query `?space=<slug>` filters to that space; `?space=`
   (empty string) filters to rows with none.
3. **Read-by-id and every lifecycle verb** (`lib/access.ts
   loadVisibleSession`): same two rules ⇒ `404` when inaccessible.
4. **Space routes** (§6): list filtered by the fold; get on an
   inaccessible one `404`; writes need `project.customize.write`.
5. **Trigger fire** (`fireGitTrigger`): the fired session inherits
   `spec.space` (no per-fire check; the trigger actor is manager tier).
6. **Warm sessions**: never adopted for a space start (web skips
   `takeWarmSessionEntry`; server refuses a warm claim/prime body carrying
   `space` ⇒ `400`).

## 6. API (`apps/api`)

New: `apps/api/src/projects/spaces.ts` (`SpaceSpec`,
`extractSpaces(manifest)`, `loadProjectSpaces(project)`,
`upsertSpaceInManifest`, `removeSpaceFromManifest`,
`stripSpaceFromTriggers`), `apps/api/src/projects/lib/space-access.ts`
(`accessibleSpaceSlugs(c, loaded, projectId, slugs)`,
`assertSpaceAccessible(...)`), `apps/api/src/projects/routes/spaces.ts`
(registered in `projects/index.ts`).

Wire shape (`SpaceSchema` in `packages/api-contract/src/index.ts`):

```json
{
  "slug": "marketing",
  "name": "Marketing",
  "description": "Campaign work.",
  "instructions": "Always write in British English.\n",
  "context": ["docs/brand.md", ".kortix/spaces/marketing/"],
  "agent": "writer",
  "sessions": "private",
  "path": "kortix.yaml#spaces.marketing",
  "session_count": 4,
  "trigger_count": 1,
  "can_manage": true
}
```

`description`, `instructions`, `agent` are `string | null`; `context` always an
array; `sessions` always present (default `private`).

| Route | Gate | Behavior |
| --- | --- | --- |
| `GET /v1/projects/:id/spaces` | `loadProjectForUser(read)` + `project.read` | `{spaces: Space[], errors: [{slug,path,error}]}`, filtered to the caller's accessible set, sorted by slug. `session_count` counts non-deleted rows the caller can see. |
| `POST /v1/projects/:id/spaces` | `manage` + `project.customize.write` | body `{slug?, name (required), description?, instructions?, context?, agent?, sessions?}`; slug via `slugify(name)` when omitted; invalid slug `400`; duplicate `409`; unknown `agent` `400`; bad `sessions`/`context` `400`; commits `kortix.yaml` (`feat(spaces): add <slug>`); `201` Space. |
| `GET /v1/projects/:id/spaces/:slug` | `read` + `project.read` | `404` when undeclared or inaccessible. |
| `PATCH /v1/projects/:id/spaces/:slug` | `manage` + `project.customize.write` | partial merge of the same fields (slug immutable, `null` clears an optional field); `{}` → `200` without a commit. |
| `DELETE /v1/projects/:id/spaces/:slug` | `manage` + `project.customize.write` | removes the block, strips `space:` from triggers naming it, one commit; session rows keep their column (managers still see them, members lose them). `404` unknown. |
| `POST /v1/projects/:id/spaces/:slug/context` | `manage` + `project.customize.write` | body `{path, content}` (UTF-8 text ≤ 256 KB) — commits `.kortix/spaces/<slug>/<basename(path)>` via `commitRepoFile`, then appends it to `context[]` (manifest commit). Returns the Space. |
| `DELETE /v1/projects/:id/spaces/:slug/context?path=` | same | removes the entry from `context[]` only; never deletes repo files. `404` when the path is not listed. |

Existing routes extended:

- `POST /projects/:id/sessions` body `+ space?: string`
  (`SessionCreateInputSchema`); response `Session.space: string | null`
  (`SessionSchema`, `serializeSession`, also on the warm/claim serializations).
- `GET /projects/:id/sessions?space=` (§5.2).
- Triggers: `GitTriggerSpec.space: string | null`; `parseTriggerEntry`
  reads it; `triggerSpecToTomlEntry` emits it only when set (after `agent`);
  `TriggerDraft`/`parseTriggerDraft` accept `space` (`null`/`''` clears);
  the POST/PATCH trigger routes validate it against the manifest (`400`);
  `specToBody`, `draftToSpec`, `loadTriggersForResponse` carry it. Round-trip
  test: PATCH of an unrelated field keeps `space`.
- `GET /projects/:id/detail` → `config.spaces` (access-filtered).

Every error is `{error, code?}`. Codes: `SPACE_NOT_DECLARED`,
`space_not_accessible`, `SPACE_SLUG_TAKEN`.

## 7. Runtime

`session-runtime-env.ts` `buildSessionRuntimeEnv` gains
`space?: SpaceEnvelope | null` and emits
`KORTIX_SPACE=<slug>` and `KORTIX_SPACE_CONTEXT=<json>` —
`{version:1, slug, name, description, instructions, context:[...], sessions}`
(instructions truncated at 32 KB with `\n…[truncated]`; whole JSON ≤ 64 KB).
Both names join `SERVER_OWNED_ENV_NAMES` (`session-runtime-context.ts`).
`buildSessionSandboxEnvVars` takes `space`; its three callers
(`lib/sessions.ts` create, `sandbox-env-sync.ts`, `session-reload.ts`) resolve
it from the session row's `space` + `loadProjectSpaces`.

`compile-agent-config.ts`: `resolveCompiledAgentConfigForSession` and
`resolveSelectedAgentConfigForSession` accept `{space?: string | null}`
and, when set and declared, emit top-level `instructions: string[]` = the
space's `context` entries (a `dir/` entry becomes `dir/**/*.md`). Agent
`prompt` is never touched (it replaces OpenCode's default system prompt).

Daemon `apps/kortix-sandbox-agent-server/src/space.ts` mirrors
`secret-capabilities.ts`: `renderSpaceInstruction(env)` →
`writeSpaceInstruction(env)` writes `/tmp/kortix/space.md`:

```
# Space: <name>

<description>

## Instructions

<instructions>

## Context

Read these before answering:
- `docs/brand.md`
- `.kortix/spaces/marketing/`

Sessions you start with `kortix sessions new` inherit this space unless you pass `--space`.
```

`buildOpencodeConfigContent` appends that path to `instructions` exactly like
`secretCapabilitiesInstructionPath`; `writeKortixOpencodeConfig` and its caller
in `main.ts` thread the new option. The daemon ships from the API image via
runtime-assets (no separate release).
