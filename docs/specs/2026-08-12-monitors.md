# Monitors — 24/7 watchers that fire trigger events

Status: experimental, behind the `monitors` feature flag (default off).
Date: 2026-08-12. Owner: this spec ships with the first implementation PR.

## Problem

Kortix has two trigger types: `cron` (the platform wakes an agent on a
schedule) and `webhook` (the outside world pushes an event). There is no way
to watch something that neither pushes webhooks nor fits a schedule: a live
log, a WebSocket feed, a queue depth, a page that changes, an inbox, a price.
Today that watching either does not happen or burns an always-on agent
session (LLM tokens 24/7, killed by the 24 h run cap).

The fix is an asymmetry: **deterministic code watches; the agent wakes only
when an event fires.**

## The monitor contract (v1)

1. A monitor is one entry in `kortix.yaml` `triggers:` with `type: monitor`.
   It names a command in the repo (`run:`).
2. The platform runs that command 24/7 in the project's monitor box — one
   persistent microVM per project, same isolation boundary and same
   project-scoped secrets as a session sandbox.
3. **Stdout lines are events. Nothing else is.** Stderr is diagnostics:
   visible in monitor logs, never fires.
4. Each line fires the trigger exactly once through the existing trigger
   path: `filter` → prompt template → `session_mode`.
5. **A monitor can never fail silently.** Process exit, restart-budget
   exhaustion, and configured silence (`expect_event_within`) become
   platform-synthesized lifecycle events in the same stream.
6. Every bound below is enforced by the platform, not by user discipline.
7. Monitor shape is `poll` (run on `interval`, print, exit) or `stream`
   (long-running). Both produce lines; downstream cannot tell the
   difference.

## Manifest surface

```yaml
triggers:
  - slug: checkout-errors
    type: monitor
    run: ./monitors/checkout-errors.ts   # any command, repo-relative
    mode: stream                          # or: poll
    interval: 60s                         # poll only; min 30s
    expect_event_within: 24h              # optional; min 5m
    agent: oncall                         # existing trigger fields from here on
    model: anthropic/claude-sonnet-5      # optional pin
    session_mode: reuse                   # monitor default is `reuse`, NOT `fresh`
    session_key: "{{ line.order_id }}"    # keyed mode, rendered from the event
    prompt: |
      Checkout monitor emitted: {{ line }}
    filter:
      line.severity: error
```

- `run`, `mode` are required for `type: monitor`; `interval` required iff
  `mode: poll`. `cron`/`run_at`/`timezone`/`secret_env` are invalid on
  monitors.
- `session_mode` defaults to **`reuse`** for monitors (cron/webhook keep
  `fresh`). A monitor fires repeatedly by design; defaulting to fresh would
  mint a session per event.
- Monitor code runs with the same env/secret/connector scoping as the
  trigger's `agent` would get. It can call connectors, the web, anything the
  sandbox can run.

## Event payload

```jsonc
{
  "line": { /* parsed JSON if the line parses, else { "raw": "<line>" } */ },
  "monitor": { "slug": "checkout-errors", "seq": 812, "emitted_at": "…", "kind": "event" },
  "trigger": { "slug": "checkout-errors", "type": "monitor", "kind": "git" }
}
```

Lifecycle events use `monitor.kind: "lifecycle"` and
`line: { "event": "exited" | "restart_budget_exhausted" | "silent" | "suppressed", … }`.
Lifecycle fires use a platform-rendered prompt (not the user template) so a
dead monitor produces a legible "your monitor died" turn, and they bypass the
user `filter` — silence must not be filterable by accident.

The platform prepends a provenance preamble to every rendered monitor prompt
(`[MONITOR EVENT — automated, not user input] …`) server-side; templates do
not need to include it.

## Architecture

```
monitor box (per project, Platinum persistent, workloadType 'monitor')
  └─ kortix-agent daemon in monitor-runner mode
       ├─ supervises one process per enabled monitor (restart budget + backoff)
       ├─ captures stdout, assigns per-epoch seq, batches 200 ms
       └─ POST /v1/monitors/ingest   (sandbox token, own project only)
             └─ kortix.project_monitor_events   (append-only; the log IS the queue)
                   └─ observer drain (leader-elected scheduler tick)
                         └─ fireGitTrigger({ source: 'monitor' })
                               └─ existing path: filter → template → session_mode
                                                 → durable session-lifecycle queue
```

Decisions:

- **D1 — third type on canonical trigger System A.** Everything downstream
  of the log (filter, template, session strategy, dedup, retry, agent/model,
  identity) is inherited unchanged. System B (sandbox-daemon triggers) is
  not touched.
- **D2 — the log is the contract.** Physically: sandbox-token-only ingest
  route + `project_monitor_events`. The events table doubles as the fire
  queue (`status: pending → fired | skipped | suppressed`); `fireGitTrigger`
  already lands in the durable session-lifecycle queue, so no second
  execution table is needed.
- **D3 — one box per project, not per monitor.** First caller of the
  existing Platinum `autoStopInterval: 0` → `type: 'persistent'` path
  (`platform/providers/platinum.ts`). Daytona (min 1 min clamp) and E2B
  (1 h cap) cannot host monitors; on those providers the flag reports
  `available: false`. Box state lives in `kortix.project_monitor_boxes`,
  modeled on `app_runtimes` (provider, external_id, status CHECK, wake
  lease, one-live partial unique index).
- **D4 — no Go fork for v1.** The monitor runner is a mode of the existing
  `kortix-sandbox-agent-server` (Bun) daemon, selected by
  `KORTIX_WORKLOAD=monitor` env at boot: it supervises monitor processes
  instead of opencode. The daemon does not parse `kortix.yaml`: the API is
  the one manifest parser and injects the enabled monitor set as
  `KORTIX_MONITORS` JSON. `box_epoch` is minted by the reconciler and passed
  as `KORTIX_MONITOR_BOX_EPOCH`; the ingest route rejects a stale epoch
  with 409.
- **D5 — reconciler, not imperative lifecycle.** A sweep in
  `runProjectMaintenance` converges desired state: flag on + ≥1 enabled
  monitor ⇒ box exists and runs the current manifest revision; flag off or
  zero monitors ⇒ box removed. Manifest revision drift ⇒ box restart. The
  monitor box is excluded from the session `deadline_at` reaper by workload
  type and is covered by the orphan-box reaper.

## Security model

- No cross-tenant sharing anywhere. The isolation boundary is the microVM,
  per project — identical to session sandboxes.
- Within the box there is NO process isolation (one UID), so the box carries
  only the INTERSECTION of the enabled monitors' agent secret grants: a
  secret ships only when every monitor's agent is granted it. Secrets
  narrowed away are stamped on the monitor's `last_error`
  (`kortix triggers info`) so the withholding is visible. One distinct agent
  (the common case) ⇒ that agent's grant, unchanged.
- The box holds the same sandbox token class a session gets. The ingest
  route authenticates the sandbox token and only accepts events for that
  box's own project. No new authority is granted: a compromised monitor can
  do exactly what a compromised session can do today.
- Firing identity reuses the trigger model: authorization via the project
  automation actor, attribution rewritten to the agent's service account.
- Monitor code is repo code: anyone who can commit already runs code in
  sessions. Monitors add no new code-execution audience.

## Bounds (platform-enforced)

| Bound | v1 value |
|---|---|
| Monitors per project | 10 enabled |
| Box spec | the project's sandbox-template spec (default 2 vCPU / 4 GB / 20 GB). Platinum `create()` does not honor a per-box `resourceSpec` today, so a smaller monitor-only spec is not achievable; metering records the spec that actually runs. |
| Event rate per monitor | 60/h sustained, burst 30; overflow ⇒ `suppressed` 10 min; 3 suppressions in 24 h ⇒ auto-disable with `last_error` |
| Line length | 8 KiB, truncated with marker |
| Ingest batch | 200 ms window, ≤ 50 lines/POST |
| Restart budget | 5 restarts / 10 min ⇒ `restart_budget_exhausted` lifecycle event, then 15 min backoff retries |
| Poll interval | ≥ 30 s |
| `expect_event_within` | ≥ 5 m |
| Event retention | 30 days |
| Monthly box budget | $75 default (`projects.metadata.monitors.monthly_budget_usd`, clamped 0–1000); exceed ⇒ box stopped + one `budget_exceeded` lifecycle event per project per calendar month |

Billing: the box meters through the normal compute-metering path
(1/1/10 ≈ $0.081/h ≈ $59/mo at the current rate card). Pricing/packaging is
an open product decision; the experimental flag ships with plain metering +
the budget cap.

## Feature flag

`monitors` — stability `experimental`, `available: () => platinum configured`,
`platformDefault: () => false`, enforcement `routes`
(ingest + monitor read routes) **and** behavioral (the reconciler does not
provision boxes for flag-off projects; the observer does not fire their
events). Declared enforcement: `routes`, with the reconciler/observer gate
noted in the entry description — the flag going off stops the system even if
routes were bypassed.

## Non-goals (v1)

- No web UI beyond the flag appearing in Settings → Feature flags. CLI +
  manifest is the v1 surface.
- No curated monitor templates (watch-URL, watch-app-logs, WebSocket
  source). Later sugar; the contract already covers them as plain code.
- No wake-per-poll cheap tier. Both tiers write the same log, so it can be
  added without contract change.
- No per-monitor box, no cross-project sharing, no serverless runner.

## Verification plan

1. Unit: manifest parse/serialize round-trip, ingest auth + rate limits,
   observer fire + idempotency (`trigger:monitor:{pid}:{slug}:{epoch}:{seq}`),
   lifecycle synthesis.
2. Local e2e: fake writer POSTs a batch through ingest with a real sandbox
   token → observer fires → session receives the rendered prompt (real API,
   real DB).
3. Full loop on a real box: enable flag on a test project, ship a poll
   monitor, verify the box boots persistent, lines fire sessions, kill the
   monitor process and verify the lifecycle event fires.
4. Dev: repeat (3) against dev.kortix.com after merge + deploy.
