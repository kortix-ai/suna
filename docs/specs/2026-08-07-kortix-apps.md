# Kortix Apps

Date: 2026-08-07

Status: implementation contract

## Problem

Kortix can run long-lived project sessions in Daytona, Platinum, E2B, and local
Docker sandboxes. It does not expose a durable application deployment product.
Users need one command and one SDK surface that deploys a static directory,
Docker build context, or OCI image to a stable Kortix URL.

The deployment product must keep provider details out of user configuration.
It must scale a runtime to zero, wake it on a public request, preserve a stable
URL across deployments, and retain enough state to explain every build and
runtime transition.

## Terms

- **App**: mutable product record with a stable hostname and active deployment.
- **Artifact**: immutable uploaded build context or immutable OCI source.
- **Deployment**: immutable app version built from one artifact and one spec.
- **Runtime**: one provider sandbox executing one deployment.
- **Hosting provider**: adapter that builds and runs a deployment.

The product name is **Kortix Apps**. Provider names never appear in a normal App
specification.

## Supported first-release workloads

1. Static HTML, CSS, and JavaScript directories.
2. JavaScript projects with one standard build command and static output.
3. Docker build contexts with a Dockerfile.
4. Public OCI images.

The first release supports one public HTTP port. HTTP streaming, SSE, and
WebSockets use the same port.

The first release does not include replicas, autoscaling, regions, UDP,
persistent volumes, private registry credentials, custom domains, or
background-only processes.

## Runtime contract

Each deployment image contains:

- `/kortix/bin/kortix-appd`, a static supervisor running as PID 1.
- `/kortix/bin/caddy`, a pinned static Caddy binary.
- `/kortix/config/app.json`, the non-secret normalized runtime specification.
- `/kortix/config/Caddyfile`, generated by `kortix-appd` at boot.

`kortix-appd` listens on control port `7331`. Caddy listens on ingress port
`8080`. Dynamic applications listen on their declared target port.

The target port cannot be `7331` or `8080`.

`kortix-appd` performs these operations:

1. Parse and validate the runtime specification.
2. Remove Kortix control credentials from the child environment.
3. Start the user process.
4. Start Caddy after the user process starts.
5. Poll the configured readiness path.
6. Expose authenticated health, status, and log endpoints.
7. Forward SIGTERM and SIGINT to both children.
8. Wait ten seconds, then force-kill remaining children.
9. Restart a failed user process up to three times with bounded backoff.
10. Exit when the restart budget is exhausted.

Control endpoints:

- `GET /v1/health`
- `GET /v1/status`
- `GET /v1/logs?after=<cursor>&limit=<n>`

Every control request requires `Authorization: Bearer <runtime-control-token>`.
The user process never receives that token.

Caddy owns public protocol behavior. Dynamic apps use `reverse_proxy` to
`127.0.0.1:<target-port>`. Static apps use `file_server` and an optional SPA
fallback. The Caddy admin endpoint is disabled.

The API sends `X-Kortix-App-Host` and `X-Forwarded-Proto`. Caddy replaces the
upstream `Host` and `X-Forwarded-Host` with the public hostname. It removes the
Kortix routing header before the request reaches the user process.

## Defaults

- CPU: `1`
- Memory: `2 GB`
- Disk: `10 GB`
- Idle timeout: `300 seconds`
- Minimum idle timeout: `120 seconds`
- Default readiness path: `/`
- Readiness timeout during deploy: `120 seconds`
- Maximum restarts per boot: `3`
- Monthly per-App compute safety limit: `$5`

Every value is server-configurable. Account policy can impose lower or higher
limits.

## Hostnames

Cloudflare Universal SSL does not cover `foo.apps.kortix.com`. Kortix will use
an Advanced Certificate Manager certificate containing `*.apps.kortix.com`.

One wildcard covers every environment because the environment is part of the
single left-most label:

- `prod-<slug>-<route-key>.apps.kortix.com`
- `staging-<slug>-<route-key>.apps.kortix.com`
- `dev-<slug>-<route-key>.apps.kortix.com`

The database stores `route_key`. It does not derive routing from a mutable slug.

Local development uses:

`http://<route-key>.apps.localhost:<api-port>`

The root domain and environment prefix are configuration values.

## Cloudflare routing

A dedicated `infra/cloudflare/workers/apps-router` Worker owns
`*.apps.kortix.com/*`.

The Worker:

1. Parses the environment prefix from the hostname.
2. Chooses the matching Kortix API backend.
3. Replaces any caller-supplied internal Apps headers.
4. Adds the original hostname and an HMAC edge signature.
5. Streams the request and response without buffering.
6. Preserves Cloudflare's WebSocket response property.

The API rejects edge headers with an invalid signature. Local development can
use direct host routing when `KORTIX_APPS_ALLOW_LOCAL_EDGE=true`.

## Artifact storage

Artifacts use a private Supabase Storage bucket named `app-artifacts`.

Limits:

- Compressed archive: `250 MiB`
- Extracted content: `1 GiB`
- File count: `100,000`
- Maximum individual path: `1024 bytes`

The API issues one signed upload URL. The CLI sends a SHA-256 and size during
finalization. The deployment worker verifies both values before extraction.

Extraction rejects absolute paths, parent traversal, devices, FIFOs, and
symbolic links that resolve outside the build context.

Artifacts never contain runtime secrets. Build secrets are outside the first
release.

Abandoned uploads expire after 24 hours. Unreferenced artifacts expire after 30
days.

## Deployment state machine

`queued -> validating -> building -> provisioning -> checking -> ready`

Any non-terminal state can transition to `failed` or `cancelled`.

Provider and network failures retry three times with exponential backoff.
Validation and build failures do not retry automatically.

The worker persists an event before and after each external operation. Provider
identifiers are persisted immediately after creation.

Activation uses one transaction:

1. Lock the App row.
2. Confirm the deployment still has status `ready`.
3. Set `active_deployment_id`.
4. Append `deployment.activated`.

A failed deployment never changes the active pointer.

## Cold request state machine

1. Resolve the App by route key.
2. Reject deleted or manually stopped Apps.
3. Resolve the active deployment and live runtime.
4. If running, proxy immediately.
5. If stopped, acquire a DB wake lease.
6. The lease owner calls `ensureRunning`.
7. Other requests wait on the same runtime state.
8. Poll `appd` and readiness.
9. Mark the runtime running.
10. Proxy the original request.

Provider starts are idempotent. A wake lease expires after 90 seconds.

The API maintains an activity lease while an HTTP stream or WebSocket remains
open. The idle reaper stops only runtimes whose idle deadline and activity lease
have both expired.

Manual stop sets `apps.desired_state=stopped` before stopping the runtime.
Public traffic cannot reverse that state.

## Billing and abuse controls

Apps reuse `sandbox_compute_sessions`. The table gains `workload_type` and
`app_runtime_id`. Existing session rows remain `workload_type=session`.

The lifecycle opens a compute session after provider start and closes it after
provider stop. Billing uses the persisted deployment resource specification.

Wake checks the account entitlement and the App monthly budget. A public caller
receives a generic unavailable response when the owner cannot fund a wake. The
authenticated App API returns the exact billing error.

The Cloudflare layer applies per-IP request limits. The API applies per-App wake
and concurrent-request limits. One runtime bounds provider compute cost even
under high request volume.

## SDK

The canonical surface is `kortix.project(projectId).apps`.

All types and functions are additive exports from the root package. The SDK
uses the existing authenticated fetch seam. Hosts do not implement Apps
transport.

The SDK supports browser `Blob` uploads and `Uint8Array` uploads. Directory
packing remains a CLI concern.

## CLI

Commands:

```text
kortix apps deploy [path] --slug <slug>
kortix apps deploy --image <image> --slug <slug> --port <port> --command <command>
kortix apps ls
kortix apps inspect <slug-or-id>
kortix apps deployments <slug-or-id>
kortix apps logs <slug-or-id> [--follow] [--build]
kortix apps rollback <slug-or-id> <version>
kortix apps start <slug-or-id>
kortix apps stop <slug-or-id>
kortix apps open <slug-or-id>
kortix apps rm <slug-or-id>
```

Deploy waits by default. `--no-wait` returns after queueing.

The packer applies `.gitignore`, `.dockerignore`, and `.kortixignore`. It always
excludes `.git`, `.env*`, `node_modules`, and existing archive output.

## Manifest

Manifest version 2 gains an optional `apps` map. It supplies local deployment
defaults. It is not the server control plane.

```yaml
apps:
  web:
    path: .
    type: dockerfile
    dockerfile: Dockerfile
    command: ["bun", "run", "start"]
    port: 3000
    readiness_path: /health
    idle_timeout_seconds: 300
    resources:
      cpu: 1
      memory_gb: 2
      disk_gb: 10
    env:
      NODE_ENV: production
    secrets:
      DATABASE_URL: DATABASE_URL
```

Literal environment values are stored with the deployment specification.
Secret mappings name existing project secrets. API responses never return
secret values.

## UI

Route: `/projects/:projectId/apps`.

The project sidebar lists Apps under Services. The page shows hostname, active
version, deployment state, runtime state, resource size, last request, and
monthly compute.

The detail view includes Overview, Deployments, Logs, and Settings. It supports
static archive upload, OCI deployment, rollback, start, stop, redeploy, and
delete.

The UI imports Apps operations from `@kortix/sdk`. It contains no raw Kortix API
fetches.

## Verification contract

The release is incomplete until these black-box cases pass:

1. Static directory deployment and asset requests.
2. SPA route fallback.
3. Dockerfile HTTP API with POST body, cookies, and authorization.
4. OCI deployment.
5. SSE delivery without aggregation.
6. WebSocket echo.
7. Failed readiness leaves the previous deployment live.
8. Concurrent cold requests produce one provider start.
9. Idle timeout stops the runtime.
10. The next request wakes the same runtime.
11. An open SSE or WebSocket prevents idle stop.
12. Manual stop blocks automatic wake.
13. Rollback restores the previous deployment.
14. Runtime and build logs are visible through API, SDK, CLI, and UI.
15. Compute billing opens and closes exactly once per runtime interval.
16. The App budget blocks an unfunded wake.
17. Daytona, Platinum, and E2B satisfy provider contract tests.
18. The real CLI exits zero and prints the live URL.
19. The deployed Dev hostname has a valid certificate and serves the App.
20. The Dev API health version contains the merged commit SHA.
