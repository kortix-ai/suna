# kortixd — the Kortix compute node

Status: **PROPOSED**. Author: Marko + Claude. Date: 2026-08-21.
Supersedes the runtime half of `2026-08-20-convergent-runtime.md` (which stays
correct; this generalizes it). Reopens, under a different structure, the
architecture reverted on 2026-07-30 (`ffc5fb769e`).

---

## 1. Problem

`apps/kortix-sandbox-agent-server` is a supervisor welded to one deployment
shape. Three facts define the limit:

1. **It cannot be installed.** A box exists because the API called
   `provider.create()`. The daemon receives an identity it cannot request. There
   is no registration endpoint in the codebase.
2. **It cannot be reached except through a provider.** `resolveIngress()` is
   mandatory on `SandboxProvider`. `sandbox_provider` is a closed Postgres enum
   of `daytona | platinum | e2b`. A machine outside those three is not
   expressible.
3. **It supervises exactly one harness.** OpenCode REST is hardcoded through
   4,532 lines. Driving `claude` or `codex` requires replacing that path, which
   is what failed in July.

The consequence: a laptop, an EC2 instance, a k8s pod, or a customer's bare
metal cannot be Kortix compute.

### 1.1 What already exists and works

Do not rebuild these. Generalize them.

| Asset | Where | State |
| --- | --- | --- |
| Convergence + staged swap + immutable floor | `src/runtime-assets.ts`, `apps/sandbox/entrypoint.sh` | Shipped, dev-verified 2026-08-20 (#6673, #6676) |
| Workstation enrollment and reverse relay | `packages/agent-tunnel`, `apps/api/src/tunnel` | Compatibility system to migrate after native `kortixd` parity. |
| Host services: files, find, pty, port-proxy, web-proxy, static-web | `src/routes/*`, `src/static-web.ts` | Shipped, already deployment-agnostic |
| Multi-workload boot | `KORTIX_WORKLOAD` in `src/main.ts` | Shipped. Three modes, no seam between them |

### 1.2 What was tried and reverted

2026-07-08 decided ACP-first. PR #4510 built it (four harnesses, live matrix
12/12). 2026-07-30 removed it. The stated cause, from `8953c09b2c`:

> the refactor did not add a parallel ACP path, it rewrote shared REST code

Three regressions survived with the flag off. This spec treats that sentence as
the primary design constraint. See §12.

## 2. Decision

Build **`kortixd`**: one binary that turns any machine into a Kortix compute
node.

- Concept name: **Kortix compute node**. Registry table: `kortix.compute_nodes`.
- **Two products, two binaries.** `kortix` is the platform CLI. `kortixd` is the
  standalone compute-node daemon (§2.1). The CLI installs, enrolls, and manages
  the daemon. A compute node needs `kortixd`; agent workloads may also receive
  `kortix` as a managed runtime tool.
- A node **enrolls** with a Kortix API and holds an outbound channel to it.
  kortixd *is* the relay client and the local API — not a thing beside one.
- A node **hosts one session at a time and many over its life**.
- A node **exposes the whole machine** — harnesses *and* raw capabilities
  (shell, filesystem, desktop) behind one gated registry (§7).
- **We do not care what the machine is.** The node's `type` is a declared
  property, not a branch in the code (§2.2).
- The API stays the brain: auth, models, secrets, policy, session state,
  and the convergence manifest are centralized.
- **A node degrades to standalone.** An unreachable API must not stop a running
  session (§5.5).
- **Agent Tunnel stays live during migration.** New filesystem, shell, desktop,
  enrollment, service, and relay behavior lands natively in `kortixd`. The old
  package is retired only after parity and migration verification. See §7.5.

### 2.1 Separate CLI and daemon

`kortix` installs and manages nodes. `kortixd` runs the node. They remain
separate compiled executables with separate release identities.

This boundary is deliberate:

| Binary | Responsibility |
| --- | --- |
| `kortix` | Login, select a host/account/project, install `kortixd`, enroll a node, and issue node-management commands. |
| `kortixd` | Persist node identity, converge runtimes, supervise workloads, expose host capabilities, and maintain the control channel. |

The installer can deliver both in one command. It must not simulate one binary
through symlinks or `argv[0]` dispatch. A CLI failure must not enlarge the
daemon artifact or change the node runtime. The runtime manifest therefore
keeps separate `cli` and `agent` components. The `agent` component is renamed
to `kortixd` additively after deployed compatibility is proven.

The release contains only `dist/kortixd`. New sandbox images install a temporary
`/usr/local/bin/kortix-agent` symlink for old entrypoints. Platinum fast-swap
patches both guest paths while old predecessor snapshots exist. The symlink and
second patch target are removed after fleet telemetry shows no old caller.

### 2.2 Node type is data, not a branch

A node declares what it is. Nothing downstream branches on it.

```
type      cloud-sandbox | vm | bare-metal | workstation | ci-runner
provider  daytona | platinum | e2b | null      (null = nobody allocated it)
os/arch   linux/amd64 | darwin/arm64 | …
```

`type` drives **policy and scheduling** — what work may be placed here, what
autostop means, whether a workspace is wiped between sessions — expressed as
data in the assignment decision, never as an `if (provider === 'daytona')` in a
code path. Principle P3 (§4), stated concretely.

Consequence: adding a node type is a row, not a release.

## 3. Non-goals

- Concurrent sessions on one node in P0–P3. `concurrency` is a declared node
  property from P1 so raising it is scheduling plus isolation work, never a
  re-architecture — but the isolation cost is real and enumerated in §8.2.
- Metering self-registered nodes. Deferred; `compute_nodes` is designed so
  metering is additive (§10.3).
- Replacing the OpenCode REST path. It becomes the first adapter and keeps
  its exact behavior (§12).
- ACP as the product↔daemon boundary. Out of scope. ACP may be how a specific
  adapter talks to a specific harness; it is not the node contract.
- A second language or toolchain. One Bun-compiled binary serves CLI and daemon
  (§2.1); the Go `appd` folds in at P4.

## 4. Principles

**P1 — The node manages compute; the API owns the product.** kortixd knows
processes, workspaces, ports, health, and convergence. It does not know
triggers, channels, connectors, billing, or entitlements.

**P2 — The image is a cache; the API is the truth.** Unchanged from
`2026-08-20-convergent-runtime.md`. Extended: it now governs harness binaries
too, and a node reports what it already has rather than being forced to a
uniform image.

**P3 — Nothing is a special case.** A Daytona box, an EC2 instance, and a
laptop are the same object with different `provisioning` metadata. If a code
path branches on "is this a real sandbox", the abstraction has failed.

**P4 — Additive, never substitutive.** A new adapter is added beside existing
ones. No new capability may edit the code path of a shipped one. This is the
July lesson, stated as a rule (§12).

**P5 — Degrade, do not fail.** Every dependency on the API has a defined
behavior when the API is unreachable, and none of them is "stop the session".

**P6 — Fail toward the binary that worked.** Preserved verbatim from the
convergent-runtime design: immutable floor, independent re-verification,
crash-budget rollback.

## 5. Architecture

```
                    Kortix API — control plane (centralized)
                     · node registry, enrollment, assignment
                     · auth · models · secrets · policy · session state
                     · /v1/runtime-assets manifest = convergence truth
                              ▲
             outbound channel │ node dials out, holds it open
              (+ REST for bulk transfer)
                              ▼
┌──────────────────────── kortixd ────────────────────────────────────┐
│ NODE CORE                                                            │
│  identity + enrollment · convergence · local store · control server  │
│  process supervisor · capability report · health                     │
├──────────────────────────────────────────────────────────────────────┤
│ SESSION MANAGER          one active · many over the node's lifetime  │
│  claim → prepare workspace → run → release → clean                   │
├──────────────────────────────────────────────────────────────────────┤
│ WORKLOAD ADAPTERS                                                    │
│  session(harness) · monitor · warm-seed · app                        │
│    └ HARNESS ADAPTERS — real binaries                                │
│        opencode-rest (today, unchanged) · claude-code · codex        │
├──────────────────────────────────────────────────────────────────────┤
│ HOST SERVICES            unchanged, already portable                 │
│  files · find · pty · port-proxy · web-proxy · static-web · egress   │
└──────────────────────────────────────────────────────────────────────┘
```

### 5.1 Node core

Target under 800 lines. Owns:

- **Identity.** Node id, node token, API base URL. Persisted in the node store,
  never in 74 environment variables.
- **Enrollment.** The sandbox phase accepts a short-lived provider bootstrap
  credential. Interactive workstation device-code enrollment is future scope.
- **Convergence.** `src/runtime-assets.ts`, lifted intact, generalized from a
  fixed component list to the manifest's `components` map.
- **Control server.** The existing Hono app. Two listeners: the network port
  (today's 8000) and a Unix socket for local/standalone use.
- **Supervisor.** Process trees, restart budgets, health, graceful drain.
- **Capability report.** What this machine is and has (§7.2).

### 5.2 What the node core must not contain

`git.ts` (1,454 lines), `project-env.ts`, `secret-capabilities.ts`,
`egress-shim/*`, `llm-proxy.ts`, `opencode*.ts`, `monitor-runner.ts`. These
become adapter-owned or host services. The current `main.ts` (2,760 lines) is
dismantled into the core plus three workload adapters.

### 5.3 Configuration contract

`config.ts` declares 29 keys. A source scan finds **62 `KORTIX_*` names read
directly from the environment**, plus a handful reached indirectly through
constant indirection (`env[SECRET_CAPABILITIES_ENV_NAME]`). The contract is
roughly 70 names, and today no single place states it.

- Source order: node store file → environment → CLI flags. Later wins.
- Every key is declared, typed, documented, owned, and validated at boot.
- `kortixd doctor` prints resolved config, what is missing, and why it matters.
  A failing install must say so in one screen.
- Legacy `KORTIX_*` names keep working through a declared compatibility map for
  one release. The map is a table, not scattered reads.

**Tripwire:** a test scans the source for environment reads and fails when it
finds a name the contract does not declare. This is what keeps the contract
true after the refactor, not review discipline.

#### 5.3.1 Config is LIVE, not a boot snapshot

**This is the subtlest constraint in the whole daemon, and getting it backwards
would break warm-seed forks.**

`reloadSessionEnv()` (`main.ts:720`) writes `process.env[k]` at runtime from
`/etc/pt-env`. A warm-seed fork boots with the *deriving* session's credentials
and adopts the real session's identity afterwards. So:

- A direct `process.env.X` read is **correct after adoption** — it sees the new
  value.
- A `cfg` captured at boot is **stale after adoption**.

The existing code handles this by deriving `cfg2 = loadConfig()` on adoption and
threading it explicitly (`server.reload(cfg2)`, `materializeRepo(cfg2)`,
`startSessionRuntime(…, cfg2, …)`). `routes/health.ts` goes further and reads
`/etc/pt-env` directly, because even `process.env` is wrong pre-adoption.

Therefore the config contract must **not** be a frozen module-level object.
Each declared key carries a `reload` mode:

| `reload` | Meaning |
| --- | --- |
| `boot` | Fixed for the process. Ports, paths, state dirs. Safe to snapshot. |
| `session` | Re-read on every claim/adopt. Identity, tokens, repo, prompt, LLM. |

A `session` key read from a snapshot is a bug, and the contract makes that
checkable rather than a thing to remember. Related incident: 2026-06-10, forks
answering health on `main` with the deriving session's credentials.

### 5.4 Transport

There is one runtime path: `kortixd` opens an outbound authenticated channel to
the Kortix API. Every sandbox, VM, bare-metal host, workstation, and CI runner
uses this path. Provider ingress is not part of the session contract.

The channel absorbs `apps/api/src/tunnel/core/{rpc-core,cluster-forwarder}.ts`.
It keeps the existing HMAC authentication, nonce protection, capability RPC,
heartbeat, replacement, and cross-instance forwarding behavior.

JSON-RPC request/response is insufficient for a session runtime. OpenCode uses
SSE, WebSockets, large file bodies, and requests that a caller can cancel. The
node channel therefore adds multiplexed byte streams:

| Frame | Direction | Meaning |
| --- | --- | --- |
| `stream.open` | API → node | Start one HTTP request with method, local port, path, and filtered headers. |
| `stream.request` | API → node | Ordered request-body bytes with a bounded sequence number. |
| `stream.request.end` | API → node | End the request body. |
| `stream.response` | node → API | Response status and filtered headers. |
| `stream.response.data` | node → API | Ordered response bytes. SSE stays incremental. |
| `stream.response.end` | node → API | End the response. |
| `stream.cancel` | either | Abort the local fetch/socket and release all buffers. |
| `stream.window` | either | Grant a bounded number of additional bytes for backpressure. |

Every frame carries `stream_id`, `seq`, and the authenticated channel nonce.
The receiver rejects duplicates, gaps, oversized frames, unknown stream IDs,
and data beyond the advertised window. Disconnect aborts every live stream.
Reconnect never replays a partially delivered HTTP request. The caller retries
only an operation whose application contract permits retry.

The API maps the existing `/p/:externalId/:port/*` compatibility surface to a
`compute_node_id`, then opens a channel stream. New code addresses the node ID
directly. No request resolves or calls a provider ingress endpoint.

The stream relay is port-generic. OpenCode REST on the session runtime port is
not a special transport. The API authorizes the node, current assignment,
caller, and requested port, then `kortixd` connects to that port through
loopback. Assignment policy and the node's local ceiling must both permit it.
This lets the same channel carry previews and future local services without a
provider SDK or a new relay implementation.

The current scheduler keeps one invariant: **one session has one compute
node**. The assignment and channel identify both IDs separately, so a future
session-to-many-nodes scheduler can add assignment rows without changing node
identity or the wire protocol. Multi-node sessions are not part of this release.

### 5.5 Standalone behavior

"Works standalone somewhat" made concrete. For each API dependency, the defined
degraded behavior:

| Dependency | API unreachable |
| --- | --- |
| Convergence manifest | Skip this pass. Keep running binaries. Retry next hook. Already the shipped behavior. |
| Turn relays (`turn-stream`, `turn-question`) | Spool to the local store, replay on reconnect, bounded by size and age. Today they are dropped. |
| Audit relay | Already spools locally. Unchanged. |
| Git clone credential | Fail the clone with a named reason. A session cannot start without a repo. |
| Session assignment | No new sessions. **Running sessions continue.** |
| Secrets | Use the last delivered set. Do not clear. |
| Local control server | Fully functional over the Unix socket. `kortixd` CLI can start, inspect, and stop a local session with no cloud at all. |

The strong statement: **a running session survives an API outage.** A node that
loses its channel keeps working and reconciles when it returns.

## 6. The workload interface

One interface. Today's three modes and tomorrow's adapters implement it.

```ts
export interface Workload {
  readonly kind: 'session' | 'monitor' | 'warm-seed' | 'app'
  /** Validate the environment before anything is spawned. */
  preflight(ctx: NodeContext): Promise<PreflightResult>
  /** Bring the workload up. Must be idempotent. */
  start(ctx: NodeContext, assignment: Assignment): Promise<void>
  /** Liveness + readiness, folded into GET /kortix/health. */
  health(): WorkloadHealth
  /** Additional routes this workload owns, mounted under its own prefix. */
  routes?(): Hono
  /** True while work would be severed by a restart. Gates the agent swap. */
  busy(): boolean
  /** Graceful stop. Must leave the node reusable. */
  stop(reason: StopReason): Promise<void>
}
```

`busy()` is load-bearing: it is the existing agent-swap blocker
(`registerAgentSwapBlocker`) promoted to a first-class member, so a new workload
cannot forget to declare when a swap would sever work.

## 7. What a node exposes

A node exposes two kinds of thing, and they are **the same kind of thing**: a
gated adapter the control plane may invoke. This is Marko's *"kortixd gives it
full access no matter what"* expressed as one registry rather than two systems.

| Adapter class | Examples | Present when |
| --- | --- | --- |
| **Harness** | `opencode`, `claude-code`, `codex` | The real binary is on the machine, or policy allows installing it |
| **Capability** | `shell`, `filesystem`, `desktop`, `ports` | Always, subject to the node's local ceiling (§7.5) |

Both are discovered, both are reported to the API as node capabilities, both
are permission-gated identically, and both are invoked over the same channel.
A session on a node uses a harness; a "computer connector" call uses a
capability; neither is special-cased.

### 7.1 The harness interface

A session workload delegates to a harness adapter. Adapters drive **real
binaries**. No SDK embedding — that was rejected on 2026-07-08 and stays
rejected.

```ts
export interface HarnessAdapter {
  readonly id: 'opencode' | 'claude-code' | 'codex'
  /** Is this harness usable on this machine, and at what version? */
  detect(): Promise<HarnessDetection>
  /** Spawn the real binary. Returns the local surface the node proxies. */
  spawn(ctx: SessionContext): Promise<HarnessProcess>
  /** How the node talks to it. Not a shared abstraction — per adapter. */
  transport: 'rest' | 'acp' | 'stdio'
  ...
}
```

`transport` is deliberately per-adapter. OpenCode keeps `rest` and its exact
current code path. Whether `claude-code` uses ACP or its own CLI protocol is
that adapter's private decision and changes nothing else.

### 7.2 Detection, not baking

July baked four adapters into every image and re-versioned every template. This
inverts it:

- At boot, `kortixd` detects which harnesses exist on the machine and at what
  version.
- It reports them as node capabilities.
- The API assigns work only to a node that advertises the required harness.
- Convergence may *install* a missing harness when policy allows it — the same
  mechanism that already installs `opencode` on mismatch.

A laptop with `claude` and `codex` already installed becomes useful with zero
image work. That is the whole point of the reframe.

### 7.3 Ordering

`opencode-rest` is the only adapter in P0–P2 and is byte-identical to today.
`claude-code` and `codex` land in P3, after the seam is proven in production by
a shipped adapter that nothing else can disturb.

### 7.3.1 The `kortix` harness — the default should be ours

**The problem, stated plainly.** OpenCode is the default Kortix experience and
it is a third-party npm package we pin, bake, and work around. The cost is
visible in the code: ~4,532 lines of the daemon exist to supervise someone
else's process — a verified-reload port pair because a bad config could take the
session down, orphan-turn finalization because the process can die mid-turn, a
`@opencode-ai/plugin` version pin that must move in lockstep, a config-deps
install step, and `OPENCODE_VERSION` sitting inside the snapshot identity so a
version bump forces a full-fleet template rebuild.

Everything else in the critical path is already Kortix-owned: the gateway, the
model catalog, secrets, skills, permissions, audit, the workspace. The harness
is the last third-party component in it.

So yes — reserve `kortix` as a harness id. But there are **two different things**
that name could mean, and they differ by roughly two orders of magnitude in
cost.

| | **(a) First-party agent loop** | **(b) Kortix-owned build of an existing loop** |
| --- | --- | --- |
| What we own | The whole loop: tool calling, context management, compaction, streaming, permissions | The build, the version, the patches, the release cadence |
| Cost | A product in itself, not a phase | Weeks. Vendor, build in our pipeline, converge as a component |
| Buys | Full control of quality and roadmap; no upstream surprises | Version control, no lockstep plugin pin, `OPENCODE_VERSION` leaves the snapshot identity, patches without a fork dance |
| Risk | We now own the hardest part of the product | Divergence from upstream accrues maintenance |

**Recommendation:** name the seam now, take (b) next, leave (a) as an explicit
strategic call rather than a drift.

1. **P3 reserves the id.** `kortix` is a harness id in the adapter registry from
   the day the registry exists. Nothing is special-cased for it later.
2. **`opencode` stays the default** until a replacement passes the same contract
   suite the other adapters pass. July's lesson applies exactly here: the
   default path must never be the experimental one.
3. **(b) is the near-term move** and it pays for itself independent of (a): a
   Kortix-owned build is what lets `OPENCODE_VERSION` leave the snapshot
   identity, which ends full-fleet template rebuilds per bump — already flagged
   as the next increment in the convergent-runtime work.
4. **(a) is a separate decision with its own spec.** It should be made on
   product grounds, not arrived at by accumulating patches in (b).

The reason this is safe to defer: **the adapter interface is what turns it into
a swap instead of a rewrite.** Get §7.1 right and "which harness is default" is
a registry entry and a migration, at any point in the future. Get it wrong and
this conversation happens again as another rollback.

### 7.4 `kortix node` — the CLI is the installer and the fleet manager

There is no separate installer. `apps/cli` already ships as a single compiled
binary, is distributed through GitHub releases, is baked into every image, and
converges itself against the API (`/v1/runtime-assets/cli`). It is the natural
place to install, enroll, inspect, and retire a node.

`kortix hosts` is a different concept and must not be conflated: it selects
*which Kortix instance* you authenticate against. `kortix node` operates *on
machines* belonging to the active host.

```
kortix node install [--version <v>] [--service]   fetch kortixd for this
                                                  platform, verify the digest,
                                                  install the OS service
kortix node enroll [--token <t>]                  device-code by default;
                                                  --token for automation
kortix node status                                this machine: enrolled?
                                                  claimed? converged? which
                                                  harnesses detected?
kortix node list                                  every node on this account,
                                                  with status and last heartbeat
kortix node logs [-f]                             tail the local daemon log
kortix node enable | disable                      accept or refuse new claims
                                                  without unenrolling
kortix node drain                                 finish the current session,
                                                  accept nothing new
kortix node restart | stop
kortix node uninstall                             remove the service, revoke the
                                                  node token, delete local state
```

Design rules:

- **`install` reuses convergence, not a new download path.** The daemon binary
  and its digest come from `/v1/runtime-assets/agent`, which already serves them
  and already verifies. One artifact path for install and for update.
- **Interactive enrollment and OS service installation use `kortixd`.** The old
  agent-tunnel service remains a compatibility path until migration completes.
- **`status` works with no network.** It reads the local node store over the
  Unix socket (§5.5). A node you cannot reach must still be able to tell you why.
- **`enable` / `disable` / `drain` are the operator's controls** on a machine
  Kortix does not own. Someone lending a laptop must be able to take it back
  mid-session without uninstalling anything. `drain` is the polite version;
  `disable` is immediate for new work.

This also collapses a duplication: `kortix node install` on a laptop and a
provider baking `kortixd` into an image become the same act, differing only in
who runs it.

### 7.5 Workstation convergence

`@kortix/agent-tunnel` already solves the laptop half of
this product: device-code enrollment, a credential file with real rules, OS
service install on three platforms, an authenticated reverse relay, and
capability implementations for shell, filesystem, and desktop
(`capabilities/desktop/cua-driver.ts`, 284 lines).

`kortixd` ports these capabilities behind the same node protocol. The existing
system remains operational until the new implementation passes parity tests.

The merge, concretely:

| agent-tunnel today | Becomes |
| --- | --- |
| `agent/device-auth.ts` | Node enrollment (§5.1) |
| `agent/service-drivers.ts` | `kortix node install --service` (§7.4) |
| `agent/credential-store.ts` | Node token store |
| `server/{relay,ws-handler,heartbeat}.ts` + `api/src/tunnel/core/*` | The node channel (§5.4) |
| `agent/capabilities/{shell,filesystem,desktop}.ts` | Capability adapters (§7) |
| `agent/capabilities/enabled-registry.ts` | The local ceiling, below |
| `tunnel_connections` table | `compute_nodes` rows with `type: workstation` |

**The local ceiling is preserved exactly.** agent-tunnel's rule — *"the local
config is the maximum boundary; a server grant cannot widen configured
filesystem paths, blocked paths, shell commands, timeouts, file sizes, or
desktop features"* — becomes the node's rule, unchanged. Full access means the
node grants what the node's owner permitted, and the API can only narrow it.
This is not a place to simplify.

**Migration.** Existing tunnel connections keep working. Their rows are
backfilled into `compute_nodes` with `type: workstation`, no harness, and their
existing capability set. `npx @kortix/agent-tunnel connect` keeps resolving for
one release and prints the `kortix node enroll` replacement.

### 7.6 Provisioning is the only provider-shaped work left

Once a machine runs kortixd and enrolls, it is a node. Nothing downstream needs
to know how it came to exist. So the provider abstraction collapses to one job:
**allocate a machine and get kortixd running on it.**

`SandboxProvider` has 15 members today. Most of them exist only because the API
had to reach *into* a box it did not control:

| Member | Fate |
| --- | --- |
| `create` / `createFromExternalId` | **Kept**, renamed `provision`. The one genuinely provider-shaped act. |
| `start` / `stop` / `remove` / `renewLifecycle` | **Kept.** Lifecycle of the *allocation*, not of the node. |
| `getStatus` / `listManagedRunningSandboxes` | **Kept**, narrowed. Reconciliation and orphan reaping still need the provider's own view. |
| `resolveEndpoint` | **Deleted.** The node holds the channel. |
| `resolveIngress` / `routeIngress` | **Deleted.** This is the entire per-provider ingress layer, plus the preview-link cache and the per-provider WebSocket quirks. |
| `ensureRunning` | **Deleted.** The node heartbeat answers it. |
| `getProvisioningStatus` | **Deleted.** The node reports its own boot progress over the channel. |
| `ensureAppRuntimeStarted` | **Deleted.** The node runs its assigned workload; that is what a node is. |
| `recoverInPlace` | **Deleted.** A node that cannot be recovered is drained and replaced. |

Nine of fifteen go. What remains is a `NodeProvisioner`:

```ts
export interface NodeProvisioner {
  readonly name: string
  provision(spec: NodeSpec): Promise<{ externalId: string }>
  start(externalId: string): Promise<void>
  stop(externalId: string): Promise<void>
  remove(externalId: string): Promise<void>
  renewLifecycle(externalId: string): Promise<void>
  getStatus(externalId: string): Promise<ProviderState>
  listManaged?(): Promise<Array<{ externalId: string; createdAt: Date | null }>>
}
```

And the enrolment handshake becomes the contract between them: a provisioner's
only obligation is to hand the machine an API URL and a **single-use enrollment
token**. Everything after that is the node's own doing.

That is also what makes a laptop and a Daytona box genuinely the same object
(§2.2): one had a provisioner, the other had a human running
`kortix node enroll`. The node cannot tell, and nothing asks.

**This lands in P4, not earlier.** Deleting nine interface members while three
providers are in production is a late-phase act, gated on the channel being
proven (§11).

## 8. Session lifecycle on a node

Decided: **one active session, many over the node's lifetime.**

```
enrolled/idle → claimed → preparing → ready → running → releasing → idle
```

- **claim** — the API assigns a session; the node accepts or refuses (busy,
  missing capability, draining).
- **prepare** — workspace materialization, secret delivery, harness spawn.
- **release** — harness stopped, ports freed, spooled relays flushed.
- **clean** — workspace removed. **Isolation between successive tenants on a
  machine Kortix does not own is a hard requirement, not a cleanup nicety.** The
  clean step is the first thing that must be adversarially tested (§13).

This breaks `session_id == sandbox_id`, which is load-bearing today. §10 covers
the data-model change. `sandbox_id` remains for provider boxes; it becomes a
property of a node, not the node's identity.

### 8.1 The claim transition already exists

**P1 is not new machinery.** `armSeedAdoption()` (`main.ts:394`) is already a
working `claim`, shipped and running in production on every Platinum warm fork:

```
adopt(trigger):
  reloadSessionEnv()                 // new identity arrives via /etc/pt-env
  cfg2 = loadConfig()                // re-derive — see §5.3.1
  server.reload(cfg2)                // re-arm the proxy with the new tokens
  configureGlobalGitIdentity(cfg2)   // re-key git
  materializeRepo(cfg2)              // prepare the workspace
  startSessionRuntime(cfg2)          // run
```

That is `claimed → preparing → ready → running` with the names removed. It is
triggered by `SIGHUP` or by `KORTIX_SESSION_ID` appearing in `/etc/pt-env`, and
it is guarded by a one-shot `adopted` latch.

The session manager generalizes this rather than inventing it:

- **claim** — generalize `adopt()`; the trigger becomes a channel message or a
  local control call, not only a file poll.
- **release** — does not exist yet. This is the genuinely new code.
- **clean** — does not exist yet, and is the risky half (§13).

Consequence for sequencing: P1 is smaller than it looks, and its real work is
`release` + `clean`, not `claim`. It also means the seam is validated by a path
already carrying production traffic.

#### 8.1.1 CORRECTION — generalize the OTHER adoption path

An adversarial review of this spec refuted the claim above as written. There are
**two** adoption implementations and they have diverged:

| | `armSeedAdoption` (`main.ts:409`) | the closure in `runWarmSeedMode` (`main.ts:1019`) |
| --- | --- | --- |
| `reloadSessionEnv()` + `loadConfig()` | yes | yes |
| `server.reload(cfg2)` | yes | yes |
| git identity + credential helper | yes | yes |
| `materializeRepo` | yes | yes |
| **`startEgressShim()`** | **no** | yes |
| **`writeAgentEnvFile(createProjectEnvStore())`** | **no** | yes |
| clear `repoMaterializationError`, re-resolve config dir, refresh catalog | no | yes |

`main.ts:1026` states why the two missing steps are mandatory: *"a warm seed
never started an egress shim … a forked session holding a network-boundary
secret would otherwise get none — its requests would leave uncredentialed and
the upstream 401 would look like a bad secret."*

In the `main.ts:355` path, `startEgressShim()` and `writeAgentEnvFile()` already
ran at boot — **with the seed's env, before `reloadSessionEnv()`**. Nothing
re-runs them. That is the 2026-06-10 identity-carryover shape one layer down.

**So P1 must generalize `main.ts:1019`, not `armSeedAdoption`** — or reconcile
the two first. Generalizing the weaker one ports the defect into the node model
and makes it permanent. This correction is the single most valuable thing the
review produced.

### 8.3 A pre-existing bug this work surfaced — revoked secrets survive

Not caused by this refactor; file separately. Recorded here because it is the
counter-example to "a snapshot is fine in this one place".

`createProjectEnvStore()` (`project-env.ts:60`) snapshots `process.env` at
construction. `runWarmSeedMode` builds it at `main.ts:892`, before any session
env exists, and that instance is what `startProxy` and
`opencode.reconfigure(…, projectEnv)` hold. Adoption builds a **second** store
and discards it after `writeAgentEnvFile`. Nothing reassigns the first.

The live store's `knownNames` is therefore empty, and `reconcileProjectEnv`
(`project-env.ts:127`) deletes only `knownNames`. Trigger: a fork receives
`ACME_KEY` via `/etc/pt-env`; the operator revokes it; the API pushes the smaller
set to `POST /kortix/env`. `ACME_KEY` is never deleted from `process.env`, and it
survives into the next opencode spawn (`mergeProjectEnv(process.env, …)`) and
into every PTY (`env: { ...process.env }`, `routes/pty.ts:122`).

**A revoked credential keeps working inside the box.** Reasoned from source, not
demonstrated — proving it needs a real warm fork, a revoke, and a read-back from
a PTY.

### 8.2 Sharing a node — what it actually costs

Marko: *"we could perhaps make an agent share a compute node, make it more
dynamic."* The scheduler side of that is easy. The isolation side is not, and
pretending otherwise is how a laptop leaks one tenant's secrets into another's
session.

`concurrency` is a declared property on `compute_nodes`, default `1`. The
assignment path reads it from day one, so raising it is a data change. What
raising it *requires* is five singletons becoming per-session, each verified:

| Singleton today | Why it blocks sharing |
| --- | --- |
| `/workspace` | One repo checkout. Two sessions would share a working tree and each other's uncommitted work. |
| `/dev/shm/kortix/agent-env.sh` | The secret file, sourced into **every** shell by `/etc/profile.d/kortix-agent-env.sh` and `/etc/bash.bashrc`. Two sessions means session B's shells load session A's secrets. This is the sharpest one. |
| Fixed ports | `8000`, `3211`, the `4096/4097` opencode pair, the egress shim, the LLM and connector proxies are all fixed constants — several of them hard contracts with `apps/web`. |
| The egress shim | One CA and one rule set, derived from the session-scoped `KORTIX_SECRET_CAPABILITIES`. Two sessions means one boundary policy for two grant sets. |
| Git credential helper | Configured globally under `OPENCODE_HOME` and repo-locally. Two sessions means one credential answering both. |

So sharing is a real project, not a flag. The honest sequence:

1. **P1 makes it possible.** `concurrency` exists, `clean` is proven, and the
   adversarial isolation probe (§13) becomes the regression test that any
   sharing work must keep passing.
2. **Sharing lands only after that probe passes with `concurrency: 2`** —
   the same probe, two live sessions instead of two sequential ones.

Until then a node advertises `concurrency: 1` and the scheduler places one
session. The dynamism Marko wants arrives as a number, once the five rows above
are true.

## 9. Convergence, generalized

Unchanged in mechanism. Three extensions:

1. The manifest's `components` map governs harness binaries as well as
   `agent | cli | opencode | managed-skills`. Every v1 and v2 key stays
   permanent — deployed daemons read them, and a test guards it.
2. `policy` gains per-component install permission, so a laptop can be told
   "converge the daemon, never touch my `claude` install."
3. The staged-swap handshake (`agent.next` + `.sha256`, exit `75`, independent
   re-verify, `agent.pinned` latch) is preserved verbatim, including the
   root-owned immutable floor.

**The binary rename is a convergence event.** `kortix-agent` → `kortixd` must
not break a box mid-update. The release publishes one artifact. Installation
boundaries retain a temporary compatibility path until old snapshots expire.

## 10. Data model

### 10.1 `kortix.compute_nodes`

```
node_id            uuid pk
account_id         uuid
name               text
status             enum(enrolling, idle, claimed, running, draining, offline, retired)
reachability       enum(inbound, channel)      -- which transport §5.4 picks
provisioning       jsonb                        -- {kind:'provider'|'self', provider?, external_id?}
capabilities       jsonb                        -- arch, cores, memory, disk, harnesses[]
concurrency        int not null default 1       -- sessions this node may host at once (§8.2)
node_type          enum(cloud-sandbox, vm, bare-metal, workstation, ci-runner)
agent_build        bigint                       -- last converged manifest build
node_token_hash    varchar(128)
last_heartbeat_at  timestamptz
enrolled_at        timestamptz
```

`provisioning` is where a Daytona box and a laptop stop differing. This is P3
of the principle list made concrete: allocation becomes metadata, not identity.

### 10.2 Relationship to today's tables

- `session_sandboxes` keeps its shape; it gains `node_id`. A provider box gets
  a `compute_nodes` row on create, so there is exactly one registry from day
  one and no dual-write.
- `sandbox_provider` enum is **not** extended. Self-hosted nodes carry
  `provisioning.kind = 'self'` and no provider. No enum migration; no repeat of
  the 2026-07-10 prod enum drift.
- `tunnel_connections` is the model for the channel and is a candidate to merge
  into `compute_nodes` in P4, not before.

### 10.3 Metering

Deferred. `compute_nodes` carries no billing column. When the product answer
arrives, metering attaches to `sandbox_compute_sessions` by `node_id` and is
purely additive. Nothing in P0–P2 forecloses either answer.

## 10.4 The fleet interface

A fleet you cannot see is a fleet you cannot operate. Nodes running on machines
Kortix does not own make this a requirement, not a nice-to-have: when someone's
laptop stops taking work, somebody has to be able to tell why.

**Surface:** a `Compute` section in `apps/web`, account-scoped, built from
existing primitives per the Kortix design system — no new chrome.

**List view.** One row per node, sorted by status then last heartbeat:

```
name            type          status    session          harnesses         build      heartbeat
laptop-marko    workstation   running   sess_8f2…        opencode codex    1787246444  4s ago
ip-10-2-4-11    vm            idle      —                opencode          1787246444  11s ago
sbx_a91f…       cloud-sandbox running   sess_c04…        opencode          1787240001  2s ago
mac-mini-01     workstation   draining  sess_11b…        opencode claude    1787246444  6s ago
dev-box-3       bare-metal    offline   —                opencode          1787211900  4h ago
```

Encoded in form, not only in text: status as a pill, a stale heartbeat as a
severity stripe, a node behind on `build` as a distinct state from one that is
offline. Those are different problems and must not look alike.

**Detail view.** Capability list with what is enabled versus what the local
ceiling permits (§7.5) — the two differing is the single most common support
question a shared machine will generate. Plus the session history for that node,
convergence state, and the last ten health reports.

**Actions**, each mirroring a CLI verb exactly so the two can never drift:
`enable`, `disable`, `drain`, `restart`, `retire`. Drain is the one that needs a
confirm; it ends someone's work.

**Enroll flow.** A `Connect a computer` button that shows the exact
`kortix node install && kortix node enroll` line with the account's enrollment
token, and a live "waiting for this machine to appear" state — the same shape as
the existing Computer Tunnel connector profile, which this replaces.

Ships with P2. A node you can enroll but not see is not finished.

## 11. Phases

Each phase ships to dev and is verified there before the next begins. P0 and P1
are invisible to users and can merge without P2 ever landing.

### P0 — Node core + standalone daemon
Extract the core. Declare the config contract. Introduce the workload interface
with today's three modes behind it. Build the daemon as the only standalone
`kortixd` artifact and make the rename a convergence-safe event (§9).
**Zero observable behavior change.**

*Exit:* `pnpm test` green; a dev session boots, runs a turn, restarts, resumes,
and converges with byte-identical `/kortix/health`; swap-handshake suite 9/9;
no undeclared env read; the merged binary is smaller than today's two.

### P1 — Session manager
`compute_nodes` table and backfill (provider boxes get rows too, so there is one
registry from day one). Generalize the `runWarmSeedMode` adoption closure —
**not** `armSeedAdoption`, see §8.1.1 — into `claim`; build `release` and
`clean`. A node hosts a second session after the first ends.

*Exit:* one dev node runs session A, releases, cleans, and runs session B, with
the adversarial isolation probe passing (§13).

### P2 — Sandbox channel
Provider bootstrap enrollment and the outbound channel. Standalone degraded
mode (§5.5). The compatibility agent-tunnel remains operational.

*Exit:* a real provider sandbox connects with no inbound runtime path. A full
session runs through the web UI. API loss and reconnection have explicit state.

### P3 — Workstation and harness expansion
Capability adapters — shell, filesystem, desktop — migrate into `kortixd`.
Harness adapters `claude-code` and
`codex` on real binaries, by detection rather than baking (§7.2). Manifest
`runtime:` re-lands behind the adapter interface.

*Exit:* the same project runs a turn on all three harnesses; the `kortix`
harness id is reserved in the registry (§7.3.1); a computer-connector call runs
against a node instead of a tunnel; the OpenCode path is provably untouched
(§12); `agent-tunnel` is deprecated with its shim resolving.

### P4 — Collapse the provider
Reduce `SandboxProvider` to `NodeProvisioner` (§7.6) — nine of fifteen members
deleted, including the whole per-provider ingress layer. Fold the Go `appd` in
as a workload adapter. Retire `agent-tunnel` and `tunnel_connections`.

*Exit:* no code path branches on a provider name outside provisioning; a
provider outage cannot break a running node.

## 12. What must not break — the July rule

The 2026-07-30 rollback happened because a second runtime rewrote shared code.
Three mechanical guards, all in P0:

1. **The OpenCode adapter is created by moving files, not editing them.**
   `opencode*.ts` moves under `workloads/session/harnesses/opencode/` with no
   content change in the same commit. The diff must be pure rename. Any
   behavior change is a separate, reviewed commit.
2. **A characterization suite is captured before the move.** Record today's
   `/kortix/health`, boot timeline, route table, and a full turn transcript from
   a real dev session. It becomes a golden test. P0 passes only if the output is
   identical.
3. **The interface is proven by two implementations before a third is designed.**
   `monitor` and `warm-seed` already exist and must fit the workload interface
   unchanged. If they need special-casing, the interface is wrong and P3 does
   not start.

Stated as a review gate: **no pull request in P0–P2 may modify a line inside
`opencode*.ts`.** If one appears to need it, the seam is in the wrong place.

## 14. Risks

| Risk | Mitigation |
| --- | --- |
| A repeat of July: the seam leaks into the REST path | §12, enforced as a review gate on the diff |
| The fleet drain — the supervisor only reaches a box on re-provision | Land the rename in the same image bump as P0. Pay it once, as already budgeted |
| A laptop node leaks state between tenants | P1 exit criterion is an adversarial isolation probe, not a cleanup review |
| Enrollment token on a personal machine is a credential | Reuse agent-tunnel's rules: `0600`, owner-checked, rotatable, revocable. Node token is node-scoped, never account-scoped |
| Scope: this touches everything | Phases ship independently. P0 and P1 are invisible to users and can be merged without P2 ever landing |
| A CLI installer and daemon release can drift | The node reports both versions. The API manifest declares compatibility. `kortix node doctor` rejects unsupported pairs. |
| Absorbing agent-tunnel weakens its security ceiling | The local ceiling is ported verbatim and is a P3 exit criterion, not a refactor detail (§7.5) |
| Deleting nine provider members while three providers run in production | P4, gated on the channel being proven. Never earlier |
