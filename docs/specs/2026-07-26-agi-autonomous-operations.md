# AGI — Autonomous Operations

Status: working document
Date: 2026-07-26
Owner: Kortix product
Related: `docs/specs/2026-07-24-agi-system.md` (identity, authorization, session
execution — assumed, not restated), `docs/specs/2026-07-14-trigger-session-strategy.md`

---

## 1. What this specifies

One agent you talk to that runs your company continuously.

The 2026-07-24 spec defines the substrate: identity, grants, sessions, triggers,
the action surface. It leaves one thing unbuilt, named in its own §15 open item
1 — *"whether goal state is a defined artifact in the repository, a first-class
platform resource, or both, and what the reconciliation loop between goal state
and session output looks like."*

This document answers that, and specifies the surface built on top of it: the
AGI agent, goals, tasks, and the loop that keeps them advancing without a human
prompt.

Everything here ships behind one experimental feature key, `agi`.

### 1.1 Prior art

Paperclip (`github.com/paperclipai/paperclip`) was surveyed in full before this
was written. §11 records what was taken and what was deliberately rejected. The
short version: its goal layer is 80 lines of CRUD and is not worth copying; its
issue-liveness contract is ~25k lines of hard-won correctness and mostly is.

---

## 2. Model

Five nouns. No more.

| Noun | What it is | Where it lives |
|---|---|---|
| **Workspace** | The company. One linked cloud project. The unit of ownership. | existing |
| **AGI** | The single agent you talk to. Platform-owned, present in every workspace. | platform |
| **Goal** | A durable objective with written completion criteria. Authored. Few. | `kortix.yaml` |
| **Task** | A unit of work. Generated, claimed, contended. Many. | DB |
| **Trigger** | The only thing that starts work without a human. | `kortix.yaml` (existing) |

R-1 — There MUST NOT be a sixth noun. Projects, spaces, milestones, epics, org
charts, and roles are deferred indefinitely; §7 explains what replaces them.

## 3. Storage: authored vs generated

The split is **who writes it and how often**, not "coordination vs memory".

R-2 — State authored by a human or proposed by an agent for human review, which
changes rarely and must be diffable, MUST live in the project repository.
Goals, triggers, agent definitions, skills, and policy are authored state.

R-3 — State generated by agents mid-run, at a rate and volume that makes review
meaningless, and which is contended by concurrent sessions, MUST live in the
platform database. Tasks, claims, and run history are generated state.

R-4 — Generated state MUST NOT be the only record of a durable outcome. When a
task produces a lasting fact, decision, or capability, the session MUST write
that back to the repository as a skill, document, or manifest change (R-9.5 of
the 2026-07-24 spec).

### 3.1 Reconciliation with R-9.1

The 2026-07-24 spec's R-9.1 requires *all durable organizational state* to be
text under version control. Tasks are not organizational state. A task is a
transient claim on work — the organizational residue is what R-4 writes back.
R-9.1 is hereby scoped to authored state as defined in R-2.

R-5 — A task MUST NOT be the system of record for anything that outlives it.

### 3.2 Why tasks cannot be files

Two sandboxes running in parallel must never both believe they own a task.
Claiming by commit is a push race with no atomic loser. This is the only reason
tasks are not in git, and it is sufficient.

## 4. Goals

A goal is the durable object. Tasks are disposable; the goal persists.

R-6 — Goals MUST be declared in `kortix.yaml` and applied by `kortix ship`,
using the manifest's existing review and change-control path.

```yaml
kortix_version: 2

goals:
  - slug: oil-desk
    title: Oil trades running 24/7
    done_when: >
      A live account executes the strategy unattended for 7 consecutive days
      with no manual intervention and a positive risk-adjusted return.
    status: active            # active | achieved | paused | abandoned
    push: "0 0 9 * * *"       # standing advance; omit for goals advanced only on demand
    agent: default            # who advances it
```

R-7 — A goal MUST carry `done_when`: prose completion criteria a session can
evaluate against evidence. A goal without `done_when` is a wish and MUST be
rejected by `kortix validate`.

R-8 — `push` MUST desugar to exactly one cron trigger in the existing trigger
subsystem. It is sugar, not a second scheduler (R-7.8, 2026-07-24 spec).

R-9 — Goal status MUST be advanced only by an explicit act with cited evidence.
A session MUST NOT mark a goal `achieved` from prose or from the absence of
remaining tasks.

R-10 — Goals SHOULD number in the single digits per workspace. The system MUST
NOT auto-create goals; only a human or the AGI acting on a human instruction
may propose one, and it lands through a change request like any manifest edit.

### 4.1 The daily push

R-11 — On each `push` fire the session MUST, in order: read the goal and its
`done_when`; read open tasks for the goal; determine the single most valuable
next move; take it or create the tasks that constitute it; and record what
changed. Exiting with an unchanged task list and no recorded reason is a
liveness failure under §6.

R-12 — A push MUST leave the goal measurably advanced or MUST state why it
could not. "Reviewed, nothing to do" is a valid outcome only with a reason.

### 4.2 Observations — how "measurably" is measured

Without this section R-12 is an adjective in a prompt string, and the only
thing evaluating `done_when` is a model grading its own homework. That is the
failure mode where the loop looks alive for three weeks while the metric has
not moved.

R-12a — A **signal is a trigger**. There MUST NOT be a `signals:` declaration,
a probe registry, or any third scheduling concept. A measurement is produced
either by a cron trigger whose session takes a reading, or by a webhook that
receives one from outside. This is R-21 applied to measurement.

R-12b — An **observation** is generated state and MUST live in the database:
`(goal_slug, metric, value, observed_at, source)`. It is a time series, queried
by range, written at machine rate — R-3 applies, and it MUST NOT go in the repo.

R-12c — A session records one with a single CLI verb, so that any agent, any
trigger, and any webhook handler all use the same path:

```
kortix goals observe <goal-slug> --metric <name> --value <number>
```

R-12d — `done_when` MAY be a **held** condition rather than a finish line
("top-3 for the core terms, sustained 30 days"). Evaluating a held condition
REQUIRES the series; prose alone cannot express "sustained". A goal whose
`done_when` names a threshold without any observation ever being recorded for
that metric MUST surface as unmeasurable rather than as on-track.

R-12e — A goal whose metric has not moved across N consecutive pushes MUST
surface as a stall (§8), exactly like a task with no live path. The system MUST
NOT require a human to notice a flat line.

R-12f — Observations are evidence, never authority. Recording one MUST NOT
change goal status; only R-9's explicit act does.

### 4.3 Reaching a human when nobody is watching

R-12g — A session that cannot proceed without a human act — a credential, an
access grant, a decision — MUST deliver that request to a surface a human will
see: a channel message, a notification, or a pending item attached to the task.
Writing it into the session log is NOT delivery.

Rationale: the interactive path is already correct (`kortix secrets request`
mints a link; the agent never sees the value). The unattended path is not. A
07:00 push that discovers it needs an access grant currently mints the URL and
writes it where only that session can see it, then stalls silently. For a fresh
workspace this is the FIRST thing that happens, before any real work.

## 5. Tasks

R-13 — Tasks are workspace-scoped. `project` is a nullable label, unset by
default. Grouping is deferred (§7).

```
tasks
  id                uuid pk
  workspace_id      uuid not null
  parent_id         uuid null            -- structure only, NOT dependency
  goal_slug         text null            -- which goal this serves
  project           text null            -- deferred grouping label
  title             text not null
  body              text null
  status            text not null        -- backlog|todo|doing|blocked|review|done|cancelled
  priority          text not null default 'medium'
  agent             text null            -- assignee (agent name), or
  assignee_user_id  text null            -- ... a human. Never both.
  blocked_by        uuid[] not null default '{}'
  trigger_slug      text null            -- set when this task IS a trigger (§6.1)
  claim_session_id  uuid null            -- atomic claim
  claimed_at        timestamptz null
  claim_expires_at  timestamptz null
  origin            text not null        -- human|agi|session|trigger
  origin_fingerprint text null           -- idempotency; see R-19
  created_at, updated_at
```

R-14 — A task MUST have at most one assignee, agent or human, never both.

R-15 — `parent_id` is structure. It explains why a task exists and enables
rollup. It MUST NOT be interpreted as a dependency.

R-16 — `blocked_by` is dependency. A task waiting on another MUST say so here.
A parent waiting on its children MUST list them in `blocked_by`; relying on
`parent_id` alone is a defect.

R-17 — A cancelled blocker does NOT satisfy the dependency. The edge stays
unresolved until removed or replaced.

### 5.1 Claiming

R-18 — A session MUST claim a task before working it. The claim MUST be a
single atomic conditional update. A failed claim means another session owns it;
the caller MUST pick different work and MUST NOT retry the same claim.

R-19 — Claims MUST expire. A claim whose session is terminal or whose
`claim_expires_at` has passed MAY be adopted. Adoption is crash recovery, not
retry: a claim held by a live session MUST NOT be broken.

R-20 — Task creation MUST be idempotent under `origin_fingerprint`. A trigger
that fires twice for the same logical event MUST NOT produce two tasks.

## 6. The loop

R-21 — There is exactly ONE mechanism that starts work without a human: the
existing trigger subsystem. There MUST NOT be a wake queue, a heartbeat
scheduler, or any second path.

This is the central design decision and the largest departure from Paperclip,
which has ~40 derived wake sources feeding a dedicated `agent_wakeup_requests`
table. Kortix already has cron, one-off `runAt`, signed webhooks, payload
filters, and `session_strategy: fresh|reuse|pinned|keyed`. That is the engine.

### 6.1 A recurring task is a trigger

R-22 — Recurrence MUST NOT be a task property. A task that should happen
repeatedly IS a trigger; the trigger's fires create task rows. `tasks.trigger_slug`
records that lineage.

R-23 — A one-off future task MUST use a one-off (`run_at`) trigger, not a
bespoke scheduler.

### 6.2 Advancing without new events

R-24 — Between trigger fires, nothing wakes. State changes (a child completing,
a blocker clearing) do NOT emit wakes in v1. The standing goal `push` observes
them on its next fire.

Rationale: this trades latency for the removal of an entire subsystem. A child
finishing at 14:00 is noticed at the next push rather than immediately. For the
goal-pursuit workload that is acceptable, and it eliminates the largest source
of complexity and loops in the surveyed prior art.

R-25 — When latency matters, an `event` trigger type MAY be added later, firing
the same trigger engine from a platform-emitted event. It MUST NOT be a second
subsystem. Out of scope for v1.

## 7. What replaces projects, roles, and org charts

Nothing, for now.

R-25a — Codified orchestrations ("workflows" — a recurring multi-agent
procedure stored as a script rather than re-improvised from prose each run) are
DEFERRED, decided 2026-07-27. The company repo already hand-rolls this as
orchestrator+worker agent PAIRS. It is a real gap and a likely sixth noun, but
the five nouns are not yet proven to run unattended overnight, and a sixth
before the fifth works is how scope escapes. Revisit after a push has run a
full night. Do not build it meanwhile; the agent pairs are not broken.

R-26 — Grouping MUST NOT be built until a workspace demonstrates enough tasks
to need it. `tasks.project` reserves the column so the eventual grouping — a
space, a tag, or a sub-workspace — lands without a migration.

R-27 — There MUST NOT be an org chart, a role hierarchy, or a chain of command.
Kortix already resolves capability through agent grants; a second authority
model that disagrees with grants is a security defect, not a feature.

## 8. Liveness

Adapted from Paperclip's execution-semantics §8, which is the one part of that
system worth copying closely. Restated as prohibitions, which is what makes it
work.

R-28 — A non-terminal task assigned to an agent MUST have an answer to "what
moves this forward next?" The valid answers are exhaustively:

1. a live session working it
2. a future trigger fire that will pick it up
3. an unresolved `blocked_by` edge whose blockers are themselves healthy
4. a human assignee
5. a pending approval or question awaiting a specific responder

R-29 — Anything else is stalled and MUST be surfaced, not retried silently.

R-30 — The following MUST NOT count as progress or as a live path:

- provisioning a sandbox, cloning a repo, or reading context
- a background process, `&` job, `nohup`, detached PTY, or polling loop
- a PID, log file, comment, or stated intention to check later
- prose in a session log claiming work will continue

R-31 — The following MUST NOT be treated as control-plane acts:

- an agent's name written in prose is NOT an assignment
- approval-sounding text is NOT an approval
- "done" in a comment is NOT a status change

R-32 — Recovery MUST be bounded and MUST preserve ownership: at most one
automatic continuation for the same stalled state, then escalation to a human
with cause and evidence. The system MUST NOT reassign work to a different agent
automatically. Repeated identical evidence MUST NOT produce repeated
continuations.

R-33 — A session that ends without either advancing a task, changing a status,
or recording why it could not, MUST be recorded as having made no progress, and
that fact MUST be visible.

## 9. The AGI agent

R-34 — Every workspace MUST have an AGI agent available without declaring it in
the repository. It is platform-owned, versioned with the platform, and identical
across workspaces.

R-35 — The AGI agent MUST NOT be resolved through `loadProjectAgents`. It is
not a manifest entry and MUST NOT require one.

R-36 — Its only inbound configuration MUST be workspace context supplied via
environment at boot. It MUST NOT require a checkout to start.

R-37 — The AGI MUST be visually elevated above workspace agents in both the CLI
picker and the web UI. It is the default thing to talk to, not one item in a
list.

R-38 — The AGI works by spawning sessions and managing goals and tasks. It
SHOULD NOT do the work itself when a session can.

R-39 — Its grant is the full authority of the human who launched it, and no
more. It MUST NOT be able to grant itself capability the launching user lacks.

## 10. Surfaces

### 10.1 CLI

R-40 — Bare `kortix` MUST present an agent picker for the linked workspace with
the AGI elevated and preselected, and MUST start a session with the chosen
agent. The current help banner moves to `kortix --help`.

R-41 — The single-workspace binding this depends on is specified and delivered
separately. Until it lands, bare `kortix` uses the currently linked project.

R-42 — Goals and tasks MUST be fully operable from the CLI, since that is how
agents operate them:

```
kortix goals ls|show|push
kortix tasks ls|show|new|claim|done|block
```

R-43 — Every capability here MUST be reachable from CLI, API, and SDK. A
UI-only capability is out of contract (R-8.1, 2026-07-24 spec).

### 10.2 Experimental gate

R-44 — All of it ships behind a single key, `agi`, in
`apps/api/src/experimental/features.ts`: `available: () => true`,
`platformDefault: () => false`, per-project opt-in. When off, no routes, no CLI
commands, no UI, no manifest keys.

## 11. Taken from Paperclip / rejected

**Taken:**

- The four-way separation of structure, dependency, ownership, and execution,
  and specifically that `parentId` is not a dependency (§5).
- The liveness contract restated as prohibitions (§8) — especially that a
  background process is not a live path and that provisioning is not progress.
- Atomic claim with no-retry-on-conflict (§5.1).
- Bounded recovery that preserves ownership and escalates rather than reassigns.
- Idempotency fingerprints on generated work.

**Rejected:**

- The goal hierarchy (`level: company|team|agent|task`). It drives nothing in
  the source system; goals never even reach the agent's prompt there.
- `agent_wakeup_requests` and the ~40 derived wake sources. Replaced by §6.
- The org chart, roles, chain of command, hiring, and budgets-as-salary. §7.
- Separate `issues` and `routines` vocabularies for the same underlying thing.
- Company/project/team nesting. One workspace, flat tasks.
- Run-liveness as a second status enum parallel to task status. Collapsed into
  §8, which is about whether a live path exists, not about labelling runs.

## 12. Build order

Each step is independently shippable and independently useful.

1. **Experimental key `agi`** — gate exists, everything below hangs off it.
2. **Tasks** — table, claim semantics, `kortix tasks` CLI, API routes. Usable by
   existing agents immediately, with no AGI and no goals.
3. **Goals** — `kortix.yaml` block, `validate` enforcement, `push` desugaring to
   a trigger, `kortix goals` CLI.
4. **AGI agent** — platform-owned resolution path, cloud boot with workspace
   context by env, prompt teaching §4.1, §5, §8.
5. **Elevation** — bare `kortix` picker; AGI elevated in web UI.
6. **Liveness** — no-progress detection (R-33) and bounded escalation (R-32).

Step 2 is the first thing that changes how a session behaves. Step 6 is what
makes the loop trustworthy overnight and MUST NOT be deferred past first
production use.

  different prompt, or an ordinary session instructed to judge. (§4.2 gives it
  a series to judge AGAINST; it does not settle who judges.)
- How many consecutive flat pushes constitute a stall (R-12e), and whether that
  count is per-goal or global.
- Whether the continuation budget in R-32 is per-goal, per-trigger, or
  per-workspace, and where it is declared.
- Whether a task may belong to more than one goal.
- Whether the AGI's own memory is a repo path per workspace or a platform
  resource, given it has no manifest entry (R-35).
