We run our own customer support on Kortix with an AI agent connected to Plain
(our support tool), our codebase, and Stripe. Most support questions need
product knowledge, engineering context, and billing data at the same time: a
help-center chatbot can quote documentation but can't read the code behind a
bug, confirm whether a subscription renewed, or take a scoped action on an
account.

This write-up covers how the setup works: the connections, the session model,
and the guardrails.

## The problem

Support volume grows faster than the team. The questions that matter most are
the ones a canned macro can't answer: "why was I charged twice?", "this button
does nothing", "does your API support X?" Each one needs someone who understands
the product, can read the code, and can check the customer's account — usually a
senior engineer.

A help-desk bot handles the easy questions but not these. Hiring scales linearly
with tickets. And giving a generic AI assistant real access to production
systems is hard to justify in a security review.

## What we built

Our support inbox in **Plain** is connected to an agent running on Kortix. Every
inbound thread spawns its own isolated session with scoped access to the systems
a support issue can touch: the product's knowledge, the codebase, and Stripe. It
investigates, resolves what it can, and stops at a human for sensitive actions.

## How it works

<Steps>
<Step title="Copy the setup prompt into a new session">

Open your Kortix project, start a new session, paste this prompt and send it.
The agent writes the agent file, the support skill and the trigger, and opens
a change request for you to review. Prefer clicks? Choose **Use this

<CopyBlock
  title="Setup prompt"
  code={`Set up a support queue agent in this project.

1. Create the agent agents/support-agent.md. Its job is to work the Plain support queue. It may read the codebase and use the PLAIN_API_KEY and STRIPE_SECRET_KEY secrets.

2. Create the skill skills/support-playbook/SKILL.md with these rules:
   - Work every new thread and every customer reply that has no answer yet.
   - For a bug report, search the codebase and recent changes for the code path before you reply.
   - For a billing question, look up the customer's plan, invoices and subscription in Stripe.
   - Resolve the thread when you can answer it fully. Otherwise draft a reply with the diagnosis attached and hand it to a person.
   - Refunds, plan changes and anything that touches a customer's money or account state need my approval. Never do them yourself.
   - Note each resolution that worked, so the next run is faster.

3. Add a cron trigger support-triage to kortix.yaml. It runs the support-agent agent every 15 minutes with the prompt "Load the support-playbook skill and work every new or unanswered thread in Plain."

4. Tell me which of these connectors are not connected yet.

5. Open a change request with all of it. Do not merge it.`}
/>

</Step>
<Step title="Connect your tools">

Open **Connectors** in your project and connect your code host. Add your
Plain and Stripe API keys as the `PLAIN_API_KEY` and `STRIPE_SECRET_KEY`
secrets. Secrets are encrypted and injected at runtime, scoped to the agents you
grant them to.

<CopyBlock
  title="Prompt"

1. Pull every new thread and every customer reply without an answer.

3. For a billing question, look up the customer's plan, invoices and subscription in Stripe.

/>

<Step title="Let the 15-minute schedule take over">

The change request added this trigger to `kortix.yaml`. From now on the agent
checks the queue every 15 minutes, each run in a new session on its own cloud
computer.
To change the time, edit the cron line, or open **Triggers** in the project.

<CopyBlock
  title="kortix.yaml"
  lang="yaml"
  code={`triggers:
  - slug: support-triage
    name: Support queue triage
    on:
      cron: "0 */15 * * * *"
    run:
      agent: support-agent
      prompt: Load the support-playbook skill and work every new or unanswered thread in Plain.`}
/>

</Step>
<Step title="Hold refunds and plan changes for approval">

The agent reads the codebase and Stripe freely and replies in Plain. A refund,
a plan change or any other change to a customer's money or account state stops
for a person. An automated session waits at most 30 minutes for a person, then
stops without changing anything, and the next run asks again.

</Step>

## Guardrails

Giving an agent access to the codebase, Stripe, and the support inbox is a
security question as much as a product one. The controls on Kortix:

- **Isolation.** Each thread runs in its own isolated sandbox on its own branch. A
  session can install, run, and experiment to reproduce a bug, and only what it's
  explicitly allowed to send is written back out.
- **Scoped secrets.** The Plain, Stripe, and GitHub credentials are encrypted in
  the secrets manager and injected into the sandbox at runtime, scoped to the agents you grant them to.
- **Human approval gates.** Irreversible actions (money, account state) require a
  person to approve.
- **Everything is code.** The agent's persona, skills, and permissions are files
  in the repo — versioned and changed through a reviewed **change request**
  rather than a dashboard setting.

The agent handles the investigation-heavy tickets that used to pull a senior
engineer off their work, and when it escalates, it escalates with the diagnosis
attached. Customers get an answer to the question at any hour.

The setup relies on four pieces: sandbox isolation to contain each session, a
secrets manager to broker tokens, human approval gates for irreversible actions,
and memory that improves as threads are resolved.
