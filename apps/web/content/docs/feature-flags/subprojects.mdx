A **subproject** is a Kortix project you install into another project: a repository
whose own `kortix.yaml` declares agents, skills, connectors and triggers.
Installing one merges that declaration into the target project.

Subprojects is a [feature flag](/docs/feature-flags). Its stability is
**experimental**, and it is off by default. Turn it on per project before you
install anything.

Building on Subprojects from TypeScript? See [SDK → Subprojects](/docs/sdk/subprojects) for the
client surface and the React hooks.

## Turn Subprojects on

Open **Settings → Feature flags** and switch **Subprojects** on for the project. You
need `project.customize.write`.

While the flag is off:

- Every project-scoped subproject route answers `403` with
  `{ error, code: "feature_disabled", feature: "subprojects" }`.
- Every project-scoped `kortix subprojects` subcommand prints `Subprojects is not enabled
for this project. Enable it in Settings → Feature flags.` and exits `1`.
- The **Marketplace** tab does not appear in the Customize tab bar, and
  **Customize** does not list a Marketplace row. `Cmd`+`K` does not offer it
  either.

The account-scoped catalog routes (`GET /v1/subprojects`, `POST /v1/subprojects`,
`GET|DELETE /v1/subprojects/:subprojectId`) are **not** flag-gated. Publishing and
browsing are account-level; only what a project installs is gated.

## The two steps

Subprojects has one lifecycle, and each step is a separate decision:

1. **Publish** — index a repo or an archive into the catalog.
2. **Install** — an agent session merges the subproject and opens a change request.

<Callout type="warn" title="Install does not install. It opens a change request.">
  Install starts an agent session that reads both manifests, resolves name collisions, and opens a
  **change request**. The subproject is not installed until that CR merges to the default branch.
  Uninstall works the same way. Neither call commits on its own.
</Callout>

<Callout type="info" title="A subproject has no on/off state and no runs of its own">
  It is a set of entries in the project's manifest. Its triggers arrive **off** and are enabled one
  at a time under [Triggers](/docs/connect/triggers) — there is no switch over a whole subproject. A
  run belongs to the **trigger** that fired, not to the subproject that contributed it, so runs are
  read from the trigger surface.
</Callout>

## Publish a subproject

A subproject comes from one of two sources, and they behave differently.

| Source             | Tracks the source                               | Re-crawls when it moves | Where       |
| ------------------ | ----------------------------------------------- | ----------------------- | ----------- |
| A GitHub repo      | yes — `owner/repo`, optionally `@branch-or-tag` | yes                     | Web and CLI |
| An uploaded `.zip` | no — the files are a snapshot                   | never                   | Web only    |

### Who can see it

Visibility has three values, and a submission can write two of them:

| Value     | Who sees it                         | How a row gets it                                                      |
| --------- | ----------------------------------- | ---------------------------------------------------------------------- |
| `account` | Everyone in the submitting account  | The **default**. Choose nothing                                        |
| `private` | The submitter alone                 | The visibility control in **Add a subproject**, `--private` on the CLI |
| `public`  | Every Kortix user, in every account | **Not submittable.** Migration, seeder or direct insert only           |

`private` is enforced by identity, not by account: the read path compares against
`submitted_by`, so a private subproject is invisible to an account co-member too.

<Callout type="warn" title="You cannot publish a globally visible subproject">
  The global catalog is curated. There is no role, flag, control or CLI option that promotes a
  submission into it. Asking for `visibility: 'public'` on the route answers `400` on both body
  shapes, with `options: ["account", "private"]` — the set you may write, not a confirmation that
  `public` is reachable. Behind that, the handler coerces any present non-`account` value to
  `private`, so a body shape added later cannot widen a subproject by skipping a validator.
</Callout>

Publishing derives the card — title, description, and what the subproject declares —
from the manifest at the resolved commit. The response carries `warnings`, which
never block: a manifest deprecation, a per-entry parse error, or a count of
files the crawl left behind. The subproject **is** indexed. Show the warnings; do not
read them as a failure.

Rejections carry a machine `code` — `manifest_not_found`, `manifest_invalid`,
`ref_not_found`, `repo_not_found`, `upstream_unavailable`, `invalid_archive`,
`archive_refused`. See [SDK → Subprojects](/docs/sdk/subprojects#rejections-worth-handling)
for what each one means.

### An upload keeps only the subproject

You can zip a whole project folder. The crawl keeps `kortix.yaml`, anything
under `.kortix/`, a root `README.md`, and a root `.env.example`. It leaves
`src/**`, tests, lockfiles, and `docs/**` behind.

That filter is not only about size. The install prompt tells the agent _these
files ARE the subproject — copy from here_, so a stored `src/server.ts` would become
a file the agent writes into **someone else's** repository.

Archive bounds, all server-side: 10 MB envelope, 5 MB of extracted text,
256 KB per file, 1000 files after filtering. Over any of them and the route
answers `400 archive_refused` naming which one.

### Or describe one and have it built

**Grow your own**, in the store page's `+ Add` menu, takes a description and starts
an agent session that builds and publishes the subproject for you. It is the same
kind of session as install: it ends in work you review, not in a finished catalog
entry.

## What an install records

An install writes a `subprojects:` entry to the target project's `kortix.yaml`, and
stamps `subproject: <slug>` on every agent, skill, connector, and trigger it
contributed. Both halves land in one commit, which is what makes `git revert` a
working uninstall.

```yaml
subprojects:
  - slug: seo-watch
    repo: acme/seo-subproject
    ref: v1.2.0
    sha: 4f1c8a2e9b7d3056a1c4e8f0b6a92d5c7e3b1f80
    title: SEO Watch
    installed_at: '2026-08-30T09:14:22Z'
    owns:
      agents: [seo-analyst]
      triggers: [seo-daily]

triggers:
  - slug: seo-daily
    type: cron
    subproject: seo-watch
    cron: '0 0 9 * * 1-5'
    prompt: Check yesterday's rankings.
```

The installed list a project reads comes from **this section**, not from the
catalog. An install outlives its catalog entry: a subproject withdrawn from the store
still appears in the project with its own recorded title and pinned `sha`.

Full field reference and validation rules:
[Manifest → `subprojects:`](/docs/project/manifest#subprojects).

## After an install merges, enable the triggers

<Callout type="warn" title="A subproject installs with every trigger OFF">
  That is deliberate: a subproject that starts firing the moment it lands is a subproject nobody
  trusts.
</Callout>

Enabling a trigger **commits to the manifest** — a trigger's `enabled` field is
configuration, visible in `git log`. Enable them one at a time, on the
**Triggers** tab or with `kortix triggers enable <slug>`.

There is no switch over a whole subproject, and that is not a gap. A trigger has
exactly two switches — its own `enabled` field, and the project-wide pause
(`kortix triggers pause`). A third, subproject-shaped switch would be a second
answer to "is this on", and two answers is how they end up disagreeing.

## The Subprojects page

One page: `/projects/<id>/customize/marketplace`, the **Marketplace** tab under
Customize. It lists the catalog with `All` / `Installed` / `Available` filters
and search, marks the project's installed subprojects with a pill, and holds a
`+ Add` menu with **Add from GitHub** and **Grow your own**.

The store used to live at `/projects/<id>/subprojects`. That URL still resolves
— it is a server redirect to the Marketplace tab — so an old bookmark works.
Nothing lives deeper under either segment: the run report that was at
`/projects/<id>/subprojects/runs` is gone, because a run belongs to the trigger
that fired.

The project home carries **no** subproject surface. It is the page you start
work from, and a store grid or a run strip answers a different question.

## From the CLI

```bash
kortix subprojects publish acme/seo-subproject --ref v1.2.0 --private
kortix subprojects list --query seo
kortix subprojects install seo-watch     # opens a change request
kortix subprojects uninstall seo-watch   # also a change request
kortix triggers enable seo-daily         # now it fires
```

Full subcommand and option reference: [CLI → Subprojects](/docs/cli#subprojects).

## From the SDK

Two surfaces, deliberately separate — the account-scoped catalog, and what one
project has installed:

```ts
kortix.subprojects; // the catalog
kortix.project(projectId).subprojects; // installed, plus install/uninstall/author
```

See [SDK → Subprojects](/docs/sdk/subprojects) for every method, the React hooks, and the
error codes.
