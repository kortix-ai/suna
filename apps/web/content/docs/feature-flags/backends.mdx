A Kortix backend is a full backend for one project: a database, server
functions, realtime queries, file storage, and schedules, powered by Convex.
Each backend is a self-hosted Convex instance in its own Platinum machine. A
project owns up to 3 backends.

Backends is a [feature flag](/docs/feature-flags). Its stability is
**experimental**, and it is off by default. It is available only where
Platinum is configured.

Building on backends from TypeScript? See [SDK → Backends](/docs/sdk/backends)
for the client surface and the React hooks.

## Turn Backends on

Backends is enabled per project by Kortix. Contact Kortix to turn it on for a
project. While it is off, Settings → Feature flags does not list it. While it is
on, Settings shows it as **Managed by Kortix**, `kortix projects features` lists
`backends on kortix`, and `kortix projects info` prints `by kortix  backends`.
Only a Kortix operator can change it: `PATCH /v1/projects/:id/features`
answers `403` `feature_operator_only` to everyone else (see
[Internal-only flags](/docs/feature-flags#internal-only-flags-apps-and-backends)).

While the flag is off, or where Platinum is not configured:

- Every backends route answers `403` with
  `{ error, code: "feature_disabled", feature: "backends" }`.
- `kortix backends <subcommand>` prints the same sentence and exits `1`.

Turning the flag on where Platinum is not configured changes nothing. The flag
is `available` only when `PLATINUM_API_KEY` is set. See
[Feature flags](/docs/feature-flags).

## What a backend is

| Property | Value |
|---|---|
| Runtime | Self-hosted Convex, one instance per machine |
| Storage | SQLite on the machine disk. See [Database and durability](#database-and-durability). |
| Machine | One per backend. Default 1 vCPU, 1 GB memory, 10 GB disk; resizable to 16 vCPU, 32 GB, 100 GB. |
| Uptime | Always on. The machine never idles to a stop. |
| Billing | Reserved CPU, memory and disk × the time the machine runs. See [Billing](#billing). |
| Limit | 3 backends per project, 10 per account |
| Name | Lowercase letters, digits, and dashes. Starts with a letter. 63 characters at most. |

Your data lives on the machine disk. Kortix backs it up with the machine disk.

## Database and durability

Convex is the database. Documents, indexes, file storage and the scheduler all
live in the backend, with transactions, realtime queries and schema
validation. A backend needs no second database.

| Question | Answer |
|---|---|
| Where is the data? | Convex's SQLite files on the machine disk, next to the uploaded files. |
| Why SQLite? | Kortix measured SQLite against Postgres 17 in the same 2 vCPU machine. Throughput and median latency were the same: Convex's own CPU use is the limit, not the database. SQLite used 3.6× less disk for the same 200,000 documents (476 MB against 1,705 MB), booted 0.85 s faster, and had a lower realtime push p99 (0.25 s against 1.45 s). |
| Can I use Postgres? | Not today. An external Postgres is a possible future opt-in. It would not scale a backend out: Convex still runs as one process on one machine. Resize to scale up. |
| How fast can it write? | Convex caps writes at about 4 MiB/s per backend and answers `TooManyWrites` above it. Batch bulk imports and retry with backoff. |
| What loses no acknowledged write? | A machine stop and start, a resize, and a crash of the Convex process. Kortix measured each with writers running. |
| What can lose data? | A host crash or a hard reset of the machine. The machine disk has no file system journal yet ([kortix-ai/platinum#1450](https://github.com/kortix-ai/platinum/issues/1450)), so the last acknowledged writes can be lost, or the data directory can be left unreadable. |
| What is the recovery point? | After a host loss, Kortix restores the machine from its last automatic backup by itself. The backup runs every hour, so up to 1 hour of writes is lost (RPO ≤ 60 minutes). An unreadable data directory keeps Convex from starting; Kortix is alerted after 3 failed health probes (15 minutes), and you restore the newest snapshot. |
| How long does recovery take? | The health probe runs every 5 minutes and starts the restore from backup on the first probe that sees the host lost. The restore copies the disk from object storage and boots it; Kortix waits up to 10 minutes for it, then retries on the next probe. Kortix has not measured a real host loss, so the recovery time (RTO) is not stated as a number yet. |
| Do snapshots survive a host loss? | Not reliably. Platinum keeps snapshots on the host's disk, so a lost host can take them with it. The automatic backup is the copy that lives off the host. |

Keep your own copy of data you cannot re-create:
`npx convex export --path backup.zip --include-file-storage`. Without
`--include-file-storage` the export holds no files.

A backend has two public URLs:

| Field | Use it for |
|---|---|
| `url` | The Convex client (`CONVEX_URL`). It is public, not secret. |
| `site_url` | Convex HTTP actions. |

The admin key is secret. It controls the backend's code and data.

## Create and deploy from the CLI

The Convex code lives in your project repo. A common layout is
`backends/main/`, with a `package.json` and a `convex/` directory.

```bash
kortix backends deploy main --dir backends/main
```

`deploy` waits until the backend is `running`, then runs `convex deploy` in
`--dir` with the backend's credentials. The default for `--dir` is the current
directory.

- **Which Convex CLI:** the project's own `node_modules/.bin/convex` when it
  exists. Otherwise `npx convex@<version>`, where `<version>` is the backend's
  `convex_version` (`1.46.0` today), never the newest release.
- **A name that does not exist:** `deploy` exits `1` and lists the existing
  backends. It creates nothing, so a typo never starts a machine. Pass
  `--create` to create the backend first.

The full subcommand list:

| Command | What it does |
|---|---|
| `kortix backends list` | List the project's backends. `--json`. |
| `kortix backends create <name>` | Create a backend without deploying to it. |
| `kortix backends get <name>` | Show one backend and its status. `--json`. |
| `kortix backends dashboard <name>` | Print the link to the backend's admin dashboard. `--open` opens it. |
| `kortix backends connect <name>` | Print how to reach the backend from an App, from outside, and from the CLI. No secret. `--json`. |
| `kortix backends env <name>` | Print the Convex CLI variables for the backend. |
| `kortix backends deploy <name> [--dir <path>] [--create]` | Deploy the Convex code. `--create` creates a missing backend first. |
| `kortix backends delete <name>` | Delete the backend, its machine, and all its data. |

`--project`, `--host`, and `--json` work on every subcommand.

A new backend starts in `provisioning`. It usually becomes `running` in a few
seconds. The first create in a region also builds the machine image and takes
up to 10 minutes. A provision older than 15 minutes reads as `error`. A failed
create ends in `error` with a short reason (for example "No machine capacity is
free right now.") and releases the machine. Delete it and create it again.

A project can have 3 backends and an account 10, across its projects. A create
past either limit answers `409` `backend_limit`. Contact Kortix to raise the
account limit.

## Connect

**Connect** on a backend (the row menu in **Customize → Backends**, or the
button on the backend's page) shows working code to reach it, in three tabs.
`kortix backends connect <name>` prints the same snippets; `--json` returns
them as `{ backend, snippets: [{ id, tab, title, file, language, code }] }`.

| Tab | What it shows |
|---|---|
| App | `npm i convex @kortix/sdk`, the `VITE_CONVEX_URL` line, `convex.setAuth(kortixAppBackendToken("<name>"))`, the backend's `convex/auth.config.ts`, and a function that calls `requireKortixMember` |
| From outside | A member token from `kortix backends token <name>` or the SDK's `backends.token(id)`; `curl` calls to `<url>/api/query` and `<url>/api/mutation` with `Authorization: Bearer`; an HTTP action on `site_url`; `verifyKortixMemberToken` on your own server with the three public `KORTIX_AUTH_*` values |
| CLI & admin | `kortix backends deploy`, `eval "$(kortix backends env <name>)"`, Convex CLI commands, `kortix backends dashboard`, and the admin key |

The admin key stays hidden until you click **Reveal**. Reveal needs
`project.backend.write` and writes one `backend.credentials.read` audit event.
Closing the dialog drops the key.

Any viewer a Kortix App admits can get a member token for any backend in the
App's project. The backend decides what each member may do, with
`requireKortixMember` and its `groups` and `roles`.

The backend's page also shows the last automatic backup, the backup interval,
and how many manual snapshots it holds against its limit. Click it to open
Backups: every snapshot shows its kind (Manual, Daily, Before resize) and when
Kortix deletes it.

## The admin dashboard

Every backend has Convex's own dashboard, inside Kortix. Open the project's
**Customize → Backends** tab and click the backend. The page signs the
dashboard in for you. The tab shows only while the flag is on.

| Page | What it does |
|---|---|
| Health | Function calls, failure rate, cache hit rate, concurrency |
| Data | Browse, filter, add, edit and delete documents in every table |
| Schema | The deployed schema and its indexes |
| Functions | Every query, mutation and action, with a runner and per-function metrics |
| Files | Stored files: upload, download, delete |
| Schedules | Scheduled functions and crons |
| Logs | Live function logs |
| History | Deploys and configuration changes |
| Settings | Environment variables, authentication, components, integrations, usage limits |

From the CLI, `kortix backends dashboard main` prints the page's link.
`--open` also opens it in the browser.

The dashboard needs `project.backend.write`, because it acts with the admin
key. Kortix records each opening as `backend.credentials.read`. The key goes
from the Kortix API straight into the dashboard frame. Kortix web never
renders or stores it.

A backend created before the dashboard shipped has none. Create a new backend
and redeploy to it to get one.

## Read and write data

Print the Convex CLI variables, then use the Convex CLI:

```bash
eval "$(kortix backends env main)"
npx convex data
npx convex run messages:list '{}'
```

`kortix backends env` prints `CONVEX_SELF_HOSTED_URL` and
`CONVEX_SELF_HOSTED_ADMIN_KEY`. Reading them needs `project.backend.write`.
Kortix audits every read as `backend.credentials.read`.

:::warning[Never commit or print the admin key]
Keep the admin key out of the repo, chat, and logs. Export it into the shell
with `eval`, as shown above. To read it for yourself, run
`kortix backends env main`.
:::

## Where the code lives

A backend does not know about repositories. A deploy pushes code with the
admin key, so the Convex code can live in the project repo (the default,
`backends/<name>/`), in another directory (`--dir`), in a separate repository,
or on a laptop or CI runner that runs
`eval "$(kortix backends env main)" && npx convex deploy`.

## Sign-in: functions know the member

Every backend trusts Kortix as its identity provider. At creation Kortix gives
the backend its own signing key and writes `KORTIX_AUTH_ISSUER`,
`KORTIX_AUTH_AUDIENCE` and `KORTIX_AUTH_JWKS` into its environment. Add this
file and deploy:

```ts
// convex/auth.config.ts
export default {
  providers: [{
    type: "customJwt",
    issuer: process.env.KORTIX_AUTH_ISSUER!,
    applicationID: process.env.KORTIX_AUTH_AUDIENCE!,
    jwks: process.env.KORTIX_AUTH_JWKS!,
    algorithm: "ES256",
  }],
};
```

Read and enforce the member with `@kortix/sdk`:

```ts
import { requireKortixMember } from "@kortix/sdk";

const me = requireKortixMember(await ctx.auth.getUserIdentity());
const finance = requireKortixMember(await ctx.auth.getUserIdentity(), { groups: ["Finance"] });
```

`me` carries `userId`, `email`, `name`, `picture`, `groups` (Kortix group
names), `groupIds`, `role` (account role), `accountId` and `projectId`. An
anonymous caller, or one outside the groups or roles, throws
`KortixMemberError`. The backend URL is public, so every function that touches
non-public data must call it first. Kortix groups need the Enterprise plan;
roles work on every plan.

Kortix mints 15-minute tokens, so a member you remove loses backend access
within 15 minutes. The App gate refuses them at once:

| Caller | Token source |
|---|---|
| A person in a Kortix App | `GET /_kortix/backend-token?backend=<name>` on the App's own origin |
| An agent, script or CLI | `kortix backends token <name>`, `POST /v1/projects/:id/backends/:backendId/token`, SDK `backends.token(id)`. An agent session's token names the agent (`kind: "agent"`), with no groups and no role. |

## Use a backend from an App

The backend `url` is public. A static App reads it at build time: commit
`VITE_CONVEX_URL=<url>` in the App's `.env.production`, then build and deploy
the built directory. A server-rendered App reads `CONVEX_URL` from its `env` in
`kortix.yaml`. The App needs no admin key.

```ts
import { ConvexReactClient } from "convex/react";
import { kortixAppBackendToken } from "@kortix/sdk";

const convex = new ConvexReactClient(import.meta.env.VITE_CONVEX_URL);
convex.setAuth(kortixAppBackendToken("main"));
```

Any other server verifies the same token with
`verifyKortixMemberToken(token)`, which reads `KORTIX_AUTH_JWKS`,
`KORTIX_AUTH_ISSUER` and `KORTIX_AUTH_AUDIENCE`.

`requireKortixMember`, `readKortixMember` and `kortixAppBackendToken` need an
`@kortix/sdk` release newer than 0.13.52. Check with
`node -e "import('@kortix/sdk').then((m) => console.log(typeof m.requireKortixMember))"`:
it prints `function` when the installed SDK has them.

The issuer is a public URL on the Kortix API:
`https://<api host>/v1/backends/<backend_id>`. Kortix fixes it when it
creates the backend. Two public routes at that URL need no credential:

| Route | Answers |
|---|---|
| `GET <issuer>/.well-known/openid-configuration` | `issuer` and `jwks_uri` (OpenID Provider metadata for verifiers; no authorization endpoint) |
| `GET <issuer>/jwks.json` | The backend's public ES256 key as a JSON Web Key Set |

So a JOSE library or an API gateway finds the key from the token's `iss`
alone, and `verifyKortixMemberToken` takes `KORTIX_AUTH_JWKS=<issuer>/jwks.json`
in place of the inline value. A backend created before the issuer was a URL
moves to its URL issuer when the Kortix API next starts. Its tokens from before
the move get one 401, and Convex clients then fetch a new token. A server that
copied the old `KORTIX_AUTH_ISSUER` must copy the new value from `auth_env`.

Any viewer the App admits gets a token for any running backend of the App's
project: `?backend=<name>` picks it, and Kortix does not bind an App to its
backends. The token proves who the member is, not what they may do. So
`requireKortixMember(identity)` without `groups` or `roles` admits every
viewer of every App in the project, including the account members and groups
a `restricted` App lists who are not project members. Check `groups` or
`roles` in every function that reads or writes data not meant for all of
them.

## Access from outside

The backend URL is public. Every path below works from anywhere: a script, a
service, CI, or your own server. Each one sends either a member token (the
functions see a Kortix member) or the admin key (no identity, full control).
In the examples, `CONVEX_URL` is the backend's `url` and `CONVEX_SITE_URL`
its `site_url` (`kortix backends get main --json`).

**1. Get a member token.** It lasts 15 minutes and names the caller, with
their groups and role. In an agent session it names the agent, with no groups
and no role.

```bash
TOKEN=$(kortix backends token main)
```

```ts
import { createKortix } from "@kortix/sdk";

const kortix = createKortix({
  backendUrl: "https://api.kortix.com/v1",
  getToken: async () => process.env.KORTIX_TOKEN!,   // a personal access token
});
const { token } = await kortix.project(projectId).backends.token(backendId);
```

**2. Call a function over HTTP.** `POST <url>/api/query`, `/api/mutation` or
`/api/action`. The answer is `{"status":"success","value":…}` or
`{"status":"error","errorMessage":…}`.

```bash
curl -s "$CONVEX_URL/api/query" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"path":"tasks:list","args":{},"format":"json"}'
```

**3. Use the Convex client from Node or Bun.** `ConvexHttpClient` takes the
token as a string. `ConvexClient` (live subscriptions) takes a function and
asks it again before the token expires.

```ts
import { ConvexHttpClient, ConvexClient } from "convex/browser";

const http = new ConvexHttpClient(process.env.CONVEX_URL!);
http.setAuth(token);
const tasks = await http.query("tasks:list" as any, {});

const live = new ConvexClient(process.env.CONVEX_URL!);
live.setAuth(async () => (await kortix.project(projectId).backends.token(backendId)).token);
live.onUpdate("tasks:list" as any, {}, (rows) => console.log(rows.length));
```

**4. Use the Python client.**

```python
from convex import ConvexClient  # pip install convex

client = ConvexClient(convex_url)
client.set_auth(token)
print(client.query("tasks:list"))
```

**5. Call an HTTP action.** Routes in `convex/http.ts` answer on `site_url`.
They are public: authenticate inside the handler.

```bash
curl -s "$CONVEX_SITE_URL/webhooks/crm" -H "Authorization: Bearer $TOKEN" -d '{}'
```

**6. Verify the token on your own server.** Set the three public
`KORTIX_AUTH_*` values from `auth_env` (or `kortix backends connect main`),
then:

```ts
import { verifyKortixMemberToken } from "@kortix/sdk";

const member = await verifyKortixMemberToken(bearer);   // checks signature, issuer, audience, expiry
```

**7. Act as admin.** The admin key bypasses sign-in and runs any function,
including internal ones. Use it for tooling, never in an App or a browser.

```bash
eval "$(kortix backends env main)"     # CONVEX_SELF_HOSTED_URL, CONVEX_SELF_HOSTED_ADMIN_KEY
npx convex run tasks:list '{}'
npx convex data tasks --limit 20
npx convex export --path backup.zip --include-file-storage
npx convex mcp start                   # the Convex MCP server for an AI tool
```

`kortix backends connect main` prints paths 1, 2, 5 and 6 with the backend's
real URLs filled in.

## Customers who are not Kortix members

Kortix sign-in is for the project's own people and stays the primary
provider. When an App also serves customers, add Convex Auth (password, magic
link, OTP or OAuth) to the same backend as a second provider. Convex's CLI does
not set Convex Auth up on a self-hosted backend; the manual setup works:

1. `npm i @convex-dev/auth @auth/core@^0.41.1` in the backend.
2. Generate an RS256 key pair (Convex's `generateKeys.mjs`) and set
   `JWT_PRIVATE_KEY` and `JWKS` with `npx convex env set <NAME> --from-file <file>`,
   and `SITE_URL` to the customer App's URL.
3. Add `{ domain: process.env.CONVEX_SITE_URL, applicationID: "convex" }` to
   `providers` in `convex/auth.config.ts`, after the Kortix provider.
4. Add `convex/auth.ts` (`convexAuth({ providers: [Password] })`),
   `auth.addHttpRoutes(http)` in `convex/http.ts`, and `...authTables` in the
   schema.
5. Tell the two kinds of user apart by the token issuer:

```ts
// Staff: only a token Kortix signed.
const identity = await ctx.auth.getUserIdentity();
if (identity?.issuer !== process.env.KORTIX_AUTH_ISSUER) throw new Error("Sign in with Kortix.");
const member = requireKortixMember(identity);

// Customers: only a token Convex Auth signed.
if (identity?.issuer !== process.env.CONVEX_SITE_URL) throw new Error("Sign in to continue.");
const customerId = await getAuthUserId(ctx);
```

`requireKortixMember` alone accepts any identity with a subject, a Convex
Auth customer included. Check the issuer first in every staff function.
Kortix verified this setup end to end on the backend's Convex image: a
customer token is refused by staff functions, and a member token is refused
by customer functions. The customer UI is a separate `public` App that uses
`ConvexAuthProvider` from `@convex-dev/auth/react`.

## Agents

Agents in Kortix sessions load the `kortix-backends` system skill before they
write Convex code, and `kortix-internal-apps` when they build a complete app.
The skill runs every backend task in six steps: install (`npm i convex`,
`npx convex ai-files install`), connect (`kortix backends env`), discover
(`npx convex function-spec`, `data`, `env list --names-only`), change
(`kortix backends deploy`, `npx convex env set`, `run`, `import`), verify
(logs and a real member token from `kortix backends token`), and hand over
(`kortix backends dashboard`).

## Size, backups and restore

Each backend is one machine. Pick its size at creation and change it later.

```bash
kortix backends create main --cpu 2 --memory 4 --disk 20
kortix backends resize main --cpu 4 --memory 8      # seconds of downtime; disk only grows
kortix backends backups main                         # automatic backup, schedule, snapshots with kind and expiry
kortix backends snapshot main                        # a manual snapshot, kept until deleted
kortix backends delete-snapshot main <snapshot-id>   # frees a manual slot
kortix backends restore main <snapshot-id> --yes     # rolls back; later changes are lost
```

| | What it is |
|---|---|
| Automatic backup | Kortix copies the machine to object storage every hour, to recover from a host loss. Kortix restores it by itself; you cannot pick one. |
| Snapshot | A point-in-time copy of the running backend: data, files, functions and environment variables, plus the machine's memory. The machine pauses for the copy (seconds; up to 90 s for 8 GB of memory). |
| Restore | Rolls the running backend back to a snapshot in place, in seconds. The call answers once the machine runs the snapshot and Convex answers. |

A snapshot has a kind, and the kind decides how long it stays:

| Kind | Taken by | Kept |
|---|---|---|
| Manual | A member or agent (`kortix backends snapshot`) | Until someone deletes it. A backend holds 10; the 11th answers `409 snapshot_limit`. |
| Daily (`automatic`) | Kortix, once a day | 7 days. The newest daily snapshot stays past that until a newer one exists. |
| Before resize (`resize`) | Kortix, before every resize | 24 hours. Outside the limit of 10. |

Every Kortix-made snapshot shows its expiry (`expires_at`) from the moment it
exists, and Kortix deletes it in the 5-minute maintenance pass after that time
while the backend runs. Kortix deletes no other snapshot. One operation runs
at a time: a snapshot, restore or snapshot delete during a resize, restore,
rotation or recovery answers `409 backend_busy`, and `operation` reads
`snapshotting` or `restoring` while one of them runs.

A snapshot holds the CPU, memory and disk image of the moment it was taken. A
snapshot from before an applied resize cannot be restored (`409
snapshot_predates_resize`): restoring it would boot the old size while the
backend records the new one. The Before resize snapshot undoes a resize that
failed before the size changed. To undo a resize that worked, resize again
(a disk cannot shrink).

Limits: 1–16 vCPU, 1–32 GB memory, 10–100 GB disk. API: `PATCH
/v1/projects/:id/backends/:backendId`, `GET …/backups`, `POST …/snapshots`,
`DELETE …/snapshots/:snapshotId`, `POST …/restore`.

## Health and logs

Kortix probes every running backend every 5 minutes: the machine state, Convex
`/version` (5 s timeout) and disk use. The result is the backend's `health`
in the API, a **Not responding** badge in Kortix web, and a `health` line in
`kortix backends get`.

| The probe finds | Kortix does |
|---|---|
| Convex does not answer | Records the failure. Convex's supervisor restarts a crashed Convex within 1 s. Three failed probes in a row alert Kortix. |
| The machine is stopped | Starts it, then re-reads the admin key. `operation` reads `recovering` meanwhile. A backend in `recovering` can still be deleted. |
| The host was lost, or Platinum removed the machine with a completed backup | Restores the machine from its last automatic backup: same URLs, data since that backup is lost (up to 1 hour). |
| The machine no longer exists | After 3 probes the backend turns `error`. Delete it and create it again. |
| Disk use at 80% or more | Shows **Disk N% full**. Resize the disk (`kortix backends resize <name> --disk <gb>`). |

A create or resize survives an API restart. Each heartbeats every 20 s. One
with no heartbeat for 2 minutes is resumed: a create replays on the same
machine, an interrupted resize or rotation ends with the machine running and
`last_operation_error` set. A create interrupted 3 times turns `error`.

The Convex process log holds startup, crash and restart lines, and one line
per request:

```bash
kortix backends logs main               # the last 200 lines
kortix backends logs main --lines 1000  # up to 1000
npx convex logs                         # function logs (console.log in your functions)
```

The machine keeps each log at 50 MB plus one previous 50 MB file. Backends
created before this cap keep their image: their logs are not capped.

## Rotate the admin key

Rotate the admin key when it may have leaked: a removed project member read
it, it was printed into a session, or a `.env.local` left the machine.

```bash
kortix backends rotate-key main --yes
eval "$(kortix backends env main)"   # read the new key
```

In Kortix web: the backend page, **⋯ → Rotate admin key**. API: `POST
/v1/projects/:id/backends/:backendId/rotate-admin-key`.

Convex derives every admin key from the backend's instance secret. Rotation
writes a new instance secret and restarts Convex: about 1 second of downtime,
and clients reconnect. After it:

- Every admin key read before answers `401 BadAdminKey`.
- Documents, files, functions and environment variables are unchanged.
- Upload URLs not yet used and open pagination cursors stop working.
- Member sign-in tokens keep working: they use a different key.
- A dashboard open in Kortix web signs in again after a reload.

A restored disk (a snapshot, or the automatic backup after a host loss)
carries the instance secret it was taken with. If the backend's admin key was
ever rotated, Kortix rotates it again after every restore, so a key you
rotated away never works again. Read the admin key again after a restore.

## Use Convex directly

A backend is plain self-hosted Convex. With its URL and admin key
(`kortix backends env main`), or a member token, everything Convex works
against it: the Convex CLI, the Convex MCP server, the JavaScript, React and
Python clients, the HTTP API, and Convex components.

## Roles and audit

| Permission | Allows |
|---|---|
| `project.backend.read` | List and view backends. |
| `project.backend.write` | Create, resize and delete backends. Read the admin credentials and the process log. Rotate the admin key. |

Reading the credentials writes a `backend.credentials.read` audit event.
Rotation is `backend.credentials.rotate`; reading the log is
`backend.logs.read`. See [Audit actions](/docs/audit-actions).

## Billing

A backend is billed like a sandbox: its reserved CPU, memory and disk ×
wall-clock time while the machine runs, at the compute rate, from the
account's wallet. The default size (1 vCPU, 1 GB, 10 GB) costs about $0.081
per hour at list price, about $59 for a 30-day month. Each charge is a
`Backend compute · <cpu>vCPU/<memory>GB/<disk>GB` line in the usage ledger.

- The health probe opens the backend's compute window when it sees the
  machine running and records it alive every 5 minutes. A machine Kortix does
  not see alive stops billing after the compute liveness grace (60 minutes).
- A resize closes the window at the old size; the next probe opens one at the
  new size.
- An account that cannot pay gets `402` on create and on a resize that grows
  the machine, with the same body as every other billing gate. A shrinking
  resize is always allowed.
- Snapshot and backup storage are not billed. A backend holds up to 10
  manual, 8 daily and the Before resize snapshots, each a full disk image.
- There is no per-backend monthly budget. The caps (3 per project, 10 per
  account) bound the spend. Delete a backend to stop its charges.

## Archive, account deletion and orphans

| Event | What happens to the machine |
|---|---|
| The project is deleted (archived) | Kortix turns Platinum's auto-resume off, stops the machine and closes its compute window, at once and again on every 5-minute maintenance tick. The data stays. A public request does not wake it. |
| The project is active again | Auto-resume goes back on and the machine starts within 5 minutes. |
| The account is deleted | Kortix deletes every backend of the account: its snapshots, then its machine. The data cannot be recovered. A failure stops the account deletion, which retries. |
| A machine no live backend references | Kortix deletes it, with its snapshots, once it is 1 hour old. This covers a create interrupted before Kortix recorded the machine, and a delete that failed. |

## Limits

- A project is capped at 3 backends, an account at 10.
- Backends are always on. A backend does not stop when idle.
- One machine per backend: it scales up (resize), not out.
- `npx convex dashboard` does not work against a self-hosted backend. Use
  the dashboard in Kortix (`kortix backends dashboard <name>`).
- Convex Auth needs the manual setup above. Custom JWT or OIDC
  authentication through `auth.config.ts` works.
- Convex Cloud-only features are absent (see the table above).
- A backend keeps the image it was created with. Image fixes (the log cap,
  a newer Convex) reach new backends only. There is no in-place upgrade.
- The backend URL is the machine's provider URL, fixed for the backend's
  life. There is no stable Kortix hostname for a backend.
- Durability depends on a journaled machine disk that is not shipped yet. See
  [Database and durability](#database-and-durability).
- `npx convex export` covers data and files. It does not cover environment
  variables or pending scheduled jobs.

## Delete a backend

```bash
kortix backends delete main
```

Delete removes the machine and every document and file in it. You cannot undo
it. Export first with `npx convex export` when you need the data.
