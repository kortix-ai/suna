A Kortix backend is a full backend for one project: a database, server
functions, realtime queries, file storage, and schedules, powered by Convex.
Each backend is a self-hosted Convex instance in its own Platinum machine. A
project owns up to 3 backends.

Backends is a [feature flag](/docs/feature-flags). Its stability is
**experimental**, and it is off by default. It is available only where
Platinum is configured.

Building on backends from TypeScript? See [SDK → Backends](/docs/sdk/backends)
for the client surface and the React hooks.

## Turn Backends on

Backends is enabled per project by Kortix and is not listed in Settings →
Feature flags. Contact Kortix to turn it on for a project.

While the flag is off, or where Platinum is not configured:

- Every backends route answers `403` with
  `{ error, code: "feature_disabled", feature: "backends" }`.
- `kortix backends <subcommand>` prints the same sentence and exits `1`.

Turning the flag on where Platinum is not configured changes nothing. The flag
is `available` only when `PLATINUM_API_KEY` is set. See
[Feature flags](/docs/feature-flags).

## What a backend is

| Property | Value |
|---|---|
| Runtime | Self-hosted Convex, one instance per machine |
| Storage | SQLite on the machine disk |
| Machine | One per backend. Default 1 vCPU, 1 GB memory, 10 GB disk; resizable to 16 vCPU, 32 GB, 100 GB. |
| Uptime | Always on. The machine never idles to a stop. |
| Limit | 3 backends per project |
| Name | Lowercase letters, digits, and dashes. Starts with a letter. 63 characters at most. |

Your data lives on the machine disk. Kortix backs it up with the machine disk.

A backend has two public URLs:

| Field | Use it for |
|---|---|
| `url` | The Convex client (`CONVEX_URL`). It is public, not secret. |
| `site_url` | Convex HTTP actions. |

The admin key is secret. It controls the backend's code and data.

## Create and deploy from the CLI

The Convex code lives in your project repo. A common layout is
`backends/main/`, with a `package.json` and a `convex/` directory.

```bash
kortix backends deploy main --dir backends/main
```

`deploy` creates the backend if it does not exist, waits until it is
`running`, then runs `npx convex deploy` in `--dir` with the backend's
credentials. The default for `--dir` is the current directory.

The full subcommand list:

| Command | What it does |
|---|---|
| `kortix backends list` | List the project's backends. `--json`. |
| `kortix backends create <name>` | Create a backend without deploying to it. |
| `kortix backends get <name>` | Show one backend and its status. `--json`. |
| `kortix backends dashboard <name>` | Print the link to the backend's admin dashboard. `--open` opens it. |
| `kortix backends env <name>` | Print the Convex CLI variables for the backend. |
| `kortix backends deploy <name> [--dir <path>]` | Create if missing, then deploy the Convex code. |
| `kortix backends delete <name>` | Delete the backend, its machine, and all its data. |

`--project`, `--host`, and `--json` work on every subcommand.

A new backend starts in `provisioning`. It usually becomes `running` in a few
seconds. The first create in a region also builds the machine image and takes
longer. A failed create ends in `error` and releases the machine. Delete it and
create it again.

## The admin dashboard

Every backend has Convex's own dashboard, inside Kortix. Open the project, choose
**Backends**, then the backend's name. The page signs the dashboard in for you.

| Page | What it does |
|---|---|
| Health | Function calls, failure rate, cache hit rate, concurrency |
| Data | Browse, filter, add, edit and delete documents in every table |
| Schema | The deployed schema and its indexes |
| Functions | Every query, mutation and action, with a runner and per-function metrics |
| Files | Stored files: upload, download, delete |
| Schedules | Scheduled functions and crons |
| Logs | Live function logs |
| History | Deploys and configuration changes |
| Settings | Environment variables, authentication, components, integrations, usage limits |

From the CLI, `kortix backends dashboard main` prints the page's link.
`--open` also opens it in the browser.

The dashboard needs `project.backend.write`, because it acts with the admin
key. Kortix records each opening as `backend.credentials.read`. The key goes
from the Kortix API straight into the dashboard frame. Kortix web never
renders or stores it.

A backend created before the dashboard shipped has none. Create a new backend
and redeploy to it to get one.

## Read and write data

Print the Convex CLI variables, then use the Convex CLI:

```bash
eval "$(kortix backends env main)"
npx convex data
npx convex run messages:list '{}'
```

`kortix backends env` prints `CONVEX_SELF_HOSTED_URL` and
`CONVEX_SELF_HOSTED_ADMIN_KEY`. Reading them needs `project.backend.write`.
Kortix audits every read as `backend.credentials.read`.

:::warning[Never commit or print the admin key]
Keep the admin key out of the repo, chat, and logs. Export it into the shell
with `eval`, as shown above. To read it for yourself, run
`kortix backends env main`.
:::

## Where the code lives

A backend does not know about repositories. A deploy pushes code with the
admin key, so the Convex code can live in the project repo (the default,
`backends/<name>/`), in another directory (`--dir`), in a separate repository,
or on a laptop or CI runner that runs
`eval "$(kortix backends env main)" && npx convex deploy`.

## Sign-in: functions know the member

Every backend trusts Kortix as its identity provider. At creation Kortix gives
the backend its own signing key and writes `KORTIX_AUTH_ISSUER`,
`KORTIX_AUTH_AUDIENCE` and `KORTIX_AUTH_JWKS` into its environment. Add this
file and deploy:

```ts
// convex/auth.config.ts
export default {
  providers: [{
    type: "customJwt",
    issuer: process.env.KORTIX_AUTH_ISSUER!,
    applicationID: process.env.KORTIX_AUTH_AUDIENCE!,
    jwks: process.env.KORTIX_AUTH_JWKS!,
    algorithm: "ES256",
  }],
};
```

`await ctx.auth.getUserIdentity()` then returns the member (`subject` = Kortix
user id, `email`, `name`), or `null` for an anonymous call. The backend URL is
public, so every function that touches non-public data must reject `null`.

Kortix mints one-hour tokens:

| Caller | Token source |
|---|---|
| A person in a Kortix App | `GET /_kortix/backend-token?backend=<name>` on the App's own origin |
| An agent, script or CLI | `kortix backends token <name>`, `POST /v1/projects/:id/backends/:backendId/token`, SDK `backends.token(id)` |

## Use a backend from an App

The backend `url` is public. A static App reads it at build time: commit
`VITE_CONVEX_URL=<url>` in the App's `.env.production`, then build and deploy
the built directory. A server-rendered App reads `CONVEX_URL` from its `env` in
`kortix.yaml`. The App needs no admin key.

```ts
import { ConvexReactClient } from "convex/react";

const convex = new ConvexReactClient(import.meta.env.VITE_CONVEX_URL);
convex.setAuth(async () => {
  const res = await fetch("/_kortix/backend-token?backend=main");
  return res.ok ? (await res.json()).token : null;
});
```

## Agents

Agents in Kortix sessions load the `kortix-backends` system skill before they
write Convex code, and `kortix-internal-apps` when they build a complete app.
Both tell the agent to install Convex's own agent rules and skills at runtime
(`npx convex ai-files install`).

## Size, backups and restore

Each backend is one machine. Pick its size at creation and change it later.

```bash
kortix backends create main --cpu 2 --memory 4 --disk 20
kortix backends resize main --cpu 4 --memory 8      # seconds of downtime; disk only grows
kortix backends backups main                         # automatic backup + snapshots
kortix backends snapshot main                        # keeps the newest 5
kortix backends restore main <snapshot-id> --yes     # rolls back; later changes are lost
```

| | What it is |
|---|---|
| Automatic backup | Kortix copies the machine to object storage every hour, to recover from a host loss. |
| Snapshot | A point-in-time copy of the running backend: data, files, functions and environment variables. A resize takes one first. |
| Restore | Rolls the running backend back to a snapshot in place, in seconds. |

Limits: 1–16 vCPU, 1–32 GB memory, 10–100 GB disk. API: `PATCH
/v1/projects/:id/backends/:backendId`, `GET …/backups`, `POST …/snapshots`,
`POST …/restore`.

## Use Convex directly

A backend is plain self-hosted Convex. With its URL and admin key
(`kortix backends env main`), or a member token, everything Convex works
against it: the Convex CLI, the Convex MCP server, the JavaScript, React and
Python clients, the HTTP API, and Convex components.

## Roles and audit

| Permission | Allows |
|---|---|
| `project.backend.read` | List and view backends. |
| `project.backend.write` | Create and delete backends. Read the admin credentials. |

Reading the credentials writes a `backend.credentials.read` audit event. See
[Audit actions](/docs/audit-actions).

## Limits

- Backends are not metered. A project is capped at 3.
- Backends are always on. A backend does not stop when idle.
- One machine per backend: it scales up (resize), not out.
- Kortix has no dashboard for a backend yet. Use the CLI or MCP.
  `npx convex dashboard` does not work against a self-hosted backend.
- Convex Auth needs manual setup. Custom JWT or OIDC authentication through
  `auth.config.ts` works.
- Convex cloud features are absent: preview deployments, the AI gateway for
  `@convex-dev/agent`, and audit logs.
- `npx convex export` covers data and files. It does not cover environment
  variables or pending scheduled jobs.

## Delete a backend

```bash
kortix backends delete main
```

Delete removes the machine and every document and file in it. You cannot undo
it. Export first with `npx convex export` when you need the data.
