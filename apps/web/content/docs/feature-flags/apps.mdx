A Kortix App is a provider-neutral deployment owned by one project. Kortix runs
it on the Fly.io model. An App owns one stable URL and an access policy. Each
deploy creates an immutable, numbered release: the artifact plus its resolved
config. A failed release never replaces live traffic. A server App runs
machines per process group, and a machine can mount a volume that outlives
every release. Apps have no monthly budget: account credits pay for App
compute.

Apps is a [feature flag](/docs/feature-flags). Its stability is **stable**, and
it is off by default. Turn it on per project before you deploy.

Building on Apps from TypeScript? See [SDK → Apps](/docs/sdk/apps) for the
client surface and the React hooks.

## The model

| Concept | What it is |
|---|---|
| Release | `vN`: an artifact (static files, a bundle or Dockerfile build, or an OCI image) plus its config (`processes`, `http_service`, `services`, `mounts`, `vm`, `deploy`). It never changes. A rollback is a new release. |
| Machine | Runs a release for one process group. Its `machine_id` stays the same across releases. Each release replaces its box, so its root disk resets. |
| Process group | A named command in `processes`. Default: one group, `app`, that runs the image's own command. |
| Service | A named HTTP port of a process group, on its own host, with its own `access`. |
| Volume | A persistent disk (Platinum) that one machine mounts at a time. It outlives every release and every machine. Daily snapshots, restore, and fork. |
| Label | A free-form tag, for example `backend`. Labels group and filter Apps. No behavior depends on them. |

A database, a queue, or any other backend is an ordinary server App with a
volume. There is no backend type. Templates (`kortix apps launch --template
<name>`) write a ready-made App's config; see
[Template `convex`](#template-convex-a-convex-backend).

Every App response carries `capabilities`, `labels`, `scale` (machines per
process group), `services` (each with its URL), `machines` (`total`,
`running`, `stopped`), `volumes` (`count`, `size_gb`), `config` (the live
release's config; `null` for a static App or before the first deploy), `uses`
and `used_by` (the Apps it uses and the Apps that use it, by slug), and `auth`
(the values that verify its sign-in tokens). Clients branch on
`capabilities`:

| Capability | The App has it when |
|---|---|
| `deployments`, `rollback`, `preview`, `member_tokens` | Always |
| `static` | The live release is static files |
| `sleep`, `machines`, `scale`, `exec` | The live release runs a server |
| `volumes`, `snapshots` | The App has a volume, or the live release mounts one |

A route gated by a capability the App lacks answers `409`:

```json
{ "error": "This App does not support rollback.", "code": "app_capability_unsupported", "capability": "rollback" }
```

The machine and volume routes of an App with no machines answer
`409 app_no_machines`.

The routes live under `/v1/projects/:projectId/apps/:appId`:

| Route | Permission |
|---|---|
| `GET machines` | `project.app.read` |
| `POST machines/:machineId/{start,stop,restart}`, `DELETE machines/:machineId` | `project.app.deploy` |
| `PUT scale` `{ count: { <group>: n } }` | `project.app.deploy` |
| `POST exec` `{ command, machine_id?, timeout_s? }` | `project.app.admin` |
| `GET volumes`, `GET volumes/:volumeId/snapshots` | `project.app.read` |
| `POST volumes`, `PATCH volumes/:volumeId`, `POST volumes/:volumeId/snapshots`, `POST volumes/:volumeId/fork` | `project.app.deploy` |
| `POST volumes/:volumeId/restore` `{ snapshot_id }`, `DELETE volumes/:volumeId?confirm=<name>` | `project.app.admin` |
| `POST token` | `project.app.read` (capability `member_tokens`) |

| Permission | Allows |
|---|---|
| `project.app.read` | List and view Apps, machines, volumes and snapshots. Mint a sign-in token. |
| `project.app.write` | Create, change, label, and delete Apps. |
| `project.app.deploy` | Deploy, roll back, start and stop. Start, stop, restart, and destroy machines. Scale. Create, extend, snapshot, and fork volumes. |
| `project.app.admin` | Run a command in a machine (`exec`), restore or destroy a volume, open an `access: admins` service, delete an App that has volumes. Granted to every role that held both `project.app.write` and `project.app.deploy` when it was introduced. |

## Turn Apps on

Apps is enabled per project by Kortix and is not listed in Settings → Feature
flags. Contact Kortix to turn it on for a project. A project that already has
it keeps it.

While the flag is off:

- Every Apps route answers `403` with
  `{ error, code: "feature_disabled", feature: "apps" }`.
- `kortix apps <subcommand>` prints the same sentence and exits `1`.
- The **Apps** tab does not appear in Customize. Opening
  `/projects/<id>/customize/apps` directly shows a gate screen. The page itself
  never enables the feature.

Volumes need the Platinum provider. A release with `mounts` on another
provider answers `400 app_volumes_unsupported`.

## Sources

A `static` App runs no server: Kortix stores its files and serves them itself,
behind the App's access gate. A deploy takes seconds, there is no cold start and
no compute bill, and a rollback is instant. The other three sources run in
machines on a Kortix sandbox provider (Daytona, Platinum, or E2B) and share
one deployment contract and one cold-wake contract. Build a `bundle` source
locally and deploy its output directory as `static` to get static hosting.

| Source | Deploy this | Kortix does |
|---|---|---|
| `static` | Plain HTML, CSS, JS, or a prebuilt SPA or `dist/` | Serves the files |
| `bundle` | A package source | Runs the install and build commands, then serves the output directory |
| `dockerfile` | A repository with a Dockerfile | Builds the image, then runs your `command` on your `port` |
| `oci_image` | A public image reference | Runs your `command` on your `port` |

Pick the fastest path for the result you want:

- Build Vite locally and deploy `dist/` as `static` for the lowest latency.
- Deploy the package source as `bundle` when Kortix must run the install and
  build.
- Export Next.js with `output: 'export'` and deploy `out/` as `static` when the
  App needs no server runtime.
- Deploy server-rendered Next.js and arbitrary services as `dockerfile`, with
  an explicit command and port.
- Deploy an existing public image as `oci_image`, with an explicit command and
  port.

`dockerfile` and `oci_image` require `--command` and `--port` (or
`http_service.internal_port`). A `kortix.yaml` block with `processes` and no
service is worker-only and needs no port. `static` and `bundle` need neither.

A static App holds at most 20,000 files of at most 50 MiB each; a larger site
fails with `invalid_site`. A static App runs no server, so it ignores `env` and
`secrets`: a deploy that sets them records an `environment_ignored` event. The
CLI never uploads `.env*` files, so a build-time value such as `VITE_*` in
`.env.production` reaches the App only through a build you run before the
deploy.

## Deploy from the CLI

```bash
npm run build
kortix apps deploy dist --type static --spa
```

`deploy` creates the App on first use, registers an immutable artifact —
uploading a `.tar.gz` for a path, or recording the reference for `--image` —
builds it, and blocks until the stable URL is ready. The wait budget is `--wait-seconds`,
default `1200`. Use `--no-wait` only when another process owns status tracking.

```bash
kortix apps deploy dist --slug docs --type static --spa --access project
kortix apps deploy . --type dockerfile --on-demand --command '["node","server.js"]' --port 3000
kortix apps deploy --image ghcr.io/acme/service:2026-08-07 --command '["node","server.js"]' --port 3000
```

The full subcommand list:

| Command | What it does |
|---|---|
| `kortix apps list` | List the Apps you may open: slug, state, URL. `--json` adds labels, scale, services, and capabilities. |
| `kortix apps create <slug>` | Create an App without deploying it. `--name`, `--cpu`, `--memory`, `--disk`, `--idle-timeout`, `--always-on` or `--on-demand`, `--uses <slugs>`. |
| `kortix apps launch --template <name>` | Add a ready-made App to `kortix.yaml` and deploy it (Fly `launch`). `--name <slug>` (default: the template name), `--no-deploy` writes `kortix.yaml` only. Template: `convex`. |
| `kortix apps deploy [path]` | Deploy a directory, a `.tar.gz`, or `--image` as a new release. `--always-on` and `--on-demand` set the run mode. With no path and several `apps` blocks, it deploys every block in link order: each after the Apps it uses, then by name. |
| `kortix apps set <id\|slug>` | Change an existing App: `--name`, `--cpu`, `--memory-gb`, `--disk-gb`, `--idle-timeout`, `--always-on`, `--on-demand`, `--uses <slugs>` (replaces; `--uses=` clears). |
| `kortix apps link <id\|slug> --uses <slugs>` | Add Apps this App uses. `kortix apps unlink` removes them. |
| `kortix apps show <id\|slug>` | Show the App: capabilities, links, the cost line (`about $N/month` for an always-on server App only), and its releases; marks the live one. `--json`. |
| `kortix apps releases <id\|slug>` | List releases (`vN`, status, strategy); marks the live one. |
| `kortix apps rollback <id\|slug> <id\|vN>` | A new release from that release's artifact and config, rolled out like a deploy. Volumes keep their data. Waits unless `--no-wait`. |
| `kortix apps machines [ls] <id\|slug>` | List machines: id, process group, state, release, size, volume. |
| `kortix apps machines start\|stop\|restart <id\|slug> <machine>` | Act on one machine. |
| `kortix apps machines destroy <id\|slug> <machine>` | Destroy one machine. Its volume stays; its group runs one machine fewer. |
| `kortix apps scale count <id\|slug> <n>` | Machines for a process group (0–20). `--process <group>` (default `app`). A group with a mount gets one new, empty volume per new machine. |
| `kortix apps scale show <id\|slug>` | Machines per process group. |
| `kortix apps exec <id\|slug> -- <command…>` | Run one command in a running machine and print its output (`project.app.admin`; audited). `--machine <id>`, `--timeout <s>` (at most 300). Exits with the command's exit code. |
| `kortix apps volumes [ls] <id\|slug>` | Volumes: name, process group, size, attached machine, snapshot retention. |
| `kortix apps volumes create <id\|slug> <name> --size <gb>` | Pre-create a volume. `--process <group>`. |
| `kortix apps volumes extend <id\|slug> <volume> --size <gb>` | Grow a volume. It never shrinks. |
| `kortix apps volumes snapshots\|snapshot <id\|slug> <volume>` | List snapshots (`daily`, `manual`, `final`), or take one now. |
| `kortix apps volumes restore <id\|slug> <volume> <snapshot>` | Restore (`project.app.admin`): its machine stops and comes back on the restored volume. |
| `kortix apps volumes fork <id\|slug> <volume> <name>` | A new, unattached copy, made at once. `--snapshot <id>` copies a snapshot instead of the current contents. |
| `kortix apps volumes destroy <id\|slug> <volume> --yes` | `project.app.admin`. Kortix keeps a final snapshot 7 days. |
| `kortix apps labels <id\|slug> [a,b]` | Show or replace labels. `--clear` removes them all. |
| `kortix apps auth-env <id\|slug>` | Print what verifies the App's sign-in tokens offline, as dotenv lines: `KORTIX_AUTH_ISSUER`, `KORTIX_AUTH_AUDIENCE`, `KORTIX_AUTH_JWKS` (the key set inline, as a `data:` URL). Public values. `--json`. |
| `kortix apps logs <id\|slug> [deployment]` | Read runtime logs. `--after N --limit N`. |
| `kortix apps connect <id\|slug>` | Print how to reach the App from code, the same snippets as Connect in Kortix web. No secret. `--json`. |
| `kortix apps token <id\|slug>` | Print a 15-minute sign-in token for the App, naming you (`member_tokens`). |
| `kortix apps start <id\|slug>` | Permit requests and start the App. |
| `kortix apps stop <id\|slug>` | Suspend compute now. The next authorized request wakes it. |
| `kortix apps access <id\|slug>` | Read or update the access policy. |
| `kortix apps access-link <id\|slug>` | Create a short-lived authenticated browser URL. |
| `kortix apps delete <id\|slug>` | Delete the App, its machines, and every release image. Its volumes keep a final snapshot 7 days. `--yes`. |
| `kortix apps delete <id\|slug> --deployment <id\|vN>` | Delete one release and its image. Not the live one. `--yes`. |

`--project`, `--host`, and `--json` work on every subcommand. A subcommand for
a capability the App lacks exits `1` with `App <slug> does not support
<capability>.` before it calls the API.

`kortix apps set` sends only the flags you pass, and needs project write
access. `--memory-gb` accepts `--memory` and `--disk-gb` accepts `--disk` as
aliases. `--idle-timeout` takes 120-86400 seconds. A machine change applies to
the next release. A run-mode change applies within 5 minutes, without a
redeploy.

### Deployment defaults from `kortix.yaml`

An `apps.<name>` block is the App's `fly.toml`: deploy defaults plus the
release config. The server stays the App control plane: the block never
carries access, passwords, or member ids.

```yaml
apps:
  docs:
    path: docs/dist
    type: static
    spa: true
    uses: [api]
  api:
    path: services/api
    type: dockerfile
    command: ["node", "server.js"]
    labels: [backend]
    always_on: true
    processes:
      app: ""                        # "" runs the image's own command
      worker: "node worker.js"       # no service: a worker
    http_service:
      internal_port: 3000
      access: app                    # public | app | admins
      processes: [app]
      checks: [{ type: http, path: /health }]
    services:
      - { name: admin, internal_port: 3001, access: admins }
    mounts:
      - { source: data, destination: /data, initial_size_gb: 10, processes: [app] }
    vm:
      - { cpu: 1, memory_gb: 2 }
      - { cpu: 1, memory_gb: 1, processes: [worker] }
    deploy:
      release_command: "node migrate.js"
    env:
      PUBLIC_BASE: https://example.com
    secrets:
      API_TOKEN: api_token
```

| Field | Meaning |
|---|---|
| `path`, `type`, `image`, `dockerfile`, `command`, `root`, `output_dir`, `install_command`, `build_command`, `spa` | The source. `command` is the image's argv. |
| `port`, `readiness_path` | Shorthand for `http_service.internal_port` and an HTTP check. |
| `always_on`, `idle_timeout_seconds`, `resources` | Run mode and the App's default machine size. |
| `env`, `secrets` | Runtime values, and runtime keys mapped to project secret **identifiers**. |
| `uses`, `labels` | Apps this App uses; free-form tags. |
| `processes` | Process group → shell command. |
| `http_service` | The primary service: `internal_port`, `access`, `auto_stop_machines` (`off`, `stop`, `suspend`), `auto_start_machines`, `min_machines_running`, `processes`, `checks`. |
| `services` | More HTTP services: `{ name, internal_port, access, processes, checks }`. |
| `mounts` | Volumes: `{ source, destination, initial_size_gb, snapshot_retention_days, processes }`. |
| `vm` | Machine size per group: `{ cpu, memory_gb, disk_gb, processes }`, or a list of them. |
| `deploy` | `strategy` (`bluegreen`, `rolling`, `immediate`, `canary`) and `release_command`. |

Select a block with `kortix apps deploy --manifest-app docs`. An explicit flag
always wins over the block. A static block needs only `path`, `type`, and
`spa`: the run mode, machine, `env`, `secrets`, and the release config apply
to server Apps. A block with `uses` replaces the App's list of used Apps on
every deploy, and a block with `labels` replaces its labels. `kortix apps
deploy` with no arguments deploys every block, used Apps first.

`kortix validate` refuses the same release config the API refuses
(`400 app_config_invalid` with `issues: [{ path, message }]`). `kind` and
`monthly_budget_usd` are retired: the validator warns, and the deploy ignores
them.

### Apps an App uses: sign-in tokens and bindings

An App can use other Apps of its project (`uses`). A new App uses none.

| Surface | Set the list |
|---|---|
| CLI | `kortix apps link <app> --uses <other>` |
| `kortix.yaml` | `uses: [db]` in the `apps.<name>` block, applied by `kortix apps deploy` |
| API | `uses` on `POST /v1/projects/:projectId/apps` and `PATCH …/apps/:appId` |

Every project has one sign-in token issuer:
`https://<api host>/v1/projects/<project_id>`. Its
`/.well-known/openid-configuration` and `/jwks.json` are public. A token is an
ES256 JWT that lives 15 minutes. Its `aud` is the id of the App it is for. Every
App response carries the three values that verify it: `auth.issuer`,
`auth.audience` and `auth.jwks_uri`.

| Who | How they get a token |
|---|---|
| A person in an App | `GET /_kortix/token?audience=<slug or id>` on the App's own origin (`kortixToken({ audience })` in `@kortix/sdk`). The audience is the App itself (the default) or an App it uses. |
| A member, the CLI, an agent | `POST /v1/projects/:projectId/apps/:appId/token`. An agent session gets a token that names its agent, never the person who started it. |

Any other audience answers `403` with `error: "app_not_linked"`. Code in one
App never gets a token for an App it does not use.

Kortix injects the verifying values into every server App's runtime:
`KORTIX_AUTH_ISSUER` (the project issuer), `KORTIX_AUTH_AUDIENCE` (the App's own
id) and `KORTIX_AUTH_JWKS` (the project key set, as a `data:` URI).
`verifyKortixToken(bearer)` from `@kortix/sdk` works in a server App with no
options. Do not set `KORTIX_AUTH_*` in the App's `env`: the `KORTIX_` prefix is

The bindings mount `/_kortix/apps/<slug>/*` on an App's origin reaches the
`http` service of an App it uses, HTTP and WebSocket, with the prefix removed.
`/_kortix/apps/<slug>--<service>/*` reaches another of its services. App code
needs one origin and no CORS (`kortixBinding("<slug>")` in `@kortix/sdk`
returns the URL and a token). The mount passes the App's own access gate first.
The used App authenticates the caller itself, with the token.

| The used App or service | Answer |
|---|---|
| Not in `uses` | `403 app_not_linked` |
| A service with `access: admins` | `403 app_binding_forbidden`: never bound |
| A static App | `409 app_binding_unsupported`: it runs no server |
| No running release | `503 app_binding_unavailable` |
| No such service | `404 app_service_not_found` |

### Machine and idle timeout

| Setting | Default | Bounds |
|---|---|---|
| `cpu` | `1` | `1` to `32` cores |
| `memory_gb` | `2` | `1` to `128` GiB |
| `disk_gb` | `10` | `1` to `500` GiB |
| `idle_timeout_seconds` | `300` | `120` to `86400`. Only for an on-demand App |
| `always_on` | `true` for a new App | `true` or `false` |

These are the App's default machine size. A release's `vm` sizes each process
group and overrides them; a resize is a new release, never an image rebuild.

Static Apps ignore the machine, idle timeout and run mode: they have no
runtime. They serve while they have an active deployment, so
`kortix apps start` and `kortix apps stop` answer `409 static_app_no_runtime`.
Delete the App to take it offline.

### Always on, or on demand

A server App (`dockerfile`, `oci_image`, `bundle`) runs in one of two modes:

| Mode | Behaviour | Use it for |
|---|---|---|
| Always on (`--always-on`, default) | Runs 24/7. Kortix restarts it within 5 minutes if it stops, and refreshes its runtime in the background. | Websockets, background loops, anything that must run without a request |
| On demand (`--on-demand`) | Stops after `idle_timeout_seconds` without requests; the next request wakes it (cold start). | Every App that only answers requests |

Every 5 minutes a keep-alive pass checks every running App and every
always-on App:

1. **Cost.** A running App (either mode) stops when its account can no longer
   pay for compute (the check that refuses a new session). The stop is
   recorded as an `app_stopped_unfunded` event on the deployment. The URL then
   shows the "paused" page.
2. **Alive.** Kortix asks the provider about each always-on App. A running one
   bills for every hour it runs, with or without traffic. A stopped one is
   started again through the same entitlement and concurrency checks as a cold
   start.
3. **Refresh.** When a release ships a new App supervisor, at most 5 always-on
   Apps rebuild per pass. A release that changes only the API rebuilds
   nothing. A rebuild that failed is not repeated for the same source and
   supervisor: never after a build or site error, and at most once an hour
   after a provider error.

Always-on depends on the provider:

| Provider | Always-on behaviour |
|---|---|
| Platinum (Kortix Cloud) | The VM is persistent. The provider never idle-stops it. |
| Daytona, E2B (self-host) | The VM keeps the provider's idle backstop. Keep-alive renews it every 5 minutes. If the provider stops the VM anyway (for example, an E2B plan's maximum sandbox length), keep-alive restarts it within 5 minutes, so the App can be unreachable for up to 5 minutes. |

An App switched from on demand to always on keeps its current VM until the
next deployment. On Platinum that VM keeps its idle backstop (12 hours without
traffic by default); keep-alive restarts it within 5 minutes if it stops.

#### Cost

Apps have no monthly budget. Account credits pay for App compute. The account
billing gate is the only cost gate: it answers `402` (for example
`app_account_unfunded`), and an unfunded account's running Apps stop.

| App | Cost |
|---|---|
| On-demand server App | Compute time while its machines are awake |
| Always-on server App | Fixed: every machine's size × 24/7 = `estimated_monthly_usd` |
| Static App | None: there is no machine. `estimated_monthly_usd` is `0`. |

`estimated_monthly_usd` is the cost of the live release's machines at list
rates, running 24/7 for a month: each process group's `vm` × its scale. An
always-on App of the default machine (1 vCPU, 2 GiB, 10 GiB disk) costs about
73.48 USD a month. One machine of 1 vCPU, 1 GiB, 10 GiB (the `convex`
template's backend) costs about 59.29 USD. The web app shows the fixed monthly
cost for an always-on server App only (for example
`About $59 a month · 1 vCPU · 1 GB`). `kortix apps show` prints a
`cost about $N/month (… 24/7)` line for the same Apps. Kortix does not bill
volume storage today.

`--budget` is retired. `kortix apps deploy`, `create` and `set` accept it only
to print `--budget is ignored: Apps have no budget.` They send nothing. The API
ignores `monthly_budget_usd` from an older client (`200`, no error).
`monthly_budget_usd` in `kortix.yaml` is retired: the validator warns and the
deploy ignores it. To lower the cost, switch to on demand, scale down, or
shrink the machines.

Change the mode with `kortix apps set <app> --always-on|--on-demand`,
`always_on` in `kortix.yaml`, or the App's menu in the web app. A new App's
mode defaults to the operator's `KORTIX_APPS_DEFAULT_ALWAYS_ON`.

### Versions kept

An App keeps its live release and the 5 newest other ready ones as
rollback targets (`KORTIX_APPS_RETAINED_DEPLOYMENTS`). Older deployments are
retired after every deploy: their runtime, image, files and build logs are
freed, and they leave the deployment list. Archives no remaining deployment
uses are deleted a day after upload. A failed or cancelled deployment keeps its
build log for 14 days.

A build log keeps the first 2,500 and the last 2,500 lines; a
`log_truncated` event records how many lines in between were dropped.

Apps reject a machine larger than the limits instead of clamping it. An App
records its requested spec and bills off that record, so a silent downgrade
would charge for compute the provider never gave. An out-of-range value answers
`400` with `code: "app_machine_out_of_range"`.

Creating an App past the account's App quota answers `402` with
`code: "app_quota_exceeded"`. A duplicate slug in the same project answers
`409`.

## Releases, machines, and volumes

This section applies to server Apps. A static App has releases but no
machines and no volumes.

### Process groups and services

```yaml
processes:
  app: ""                      # "" runs the image's own command
  worker: "node worker.js"     # a shell command
http_service:                  # the primary service: the App's own host
  internal_port: 3000
  access: app                  # public | app | admins
  auto_stop_machines: stop     # off | stop | suspend
  auto_start_machines: true
  min_machines_running: 0
  processes: [app]
  checks: [{ type: http, path: /health, interval_s: 15, timeout_s: 5, grace_period_s: 10 }]
services:
  - { name: site, internal_port: 3001, access: public }
```

- Without `processes`, the App has one group, `app`, that runs `command`.
- The primary service answers on the App's host. Another service answers on
  `<env>-<slug>-<route-key>--<name>.apps.kortix.com` (locally
  `<route-key>--<name>.apps.localhost`). `app.services[].url` holds each URL.
  An unknown service host answers `404 app_service_not_found`.
- `access` gates the service host. `public`: no gate. `app` (the default): the
  App's [access mode](#access-modes). `admins`: the access mode, then project
  managers only; anyone else gets `403 app_service_admins_only`.
- The proxy spreads requests over the group's running machines. With
  `auto_stop_machines: stop`, an idle machine stops and the next request
  starts one. `min_machines_running` keeps that many up. `suspend` stops the
  machine like `stop` today. `always_on: true` is the shorthand for
  `auto_stop_machines: off` and `min_machines_running: 1`.
- A group that no service names is a worker. It runs and is never idle-stopped.
- Checks run inside the machine. Defaults: `interval_s` 15, `timeout_s` 5,
  `grace_period_s` 10. A release goes live only when every check of every new
  machine passes. `port` plus `readiness_path` is the shorthand for one HTTP
  check.
- Ports `7331` and `8080` belong to the App supervisor and are refused.

Every machine gets this environment, besides the release's `env` and
`secrets`:

| Variable | Value |
|---|---|
| `KORTIX_APP_SLUG` | The App's slug |
| `KORTIX_APP_URL` | The App's URL (its primary service) |
| `KORTIX_SERVICE_URL_<NAME>` | The URL of every other HTTP service (`-` becomes `_`) |
| `KORTIX_MACHINE_ID` | The machine id, stable across releases |
| `KORTIX_PROCESS_GROUP` | The machine's process group |
| `KORTIX_AUTH_ISSUER`, `KORTIX_AUTH_AUDIENCE`, `KORTIX_AUTH_JWKS` | Verify the App's sign-in tokens (see [Apps an App uses](#apps-an-app-uses-sign-in-tokens-and-bindings)) |

### Deploy strategies and the release command

| Strategy | What happens | Default when |
|---|---|---|
| `bluegreen` | Every new machine starts and passes its checks. Then traffic moves and the old machines go. No downtime. | The release has no mount |
| `rolling` | One machine at a time. A machine with a volume hands it over: the old machine stops, the volume detaches, the new machine mounts it. Seconds of downtime. | The release has a mount |
| `immediate` | Every machine is replaced at once. Traffic moves without waiting for checks. | — |
| `canary` | One new machine first. When it is healthy, the rest roll. | — |

`bluegreen` and `canary` are refused with a mount: they would put two machines
on one volume. A release that never gets healthy is abandoned: its machines
go, traffic stays on (or returns to) the previous release, and a replaced
machine comes back on its own volume.

`deploy.release_command` runs once per release, after the build and before any
machine changes. It runs in a temporary machine with the new image, the
release's `env` and `secrets`, and no volume. A non-zero exit fails the release
with `release_command_failed`, and nothing changes. Use it for schema
migrations of an external database. A release records
`release_command_status` (`running`, `succeeded`, `failed`).

### Machines and scale

```bash
kortix apps machines api                        # id, group, state, release, size, volume
kortix apps scale count api 3 --process worker  # 0–20 machines per group
kortix apps machines restart api <machine>
kortix apps exec api -- node scripts/report.js  # project.app.admin; audited
```

- `scale count` sets the machines of one process group. Kortix applies it in
  the background (`202`). Default: 1 machine per group.
- A machine keeps its id across releases. Destroying a machine keeps its
  volume, and its group runs one machine fewer.
- `exec` runs one command in a running machine of the live release, or in
  `--machine <id>`. Timeout 1–300 s, default 60. `stdout` and `stderr` are
  cut at 1 MiB each (`truncated: true`). A stopped machine answers
  `409 machine_not_running`.

### Volumes

```yaml
mounts:
  - { source: data, destination: /data, initial_size_gb: 10, snapshot_retention_days: 5 }
```

- A volume is a persistent disk on Platinum. It outlives every release and
  every machine. Each machine of a mounted group has its own volume. A new
  machine takes a free volume of that name first, else gets a new, empty one
  (`initial_size_gb`, default 1).
- One machine writes a volume at a time, and a machine mounts at most one
  volume. Two read-write mounts of one volume lose data, so Kortix holds a
  single-writer lock per volume.
- Size: 1 to 100 GB. `volumes extend` grows a volume; it never shrinks
  (`400 volume_shrink_refused`).
- A `destination` cannot be `/` or sit under a system directory (`/bin`,
  `/boot`, `/dev`, `/etc`, `/lib`, `/lib64`, `/proc`, `/root`, `/run`, `/sbin`,
  `/sys`, `/usr`, `/var`, `/kortix`). Use `/data` or `/srv/...`.
- `volumes create` pre-creates a volume: a later machine of its group with a
  mount of that name takes it.

| Operation | What it does |
|---|---|
| Daily snapshot | Kortix takes one per volume per day. |
| `volumes snapshot` | A `manual` snapshot of the latest committed contents. The last ~1 s of writes to a mounted volume can be missing. |
| Retention | `daily` and `manual` snapshots are kept `snapshot_retention_days` (1–60, default 5). |
| `volumes restore` | `project.app.admin`. The machine stops, the volume returns to the snapshot, and the machine starts on it (`202`). A restore is a new version: the replaced contents stay in the volume's history. |
| `volumes fork` | A new, unattached volume in the same App, from a snapshot or the current contents. Made at once. |
| `volumes destroy` | `project.app.admin`, with `confirm=<volume name>`. Refused with `409 volume_attached` while a machine mounts it. Kortix takes a `final` snapshot and purges the data after 7 days. |

Volume errors: `400 volume_name_invalid` (1–30 lowercase letters, digits or
`_`), `400 volume_size_invalid`, `400 volume_retention_invalid`,
`400 snapshot_invalid`, `404 volume_not_found`, `409 volume_attached`.

Not supported yet: TCP services (a Postgres or Redis client protocol) and
private networking between Apps. A service with `protocol: tcp` is refused at
validate and deploy time. Until then a database that speaks raw TCP is
reachable only from inside its own machine (`kortix apps exec`).

## Template `convex`: a Convex backend

The `convex` template is a full backend for one project: a database, server
functions, realtime queries, file storage, schedules, and search, powered by
self-hosted Convex, with Kortix sign-in. It is an ordinary server App: a
pinned image, a volume, two services, and a dashboard App next to it. Every
command in this section works for any App.

```bash
kortix apps launch --template convex --name db
```

`launch` writes two blocks into `kortix.yaml` and deploys them:

| App | What it is |
|---|---|
| `db` | The backend: the self-hosted Convex image, pinned by digest. `http` service on port 3210 (`access: public`, a `/version` check): the Convex client URL, the sync WebSocket, and the admin API. `site` service on port 3211 (`access: public`): HTTP actions, on `<db host>--site`. A `data` volume at `/convex/data`. Always on, 1 vCPU / 1 GB / 10 GB, label `backend`. |
| `db-dashboard` | Convex's dashboard, `access: admins`, on demand. It `uses: [db]` and reaches the backend through its own origin (`/_kortix/apps/db`). |

Both backend services are `public` on purpose: Convex enforces sign-in in its
functions. The dashboard is for project admins (`project.app.admin`) only. `--no-deploy` writes
the blocks and deploys nothing.

| Property | Value |
|---|---|
| Storage | Convex's SQLite files on the `data` volume |
| Machines | One. Scaling the group above 1 gives each machine its own, empty volume: two independent databases behind one URL. |
| Cost | Fixed: about 59 USD a month (one always-on 1 vCPU / 1 GB machine). The dashboard costs only while it is open. |
| Resize | Change `vm` in the block and deploy: a new release; the volume keeps the data. |
| Convex CLI | `convex@1.46.0`, the version that matches the pinned backend. A newer CLI can need server APIs the backend lacks. |

### Connect and deploy Convex code

The Convex code lives in the project repo, for example `apps/db/` with a
`package.json` and a `convex/` directory. The admin key comes from the machine
itself:

```bash
kortix apps exec db -- sh -c "cd /convex && ./generate_admin_key.sh"   # project.app.admin
kortix secrets set CONVEX_SELF_HOSTED_ADMIN_KEY=<key>                  # keep it as a project secret

cd apps/db
npm install convex@1.46.0 @kortix/sdk
export CONVEX_SELF_HOSTED_URL=<the db App URL> CONVEX_SELF_HOSTED_ADMIN_KEY=<key>
kortix apps auth-env db | while IFS='=' read -r k v; do printf '%s' "$v" | npx convex env set "$k"; done
npx convex deploy
```

`npx convex deploy` pushes functions, schema, and indexes. A type error, or a
schema that existing documents violate, fails the push before anything
changes. `auth-env` sets `KORTIX_AUTH_ISSUER`, `KORTIX_AUTH_AUDIENCE`, and
`KORTIX_AUTH_JWKS` (the key set as a `data:` URL) on the Convex deployment, so
`convex/auth.config.ts` verifies Kortix tokens. Take
`kortix apps volumes snapshot db data` before a migration, a bulk import, or a
destructive backfill.

:::warning[Never commit or print the admin key]
The admin key controls the backend's code and data. Keep it out of the repo,
the chat, the logs, and every web App. A leaked key cannot be rotated in place
today: export the data (`npx convex export --include-file-storage`), launch a
new backend App, import it there, then delete the old App.
:::

The dashboard: `kortix apps access-link db-dashboard` prints a five-minute
browser link (project admins). Log in with the admin key.

### Sign-in: functions know the member

Add this file and deploy:

```ts
// convex/auth.config.ts
export default {
  providers: [{
    type: "customJwt",
    issuer: process.env.KORTIX_AUTH_ISSUER!,
    applicationID: process.env.KORTIX_AUTH_AUDIENCE!,
    jwks: process.env.KORTIX_AUTH_JWKS!,
    algorithm: "ES256",
  }],
};
```

Read and enforce the member with `@kortix/sdk`:

```ts
import { requireKortixMember } from "@kortix/sdk";

const me = requireKortixMember(await ctx.auth.getUserIdentity());
const finance = requireKortixMember(await ctx.auth.getUserIdentity(), { groups: ["Finance"] });
```

`me` carries `userId`, `email`, `name`, `picture`, `groups` (Kortix group
names), `groupIds`, `role` (account role), `accountId` and `projectId`. An
anonymous caller, or one outside the groups or roles, throws
`KortixMemberError`. The App's URL is public, so every function that touches
non-public data must call it first. Kortix groups need the Enterprise plan;
roles work on every plan.

In a React client, set up the Convex client with `ConvexProvider` and
`convex.setAuth(binding.token)`. Do not call `useConvexAuth()`: it throws under
a plain `ConvexProvider`, because it needs `ConvexProviderWithAuth`. Read the
signed-in member with a query:

```ts
// convex/members.ts
import { query } from "./_generated/server";
import { readKortixMember } from "@kortix/sdk";

export const me = query({
  args: {},
  handler: async (ctx) => readKortixMember(await ctx.auth.getUserIdentity()),
});
```

```tsx
const me = useQuery(api.members.me);
// undefined while loading, null when signed out, the member otherwise.
```

`readKortixMember` returns `null` for an anonymous caller. Use
`requireKortixMember` only where a function must throw.

Tokens last 15 minutes, so a member you remove loses access within 15
minutes. The App gate refuses them at once. Which callers get a token, and
from where: [Apps an App uses](#apps-an-app-uses-sign-in-tokens-and-bindings).

The token proves who the member is, not what they may do. Every person an App
admits gets tokens for every App that App uses. Check `groups` or `roles` in
every function whose data is not meant for all of them.

### Access from outside

The App's URL is public. Every path below works from anywhere: a script, a
service, CI, or your own server. Each one sends either a member token (the
functions see a Kortix member) or the admin key (no identity, full control).
`CONVEX_URL` is the App's `url` and `CONVEX_SITE_URL` the URL of its `site`
service (`app.services`).

**1. Get a member token.** It lasts 15 minutes and names the caller, with
their groups and role. In an agent session it names the agent, with no groups
and no role.

```bash
TOKEN=$(kortix apps token db)
```

```ts
import { createKortix } from "@kortix/sdk";

const kortix = createKortix({
  backendUrl: "https://api.kortix.com/v1",
  getToken: async () => process.env.KORTIX_TOKEN!,   // a personal access token
});
const { token } = await kortix.project(projectId).apps.token(appId);
```

**2. Call a function over HTTP.** `POST <url>/api/query`, `/api/mutation` or
`/api/action`. The answer is `{"status":"success","value":…}` or
`{"status":"error","errorMessage":…}`.

```bash
curl -s "$CONVEX_URL/api/query" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"path":"tasks:list","args":{},"format":"json"}'
```

**3. Use the Convex client from Node or Bun.** `ConvexHttpClient` takes the
token as a string. `ConvexClient` (live subscriptions) takes a function and
asks it again before the token expires.

```ts
import { ConvexHttpClient, ConvexClient } from "convex/browser";

const http = new ConvexHttpClient(process.env.CONVEX_URL!);
http.setAuth(token);
const tasks = await http.query("tasks:list" as any, {});

const live = new ConvexClient(process.env.CONVEX_URL!);
live.setAuth(async () => (await kortix.project(projectId).apps.token(appId)).token);
live.onUpdate("tasks:list" as any, {}, (rows) => console.log(rows.length));
```

**4. Use the Python client.**

```python
from convex import ConvexClient  # pip install convex

client = ConvexClient(convex_url)
client.set_auth(token)
print(client.query("tasks:list"))
```

**5. Call an HTTP action.** Routes in `convex/http.ts` answer on
the `site` service URL. They are public: authenticate inside the handler.

```bash
curl -s "$CONVEX_SITE_URL/webhooks/crm" -H "Authorization: Bearer $TOKEN" -d '{}'
```

**6. Verify the token on your own server** with the App's `auth` values:

```ts
import { verifyKortixToken } from "@kortix/sdk";

const member = await verifyKortixToken(bearer, {
  issuer: app.auth.issuer,
  audience: app.auth.audience,
  jwks: app.auth.jwks_uri,
});   // checks signature, issuer, audience, expiry
```

**7. Act as admin.** The admin key bypasses sign-in and runs any function,
including internal ones. Use it for tooling, never in an App or a browser.

```bash
export CONVEX_SELF_HOSTED_URL="$CONVEX_URL" CONVEX_SELF_HOSTED_ADMIN_KEY=<key>
npx convex run tasks:list '{}'
npx convex data tasks --limit 20
npx convex export --path backup.zip --include-file-storage
npx convex mcp start                   # the Convex MCP server for an AI tool
```

`kortix apps connect db` prints these paths with the App's real URLs filled
in.

### Customers who are not Kortix members

Kortix sign-in is for the project's own people and stays the primary
provider. When an App also serves customers, add Convex Auth (password, magic
link, OTP or OAuth) to the same backend App as a second provider. Convex's CLI
does not set Convex Auth up on a self-hosted deployment; the manual setup
works:

1. `npm i @convex-dev/auth @auth/core@^0.41.1` in the App's directory.
2. Generate an RS256 key pair (Convex's `generateKeys.mjs`) and set
   `JWT_PRIVATE_KEY` and `JWKS` with `npx convex env set <NAME> --from-file <file>`,
   and `SITE_URL` to the customer App's URL.
3. Add `{ domain: process.env.CONVEX_SITE_URL, applicationID: "convex" }` to
   `providers` in `convex/auth.config.ts`, after the Kortix provider.
4. Add `convex/auth.ts` (`convexAuth({ providers: [Password] })`),
   `auth.addHttpRoutes(http)` in `convex/http.ts`, and `...authTables` in the
   schema.
5. Tell the two kinds of user apart by the token issuer:

```ts
// Staff: only a token Kortix signed.
const identity = await ctx.auth.getUserIdentity();
if (identity?.issuer !== process.env.KORTIX_AUTH_ISSUER) throw new Error("Sign in with Kortix.");
const member = requireKortixMember(identity);

// Customers: only a token Convex Auth signed.
if (identity?.issuer !== process.env.CONVEX_SITE_URL) throw new Error("Sign in to continue.");
const customerId = await getAuthUserId(ctx);
```

`requireKortixMember` alone accepts any identity with a subject, a Convex Auth
customer included. Check the issuer first in every staff function. The
customer UI is a separate `public` App that uses `ConvexAuthProvider` from
`@convex-dev/auth/react`.

### Database and durability

Convex is the database. Documents, indexes, file storage, and the scheduler
all live in the backend, with transactions, realtime queries, and schema
validation. The backend needs no second database.

| Question | Answer |
|---|---|
| Where is the data? | Convex's SQLite files on the `data` volume, next to the uploaded files. |
| What happens on a redeploy? | The `rolling` strategy stops the old machine, detaches the volume, and mounts it on the new machine: seconds of downtime, no data lost. |
| What loses no acknowledged write? | A redeploy, a machine stop and start, and a hard kill of the machine or its host. Kortix measured 0 lost writes in 27 crash cycles on Platinum (2026-10-10). |
| How fast can it write? | Convex caps writes at about 4 MiB/s per deployment and answers `TooManyWrites` above it. Batch bulk imports and retry with backoff. |
| How do I go back in time? | `kortix apps volumes restore db data <snapshot>`: the machine stops, the volume returns to the snapshot, the machine starts. Confirm with the user first: the live data goes back to the snapshot. |
| Can I use Postgres? | Not as a separate App yet: Apps have no TCP services or private networking. |

```bash
kortix apps volumes snapshots db data            # daily, manual, and final snapshots
kortix apps volumes snapshot db data             # before a risky change
kortix apps volumes restore db data <snapshot>   # project.app.admin
kortix apps volumes fork db data db_copy         # an unattached point-in-time copy
```

Keep your own copy of data you cannot re-create:
`npx convex export --path backup.zip --include-file-storage`. Without
`--include-file-storage` the export holds no files. The export does not cover
environment variables or pending scheduled jobs.

### Delete the backend

`kortix apps delete db --yes` removes the machines and images. The `data`
volume keeps a `final` snapshot for 7 days, then Kortix purges it. Export first
with `npx convex export` when you need the data.

## The stable URL

Kortix assigns the hostname when the App is created and never changes it. On
Kortix cloud it is `<env>-<slug>-<route-key>.apps.kortix.com`. Self-hosted
deployments serve their own wildcard domain from `KORTIX_APPS_BASE_DOMAIN`.
Every other service of the App answers on the same host plus `--<service>`,
for example `<env>-<slug>-<route-key>--site.apps.kortix.com`.

A static App answers every request at once. HTML revalidates on every load
(`no-cache`, with an ETag), hashed build assets (`index-D8j1YYcB.js`) are cached
for a year, text files are compressed (Brotli or gzip), a page navigation to an
unknown path gets `index.html` when the App is an SPA, and a missing file gets
your `404.html` with status `404`. A directory URL without its trailing slash
(`/docs`) redirects `308` to `/docs/`, so relative links in `docs/index.html`
resolve. Only build output with a content hash in its name (`_next/static/`,
and files under `assets/` or `static/js|css|media/`) is immutable; every other
file revalidates. Files over 4 MiB are streamed uncompressed and support
`Range` requests. A static publish never includes `.git/`, `.env*` or
`.DS_Store`, and a symlink that resolves outside the upload fails the deploy.
Responses are `private` to shared caches unless the App is public. On Kortix cloud, a public App's hashed build assets
are also cached at the edge for up to 1 hour. After the App turns non-public or
is deleted, those copies stay reachable by exact URL for up to 1 hour.

App code in the browser reaches the Kortix API, as the viewer, through
`/_kortix/api/v1/*` on the App's own origin. The Kortix API refuses a direct
cross-origin call from an App. The path needs `--viewer api`; see
[SDK → Apps](/docs/sdk/apps).

An authorized request to a suspended server App resumes its sandbox, waits for
readiness, and proxies that same request. You do not have to wake it first.

While the App is waiting for its first deployment, queued, validating,
building, provisioning, checking, activating, or starting:

- A browser navigation gets a branded status page, HTTP `202`, `retry-after: 3`,
  and a 3-second meta refresh.
- A machine client gets `202` and JSON — for a cold start,
  `{ code: "app_starting" }` with `retry-after: 3`.

Terminal and paused states answer differently:

| State | HTTP | `code` |
|---|---|---|
| Deployment failed | `503` | `app_deployment_failed` |
| Deployment cancelled | `503` | `app_deployment_cancelled` |
| Account cannot start compute | `402` | `app_account_unfunded` |
| Account at its concurrent-App limit | `429` | `app_concurrency_limit` |

`kortix apps stop` suspends a server App's compute immediately; the next
authorized request resumes it. `kortix apps start` warms it before traffic
arrives. Neither applies to a static App.

:::info[Cold starts stay invisible]
The stable URL never exposes an `app_stopped` state. A provider edge that
answers `502` during the first request after a resume is served as the ordinary
cold-start page instead. A warm App owns its own HTTP status, including a
deliberate application `502`.
:::

## Access modes

An App's access mode is a per-resource visibility setting on top of the role
model, not a role. It decides who can open this one App. It grants no permission
the role verdict denies. See
[Accounts & access](/docs/accounts#per-feature-access-settings).

New Apps are private. Choose one mode:

| Mode | Who can open the App |
|---|---|
| `private` | The creator only |
| `project` | Every principal who can read the project |
| `restricted` | Selected users and groups |
| `public` | Anyone, with no authentication |
| `password` | Anyone with the App password |

Set it at deploy time or afterwards:

```bash
kortix apps deploy . --access restricted --members m1,m2 --groups g1
kortix apps access docs --mode password --password 's3cret'
kortix apps access-link docs --json
```

Kortix access uses a five-minute exchange URL and an eight-hour, host-only,
secure cookie. `access-link` mints that exchange URL without changing the
policy — treat it as a secret.

Changing an access policy increments its revision, which revokes every existing
App cookie. Passwords are Argon2id hashes; the API, the CLI, and the SDK never
return a password or its hash.

:::warning[Never put an App password in your repo]
`kortix.yaml` holds deployment defaults only. Pass a password with `--password`,
or set it from the access modal.
:::

The Apps list shows only the Apps the caller may open. Private: the creator.
Restricted: the listed members and groups. Project, password and public: the
project team. A project manager sees every App in the project, so a private App
stays manageable when its creator leaves. An account owner and an account admin
hold manager-equivalent access on every project, so the same applies to them.
The same rule decides token minting.

`GET /v1/projects/:projectId/apps` applies the filter. The SDK (`listApps`,
`useProjectApps`), the web Apps grid, `kortix apps list`, and agents all read
this route. `viewer_can_access` is `true` for every listed App. A `GET` of an
App the caller cannot open answers `404`, not `403`.

## Agents and Apps

An agent session can call an App with its session credential. The App gate
checks that credential in `Authorization: Bearer` or in
`X-Kortix-App-Authorization: Bearer`. Use `X-Kortix-App-Authorization` when the
App reads `Authorization` for its own API key. The gate deletes
`X-Kortix-App-Authorization` before it forwards the request, so the App never
receives it. The gate also deletes an `Authorization: Bearer` header whose
token is a Kortix credential (`kortix_…`), and it removes the Kortix App access
and preview cookies from `Cookie`. Any other `Authorization` value and every
other cookie reach the App unchanged. App code never receives a Kortix
credential.

The gate judges a governed agent session as the agent, not as the person who
started it. List the
Apps an agent may open in `kortix.yaml`:

```yaml
agents:
  report-writer:
    kortix_permissions: [project.app.read]
    apps: [reports-dashboard]   # App slugs, `all`, or `none` (the default)
```

| App mode | The agent session is admitted when |
|---|---|
| `public` | Always |
| `project` | `project.app.read` is in the agent's effective permissions |
| `restricted`, `private` | The App slug is in `apps` and `project.app.read` is effective |
| `password` | Never |

An agent session only opens Apps of its own project. A refused request answers
`401 app_auth_required`.

Three paths write the same `apps` list:

- **Dashboard** — Customize → Agents → the agent → **Apps**. Pick App slugs, or
  choose `All` to cover Apps added later. The page appears only when this flag
  is on for the project.
- **CLI** — `kortix agents scope <agent> --apps reports-dashboard,example-org`
  (also `--apps all` and `--apps none`). Needs a v2 `kortix.yaml`.
- **A change request** that edits `kortix.yaml` directly.

The App's **Access** dialog reads the list back and shows every agent admitted
to that App.

A connector whose base URL is an App of the same project (an `openapi` or `http`
connector built from the App's OpenAPI document) needs no Kortix credential in
its configuration. When an agent session calls it, the connector gateway adds a
signed assertion for that session in `X-Kortix-App-Authorization`. The
assertion names the calling session, binds to one App and one project, and
expires after 60 seconds. The gateway never adds it for any other host.

## Versions and rollback

Each deploy creates a release with the next version number for its App. A
release is immutable. Its record keeps its source kind, hosting provider,
build spec, release `config`, `strategy`, `release_command_status`, attempt
count, and error code.

Every release also records who made it: `created_by`, `actor_type`
(`human`, `agent`, `service_account`, or `system`), and the originating
`source_session_id` when an agent deployed it.

Roll back to any ready release:

```bash
kortix apps releases docs
kortix apps rollback docs v3
```

A rollback creates a NEW release from the target's artifact and config and
rolls it out like a deploy, with the target's strategy. Volumes keep their
data: a rollback changes code and config, never the data. The API answers
`202` with the App and the queued release in `deployment`. A target that is
not `ready` answers `409 release_not_ready`. A new release that never gets
healthy is abandoned, and the previous release keeps serving.

## Delete deployments and Apps

A server deployment runs from an image on the hosting provider. Deployments
with the same build inputs share one image: the same artifact (archive digest,
or an OCI reference pinned with `@sha256:`), source settings, Dockerfile,
runtime spec, machine, and App supervisor version. A redeploy that changes only
environment variables or secrets, an unchanged redeploy, and a retry reuse the
image and record a `build_reused` event instead of building. An OCI tag such as
`:latest` is pulled again on every deploy and never shares an image.

Providers limit how many images an organization may hold, and an old deployment
keeps its image so you can roll back to it. When a build hits the provider's
template quota, Kortix deletes images no deployment uses and builds once more.
If the quota is still full, the deployment fails with
`app_image_quota_exceeded`. Delete what you no longer need:

```bash
kortix apps show docs                               # v3 ready … live, v2 ready, v1 failed
kortix apps delete docs --deployment v1 --yes       # one deployment and its image
kortix apps delete docs --yes                       # the App and every image it built
```

- The live deployment cannot be deleted (`409 deployment_live`). Roll back to
  another deployment first, or delete the App.
- A deployment that is still building cannot be deleted
  (`409 deployment_in_progress`). Delete it after it finishes or fails.
- A deleted deployment leaves `show`, the deployment list, and its logs, and
  can no longer receive rollback traffic.
- The output reports how many images were freed. An image another deployment
  still uses stays, and that deployment reports no image of its own. An image
  still held by a stopping runtime, or by a provider that did not answer, is
  reported as not released yet; Kortix retries it automatically.

Failed deployments and deleted Apps also release their images without any
action: project maintenance removes them every few minutes.

Deleting an App removes its machines first, then destroys its volumes: each
keeps a `final` snapshot for 7 days, then Kortix purges it. Deleting an App
needs `project.app.write`; an App with volumes also needs `project.app.admin`.
Export data you need first.

A static App's files are content-addressed and shared between its
deployments. Deleting a deployment or the App releases its file list at once;
maintenance deletes each stored file 1 hour after no deployment names it.
Deleting the account deletes every stored file of the account immediately.

When a Kortix release changes the App supervisor image (`kortix-appd` and
Caddy), a server App gets one immutable replacement built from the same
artifact: on its next cold start (on demand), or in a keep-alive pass (always
on). The old deployment keeps serving until the replacement passes readiness.
A PostgreSQL advisory lock prevents duplicate refreshes. A static App has no
runtime to refresh.

## The Apps page

Once the flag is on, an **Apps** tab appears at the end of the project's
Customize bar (`/projects/<id>/customize/apps`). The page is operational, not a creation surface: it lists the
project's Apps with live state, a signed preview of each running App, and the
access controls. Deploying is `kortix apps deploy .`.

An App with no active deployment reads **Not deployed**, never **Running**. A
static App with an active deployment always reads **Running**. A suspended
server App's preview issues the request that wakes it.

An App's detail header lists its other services (each a link to its host),
its labels, the Apps it uses, and the Apps that use it. A server App's history
panel has three tabs: **Releases**, **Machines** (state, process group,
release, size, volume; start, stop, restart, destroy, and scale per group),
and **Volumes** (size, attached machine, retention; snapshot, restore, fork,
extend, and destroy). Restore and destroy show only to `project.app.admin`
holders. The old
`/projects/<id>/backends` URLs redirect to the Apps page.

The App's **Earlier versions** drawer states how it runs (static site, or a
server that is always on or on demand) and how many
earlier versions it keeps. Each version unfolds to its events and build log; a
failed deploy's **Update failed** badge opens that log. An always-on server
App shows its fixed monthly cost. An on-demand or static App shows no
cost.

Kortix opens `*.apps.kortix.com` and `*.apps.localhost` on their direct origin
rather than through a session's web forward proxy. That preserves the host-only
access cookie and removes one network hop.
