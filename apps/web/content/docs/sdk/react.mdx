`@kortix/sdk/react` adds React hooks on top of the SDK. This page covers
`useSession`, the hook that runs a session end to end, and the other hooks
confirmed stable for React apps.

## useSession(projectId, sessionId, options?)

`useSession` starts the session, opens the server-selected event transport, and
syncs messages, status, and pending prompts. Call it once per session view.

```tsx
import { useSession } from '@kortix/sdk/react';

function Chat({ projectId, sessionId }: { projectId: string; sessionId: string }) {
  const s = useSession(projectId, sessionId);

  if (s.phase !== 'ready') return <Booting stage={s.stage} onRetry={s.retry} />;

  return (
    <>
      {s.messages.map(({ info, parts }) => (
        <Message key={info.id} info={info} parts={parts} />
      ))}
      <Composer busy={s.isBusy} onSend={s.send} onStop={s.cancel} />
    </>
  );
}
```

Readiness is server truth. The runtime is ready when `POST /start` returns
`stage: 'ready'`. `useSession` does not run a separate client-side health check.

### Returns

| Field | Type | What it holds |
|---|---|---|
| `phase` | `'starting' \| 'ready' \| 'error'` | Overall state. Render a boot screen until `ready`. |
| `messages` | `{ info, parts }[]` | The message list. Parts stream in live. |
| `status` | `SessionStatus` | The session status. |
| `isBusy` | `boolean` | The agent is generating a reply. |
| `questions`, `permissions` | array | Pending agent questions and tool-approval requests. A `permission` here is one runtime tool approval, not an IAM permission. |
| `diffs`, `todos` | array | Live file diffs and todo items. |
| `sendError` | `KortixSendError \| null` | The last `send` failure: `billing`, `runtime-not-ready`, or `runtime-error`. |
| `rewindMessageId` | `string \| null` | The selected user message while a reversible rewind is staged. |
| `rewindPending` | `boolean` | A rewind or restore request is in progress. |
| `rewindError` | `KortixSendError \| null` | The last rewind or restore failure. |
| `models`, `agents`, `defaultAgent`, `commands` | — | Selectable models, selectable agents, the default agent, and slash commands. Available before the runtime starts. |
| `retry` | `() => void` | Force a re-check of `/start`. |

### Actions

| Action | What it does |
|---|---|
| `send(text, override?)` | Send a prompt. `override` sets `{ model?, agent? }` for this message only. |
| `sendParts(parts, override?)` | Send text and runtime URL file parts through the selected transport. Private staged handles use platform prompt routes. |
| `rewind(messageId)` | Rewind this canonical session to a user message. The selected message and later path become hidden and recoverable. |
| `restoreRewind()` | Restore the removed path before another prompt commits its replacement. |
| `cancel()` | Stop the current run and clear pending questions and permissions. |
| `runCommand(command, args)` | Run a project slash command. |
| `answerQuestion(id, answers)` | Answer a pending agent question. |
| `rejectQuestion(id)` | Reject a pending agent question. |
| `answerPermission(id, reply, message?)` | Answer a tool-approval request. `reply` is `'once'`, `'always'`, or `'reject'`. |

`useSession` also returns `removeQuestion` and `removePermission`. Do not use
them. They clear the prompt from local state but never notify the agent, so
the run stays blocked. Use `answerQuestion`, `rejectQuestion`, or
`answerPermission` instead.

### Options

| Option | Default | What it does |
|---|---|---|
| `waitMs` | `15000` | The long-poll budget sent to `/start`. |
| `replayStartStash` | `true` | Replay a prompt saved before the session existed, once the session is ready. |
| `enabled` | `true` | Set `false` to delay the hook, for example until a billing check passes. |
| `chatEngine` | `true` | Set `false` if your app mounts its own chat surface for this session, to avoid syncing messages twice. |
| `repositoryMode` | — | Set `'previous'` only after the user confirms they want to resume a preserved pre-replacement workspace. Git access remains disabled. |

Sending is optimistic. `send` shows your message right away, then stream
events fill in the agent's reply.

`rewind(messageId)` never creates a session. It uses the canonical session from
`POST /start`. The runtime restores file state and keeps the removed transcript
path recoverable. The next accepted prompt commits the replacement path.

## Other stable hooks

`@kortix/sdk/react` also exports React Query hooks for data that does not
need a running session. Each mirrors a method on the
[client](/docs/sdk/reference) and needs no provider.

| Hook | Reads |
|---|---|
| `useProjectModels(projectId)` | Selectable models for the project. |
| `useProjectModelPickerCatalog(projectId)` | The raw `/model-picker` record per wire model (`reasoning_options`, `temperature`, `limit`) for capability-gated controls. |
| `useVisibleAgents({ projectId })` | The project's visible agents. |
| `useProjectConfig(projectId)` | The project's runtime config: default agent, commands. |
| `useProjectSecrets(projectId)` | Secrets: list, add, remove, and personal overrides. |
| `useAccountSecretResources(accountId)` | Account provider-secret metadata and use grants. Values are never returned. |
| `useSessionProviderSecretPools(projectId, sessionId)` | Configured pools, including empty selections; `setPool` updates one provider and refreshes the session cache. |
| `useProjectTriggers(projectId)` | Triggers: list, create, update, remove, fire. |
| `useChangeRequests(projectId, status?)` | Change requests: list, open, merge, close, request changes. |

## Start the open read early

`prefetchSessionOpen(queryClient, projectId, sessionId)` starts the session-open
read before the session view mounts. It issues one `GET .../snapshot` request
(session row, turn, queue, and the first 40 transcript messages) and seeds the
session row cache from it. `useSession` then uses that request instead of
starting its own.

Call it when a route names a session, or on hover, focus, or touch of a session
link. It is read-only: it never calls `/start` and never wakes a computer. It
never rejects. A repeat call for the same session within 30 seconds sends no
request.

```tsx
import { prefetchSessionOpen } from '@kortix/sdk/react';

<a
  href={`/projects/${projectId}/sessions/${sessionId}`}
  onFocus={() => void prefetchSessionOpen(queryClient, projectId, sessionId)}
/>;
```

## Saved history during startup

Enable **Session Transcript History** in a project's **Settings → Feature flags** to let
`useSession(projectId, sessionId)` show saved chat history while its computer starts.
The SDK reads the database independently of runtime readiness. Live messages then reconcile
by their original IDs. Hosts do not need a separate history request or message store.

This flag is off by default. Sessions without saved history use the existing runtime read.
The initial history window contains the last 40 messages. Older-message loading and attachments
that require the computer become available when the runtime is ready.
### Pending prompts

`useSessionPrompts(projectId, sessionId)` submits to the durable session inbox.
The server runs pending prompts automatically.

Pass `placement: 'transcript'` to display a pending message in the conversation.
It runs before every `composer` entry. What it does to the active response
depends on what that response is doing:

- **Running a tool, or between steps.** The prompt steers. The server places it
  into the running turn and the model reads it at its next step boundary. The
  work in progress is kept and one answer accounts for both. A step that has a
  pending or running tool steers even while it also shows reasoning.
- **Streaming text or reasoning.** A streaming step has no step boundary, so
  nothing reads a steer until it finishes. The server ends that response
  immediately and runs the prompt as the next turn. Only a prompt submitted
  after the response started ends it; a prompt that was already waiting steers
  or waits.

Some models write their whole answer inside the reasoning part, and the chat
shows it streaming, so streaming reasoning is ended like streaming text. A
reasoning step can precede a tool call; ending it discards that reasoning but
no tool work, because no tool has started. If the runtime cannot be read
within 6 seconds, the prompt steers.

The ended response stays ended, but the model decides what to write next. A
response stopped before it wrote any answer text leaves nothing in the
transcript, so a model may answer the cancelled request anyway in the turn
that follows, alongside your new prompt.

**Consecutive `transcript` prompts are answered together.** The server delivers
every pending `transcript` row of one session as one group, in submission
order, and only the last one of the group starts a reply. So five Quick Queue
prompts produce five user messages and ONE answer that addresses all five, in
order, instead of five separate turns. Nothing changes in your client: each
prompt is still its own row, each keeps its own message id, and each renders as
its own bubble. The answer is parented on the LAST message of the group, and
the earlier messages render as ordinary finished user messages — not as pending
or queued. A `composer` row, a row with no placement, and a held row are never
grouped.

Pass `placement: 'composer'` to keep it in the editable list above the input.
It waits for the active response to finish, never steers, never ends a
response, and receives its own turn. Each placement keeps submission order.
The web composer uses Enter for transcript placement and Command+Enter
(Control+Enter on Windows/Linux) for composer placement. Shift+Enter inserts a newline.

List rows include `full_text` for complete previews after reload. `text` remains
the bounded preview for older clients. Attachment bytes are excluded from list
responses. Delete returns the complete prompt for lossless undo.

A row carries two ids: `wire_message_id`, the id your client minted and painted
its bubble under, and `message_id`, the id the server delivered it under (the
server re-mints a prompt it places into a live turn). A row is not always
observable with both: a steered row leaves `prompts` the moment the turn
accepts it, often inside one poll of the re-mint. `placed` on the hook result
carries the pairings of rows that left within the last ten minutes and were delivered
under an id other than their `wire_message_id` — `{ prompt_id,
client_message_id, wire_message_id, message_id, message_ids, placed_at }`. A
client that paints prompts under their wire id announces every pairing from
`prompts` AND `placed` to its transcript store, so the runtime's echo replaces
the bubble instead of landing beside it. `placed` is empty on servers without
the field.

`failure_code` on a row is why delivery gave up, as a stable code you map to
your own words (`last_error` stays the server's prose). It is `null` unless
`state` is `failed`, and a row failed before the server recorded codes reads
`unknown`. The vocabulary is `out_of_credits`, `model_unavailable`,
`connector_required`, `runtime_unreachable`, `not_landed`,
`redelivery_exhausted`, `rewound`, `session_gone`, `refused`, `unknown`. Treat
an unrecognized code as `unknown`.

### Queue row actions

`remove` and `retry` are one request per row intent, shared by every mounted
`useSessionPrompts` of the session. Calling the same action again while the
first is in flight returns that promise and sends nothing. Calling the other
action rejects without sending, with `code: 'prompt_action_pending'`. A
`remove` of a row this tab already removed, inside the 15 s tombstone window,
resolves that earlier removal and sends nothing.

`pendingActions` maps `prompt_id` to the action in flight (`'retry'` or
`'remove'`). Disable a row's other actions — Retry, Remove, Edit — while it has
an entry. Both actions resolve on their own request; the list refetch that
follows does not hold the caller.

`classifyPromptActionError(error)` turns any refusal into `gone` (404, the row
left the inbox), `already_sent` (409, a model step already read it),
`unreachable` (409 `prompt_cancel_unreachable`, a timeout, or no answer at
all), `pending` (the other action on this row is running), or `failed`. Map the
outcome to your own copy; never show `error.message`.

`retry` has no optimistic state: the row keeps its listed state until the
server answers, and `pendingActions` is what says it is being retried. The
response carries `observed_at`, the server's clock after the write, so a list
read stamped before it cannot repaint the row `failed`.

Undo re-creates a removed row with `enqueue`/`createSessionPrompt` and
`restore: true`. A restore does not release the session's hold, so Undo after
Stop does not resume the queue. Pass back the removed row's `held` so the
restored row keeps its own hold. A restore reaches the host error sink only for
a `402`.

A `remove` that races delivery is decided on the server. If the drain has not
yet sent the prompt, the prompt never reaches the runtime. If the runtime has
it and no model step read it, the server takes it back out; while the agent
loop runs, the runtime keeps a part-less copy of the message until the loop is
idle, and the server then deletes it. Group turns with
`groupMessagesIntoTurns(messages, { hidePartlessUserMessages: true })` so that
copy is never drawn. Pass every id in `removed.removed_message_ids` to the sync
store's `forgetControlPlaneMessage`: its message and part frames are then
dropped for the rest of the session. If a step already read the prompt, the
remove is refused with `already_sent`.

Stop holds the queue on the server. Any abort of the session's root runtime
session through the Kortix API — `cancel()`, `abort()`, a raw OpenCode
`POST /session/:id/abort` — holds every queued prompt before the abort reaches
the runtime, so no queued prompt runs because the turn ended. Held prompts go out
on the next send, "send now", or `hold(false)`. `hold(true)` sends the Stop
instant on this client's clock; a send whose `clientSentAtMs` is earlier was
typed before the Stop, so it joins the hold instead of releasing it, even when
its POST reaches the server after the hold.

### Pending delivery and active responses

`useSessionWorking()` keeps `state: 'working'` while a prompt waits in the durable
inbox. This keeps Stop available. `pendingDelivery: true` marks a prompt still on
its way to the runtime; the web app shows one working indicator whenever `state`
is `working`, whatever that flag says. Active runtime turns and fresh runtime
activity clear it. A timed-out cancel does not confirm that execution stopped.

A worker claim only checks admission and keeps the prompt waiting. Delivery starts
after admission succeeds. A confirmed active turn clears the pending presentation
even if the previous inbox snapshot still lists that prompt. A `/turn` read
issued after the busy phase began preserves the active turn's message ID during
this handoff.

`turnId` names a turn only from a `/turn` read issued after the current busy
phase began. Right after a busy frame it is `null` until that read lands, which
costs one round trip. A session-open bundle's `/turn` answer never names a turn
against a busy-phase stamp and never retires the inbox drain floor. A queued
send's receipt names the running turn only while that turn runs; the wire idle
frame, or a new busy phase, ends the association.

`serverOpenTurnToken` is the `turn_token` the control plane holds open in the
freshest read, deliberately age-free so the transcript liveness poll keeps
running. A control you HOLD on that token — Stop pinned by a retrying assistant,
for example — must read `serverOpenTurnFresh` instead: it is `true` only while
the token is set and the read behind it is still young.

`useSession` passes the open `turn_token`s to `useSessionSync` for you. A host
that mounts `useSessionSync` itself passes them as
`useSessionSync(sessionId, { openTurnTokens })`, where `null` means unknown.
When a token of the last set is absent from the next one, the hook issues one
`'turn-end'` transcript read while the session stays busy, so a turn that ends
straight into a queued prompt still settles without an idle frame.
`openTurnTokensEnded(previous, next)` is that set comparison, exported for hosts
that hold the list themselves.

The web composer names Enter **Quick Queue** and Command/Ctrl+Enter **Queue List**.
Quick Queue entries run first. A waiting Quick Queue entry is a tinted bubble after
delivered turns, with no status text. Queue List entries remain editable until delivery starts.
The server recovers missed completion events from exact runtime evidence, including
after reload, without treating an unreachable runtime as a completed turn.

Each distinct Enter displays its pending prompt immediately, even while an earlier
acceptance request is unresolved. Only a delivery failure adds text: its cause,
Retry, and Remove. The server inbox continues to own execution order.

A waiting Quick Queue bubble offers **Remove from queue** in its action row, by
the rule the Queue List row uses: while `prompts` lists the row as `queued` or
`waiting`, not while it is `delivering` or has an entry in `pendingActions`. The
removal shows the same notice with Undo, and Undo restores the prompt as a Quick
Queue bubble.

A restored prompt is a new row created at Undo time. Unless it was held, it
steers into the turn that runs at that moment. It also counts as typed at Undo
time: as the head of the Quick Queue it ends a response that is streaming text
or reasoning, even when the removed prompt was already waiting before that turn started.

### Why a turn ended

The transcript of an interrupted turn only carries `MessageAbortedError`. The
control plane keeps what it knows about how each turn ended: the cause the
sandbox named, for example `SandboxMemoryGuard`, and which turns died with no
cause named. A stop somebody asked for — the Stop button, `abort()`, a prompt
sent into a busy session — is recorded as a request and is never reported as a
failure.

`useSessionTurnOutcome(projectId, sessionId)` returns `last_ended`,
`recent_failures` and the read time `atMs` from the cache `useSessionWorking()`
keeps fresh. It makes no request. Pass the result to `turnEndNotice`, with what
the transcript says about the turn:

```tsx
const outcome = useSessionTurnOutcome(projectId, sessionId);
const notice = turnEndNotice(outcome, turn.userMessage.info.id, {
  hasError: Boolean(turnError),
  isAbort: turnErrorIsAbort,
});
// notice: { kind: 'sandbox-memory', usedPct: 97, detail: 'sandbox memory at 97% …' }
//       | { kind: 'cause', name: 'SomeGuard', message: '…' }
//       | { kind: 'unexplained' }
//       | null
```

The host maps each `kind` to its own copy and never parses the sandbox's
message. `null` means "show what the transcript shows": a real error stays, an
abort renders nothing. An unexplained failure is reported only once the reading
is a few seconds past the turn's end, because the cause often arrives one frame
after the abort. `turnEndCause(outcome, messageId)` returns the raw recorded
cause, or `null`.
