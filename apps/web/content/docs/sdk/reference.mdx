This page lists the public surface of `@kortix/sdk`: each entry point, each member of the client, each method of the project and session handles, and the framework-free modules. It is for developers who already have a client and need the exact method name and arguments. The client table gives the route prefix of each member. To install the package and run a first session, start at [SDK](/docs/sdk).

```ts
import { createKortix } from '@kortix/sdk';

const kortix = createKortix({ backendUrl: 'https://api.kortix.com/v1', getToken });

const p = kortix.project(projectId);           // every project resource, id bound
const s = kortix.session(projectId, sessionId); // one session, both ids bound
await p.secrets.list();
await s.send('Run the tests.');
```

Each client method calls the Kortix API. Session runtime methods reach the session's sandbox through the API at `{backendUrl}/p/…`. Route paths on this page are relative to `backendUrl`, which ends in `/v1`. Each route is in the [REST reference](https://api.kortix.com/v1/docs). A failed call throws an `ApiError` with `status`, `code` and `details`.

## Entry points and stability

| Import | Status | What it holds |
| --- | --- | --- |
| `@kortix/sdk` | Stable | The client and every framework-free module. It never imports React or `node:*`. It runs in browsers, Node 18 or later, Bun and edge runtimes. |
| `@kortix/sdk/react` | Stable | The React hooks. It is the only entry that imports React. See [React](/docs/sdk/react). |
| `@kortix/sdk/server` | Stable | Server helpers for Node and Bun (table below). It imports `node:async_hooks`. Never bundle it for a browser. |
| `@kortix/sdk/wire-message-id` | Stable | `mintWireMessageId` and `WIRE_MESSAGE_ID` in one module with no imports. The root exports the same names. |
| `@kortix/sdk/workspace-search` | Stable | `createWorkspaceSearchClient(fileClient)`: ranked file and folder search over a session workspace, with a cached index. `fileClient` has `listFiles(path)` and `findFiles(query, options?)`. |
| `@kortix/sdk/message-queue` | Deprecated | Client-side prompt queue reducers. Kortix orders prompts on the server: use `s.send` or `useSession().send`. |
| `@kortix/sdk/turns`, `/files`, `/session`, `/session/url`, `/projects-client`, `/platform-client`, `/api-client`, `/auth`, `/config`, `/event-stream`, `/opencode-client`, `/opencode-errors`, `/feature-flags`, `/fresh-sessions`, `/instance-routes` | Deprecated | Aliases. Each re-exports names that the root already exports. Import from the root. |
| `@kortix/sdk/sync-store`, `/server-store`, `/sandbox-connection-store`, `/opencode-pending-store`, `/idb-sync-cache` | Deprecated | Aliases of the internal web-app stores. They have no replacement. Read session state with `useSession` from `@kortix/sdk/react`. |
| `@kortix/sdk/internal/*` | Internal | State stores for the Kortix web app. Outside semver. Do not import. |

Deprecated subpaths and names resolve until the next major version. The package also ships two browser bundles, `dist/kortix.esm.min.js` and `dist/kortix.global.js` (`window.Kortix`). See [Install](/docs/sdk#install).

### `kortix.iam`

Kortix has one grant record, the assignment: one principal (`user`, `group`, `service_account`, `pending` or `project`), one role, one scope (`account` or one `project`), an optional object (`agent`, `skill`, `secret`, `app`, `trigger` or `connection`) and an optional `expiresAt`.

| Method | What it does |
| --- | --- |
| `assignments.list(accountId, filter?)` | Live assignments. Filter by `principalType` with `principalId`, `scopeType`, `scopeId`, `objectType`, `objectId`, `roleId`, `includeExpired`. |
| `assignments.create(accountId, { principal, scope, object?, expiresAt?, roleId \| roleKey })` · `assignments.revoke(accountId, assignmentId)` | Grant · revoke. `roleKey` names a built-in role: `owner`, `admin`, `member`, `manager`, `agent-user`. |
| `permissions.list(accountId)` · `permissions.forRole(…)` | The permission catalog as data (`action`, `scope_type`, `resource_type`, `delegable`, `description`, `area`, `level`, `implies`) · one role's permissions. |
| `roles.list` · `.create` · `.update` · `.setPermissions` · `.remove` · `.usage` | Custom roles. Without the account's `rbac` entitlement the API returns `402 entitlement_required`. |
| `groups.list` · `.get` · `.create` · `.update` · `.remove` · `groups.members.list` · `.add` · `.remove` | Groups and their members. |
| `agentIdentities(accountId)` | Agent principals, for binding a role to an agent. |
| `oauthClients.list` · `.get` · `.create` · `.update` · `.rotateSecret` · `.remove` | Sign in with Kortix clients. The secret is returned once, on create and on rotate. |
| `can(accountId, userId, { action, resourceType?, resourceId? })` · `canBatch(accountId, userId, probes)` | Ask whether a principal may do one action · many, in one round trip, answers in input order. |

Gate a control in your UI with `can` or `canBatch` on the action the route checks, not on a role name. `PROJECT_ACTIONS` (root export) names every project action the API answers about, for example `PROJECT_ACTIONS.PROJECT_GITOPS_MERGE` is `project.gitops.merge`. The API answers an unknown action with `400`. For triggers, probe `TRIGGER_CONTROL_ACTIONS` and pass the result to `triggerControlsFrom(cans)`: it returns `{ canCreate, canFire, canUpdate, canDelete }`, one flag per trigger route, each `false` until the probe allows it. Create, update and delete also need `project.write`, because their routes load the project for write first.

For change requests and the review inbox, probe `REVIEW_CONTROL_ACTIONS`. `changeRequestControlsFrom(cans)` returns `{ canOpen, canMerge, canClose }`: open needs `project.write` + `project.gitops.push`, merge needs `project.write` + `project.gitops.merge`, close and reopen need `project.write`. `reviewVerdictAllowed(item, verdict, cans)` says whether to offer one verdict on one review item. Approving a change request merges it, so it follows `canMerge`. Every other verdict on a change request or a native item needs `project.write` + `project.review.act`. A connector call offers approve and reject to the viewer the API lets decide it: a project manager, or the person who launched the session when a person started it (not an API token or a service account). The API says so per call: `can_resolve` on each `SessionAuditAction` (`getSessionAudit`, and the session snapshot's `audit` leg), and `canResolve` on a connector call's review action (`mapApiReviewItem`). Show Approve and Deny only when it is not `false`. A viewer the API would refuse gets the review item with status `waiting`. `resolvers` (both shapes) says who decides instead: `managers` for a session started with an API token or a service account, else `managers_and_launcher`.

### `kortix.accountInvites`

`listMine()` lists pending invites addressed to your email. `describe(inviteId)`, `accept(inviteId)` and `decline(inviteId)` act on one invite. They need no account membership.

`acceptAndLand(inviteId, invite?)` accepts and returns `{ accepted, landing }`. `landing` is where to open: `{ kind: 'project', projectId, accountId }` for the first project the invite granted, or `{ kind: 'account', accountId }` for a workspace invite. Pass the invite you already read (from `listMine()` or `describe()`): an accept that grants nothing, such as an admin invite, then lands in the first project the invite names. `accountInviteLanding(accepted, invite?)` is the same rule without the request, for an invite accepted earlier.

| `usageHistory(params?)` · `usageRollup(params?)` | Usage over time · usage grouped by model, provider or day. |

### `kortix.capture`

Account owners and admins have it by default. See [Capture](/docs/capture).

| `account(id).devices.list({ userId?, scope? })` · `.devices.revoke(deviceId)` · `.devices.assetUrl(deviceId, name)` | Devices with live status (`recording`, `paused`, `permission_missing`, `not_recording`, or `offline` after 120 s without a status). `scope: 'account'` lists every member's devices. · Revoke a device's token. · A 5-minute signed URL of an action screenshot. |

| `account(id).timeline.get(query?)` · `.timeline.items(query?)` · `.timeline.days(query?)` | App and window runs for a UTC day or a window up to 31 days · frames, actions and audio in a window, 500 of each · the days with recorded items, newest first. |

| `deviceGrant(userCode)` · `approveDevice(userCode, accountId?)` · `denyDevice(userCode)` | The person's half of the device sign-in. |

React (`@kortix/sdk/react`): `useCaptureWorkspace`, `useSetCaptureEnabled`, `useCaptureDevices` (polls every 10 s), `useRevokeCaptureDevice`, `useCapturePolicy`, `useSetCapturePolicy`, `useCaptureDays`, `useCaptureTimeline`, `useCaptureTimelineItems`, `useCaptureSearch`, `useCaptureChunkMedia`, `useCaptureDeviceGrant`, `useApproveCaptureDevice`, `useDenyCaptureDevice`. ### Files, git and change requests

These methods read the project repository. To read and write files in a running session, use `s.files`.

| Method | What it does |
| --- | --- |

### Files

```ts
import { FileExistsError, files } from '@kortix/sdk';

const { content } = await files.read('/workspace/README.md');
await files.upload(file, '/workspace/uploads', file.name, {
  onProgress: ({ loadedBytes, totalBytes }) => console.log(loadedBytes, '/', totalBytes),
});

try {
  await files.create('/workspace/notes.md');
} catch (error) {
  if (error instanceof FileExistsError) console.log('exists:', error.path);
  else throw error;
}
```

- `upload` sends a file of 8 MiB or less in one request. A larger file goes in 8 MiB chunks, and each chunk is checked on arrival. `onProgress` runs after each chunk.
- `write(path, blob)` replaces the file at `path`. It fails when `path` is a folder.
- `create(path)` makes an empty file and never overwrites. When anything exists at `path` it throws `FileExistsError` (`status` `409`, `code` `FILE_EXISTS`).
- `uploadNativeFile({ uri, name, type? }, targetPath?, baseUrl?)` uploads a React Native device file in one request. The bytes stream from `uri` and never enter the JS heap.

### Session health

`getSessionHealth()` never throws on a non-2xx status. It returns `{ status, ok, health, body, hop, upstreamStatus }`. `isRuntimeReady(health)` is `true` when the runtime accepts work. `s.health()` is the same probe for one session.

## Custom transcript rendering

Pure functions that turn session messages into renderable parts. Use them to build your own chat view. They have no React and no DOM.

### Classify parts and turns

`classifyPart(part)` turns one part of the Kortix transcript format (`kortix.transcript.v1`, `KORTIX_TRANSCRIPT_SCHEMA`) into a `ClassifiedPart`, keyed by `kind`:

| `kind` | Fields |
| --- | --- |
| `text` | `id`, `text`, `synthetic`. Do not render a `synthetic` part as a chat bubble. |
| `reasoning` | `id`, `text` |
| `tool` | `id`, `tool: ToolView` |
| `file` | `id`, `filename?`, `mime`, `url`, `isImage`, `isPdf` |
| `subtask` | `id`, `description`, `agent`, `prompt`, `model?` |
| `patch` | `id`, `hash`, `files`, `fileCount` |
| `snapshot` | `id`, `snapshot` |
| `agent` | `id`, `name` |
| `retry` | `id`, `attempt`, `message`, `createdAt` |
| `compaction` | `id`, `auto`, `overflow`, `tailStartId?` |
| `step` | `id`, `phase: 'start' \| 'finish'`, `snapshot?`, `reason?`, `cost?`, `tokens?` |
| `unknown` | `raw`: a part type this SDK version does not know. It never throws. |

`ToolView` fields: `name`, `kind` (from `toolKind`), `title`, `status` (`pending`, `running`, `done`, `error`), `input`, `output`, `error`, `outputParsed` (the parsed JSON output, for output up to 256 KiB), `outputText`, `files`, `diff`, `diagnostics`, `answers`, `childSessionId`. A tool that reports `success: false` inside a completed state has `status: 'error'`. `toToolView(part)` builds a `ToolView` from one tool part or one session-log `ToolCallBlock`. Read these fields, not a harness's own metadata: the same card then renders every harness.

`classifyTurn(message)` returns `{ parts, error?, isEmpty }` for one assistant message. `isEmpty` is `true` when the turn has no error and no visible part.

```ts
import { classifyTurn, toolViewModel } from '@kortix/sdk';

for (const part of classifyTurn(message).parts) {
  if (part.kind === 'text' && !part.synthetic) render(part.text);
  if (part.kind === 'tool') {
    const view = toolViewModel(part.tool);
    if (view.kind === 'shell') render(view.command, view.stdout, view.exitCode);
  }
}
```

### Tools

- `toolKind(name)` maps any harness's tool name to one `ToolKind`: `read`, `list`, `glob`, `grep`, `write`, `edit`, `apply_patch`, `bash`, `pty`, `web_search`, `webfetch`, `media`, `show`, `task`, `delegate`, `sessions`, `todowrite`, `question`, `memory`, `connectors`, `automations`, `projects`, `skill`, `context`, `retired` or `other`.
- `toolInfo(name)` returns `{ label, category }`. `getToolInfo(name, input)` returns `{ icon, title, subtitle }` for a tool card. An unknown name falls back to `humanizeToolName(name)`.
- `inputPath(input)` reads a file tool's path from `filePath`, `file_path` or `path`.
- `toolViewModel(tool)` returns one shape per tool family:

| `kind` | Fields |
| --- | --- |
| `web-search` | `query`, `results?`, `answer?`, `error?` |
| `shell` | `command`, `stdout?`, `exitCode?` |
| `file-read` · `file-write` | `path`, `preview?` |
| `file-edit` | `path`, `diff?` (lines of `{ type: 'added' \| 'removed' \| 'unchanged', text }`) |
| `search` | `pattern`, `matches?` |
| `task` | `description`, `agent?` |
| `todo` | `items` |
| `question` | `questions`, `answers?` |
| `generic` | `label`, `inputPretty?`, `outputPretty?`. Every other tool. Always safe to render. |

## Session log types

The root exports the types of the Kortix session log, the harness-neutral record of a session, schema `kortix.session/2`. Kortix stores every session as a session log. The SDK exports the types and three constants, with no validators. In React, `useSessionLog` and `useSessionLogThread` return a session's log once the session reads it: see [Read the session log](/docs/sdk/react#read-the-session-log).

| Name | What it is |
| --- | --- |
| `SESSION_LOG_SCHEMA` · `SESSION_LOG_MINOR` | `'kortix.session/2'` · `1` |
| `SessionLog` | The record: threads, todos, pending questions and permissions, harness history, `restore_grade`. |
| `SessionLogThread` · `SessionLogMessage` | One thread (the main thread or a sub-agent) · one message with `seq`, `role`, `kind`, `status`, `model`, `usage`, `blocks`. |
| `SessionLogBlock` | The union of `TextBlock`, `ReasoningBlock`, `AttachmentBlock`, `ToolCallBlock`, `CompactionBlock`, `SubtaskBlock`, `StepBlock`, `HarnessBlock`, keyed by `type`. |
| `ToolResultContent`, `CompactionLayoutEntry`, `ThreadInteraction`, `ModelRef` | Parts of the records above. |
| `KNOWN_TOOL_KINDS` · `KnownToolKind` · `SessionLogToolKind` | The tool kinds every reader renders: `shell`, `read`, `write`, `edit`, `patch`, `list`, `glob`, `grep`, `web_fetch`, `web_search`, `todo`, `task`, `question`, `plan`, `mcp`, `other` · the tool kind of a block, any string. Render an unknown kind as `other`. |
| `SessionLogTodo` | One todo item. |
| `RestoreGrade` · `GradeCounts` | How faithfully the record restores (`native`, `converted` or `partial`) · what is missing. |

A text over 256 kB is stored by reference. This applies to a `TextBlock` and to a `text` item of a tool result (`ToolResultContent`). Its `text` holds the first 16 kB, `bytes` holds the UTF-8 length of the full text, and `ref` is `kortix-attachment://<project_id>/<session_id>/<attachment_id>`. `kortix.session(projectId, sessionId).attachments.read(attachmentId)` returns the full text as a `Blob` (`text/plain; charset=utf-8`), also while the sandbox is stopped. The v1 transcript reads return the full text.

```ts
import type { SessionLog, SessionLogBlock } from '@kortix/sdk';

function toolCalls(log: SessionLog): SessionLogBlock[] {
  return log.threads.flatMap((t) => t.messages.flatMap((m) => m.blocks)).filter((b) => b.type === 'tool_call');
}
```

### Tool calls from v1 parts (transitional)

Three functions bridge a host that renders blocks while its rows are still v1 (`useSessionMessages`). All three are transitional.

| Name | What it does | Removed |
| --- | --- | --- |
| `toolCallBlock(part)` | The `ToolCallBlock` of a v1 tool part: the block `fromV1` builds for it. An open call stays open (`pending` or `running`, no `result`). A call that streams its input has the text so far as its `input`. The same part object returns the same block. | In the SDK major that removes the v1 rows. |
| `toolCallMetadata(call)` | The harness's display metadata of a tool call: the whole `state.metadata` of the v1 part it came from, such as bash `command`, read `loaded`, task `sessionId` or edit `filediff`. A record a harness wrote natively carries its `details` (`result.details`, else the adapter's own ext: pi keeps them in `ext.pi.data.details`) and `exit` (from `result.exit_code`). One shared empty object when there is none. | When the session-log schema carries display metadata. |
| `sessionLogOfV1Rows(sessionId, runtimeSessionId, rows)` | The `fromV1` live view of one runtime session's v1 rows: the `SessionLog` `useSessionLogThread` returns on v1 (one root thread, the runtime session id as its id, the open turn kept open). For rows a host reads without a `useSession`, such as a sub-agent's chat. A message keeps its identity while its row object is unchanged. | In the SDK major that removes the v1 rows. |

`toToolView`, `getChildSessionId`, `partOutcome`, `contextToolTrigger` and `shouldShowToolPart` accept a `ToolCallBlock` as well as a v1 tool part, and return the same answer for both.

```ts
import { getChildSessionId, toolCallBlock, toolCallMetadata } from '@kortix/sdk';

const call = toolCallBlock(part); // part: a v1 tool part from useSessionMessages
const child = getChildSessionId(call); // a running task's child session
const command = toolCallMetadata(call).command; // bash
```

### Reading a tool call

What a host draws a `ToolCallBlock` with. Block-native: they stay.

| Name | What it does |
| --- | --- |
| `toolCallStatus(call)` | The status in the words a renderer compares: `pending`, `running`, `completed` or `error`. |
| `toolCallRawOutput(call)` | A completed call's output text as the tool returned it (its result's text items, joined); `''` for any other call. One string per call object. |
| `toolCallError(call)` | A failed call's error text: its semantic error (`result.error.message`), else its result text, as `toV1` gives a v1 part's `state.error`. A harness that closes a failed call with `is_error` and the tool's text only still shows that text. `undefined` for a call that did not fail. |
| `subAgentCalls(thread)` | The tool calls a sub-agent row lists: every shown call (`shouldShowToolPart`) of the thread's replies, in order. One array per thread object; the same empty array for `null`. |
