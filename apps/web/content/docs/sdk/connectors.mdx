---
title: Connectors from code
description: Call a connector from an App, a Convex action, or an external program, with the right Kortix credential.
---

A connector call from code is one request to the Kortix connector gateway,
made with `@kortix/sdk`. The gateway holds the provider credential, applies
the project's policy, picks the account, calls the provider, and writes the
audit event. Your code holds only a Kortix credential.

This page shows the four places code calls a connector from, and which
credential each one uses. For connectors, accounts, and policy, read
[Connectors](/docs/connect/connectors).

:::info[The working rule]
The Kortix credential decides which accounts a call can use. Never put a
provider API key in an App or a Convex deployment when a connector for that
provider exists: a raw key skips the project's policy, approvals, and audit.
:::

## Pick the credential

| Where the code runs | Credential | Acts as | Accounts it reaches |
|---|---|---|---|
| An App, in the browser | The App viewer token, through `/_kortix/api/v1` on the App's own origin | The person viewing the App | Shared accounts that person may use, and that person's own private accounts |
| An App, on its server | The App viewer token in `x-kortix-app-viewer-token` | The person viewing the App | The same as in the browser |
| A Convex action, or an App job with no viewer | A service account bearer (`kortix_sa_…`) | The service account | Shared accounts that nobody narrowed. Never a private account, never a narrowed account |
| An external program or CI job | A personal access token (`kortix_pat_…`) | You | Shared accounts you may use, and your own private accounts |

A session sandbox carries its own `KORTIX_TOKEN`. Its reach is the agent's
connector grant: see [Grant an agent access](/docs/connect/connectors#grant-an-agent-access).

The call is the same for every credential. `connector(slug)` is one
connector of the project:

```ts
import { createKortix } from '@kortix/sdk';

const kortix = createKortix({ backendUrl, getToken });
const crm = kortix.project(projectId).connector('crm');

const deals = await crm.run('list_deals', { stage: 'won' }, {
  account: 'Team CRM', // a label, a connection id, `me`, or `project`
});
// `deals` is the provider payload, without the binding's envelope.
```

| Method | Returns |
|---|---|
| `run(action, args, options)` | The action's `output`. Throws a typed error for every other outcome: see [Errors](#errors) |
| `call(action, args, options)` | The raw result (`ok`, `data`, `output`, `account`, `binding`, …). A `202` resolves with `ok: false` |
| `describe()` | The connector with every action's input and output schema, or `null` |
| `describe(action)` | One action with its input and output schema, or `null` |
| `accounts()` | The accounts this credential may run the connector as, default first |
| `paginate(action, args, { next, maxPages })` | An async iterator over each page's `output`: see [Pages](#pages) |
| `uploadAttachment(content, input)` | An attachment reference for a later call of this connector |

`kortix.connector(slug)` is the same handle for a token that carries its
project (a session token, or a token bound to one project).

Omit `account` to use the caller's own default account first, then the
project's. `run` and `call` wait 90 seconds (`timeoutMs`), above the gateway's
60 s upstream deadline, and accept an `AbortSignal` (`signal`).

For typed `args` and output, generate a declaration file with
`kortix connectors types`: see
[Typed calls from code](/docs/connect/connectors#typed-calls-from-code). The
handle reads it, so `run('list_deals', { stage: 1 })` is a compile error and
the result has the generated type.

## From an App in the browser

The App calls the Kortix API through its own origin. The Apps gate answers
`/_kortix/api/v1/*` on the App's hostname and forwards the request to the
Kortix API. The browser makes no cross-origin request, so no CORS rule is
involved.

1. Give the App a viewer token that can call the API:

```bash
kortix apps access <app> --viewer api
```

2. Point the SDK at the same-origin path, with the viewer token:

```ts
import { createKortix, kortixAppViewerToken } from '@kortix/sdk';

const kortix = createKortix({
  backendUrl: '/_kortix/api/v1',
  getToken: kortixAppViewerToken(),
});

const deals = await kortix
  .project(projectId)
  .connector('crm').run('list_deals', { stage: 'won' });
```

- The call runs as the person who opened the App, inside their own role.
- With `--viewer identity` (the default) the token has no `kortix` scope. A
  connector call answers `403` with `insufficient_scope`.
- The viewer token reaches every project the viewer can read, not only the
  App's project. Pass the App's own `projectId` on every call.

## From an App's server

The gate puts a live viewer token on every request it forwards. Build one
client per request:

```ts
import { createAppViewerKortix } from '@kortix/sdk/server';

export async function GET(request: Request) {
  const kortix = await createAppViewerKortix(request, {
    backendUrl: 'https://api.kortix.com/v1',
  });
  const deals = await kortix
    .project(projectId)
    .connector('crm').run('list_deals', { stage: 'won' });
  return Response.json(deals);
}
```

Do not store the token across requests. It lasts one hour, and an
access-policy change revokes it. See
[Your App already knows who is looking](/docs/sdk/apps#your-app-already-knows-who-is-looking).

## From a Convex action

Code that runs with no viewer (a Convex cron, an action, a webhook handler)
needs its own credential. Kortix does not mint one for App or backend code.
A person creates a service account and stores its bearer in the deployment.

1. A person creates the service account. The bearer prints once. An agent
   session cannot create one.

```bash
kortix tokens service-accounts new crm-sync --description "Convex CRM sync"
```

2. Give it a role on the project. A new service account holds no
   permissions, and every call answers `403` until it has one.

```bash
kortix access grant --service-account <service-account-id> --role member --project <project-id>
```

3. Store the bearer and the target in the Convex deployment:

```bash
npx convex env set KORTIX_API_URL https://api.kortix.com/v1
npx convex env set KORTIX_PROJECT_ID <project-id>
npx convex env set KORTIX_API_KEY <kortix_sa_…>
```

4. Call the connector from a Node action:

```ts
'use node';
import { internalAction } from './_generated/server';
import { createKortix } from '@kortix/sdk';

export const syncDeals = internalAction({
  args: {},
  handler: async () => {
    const kortix = createKortix({
      backendUrl: process.env.KORTIX_API_URL!,
      getToken: async () => process.env.KORTIX_API_KEY!,
    });
    const result = await kortix
      .project(process.env.KORTIX_PROJECT_ID!)
      .connector('crm').run('list_deals', { stage: 'won' });
    return result;
  },
});
```

- The service account reaches only shared accounts that nobody narrowed.
  Naming a private or a narrowed account answers `403`
  `connector_not_connected`. Share the account with the whole project, or
  keep the call in the browser, where it runs as the viewer.
- Anyone who holds the deployment's admin key can read its environment
  variables, the bearer included.
- `@kortix/sdk` is verified on Node. Use a `'use node'` action. The default
  Convex runtime is not verified.
- To revoke the credential, disable or delete the service account:
  `kortix tokens service-accounts disable <id>`. Every call then answers
  `401`.

A server App job with no viewer uses the same service account. Store the
bearer as a project secret and map it into the App in `kortix.yaml`. Names
that start with `KORTIX_` are reserved for Kortix:

```yaml
apps:
  crm:
    secrets:
      CRM_SYNC_TOKEN: crm-sync-service-account
```

## From an external program

A script on your machine or a CI job uses a personal access token. It acts as
you. Bind it to one project so it can never reach another:

```bash
kortix tokens new crm-export --project <project-id> --expires 90d
```

```ts
import { createKortix } from '@kortix/sdk';

const kortix = createKortix({
  backendUrl: 'https://api.kortix.com/v1',
  getToken: async () => process.env.KORTIX_API_KEY!,
});
const deals = await kortix
  .project(process.env.KORTIX_PROJECT_ID!)
  .connector('crm').run('list_deals', { stage: 'won' });
```

The token carries your whole connector reach in that project, your private
accounts included. For unattended work that must not run as one person, use a
service account.

## Errors

`run` and `paginate` throw one of two errors. Nothing is retried for you: a
connector call is not idempotent.

```ts
import { ConnectorApprovalPendingError, ConnectorCallError } from '@kortix/sdk';

try {
  return await crm.run('create_deal', { name: 'Acme renewal' });
} catch (error) {
  if (error instanceof ConnectorApprovalPendingError) return showLink(error.approvalUrl);
  if (error instanceof ConnectorCallError && error.connectUrl) return showConnect(error.connectUrl);
  if (error instanceof ConnectorCallError && error.upstreamStatus === 429) {
    return retryLater(error.retryAfterSeconds);
  }
  throw error;
}
```

`ConnectorCallError` extends `ApiError`. Its fields:

- `status`: the HTTP status of the Kortix answer. `200` for `upstream_error`.
- `code`: the machine reason. `upstream_<status>` when the upstream answered
  with a failure (`upstream_429`, `upstream_404`). `upstream_error` when the
  upstream reported a failure inside a 2xx (an MCP `isError` result, GraphQL
  `errors` with no data). Otherwise the gateway's reason, for example
  `connector_not_connected`, `account_required`, `upstream_timeout`,
  `computer_offline`, `invalid_json`; `connector_error` when it is free text.
- `reason`: the full reason text. `message`: the server's explanation.
- `upstreamStatus`, `retryAfterSeconds`, `binding`.
- `connectUrl`, `hint`, `availableAccounts`, `requestedAccount`.
- `details`: the parsed body.

`ConnectorApprovalPendingError` (not an `ApiError`) has `executionId`,
`approvalUrl`, `approvalSummary`, `approvalInstructions` and `retryable`.

`call` resolves `200` and `202` and throws a plain `ApiError` for the rest.

| Answer | `run` throws | What to do |
|---|---|---|
| `202`, `status: "pending_approval"` | `ConnectorApprovalPendingError` | Show `approvalUrl` to a person. Do not repeat the call in a loop |
| `401` | `ConnectorCallError` | Get a new credential |
| `403` `insufficient_scope` | `ConnectorCallError` | Set the App to `--viewer api` |
| `403` `forbidden` | `ConnectorCallError` | Grant a project role |
| `403` `connector_not_connected` | `ConnectorCallError` with `connectUrl` when a person can connect one | Show `connectUrl`, or read `availableAccounts` |
| `403` `account_required` | `ConnectorCallError` with `availableAccounts` | Pass `account` |
| `403` `credential_not_shared` | `ConnectorCallError` | Share the secret with the caller |
| `429`, `503` | `ConnectorCallError` with `upstreamStatus` and `retryAfterSeconds` | Wait, then repeat |
| `500` `upstream_timeout: …` | `ConnectorCallError` | The call may have run. Check the effect before you repeat a write |

## Pages

`paginate` runs the action once per page. `next` builds the next page's args
from this page's output, and returns `undefined` after the last page.
`maxPages` (default 100) stops a cursor that never ends.

```ts
for await (const page of crm.paginate('list_deals', { limit: 100 }, {
  next: (page, args) => (page.next_cursor ? { ...args, cursor: page.next_cursor } : undefined),
})) {
  await save(page.deals);
}
```

A failed page throws the same errors as `run`. Each page is a separate call,
with its own policy check and audit event.

## React

`useConnectorQuery` from `@kortix/sdk/react` reads one action's output as a
cached query:

```tsx
import { ConnectorCallError } from '@kortix/sdk';
import { useConnectorQuery } from '@kortix/sdk/react';

const { data, error, isLoading } = useConnectorQuery(projectId, 'crm', 'list_deals', { stage: 'won' });
if (error instanceof ConnectorCallError && error.connectUrl) return <a href={error.connectUrl}>Connect CRM</a>;
```

- Use it only for an action that reads. Every fetch runs the action and
  writes an audit event.
- The output stays fresh for 30 seconds (`staleTime`). A window focus does
  not refetch.
- Only an upstream `429` or `503` is retried, twice, after `Retry-After`.

See [Call results](/docs/connect/connectors#call-results) for the result
fields.
