title: Connectors
description: "Give agents and your own code governed access to external apps, MCP servers and APIs: Kortix holds the credential, applies your policies and records every call."

A connector gives a project governed access to one external app, MCP server or API. Agents call it as a tool, and your own code calls it through the SDK. Kortix stores the credential, picks the account, applies the project's policies, calls the provider and writes an audit event for every call. The credential never enters a sandbox.

This page is for project members who connect apps, decide who may use them, and call them from sessions or code.

## Profile, account, rule set

Three things answer three questions:

| Thing | Answers | Example | Where it lives |
| --- | --- | --- | --- |
| **Profile** (a connector) | How does Kortix reach the app? | Linear over its MCP server | `connectors:` in `kortix.yaml` |
| **Account** (a connection) | Who does a call run as? | the team inbox, your own inbox | Kortix, never `kortix.yaml` |
| **Rule set** (a policy set) | What may this agent do? | `read_only` for the support agent | `connectors[].policy_sets`, given in `agents.<name>.policy_sets` |

- Install an app once for each way you connect it. A second sign-in is a new account on the same profile. Different rules for one agent are a rule set on the same profile.
- Every call is decided in this order, and the first layer with a matching rule decides: project rules → the calling agent's rule set → the profile's base rules → sensitive tools need approval → the project default mode. See [Policies and approvals](#policies-and-approvals).

## What a connector is

A connector has:

- a slug, unique in the project (`[a-z0-9][a-z0-9_-]`, up to 128 characters);
- a display name;
- a provider, which decides how Kortix reaches the service;
- its actions, the tools an agent calls (`<slug>.<action>`);
- its policies, which decide which actions run, need approval, or are blocked: base rules for every caller, plus named [policy sets](#policy-sets) that you give to single agents.

A connector holds one or more [accounts](#connectors-connections-and-accounts). An account is the authorized identity a call runs as.

Connectors live in `kortix.yaml` under `connectors:`, or in a file it lists under [`imports:`](/docs/project/manifest#imports). The manifest never holds a credential.

| Provider | Use it for | Required fields |
| --- | --- | --- |
| `composio` | The managed catalog of SaaS apps (Gmail, GitHub, Linear, …). The default for managed apps. | `app` (the toolkit slug) |
| `mcp` | A remote MCP server. | `url`; `transport` is `http` (default) or `sse` |
| `openapi` | An API with an OpenAPI document. | `spec` (a URL or a repo path) |
| `postman` | An API described by a Postman collection. | `spec` |
| `graphql` | A GraphQL endpoint. Kortix introspects it when `spec` is absent. A server that answers but refuses introspection gets one `graphql` action that takes the document; it asks for approval unless a policy names `graphql` exactly. | `endpoint` |
| `shopify` | A Shopify store's Admin API, connected with your own Shopify app. See [Shopify](/docs/connect/shopify). | none; `shop` and `scopes` are optional |
| `http` | A raw HTTP API. | `base_url` |
| `channel` | Slack, Microsoft Teams or email. Kortix writes it when you connect a [channel](/docs/connect/channels). | `platform` |
| `computer` | Built in. Each connected [computer](/docs/connect/computers) is one account. It is never written to `kortix.yaml`. | — |

`pipedream` is a legacy provider: existing connectors run, and new managed apps use `composio`. To leave Pipedream, [move a Pipedream or Composio connector to Kortix](#move-a-pipedream-or-composio-connector-to-kortix).

A `provider: mcp` connector is Kortix calling someone else's MCP server. The [Kortix MCP server](/docs/connect/mcp) is the other direction: your MCP client calls Kortix.

## Add a connector

### From the web app

1. Open **Customize → Connectors**.
2. On the **All** tab, find the app and select **Install**.
3. When the app has its own hosted MCP server with one-click sign-in, **Connect** *app* opens. That means OAuth with dynamic client registration, for example Linear, Notion or Sentry. Choose **Who can use it** (**Only you** by default) and select **Connect**. You sign in to the app and return to the connector's page with its tools loaded.
4. Otherwise Kortix adds the managed app, opens its page and opens **Add account** with **Only you** selected. [Authorize an account](#authorize-an-account) there.

- **Install** shows only to members who can change the project's connectors. Other members add their own account on an installed connector's **Accounts** tab.
- Installing an app that the project already has adds an account to the existing connector. It does not create a second connector.
- An app page lists its **Ways to connect** (for example an MCP server and a REST API). **Install** uses the MCP server when the catalog lists one.
- Kortix checks the app's MCP server when you select **Install**. A server that needs a pasted token, or has no dynamic client registration (for example GitHub's remote MCP server), installs as the managed app instead.
- For an MCP server, [add it from its URL](#add-an-mcp-server-from-its-url). For another API that is not in the catalog, select **New → Add a custom connector** and choose OpenAPI, Postman, GraphQL, MCP or HTTP. Paste the source URL and Kortix proposes the slug: the document's title, or else the URL's domain. Kortix then opens the connector's page. An MCP server that asks for sign-in (HTTP `401` or `403`) opens **Add account** there, as **Install** does. This needs an auth scheme: one you pick under **Auth**, or one **Auto-detect** finds in the server's `WWW-Authenticate` challenge. Without one, the `401` or `403` is shown as the failure. **New → Create in chat** has an agent scaffold the connector and open a change request.
- When Kortix cannot load a new connector's tools, the connector's page shows the reason and **Retry**. The connector stays in the project. OAuth 2.0 client credentials entered in the form are saved as well, so **Retry** uses them.
- With OAuth 2.0 client credentials, **Added and connected** means the tools loaded with them. When the server still refuses them, the page shows the refusal and **Retry**.

A connector page has up to four tabs:

| Tab | Shows | Who sees it |
| --- | --- | --- |
| **Accounts** | The accounts the connector can run as. | Everyone with access to the project. |
| **Tools** | Each action, and whether it runs, needs approval, or is blocked. | Members who can change connectors. |
| **Triggers** | [Connector event](/docs/connect/triggers#connector-events) on this connector. | Everyone, when the app has events. |
| **Settings** | Connection details and **Remove connector**. | Members who can change connectors. Absent on the computer connector. |

### Add an MCP server from its URL

1. Open **Customize → Connectors** and select **New → MCP server**.
2. Paste the server's URL, for example `https://mcp.linear.app/mcp`. Kortix names the connector after the domain (`linear`) and shows the name under the field.
3. Choose **Who can use it**. **Only you** is selected by default.
4. Select **Connect**. Kortix adds the connector and the account, then opens the server's sign-in. After you approve, you return to the connector's page with its tools loaded.

- **Only you** adds no shared account. Your login stays in your private account.
- **Everyone in** *project* and **Specific people, groups, or agents** need permission to manage the project's connections.
- A server that needs no sign-in (for example DeepWiki) is ready when the account exists.
- A server that asks for a credential but has no one-click OAuth opens credential entry on the connector page.
- A sign-in that cannot start shows the server's reason. The connector and the account stay; select **Sign in** on the connector page to try again.

### The app catalog

The **All** tab lists one catalog of every way to connect: the Kortix MCP apps below, every MCP server and every REST (OpenAPI) and GraphQL API in the [integrations.sh](https://integrations.sh) registry, and the Composio apps.

Each app shows once, by its best way in:

0. **Kortix.** What Kortix built itself, with no third party: the [channels](/docs/connect/channels) Slack, Microsoft Teams, Email and Telegram, where people message the agent, and **Computer**, the machine the agent works on. Each leads its app and is set up on its own page with **Set up**, never through Install.
1. **A one-click MCP server.** The vendor's server is public, or its OAuth server registers Kortix on the fly. You only sign in.
2. **Composio.** A third-party partner that runs the sign-in for you, for an app with no one-click MCP server, for example Gmail or Outlook. You only sign in.
3. **Everything else.** An MCP server that needs your own OAuth app or an API key, then the REST (OpenAPI) and GraphQL APIs.

- **One-click only** is on by default and lists ways 1 and 2. Turn it off to see every app.
- The type filter (**MCP**, **Composio**, **REST API**, **GraphQL**, **Kortix**) lists the apps that connect that way. The **Kortix** tab shows all five on one page, each with its setup or, once connected, what it is connected to. In the API, the CLI (`--kind kortix`) and the agent's tools the type is `kortix`, with ids `native:slack`, `native:teams`, `native:email`, `native:telegram` and `native:computer`.
- An app's page lists every way to connect it, best first. The first is marked **Recommended**; **One click** marks the ways where you only sign in. **Install** at the top installs the recommended way; each row installs its own way.
- **Tools** on each way lists what it can do before you install it: a public MCP server's own tools, the tool names a public MCP directory lists for an OAuth server, Composio's tools, or the operations in an OpenAPI document.
- Install asks for a **name**. It is the name of the connector profile Kortix adds: the project's entry in `kortix.yaml`. The profile's accounts, who can use them and its tool rules live on it.
- Install one profile for each way you connect an app, for example Stripe's MCP server and Stripe's REST API: each way has its own tools and its own sign-in. Do not install a second profile of the same way to give an agent different rules. Give the agent a [policy set](#policy-sets) on the one profile, so each account is connected once.

Kortix probes every MCP server in the registry for its sign-in and its tools; `apps/api/scripts/probe-one-click-mcp.ts` refreshes both lists.

To install a catalog MCP app:

1. Find the app and select **Install**.
2. **Connect** *app* opens. Choose **Who can use it** and select **Connect**.
3. You sign in to the app and return to the connector's page with its tools loaded.

Apps sign in one of three ways:

| Sign-in | Apps | Setup |
| --- | --- | --- |
| The vendor registers Kortix on the fly | Linear, Notion, Atlassian, Figma, Stripe, Sentry, Airtable, Dropbox, Canva, Miro, monday.com, ClickUp, Intercom, PostHog, Supabase, Vercel, Cloudflare and more | None |
| Kortix's own OAuth client | Gmail, Google Calendar, Google Drive, Google Docs, Google Sheets, GitHub, Slack, HubSpot, Asana, Box | The operator configures the client (`KORTIX_OAUTH_CLIENTS`, see [Kortix OAuth clients](/docs/host#kortix-oauth-clients)). Until then the app is not listed. |
| None | DeepWiki, Context7 | None. The app is ready when it is installed. |

- Kortix's own OAuth client is used only for the exact MCP server URL in the catalog, with the catalog's endpoints and scopes. Its client secret stays on the server.
- Connectors you added from the managed catalog keep working.
- Agents see the same catalog: the `search_connector_apps` tool of the [Kortix MCP server](/docs/connect/mcp) lists every app, with `kind` and `one_click` filters, and `add_connector` with `app` installs its recommended way, or `way`. The catalog is large, not complete: for an app it lacks, agents search the web for the vendor's MCP server or API and add it directly.

Catalog apps can start [triggers](/docs/connect/triggers#connector-events). With the project flag `event_triggers` on, Kortix checks an installed app's MCP server for new items, such as a new email in Gmail, and fires the trigger once for each one. Every tool that lists items and only reads can be an event, on catalog apps and on your own MCP servers. The trigger runs on an account shared with the whole project.

#### Move a Pipedream or Composio connector to Kortix

Kortix retires Pipedream. A Pipedream or Composio connector moves to the catalog app for the same service and keeps its slug. Their sign-ins belong to their own OAuth clients, so they do not carry over: one person signs in to the app once, and the connector switches.

What stays:

- The slug. Agent grants (`agents.<name>.connectors`), session bindings and every other reference to the slug keep working.
- The display name, the entry's `sensitive` flag, its [policy sets](#policy-sets), and a `*` rule in its `policies` or in a set. A rule that names a tool (for example `send_email` on the connector or in one of its sets, or `gmail.send_email` in the project's rules) names the old provider's tool, and the Kortix app names its tools differently: a connector with such a rule does not move until you remove it. Add rules for the new tool names after the move.
- Every account row, with its name, owner and audience.
- The old provider serves the connector until the sign-in completes.

What changes:

- Kortix rewrites the `kortix.yaml` entry to `provider: mcp` with the app's `url`, commits it to the default branch and syncs the connector.
- The tools now come from the vendor's own MCP server, so the tool names differ. Check the agent prompts that name an old tool.
- The account that signed in holds the new sign-in. Every other account on the connector loses its old sign-in. It reads not signed in until its owner signs in again.
- A Composio [event trigger](/docs/connect/triggers#connector-events) on the connector moves to the Kortix event that replaces it, in the same `kortix.yaml` commit, and its Composio subscription is deleted. Kortix then checks the app itself.

```yaml
# Before
connectors:
  - slug: issues
    name: Issues
    provider: composio
    app: linear

# After
connectors:
  - slug: issues
    name: Issues
    provider: mcp
    url: https://mcp.linear.app/mcp
    transport: http
```

Composio event triggers that move:

| Composio event | Kortix event | Config |
| --- | --- | --- |
| `GMAIL_NEW_GMAIL_MESSAGE` | `gmail.message.received` | `query` becomes `in:inbox (<query>)`, so the trigger stays inbox-only. `labelIds` must be empty or `INBOX`. |
| `GOOGLECALENDAR_GOOGLE_CALENDAR_EVENT_CREATED_TRIGGER` | `google_calendar.event.created` | `calendarId` becomes `calendar_id`. `lookahead_days` is `365`, so an event created far ahead still fires. `showDeleted` is dropped. |
| `GOOGLEDRIVE_FILE_CREATED_TRIGGER` | `google_drive.file.created` | `folder_id` and `query` stay; a `folder_id` that is not a Drive folder id blocks the move. `max_results` is dropped. |

`interval` (minutes; Composio checks every minute when it is unset) rounds up to the next Kortix value: 1, 5, 15, 30, 60, 360 or 1440. A trigger in an imported file is rewritten in that file. A connector with any other Composio event trigger does not move until you delete or change that trigger.

A move needs permission to change the project's connectors.

**In the web app**, open the connector in **Customize → Connectors**. The Connected tab names the connectors that can move. The connector page offers **Move to Kortix**. Sign in to the app when it opens.

**From the CLI:**

```bash
kortix connectors moves                  # each Pipedream and Composio connector and its Kortix app
kortix connectors move issues            # sign in once; the connector switches
kortix connectors move issues --connection <connection-id> --no-open
```

- `moves` prints `SLUG`, `PROVIDER`, `APP` (the app on that provider), `MOVES TO`, `STATE` and `ACCOUNTS`. `STATE` is `ready`, `signing in`, `signed in`, or `no Kortix app yet`. `--json` prints the API response.
- `move` opens the app's sign-in in your browser and waits up to 10 minutes for it. `--no-open` prints the URL only. `--device` uses the device flow on a server that offers it.
- `--connection` signs in on that account. Without it, `move` uses the connector's shared project account.

**Through the API:**

```http
GET /v1/projects/{projectId}/connector-moves
```

```json
{
  "moves": [
    {
      "slug": "issues",
      "name": "Issues",
      "provider": "composio",
      "app": "linear",
      "to": { "slug": "linear", "name": "Linear", "icon": "/connector-icons/linear.svg" },
      "connection_id": null,
      "signed_in": false,
      "accounts": 2
    }
  ]
}
```

`to` is `null` when the app has no Kortix equivalent on the deployment. `connection_id` is the account a started move signs in on. `signed_in` is `true` when that sign-in completed and only the switch is left.

```http
POST /v1/projects/{projectId}/connectors/{slug}/move
Content-Type: application/json

{ "connection_id": "11111111-1111-4111-8111-111111111111" }
```

`connection_id` is optional. A connector that already moved answers `{ "status": "moved" }`. Otherwise the answer is the next step:

```json
{
  "status": "sign_in",
  "connection_id": "11111111-1111-4111-8111-111111111111",
  "to": { "slug": "linear", "name": "Linear", "url": "https://mcp.linear.app/mcp" }
}
```

1. Sign in on `connection_id` with the OAuth routes: `POST /v1/projects/{projectId}/connections/{connection_id}/oauth2/discover-resource`, then `/oauth2/register`, then `/oauth2/authorize`. Open `authorization_url`. When discovery returns `kortix_client: true`, send `register` without `registration_endpoint`: Kortix signs in with its own OAuth client.
2. Poll `GET /v1/projects/{projectId}/connections/{connection_id}/oauth2/status` until `status` is `active`. Kortix switches the connector when the sign-in stores its token.
3. Wait for the switch: the connector leaves `GET /v1/projects/{projectId}/connector-moves`. If it is still listed with `signed_in: true` after 30 seconds, call `move` again. That call finishes a switch that failed and answers `{ "status": "moved" }`.

| Status | Meaning |
| --- | --- |
| `400` | `connection_id` is an account of another connector. |
| `403` | No permission to change the project's connectors, or no `connection_id` and no permission to manage the project's accounts. |
| `404` | No connector with this slug, or `connection_id` is an account you cannot change. |
| `409` | The connector is not a Pipedream connector, its app has no Kortix equivalent on this deployment, or it has tool rules other than `*`. The message names the rules. |
| `502` | The `kortix.yaml` write failed. Call `move` again. |

The SDK has the same two calls: `p.connectors.listMoves()` and `p.connectors.move(slug, { connectionId })`. See the [SDK reference](/docs/sdk/reference#connectors-and-policies).

### From the CLI

```bash
kortix connectors catalog gmail                  # find the app; `installed as <slug>` marks one the project has
kortix connectors catalog install composio:gmail # add the profile, the recommended way
kortix connectors connect gmail                  # authorize your account
```

- `catalog install` is idempotent. When the project already has a profile for the same app and way (the same MCP URL, Composio toolkit, OpenAPI spec, GraphQL endpoint or Kortix provider), it changes nothing, names that slug with the three next steps, and exits `3`. `--new-profile` adds a second profile anyway, with the slug suffix `-2`, `-3`, ….
- After install the CLI prints one next step: `Ready` (the app needs no sign-in: call it), `connect <slug>`, `credential <slug>`, or, when the profile's first sync failed, the reason, with exit `1`.
- `kortix connectors add <slug> --provider <p> …` declares a profile by hand, for an app the catalog lacks.

- Without `--apply`, `add` and `rm` edit your local `kortix.yaml`. Run `kortix ship` to apply the change, then `kortix connectors sync` to reconcile the connector.
- With `--apply`, Kortix commits the change to the default branch and syncs the connector at once, like the web app.
- `kortix connectors rm <slug> [--apply]` removes a connector. `kortix connectors rename <slug> <name>` sets its display name and applies at once.
- `kortix connectors catalog [<query>]` lists every app you can install as a connector, one row per app by its best way in. `--kind mcp,composio,openapi,graphql` filters by how it connects, `--one-click` keeps the apps you connect by signing in, and `--category` and `--limit` narrow the page.
- `kortix connectors catalog show <id>` lists every way to connect the app, recommended first, and the tools of one way (`--way <id>`). `catalog tools <id> --way <id>` lists every tool of one way.
- `kortix connectors catalog categories [--kind …] [--one-click]` lists the category keys `--category` takes, with how many apps each holds. Every catalog command takes `--json`.
- `kortix connectors catalog install <id> [--way <id>] [--name <name>] [--slug <slug>]` adds the connector profile, the recommended way unless `--way`. Then `kortix connectors connect <slug>`.
- `--auth-type none|bearer|basic|custom|oauth1` overrides the authentication Kortix detects from the source.

### In kortix.yaml

```yaml
connectors:
  - slug: gmail
    name: Gmail
    provider: composio
    app: gmail

  - slug: docs-search
    provider: mcp
    url: https://mcp.example.com/mcp

  - slug: billing-api
    name: Billing API
    provider: openapi
    spec: https://api.example.com/openapi.json
    auth:
      type: bearer
    headers:
      Accept: application/json
      X-Api-Version: "2026-01-01"
    policies:
      - match: "get_*"
        action: always_run
      - match: "*"
        action: require_approval
```

A change to `connectors:` applies when it reaches the default branch, through a change request merge or a direct push. A merge syncs at once. After a push, Kortix syncs on its next periodic pass. Run `kortix connectors sync` to apply it now. See [Change requests](/docs/git#change-requests).

| Field | Rule |
| --- | --- |
| `auth.type` | `bearer`, `basic`, `custom`, `api_key`, `oauth1`, `hmac`, `aws_sigv4`, `mtls` or `none`. Omit `auth` on a direct provider and Kortix detects it. `none` opts out. `oauth1` works on `openapi`, `postman` and `http` only. |
| `auth.in`, `auth.name`, `auth.prefix` | Where a `custom` or `api_key` credential goes: `in` is `header` (default), `query` or `cookie`. `name` is required for both types. |
| `auth` on `composio` or `channel` | Not allowed. The provider authorizes the account. |
| `headers` | Static headers sent on every call: at most 32, names up to 128 characters, values up to 2,048 characters, no line breaks. Transport headers such as `Host` and `Content-Length` are refused. The auth header always wins over a static header of the same name. Not allowed on `composio`, `pipedream` or `channel`. Values are plaintext in git: never put a credential in a header. |
| `sensitive: true` | Every action that no rule matches needs approval, reads included. See [Policies and approvals](#policies-and-approvals). |
| `policies` | The base rules: `{ match, action, conditions? }`. See [Policies and approvals](#policies-and-approvals). |
| `policy_sets` | Named rule sets that an agent is given with `agents.<name>.policy_sets`. See [Policy sets](#policy-sets). |
| `enabled: false` | Kortix keeps the connector but refuses its calls with `connector_disabled`. |
| Reserved slugs | `kortix_slack`, `kortix_teams` and `kortix_email` belong to channel connectors. `computer` belongs to the built-in computer connector. A new connector added from the web app, `--apply` or MCP also cannot take `slack` or `email` (`400`): connect Slack with `kortix channels connect`. |

The full schema is in the [`kortix.yaml` reference](/docs/project/manifest#triggers-connectors-apps).

## Connectors, connections and accounts

A connection is one **account**: one authorized identity for a connector, such as an OAuth grant or an API key. A connector can hold several accounts, for example a team inbox and your own inbox. The connector's rules apply to every account. Which rules apply depends on the calling agent: see [Policy sets](#policy-sets).

Each account has an owner type that decides who may run a call as it:

| Account | `owner_type` | Who can use it |
| --- | --- | --- |
| Shared | `project` | Everyone in the project, and every agent whose `connectors` grant lists the connector, triggers included. You can [narrow it](#share-accounts-and-give-agents-access) to specific people, groups or agents. |
| Private | `member` | Only its owner, and only in the owner's private sessions. An unattended run (a trigger, or code that uses a service account key, `kortix_sa_…`) never uses a private account. |

`connected_as` is the identity the provider reports for an account, such as an email address or login. It shows on the **Accounts** tab, in `kortix connectors accounts <slug>`, and in `kortix connectors connections ls`. An account with a default label takes `connected_as` as its label. A label someone chose never changes.

Rename an account without a new authorization:

```bash
kortix connectors connections rename <connection-id> Support inbox
```

In the web app, open the account row's menu and select **Rename**. The label cannot be `me`, `project` or UUID-shaped (`400`), and it must be unique among the same owner's accounts, ignoring case (`409`).

## Authorize an account

**Add account** on a connector page asks for a name and **Who can use it**:

- **Everyone in** *project* creates a shared account.
- **Only you** creates a private account. It is selected by default.
- **Specific people, groups, or agents** creates a shared account for that audience only.

Then sign in to the app, or enter its API key.

A connector with exactly one shared account uses it as its default. Kortix makes an empty shared account when it adds a connector, except an MCP server added for **Only you**. The **Accounts** list does not show that empty account, so the connector reads **has no account** until someone adds one. While that account is still not signed in and is the only shared account, a new shared account reuses it instead of adding a second one. It keeps its name unless you type another. Two shared accounts with no default pinned leave the connector with no default. A sign-in on a shared account that is not the default does not reload an MCP connector's tools.

When you have no account of your own on a connector, the **Sign in**, **Set credential** or **Connect** button at the top of the connector page opens **Add account**. It never signs a shared account in with your login. To sign in a shared account, select **Connect** on its row.

| Method | Web app | CLI |
| --- | --- | --- |
| Managed OAuth (`composio`) | **Add account**, then sign in. | `kortix connectors connect <slug>` |
| API key or token | **Add account**, then enter the key. | `kortix connectors credential <slug> [value]`. Without a value it prompts. `-` reads stdin. |
| Project secret | — | `kortix connectors secret <slug> <identifier>`. `--clear` removes the binding. |
| OAuth 2.1 (`mcp`) or OAuth2 (direct APIs) | **Add account**, then sign in. | `kortix connectors connect <slug>` on an MCP server with one-click sign-in. Otherwise `kortix connectors authorize <slug>`. See [OAuth for MCP servers and direct APIs](#oauth-for-mcp-servers-and-direct-apis). |

```bash
kortix connectors connect gmail                          # a private account (--owner me, the default)
kortix connectors connect gmail --owner project          # a shared account
kortix connectors connect gmail --label "Support inbox"  # name a new account
kortix connectors connect-finalize gmail                 # confirm; pass the same --owner
```

- `connect` prints a link. Open it and approve the app. `connect-finalize` exits `1` while authorization is incomplete.
- `connect`, `--label` and agent connect links work on `composio` connectors and on `mcp` connectors with one-click sign-in. One-click sign-in means the server publishes OAuth metadata and supports dynamic client registration, or it is a catalog app on a Kortix OAuth client. For such an `mcp` connector, the link is the app's own consent page: Kortix runs discovery, client registration and PKCE on the server. A legacy `pipedream` connector gets a link for its shared account only.
- `--owner project` needs permission to change the project's connectors.
- `--label` names a new account. The person who opens the link confirms the name and who can use it.
- A project secret works as the credential when it is an active project secret, not a personal one, stored with `--scope connector`: `kortix secrets set BILLING_KEY=- --scope connector`. A binding answers `409` when the connector needs no credential, is a channel, or already has a stored credential, or when the secret is missing, inactive or not connector-scoped. A secret narrowed to some people works only in their private sessions (`credential_not_shared`). See [Secrets](/docs/project/secrets).
- A connect link for an account that is already authorized shows **Already connected**. To change the login, add a new account, [make it the default](#which-account-a-call-uses), then disconnect the old one.

### Connect Shopify

Use a `shopify` connector: Connect asks for the store and your Shopify app's Client ID and secret, then Shopify asks you to approve the app. See [Shopify](/docs/connect/shopify).

A `composio` connector with `app: shopify` keeps its own form: the Client ID and secret of an app in the same Shopify organization as the store, then Composio runs Shopify's client-credentials grant. A refused exchange answers `422` `shopify_refused` with Shopify's reason. Composio's shared app cannot read orders, so prefer the `shopify` connector.

### Connect links inside a session

A session starts even when a granted connector has no account. The first call is denied with `connector_not_connected` and a `connect_url`. The web transcript shows it as a **Connect** button. This works on `composio` connectors and on `mcp` connectors with one-click sign-in. The button opens the **Add account** dialog with the name and audience the agent suggests. By default the account is private. Kortix tells the agent the new account's name. For a shared account from a terminal, run `kortix connectors connect <slug> --owner project`.

### OAuth for MCP servers and direct APIs

Kortix discovers the server's OAuth metadata (RFC 9728, RFC 8414), registers itself as a client when the server supports dynamic client registration (RFC 7591), and runs PKCE (S256) with a `resource` parameter (RFC 8707). With registration support you create no OAuth app.

When the server does not support registration, the web app opens credential entry. Enter the client ID (and secret) of an OAuth app you create with the provider, and register this redirect URI with it:

```text
https://api.kortix.com/v1/connectors/oauth2/callback
```

On a self-hosted instance the URI is `<KORTIX_URL>/v1/connectors/oauth2/callback`. `KORTIX_URL` must be stable. See [Self-hosting](/docs/host#integrations).

From a terminal or an agent session:

```bash
kortix connectors authorize docs-search --json     # prints authorization_url
kortix connectors authorize docs-search --status   # exits non-zero on error
```

| Flag | Effect |
| --- | --- |
| `--device` | Uses the device flow (RFC 8628): prints a code and a URL, then polls until approval, denial or expiry. |
| `--scope "a b"` | Requests only these scopes. |
| `--client-id`, `--client-secret` | Uses an existing OAuth app, for servers without dynamic registration. |
| `--success-redirect`, `--error-redirect` | Where the browser lands after approval or denial. Without them the browser shows **Connected. You can close this tab and return to Kortix.**, or the failure with its reason code. |

Kortix refreshes the connector's tool catalog when authorization completes. Kortix refreshes access tokens before they expire and stores each rotated refresh token.

#### OAuth2 client credentials

An OpenAPI or HTTP API that issues tokens to a client id and secret (machine-to-machine) needs no sign-in:

```bash
kortix secrets get BILLING_CLIENT_SECRET | kortix connectors credential billing-api \
  --oauth2-client-credentials \
  --token-url https://auth.example.com/oauth/token \
  --client-id abc123 --client-secret-from - --scope "read write"
```

- The secret comes from stdin (`-`), a file path, or a prompt. Kortix never prints it back.
- Kortix requests a token before it stores anything. A refused token request answers `503`, `oauth2_token_failed`, with the provider's reason in `detail`, and nothing is stored.
- `--audience <aud>` adds the `audience` parameter some providers require.
- A bad body answers `400`, `invalid_oauth2`.
- The API route is `PUT /v1/connectors/projects/<project_id>/connectors/<slug>/oauth2/connection` `{ token_url, client_id, client_secret, token_endpoint_auth_method?, scopes?, audience?, resource? }`. `token_endpoint_auth_method` is `client_secret_basic` (default), `client_secret_post`, `client_secret_jwt`, `private_key_jwt` or `none`. It answers `{ ok, slug, account, expires_at }`. `DELETE …/connectors/<slug>/credential` removes it.

## Share accounts and give agents access

Two checks decide whether a call can run: the agent's grant to the connector, and the caller's right to use the account.

### Give an agent a connector

An agent reaches a connector only when `agents.<name>.connectors` in `kortix.yaml` lists its slug or is `all`. An omitted value means `none`.

```yaml
agents:
  release-bot:
    connectors: [github, linear]
```

```bash
kortix agents scope release-bot --connectors github,linear
```

A change applies to a running session on its next call. To give one agent other rules on a connector than the rest, give it a [policy set](#policy-sets). The channel connector that started a session (Slack, Teams or email) is always callable from that session, so the agent can always answer where it was asked. See [Agents & permissions](/docs/project/agents#give-an-agent-access).

### Narrow a shared account

A shared account is open to everyone in the project until you narrow it. Select **Share** on the account and add groups, people or agents. Nothing changes until you select **Save**.

```bash
kortix access grant --group <group-id> --connection <connection-id>
kortix access grant --user <email> --connection <connection-id>
kortix access revoke <assignment-id>
```

- A person in the audience uses the account only in a private session.
- An agent in the audience uses it in all its sessions, triggers included. Anyone who can run that agent can use the account through it.
- A session that binds a narrowed account cannot be shared, unless the account is shared with that session's agent.
- Only a person changes an audience. An agent session gets `403`.
- People outside the audience do not see the account. Connection managers see it marked **Not shared with you**.
- Removing the last group or person opens the account to everyone again.
- Only a shared account can be narrowed. A private account answers `404`.

### Share your private account

**Share** on your own **Only you** account turns it into a shared account for the people and groups you pick, or for everyone. Connection managers can then manage it too.

```bash
kortix connectors connections share <connection-id> --group <group-id>
kortix connectors connections share <connection-id> --everyone
```

Sharing needs permission to manage the project's connections. A shared account with the same name answers `409`: rename one first.

### Pin an account for one session

A session can pin one account per connector for every call it makes:

```bash
kortix sessions new --connector gmail=<connection-id>
kortix sessions scope <session-id> --connector gmail=<connection-id>
```

`--no-connectors` removes the pins. A change applies on the next call, with no restart.

## Which account a call uses

A call that names no account, or names `me` or `project`, uses an account only when the choice is certain:

1. Exactly one account is reachable: the call uses it.
2. Several are reachable and exactly one is pinned as the default: the call uses the default.
3. Otherwise the call is denied with `account_required` and `available_accounts`.

`me` limits the choice to your private accounts. `project` limits it to shared accounts.

```bash
kortix connectors accounts gmail                         # accounts you may use, default first
kortix connectors accounts gmail --default "Support inbox"
kortix connectors call gmail <action> '{}' --account "Support inbox"
```

- `--account` takes a label (any case), a connection id, `me` or `project`.
- A named account that does not match is denied with `connector_not_connected` and the names you can use. Kortix never substitutes another account.
- Every result carries `account: { connection_id, label, owner_type }`, so the transcript shows which identity ran the call.

## Policies and approvals

A policy decides what happens when an action is called: **Allow** (`always_run`), **Ask** (`require_approval`) or **Block** (`block`). Kortix evaluates each call in this order. Inside a layer the first matching rule wins, and the first layer with a match decides:

1. Project-wide `policies:` in `kortix.yaml`. Patterns are fully qualified (`gmail.send_email`, `*.delete*`). A connector rule or a policy set cannot override them.
2. The calling agent's [policy set](#policy-sets) on this connector, when `agents.<name>.policy_sets` gives it one. Patterns are relative to the connector (`send_*`).
3. The connector's base `policies:`. Patterns are relative to the connector.
4. `sensitive: true` on the connector: every remaining action needs approval, reads included.
5. `policy.default_mode`: `allow_all` (the default) runs every remaining action. `risk` runs reads and holds writes and destructive actions for approval.

A caller without a policy set skips layer 2. When an agent's set does not exist on the connector, every call that agent makes on the connector is blocked before layer 1: see [When a set is missing](#when-a-set-is-missing).

Patterns are globs, case-insensitive, or `/regex/` in slashes. A rule can also test the call's arguments:

```yaml
policy:
  default_mode: risk

policies:
  - match: gmail.send_email
    action: always_run
    conditions:
      - arg: to
        match: "*@example.com"
  - match: gmail.send_email
    action: require_approval
```

- `arg` is a dot path into the arguments (`message.channel`). `negate: true` inverts a condition. A rule holds up to 10 conditions, and all must match.
- A missing argument never matches the pattern, so a negated condition on it holds. An array matches only when every element matches.
- A malformed condition fails closed: it never opens an action.

```bash
kortix connectors policy ls                                   # project-wide rules
kortix connectors policy set --default risk --apply           # or allow_all; without --apply it edits the local kortix.yaml
kortix connectors policy add "gmail.send_*" ask --condition to='*@example.com'   # project-wide rule; k!=v negates
kortix connectors policy rm "gmail.send_*"
kortix connectors policy gmail set send_email block           # connector rule: allow, ask or block
kortix connectors policy gmail ls                             # also: rm <match>, clear
kortix connectors sensitive gmail on                          # or off
```

`policy add`, `policy rm`, `policy <slug> …` and `sensitive` apply at once. The **Tools** tab on a connector page edits the same connector rules.

### Policy sets

A policy set is a named list of rules on one connector profile. You give an agent a set, and that agent's calls on the connector use the set's rules before the base rules. Two agents can then share one profile and its accounts with different rules: each account is connected once.

```yaml
connectors:
  - slug: gmail
    provider: composio
    app: gmail
    policies:               # rules for callers without a set, and the fallback after a set's rules
      - match: delete_*
        action: block
    policy_sets:
      read_only:
        description: Read and search, never send
        policies:
          - match: send_*
            action: block
      outreach:
        description: Send to customers, with approval
        policies:
          - match: send_email
            action: require_approval
            conditions:
              - arg: to
                match: "*@example.com"

agents:
  support:
    connectors: [gmail, stripe]
    policy_sets:            # connector slug -> set name; no entry = the base rules
      gmail: read_only
  sales:
    connectors: [gmail]
    policy_sets:
      gmail: outreach
```

Here `support` cannot send mail, `sales` sends to `example.com` addresses after an approval, and both are blocked on `delete_*` by the base rules. Both use the same Gmail accounts.

Rules:

- A set name matches `[a-z0-9][a-z0-9_-]{0,63}`. `base` is reserved: it names the base rules in the API, the CLI and the web app.
- A set's `policies` take the same `{ match, action, conditions? }` rules as the base `policies`. A set may hold no rules: it then behaves like the base rules.
- A connector holds at most 32 sets, and a set at most 200 rules.
- Policy sets need `kortix_version: 2` or `3`. A v1 manifest (`kortix.toml`) cannot declare them (`400`, `unsupported_in_v1`).
- Channel connectors (`kortix_slack`, `kortix_teams`, `kortix_email`) and the `computer` connector cannot hold sets (`400`, `policy_sets_unsupported`).
- A set can loosen a base rule for its agent: an `always_run` rule in the set decides before a base `block`. A rule that must hold for every caller belongs in the project-wide `policies:`.

**Which calls use a set.** The credential of the call decides, never its arguments. A request cannot pick a set.

| Caller | Rules |
| --- | --- |
| A session: the `kortix` CLI in its sandbox, the SDK with its `KORTIX_TOKEN`, the agent's MCP tools | The session agent's set. |
| A pi subagent | The set of the agent that started the root session. The subagent shares that session's token. |
| A person's token with `X-Kortix-Session-Id` | Refused (`403`). Only a session's own token carries a session, so a person cannot act as a session's agent. |
| A person's token or API key without a session, the web app, a script, an App | The base rules. |
| A trigger's poll for new items | The base rules. The session the trigger starts uses its agent's set. |

An agent that holds `project.session.start` can start a session as another agent. That session runs under the other agent's set, in the same way it gets the other agent's `connectors` grant. A set bounds an agent only as far as its launch rights do.

**Give an agent a set.**

```bash
kortix connectors policy-sets gmail ls                                   # sets on gmail, with the agents that use each
kortix connectors policy-sets gmail create read_only --template read-only --description "Read and search, never send"
kortix connectors policy gmail --policy-set read_only set "send_*" block   # the set's rules: ls, set, rm, clear
kortix connectors policy gmail effective --policy-set read_only           # what each tool does for that agent
kortix connectors policy-sets gmail rename read_only readonly             # also rewrites every agent that uses it
kortix connectors policy-sets gmail rm readonly                           # refused while an agent uses it
kortix agents scope support --policy-set gmail=read_only                  # repeat the flag per connector; gmail=base removes the entry
kortix connectors agents gmail                                            # which agents may call gmail, and their set
kortix connectors rules                                                   # every agent × every connector: access and set
```

**Templates.** `--template` starts a set from each tool's likely risk. A tool the provider marks as a read is a read. On an MCP server or a managed app, Kortix also reads the tool name: `get_`, `list_`, `read_`, `search_`, `fetch_`, `find_`, `query_`, `describe_` and `lookup_` are reads. On an OpenAPI, HTTP or GraphQL API the method decides.

| Template | Every tool that is not a read | Reads |
| --- | --- | --- |
| `read-only` | `block` | no rule |
| `ask-before-writes` | `require_approval` | no rule |

A tool whose risk is unknown gets the rule, so a template never lets an unclassified tool run. A read falls through to the base rules. Run `policy <slug> effective` to see the result for every tool.

**Effective rules.** `kortix connectors policy <slug> effective [--policy-set <name>]` lists every tool with its risk, its decision (`runs`, `asks`, `blocked`) and the layer that decided: project rule, rule set, base rules, sensitive, or default mode.

- Every command commits `kortix.yaml` on the default branch and syncs the connector at once.
- Changing an agent's `policy_sets` needs `project.agent.write` and `project.connector.write`. An agent session needs `project.connector.write` in its own grant to add, change or remove any `policy_sets` entry, its own included (`403`, `agent_grant_escalation`). See [Changes to agents are governed](/docs/project/agents#changes-to-agents-are-governed).
- Removing a connector from an agent keeps the agent's entry for it. The entry has no effect until the connector is granted again, and then the set applies again. Remove the entry with `--policy-set <slug>=base`.
- Deleting a connector removes every agent's entry for it, in the same commit. An agent session that removes an agent which has a set needs `project.connector.write` too.
- A change reaches a running session on its next call.

In the web app, the **Tools** tab on a connector page switches between the base rules and each set, and shows the agents that use a set. The agent editor picks the set for each granted connector that defines sets.

**API.** The routes are under `/v1/connectors/projects/<project_id>/connectors/<slug>` and need `project.connector.write`.

| Route | What it does |
| --- | --- |
| `GET …/policy-sets` | `{ sets: [{ name, description, policies, agents }] }`, sets with no rules included. |
| `PUT …/policy-sets/<name>` `{ description?, template? }` | Creates the set, or sets or clears its description. `template` is `read_only` or `ask_before_writes`. Answers `created`. |
| `PUT …/policy-sets/<name>/name` `{ name }` | Renames the set and every agent reference in one commit. `409`, `policy_set_exists` when the new name is taken. |
| `DELETE …/policy-sets/<name>` | Deletes the set. `409`, `policy_set_in_use` with `agents` while an agent uses it. |
| `GET`/`PUT …/policies?policy_set=<name>` | Reads or replaces the set's rules. Without `policy_set`, or with `base`, the base rules. `404`, `policy_set_not_found` for an unknown set. `GET` also answers `effective: [{ path, action, source, risk, rule? }]`, every tool after every layer, and `sensitive`. `source` is `project`, `policy_set`, `connector` (the base rules), `risk_default` or `allow_all` (the default mode, or sensitive when `sensitive` is `true`). |
| `GET …/agents` | `{ slug, agents: [{ agent, granted, policy_set }] }`. |
| `GET /v1/connectors/projects/<project_id>/rules-matrix` | Every connector with its sets, and every agent with `{ granted, policy_set }` per connector. |

`PUT /v1/projects/<project_id>/agents/<agent>/scope` takes `policy_sets: { <slug>: <name> | null }`. It merges per connector, and `null` or `base` removes the entry. In the SDK, use `p.connectors.policySets` and the `policySet` option of `p.connectors.policies`: see the [SDK reference](/docs/sdk/reference#connectors-and-policies).

#### When a set is missing

`kortix validate` and the change request merge check report an agent entry that names an unknown set, or `base`, as an error. A `policy_sets` key for a connector the agent is not granted is a warning.

A bad entry never disables the agent, and Kortix never drops it. When the manifest on the default branch still names a set the connector does not define, Kortix blocks every call the agent makes on that connector, with reason `policy_set_missing`. The agent's other connectors keep working, the channel it answers on included. A `policy_sets` value that is not a map is different: it blocks every connector for that agent, channels included. Fix the entry or add the set. Kortix never falls back to the base rules, because they can be looser than the set.

**Audit.** When a set decides a call, the audit event records `policy_source: "policy_set"`, `policy_set`, `agent` and `manifest_commit`. The approval card's summary and the approval link view (`GET /v1/approval-links/<token>`) carry `policy_set` and `agent` when the set decided.

### Approve a held call

A held call returns `202` with `status: "pending_approval"`, `approval_url`, `approval_summary` and `execution_id`. Nothing ran.

1. A person opens the approval in **Review → Needs you**, through `approval_url`, or on the approval card in a [Slack or Teams thread](/docs/connect/channels#approvals-and-stopping-a-run). The page asks for a signed-in Kortix account that can approve actions in the project.
2. The page shows the redacted arguments the provider will receive. They decide **Approve** or **Deny**, with an optional message back to the agent.
3. Kortix sends the decision into the session, and the agent continues.

- An approval covers one exact request: the same connector, action, arguments and account. A changed argument needs a new approval.
- After an approval, the identical call runs once when it repeats within 15 minutes.
- A held call expires when nobody decides it within 24 hours, or within the project's [`approvals.ttl`](/docs/project/manifest#policy-and-policies). `approval_url` expires at the same time. An expired call leaves **Review → Needs you**, its chat card shows **Expired**, and `POST /v1/projects/<project_id>/approvals/<execution_id>` returns `409` with `code: "APPROVAL_EXPIRED"`. The session does not resume. The agent asks again with a new call.
- There is no session-wide approval. An action that must run unattended needs an **Allow** rule.
- A project manager or the person who started the session decides a held call. A session started with an API token (the CLI, a service account) is decided by project managers only.
- Anyone else who can open the session sees the call and who decides it, with no **Approve** or **Deny**. They can copy `approval_url` and send it to that person: the approval page answers them with `403` too. In **Review**, the call is under **Waiting** for them, not **Needs you**.
- `GET /v1/projects/<project_id>/sessions/<session_id>/audit` and `GET /v1/projects/<project_id>/review/items` return `can_resolve` and `resolvers` on each pending call. `can_resolve` is `true` only when the caller's `POST /v1/projects/<project_id>/approvals/<execution_id>` would succeed. Any other caller gets `403`. `resolvers` is `managers` or `managers_and_launcher`.
- `--reason` (SDK: `approvalContext`) describes the effect when the arguments are only ids, for example who a draft goes to. The approver sees it marked as unverified. Kortix never sends it to the provider.

## Call a connector from a session

An agent calls connectors with the `kortix` CLI in its sandbox. The same commands work from your terminal.

```bash
kortix connectors ls                            # connectors in scope and their status
kortix connectors discover "send an email"      # find an action by intent
kortix connectors show gmail.send_email         # one action's input schema
kortix connectors call gmail send_email @mail.json --account "Support inbox" --reason "Weekly report to the team"
```

`call` takes the arguments as inline JSON, `@file.json`, or `-` for stdin. `--account`, `--reason`, `--attach` and `--out` are optional.

### Read the result

- Read `output ?? data`. `data` is the raw upstream answer. `output` is the payload without the provider's envelope, present only when it differs from `data`.
- `upstream_error` reports a failure inside a `2xx` answer (an MCP `isError` result, GraphQL `errors`). `ok` stays `true`.
- An upstream `429` or `503` keeps its status. When the provider sent `Retry-After`, the body carries `retry_after_seconds`. Wait, then call again.
- Every other upstream failure answers `500` with the cause in `reason`.
- The upstream deadline is 60 seconds (`upstream_timeout`). Answers over 64 MiB are refused (`upstream_response_too_large`).
- A call is not idempotent. After a timeout it may have run upstream. Check the effect before you repeat a write.

For a list or search result too large to read, write it to a file:

```bash
kortix connectors call linear list_issues '{"first":250}' --out /workspace/output/issues.json
jq '.data' /workspace/output/issues.json
```

`--out` writes the full JSON and prints only `saved_to`, `bytes` and the `shape` of `data` (keys, array lengths, `pageInfo`).

### Attach files

Arguments never carry file bytes. Stage the file, and Kortix writes the bytes into the provider request server-side.

```bash
kortix connectors call outlook send_mail @mail.json --attach /workspace/artifacts/report.pdf
kortix connectors upload /workspace/artifacts/report.pdf --connector outlook   # prints ref
```

- `--attach` appends a reference to the action's attachments array. Name the array with `--attach-path body.message.attachments` when Kortix cannot find it.
- `upload` returns `ref`, `{"$kortix_attachment": "<id>"}`. In an attachments array it becomes the provider's attachment item. In a string field it becomes the file's base64. On the email channel it becomes a signed download URL.
- Files come from `/workspace/output`, `/workspace/artifacts`, `/workspace/reports` or `/workspace/deliverables`. Symbolic links and hard links are refused.
- One call carries at most 20 files and 25 MiB. A staged file is single-use, private to its session, and deleted after 24 hours.
- `composio`, `pipedream` and `computer` connectors do not accept staged files (`connector_attachments_unsupported`).

From an MCP client, the [Kortix MCP server](/docs/connect/mcp) offers the same flow through `list_connectors`, `search_connector_actions`, `describe_connector_action`, `call_connector` and `upload_connector_attachment`.

## Call connectors from code

Code calls a connector through `@kortix/sdk` and holds only a Kortix credential. Do not put a provider API key in an App or a backend when a connector for that provider exists: the key skips policies, approvals and audit.

### Pick the credential

| Where the code runs | Credential | Acts as | Accounts it reaches |
| --- | --- | --- | --- |
| An App, in the browser | `createKortix({ backendUrl: '/_kortix/api/v1', getToken: kortixAppViewerToken() })`. Set the App to `kortix apps access <app> --viewer api`. | The person viewing the App | Shared accounts that person may use, and their private accounts |
| An App, on its server | `await createAppViewerKortix(request, { backendUrl })` from `@kortix/sdk/server`. Build one client per request. | The person viewing the App | The same |
| Unattended code (a backend job, a cron, an App job) | A service account key, `kortix_sa_…` | The service account | Shared accounts nobody narrowed. Never a private or narrowed account |
| A script or CI job | A personal access key, `kortix_pat_…`. Bind it with `kortix tokens new <name> --project <project-id>`. | You | Shared accounts you may use, and your private accounts |
| A session sandbox | `KORTIX_TOKEN` | The session | Limited by the agent's connector grant |

- A viewer token reaches every project the viewer can read. Pass the App's own project id on every call.
- Create a service account with `kortix tokens service-accounts new <name>`. The key prints once. Give it a role with `kortix access grant --service-account <id> --role member --project <project-id>`: until then every call answers `403`. `kortix tokens service-accounts disable <id>` revokes it. See [API keys and tokens](/docs/accounts/identity#api-keys-and-tokens).
- For the viewer token, see [Know who is looking](/docs/apps#know-who-is-looking).

### The connector handle

```ts
import { createKortix } from '@kortix/sdk';

const kortix = createKortix({ backendUrl: 'https://api.kortix.com/v1', getToken });
const crm = kortix.project(projectId).connector('crm');

const deals = await crm.run('list_deals', { stage: 'won' }, { account: 'Team CRM' });
```

`kortix.connector(slug)` is the same handle for a token bound to one project, such as a session token.

| Method | Returns |
| --- | --- |
| `run(action, args, options)` | The action's `output`. Throws a typed error for every other outcome. |
| `call(action, args, options)` | The raw result (`ok`, `data`, `output`, `account`, `binding`, …). `200` and `202` resolve. Other statuses throw `ApiError`. |
| `describe()`, `describe(action)` | The connector or one action with input and output schemas, or `null`. |
| `accounts()` | The accounts this credential may use, default first. |
| `paginate(action, args, { next, maxPages })` | An async iterator over each page's `output`. |
| `uploadAttachment(content, { filename, contentType })` | A `ref` for a later call of this connector. |

| Option | Value |
| --- | --- |
| `account` | A label, a connection id, `me` or `project`. Omit it for the [account rule](#which-account-a-call-uses). |
| `approvalContext` | Text for the approver. Never sent to the provider. |
| `timeoutMs` | Client deadline. Default 90,000 ms, above the gateway's 60 s upstream deadline. |
| `signal` | An `AbortSignal`. The call may still run upstream. |

### Typed calls

```bash
kortix connectors types --out src/kortix-connectors.d.ts
kortix connectors types --connector linear,github --out src/kortix-connectors.d.ts
```

The file fills `ConnectorActionRegistry` in `@kortix/sdk`. Include it in `tsconfig.json`, and `run` and `kortix.project(projectId).connectors.callAction(slug, action, args)` type-check arguments and `output`. `composio` and `pipedream` connectors publish no output schema, so their output is `unknown`. Run the command again after you add a connector.

### Errors in code

```ts
import { ConnectorApprovalPendingError, ConnectorCallError } from '@kortix/sdk';

try {
  return await crm.run('create_deal', { name: 'Renewal' });
} catch (error) {
  if (error instanceof ConnectorApprovalPendingError) return showLink(error.approvalUrl);
  if (error instanceof ConnectorCallError && error.connectUrl) return showConnect(error.connectUrl);
  if (error instanceof ConnectorCallError && error.retryAfterSeconds) return retryLater(error.retryAfterSeconds);
  throw error;
}
```

- `ConnectorApprovalPendingError` means a policy held the call and nothing ran. It has `approvalUrl`, `approvalSummary`, `approvalInstructions`, `executionId` and `retryable`. Show the link. Do not repeat the call in a loop.
- `ConnectorCallError` extends `ApiError`. `code` is `upstream_<status>` for an upstream failure, `upstream_error` for a failure inside a `2xx` (`status` 200), or the gateway reason from [Errors](#errors). It also has `reason`, `hint`, `connectUrl`, `availableAccounts`, `requestedAccount`, `upstreamStatus`, `retryAfterSeconds` and `binding`.
- The SDK retries nothing, because a connector call is not idempotent.

### Pages

```ts
import { ConnectorPageLimitError } from '@kortix/sdk';

try {
  for await (const page of crm.paginate('list_deals', { limit: 100 }, {
    next: (page, args) => (page.next_cursor ? { ...args, cursor: page.next_cursor } : undefined),
    maxPages: 20,
  })) await save(page.deals);
} catch (error) {
  if (error instanceof ConnectorPageLimitError) await resumeLater(error.nextArgs);
  else throw error;
}
```

`next` returns the next page's arguments, or `undefined` after the last page. `maxPages` defaults to 100. When pages remain after it, `paginate` throws `ConnectorPageLimitError` (`code: 'max_pages_exceeded'`) with `nextArgs`, so a capped listing never reads as complete. Each page is one call, with its own policy check and audit event.

In React, `useConnectorQuery(projectId, slug, action, args)` from `@kortix/sdk/react` reads one action as a cached query. Use it for read actions only. See [React hooks](/docs/sdk/react#hooks).

## Errors

A denied call answers `{ ok: false, status: "denied", reason }` plus a `hint` or `message` that names the fix. A failed call answers `{ ok: false, status: "error", reason, upstream_status }`.

A tool that ran and reported its own failure (an MCP result with `isError: true`) answers HTTP `200` with `{ ok: false, status: "tool_error", error, result }`: `error` is the tool's first text block, `result` the raw result. The call reached the tool, so the transport and the rules worked; fix the arguments. `kortix connectors call` exits `1` on a denial, an error and a `tool_error`. A rejected token prints `Token rejected … Run kortix login` (with `--json`, `{ ok: false, code: "unauthorized" }`).

An `error` reason starts with the code in the table. Text after the first `:` is detail (`upstream_timeout: …`). For an upstream failure, read `upstream_status`: `reason` can be the provider's own text. In the SDK, `ConnectorCallError.code` is always the bare code or `upstream_<status>`.

| `reason` | HTTP | Meaning | Fix |
| --- | --- | --- | --- |
| `connector_not_assigned` | 403 | The agent's `connectors:` grant does not list this connector. The body names `agent` and `granted`. | Add the slug to `agents.<name>.connectors`. |
| `connector_not_connected` | 403 | No usable account, or `--account` named one that does not exist. | Open `connect_url`, or retry with a name from `available_accounts`. |
| `account_required` | 403 | Several accounts are reachable, none is named, none is pinned. | Pass `--account`, or pin a default. |
| `credential_not_shared` | 403 | The connector's project secret is not shared with the person this call acts for. | Ask the secret's owner to share it. |
| `credential_undecryptable` | 403 | Kortix cannot decrypt the connector's stored credential, or the project secret it uses: the server's encryption key changed, or the stored value is damaged. `message` names the connector or the secret. | Reconnect the account, or enter the credential or the secret again. For an OAuth 2.0 account, save its OAuth application again first: the same key encrypts it, and until then its routes answer `409 SECRET_UNDECRYPTABLE`. |
| `connector_disabled` | 403 | The connector is declared with `enabled: false`. | Enable it. |
| `policy_block` | 403 | A **Block** rule matched. Final. When the agent's policy set decided, the body names `policy_set` and `agent`. | Do not retry. Change the policy, or the agent's set. |
| `policy_set_missing` | 403 | The agent's `policy_sets` names a set that this connector does not define. Every call on the connector is blocked for this agent. The body names `policy_set` and `agent`. | Fix `agents.<name>.policy_sets`, or add the set. See [When a set is missing](#when-a-set-is-missing). |
| `connector_not_found` | 404 | No connector with this slug. | Run `kortix connectors ls`. |
| `action_not_found` | 404 | The connector has no such action. | Run `kortix connectors show <slug>`. |
| `computer_*` | 403 or 409 | The computer refused, is offline, or is not paired. | See [Computers](/docs/connect/computers#errors). |
| `insufficient_scope` | 403 | An OAuth token without the `kortix` scope. | Use a token with the `kortix` scope. |
| `viewer_api_disabled` | 403 | An App's browser call while the App is not `--viewer api`. | `kortix apps access <app> --viewer api`. |
| `upstream_<status>`, `upstream_timeout`, `upstream_response_too_large` | 500 (429 and 503 keep their status) | The provider failed, did not answer in 60 s, or answered over 64 MiB. | Wait for `retry_after_seconds`, or ask for a smaller page. Check the effect before you repeat a write. |
| `connector_egress_blocked` | 500 | The target resolves to a private or internal address. | See [Network safety](#network-safety). |
| `connector_attachments_unsupported` | 500 | A staged file on a `composio`, `pipedream` or `computer` connector. | Send the file through the provider's own input. |

## Network safety

Kortix checks every connector request before it leaves: calls to `http`, `openapi`, `graphql`, `mcp`, `postman` and `channel` connectors, and the catalog reads of a sync.

- The host must resolve to public addresses. A private or internal address is refused with `connector_egress_blocked`.
- Kortix follows redirects itself and checks each hop again. A redirect to another origin drops the `Authorization` header.
- Both `http` and `https` are allowed.

A self-hosted instance can allow internal hosts with `KORTIX_CONNECTOR_EGRESS_ALLOW_HOSTS`. Managed apps that need your own OAuth app, and the other integration settings, are on [Self-hosting](/docs/host#integrations).
