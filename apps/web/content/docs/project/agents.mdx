An agent is a markdown file that defines how OpenCode acts in a
[session](/docs/work/sessions). This page covers agent files, skills, and
how a session picks an agent.

## OpenCode runs every session

OpenCode, the open-source coding-agent runtime, runs every session. The
`kortix-agent` daemon starts it as `opencode serve`. OpenCode reads the
project's agents from `agents/`, its skills from `skills/`, and the files only
OpenCode reads from `harnesses/opencode/`.

Projects created before 2026-09 keep agents and skills under
`.kortix/opencode/`. Kortix reads both layouts.

## An agent is two files

Each agent has two parts:

- **Behavior** — a markdown file, `agents/<name>.md` by default. Its
  frontmatter sets the model, mode, and tools. Its body is the system prompt.
- **Governance** — an entry in `kortix.yaml`'s `agents` map, keyed by the agent
  name. It sets what the agent may access on Kortix: connectors, secrets,
  skills, Apps, and Kortix permissions. Its `file` field names the behavior
  file.
  The map can live in a file the manifest lists under
  [`imports:`](/docs/project/manifest#imports); `default_agent` stays in `kortix.yaml`.

The manifest never sets a prompt, mode, or tool. The `.md` file never sets
platform access. See [the manifest reference](/docs/project/manifest) for
every governance field.

### Where the agent file lives

```yaml
agents:
  support:
    file: agents/support.md
```

- `file` is a repo-relative path. It must end in `.md`.
- It must not start with `/`. It must not contain a `.` or `..` segment.
- Without `file`, Kortix reads `agents/<name>.md`, then
  `.kortix/opencode/agents/<name>.md`.
- When the dashboard saves an agent that has a `.md`, it writes `file` with that path.
- The API refuses to change `file`. To move an agent, move its `.md` and
  update `file` in `kortix.yaml` in the same commit.

The full path rules are in
[the manifest reference](/docs/project/manifest#the-agent-file).

## Governance is deny-by-default

An agent with no `connectors`, `secrets`, `skills`, `apps`, or `kortix_permissions` key gets
none of that access. `apps` lists the [Kortix Apps](/docs/feature-flags/apps#agents-and-apps)
the agent may open when an App is restricted or private. This grant is the second of the two bindings: the agent
also holds a role as a `service_account` principal — its ceiling — and a
session can only do what both allow. See
[Agent permissions](/docs/project/permissions) and
[One vocabulary, two bindings](/docs/accounts#one-vocabulary-two-bindings). Set a field to `all` to grant full access, or list
specific names. `default_agent` in `kortix.yaml` names the agent a session
starts when you request no agent.

Set each grant from the dashboard — Customize → Agents → the agent, one page
per grant set on the Access rail: Skills, Connectors, Secrets, Apps, Kortix
permissions — or from the CLI with `kortix agents scope <agent>`
(`--secrets`, `--connectors`, `--apps`). The Apps page appears only when the
project has the [Apps](/docs/feature-flags/apps) feature flag on. Every path
writes the same `agents.<name>` block in `kortix.yaml`.

Legacy `kortix.toml` (v1) projects list agents in an array, not a map, and
grant full access by default. Set specific grants to restrict access. See
[the manifest reference](/docs/project/manifest).

## Skills give an agent know-how

A skill is a markdown file at `skills/<name>/SKILL.md`.
OpenCode loads a skill on demand when the agent calls it — Kortix does not
inject skills into every prompt. An agent's `skills` grant in `kortix.yaml`
controls which skills it may load.

## How a session picks its agent

Creating a session accepts an `agent_name`. Kortix starts that agent for the
session. If you omit `agent_name`, Kortix uses the project's `default_agent`.
Set the default agent from the dashboard, the API, or the SDK. Each writes
`default_agent` to `kortix.yaml` and commits the change to the project's
default branch.

An agent acts as itself: its Kortix permissions within its ceiling role,
whoever runs it. Starting a session does not lend the agent your own role.
See [Agent permissions](/docs/project/permissions).

New or changed agents and skills reach future sessions only after a
[change request](/docs/work/change-requests) merges them into the default
branch. Connect external tools before an agent can use them; see
[Connectors](/docs/connect/connectors).
