description: "The kortix_version 3 manifest, available as an opt-in: the project registers skills, tools, commands and extensions, and each agent enables what it uses. A complete example, a split repository layout, and every key with its default and what it compiles to."
---

`kortix.yaml` is the manifest at the root of a project repository. It does two things:

1. **It registers what exists.** Skills, tools, commands, extensions, connectors, Apps, secret names and sandbox templates. A registry entry gives a thing a name. It gives no agent access to it.
2. **It defines every agent.** Each agent is one block: its prompt, its model, its tool policy, and the registered things it enables by name.

Nothing in the manifest applies to every agent. There is no project-wide permission, command or extension. Harness-specific code lives only under `extensions`, with one implementation per harness. This page describes `kortix_version: 3`, available as an opt-in. New projects are created on `kortix_version: 2`, and a project keeps its version until you migrate it: see [Versions 1 and 2](#versions-1-and-2).

## A complete example

This manifest is valid as written. It has a primary agent, a subagent, and a scheduled reporter:

```yaml
# yaml-language-server: $schema=https://kortix.com/schema/kortix.v3.schema.json
kortix_version: 3

project:
  name: acme-support
  description: Answers help desk tickets and reports on them.

default_agent: assistant
runtime: opencode

env:
  required: [HELPDESK_TOKEN]
  optional: [SLACK_WEBHOOK_URL]

sandbox:
  default: support
  templates:
    - slug: support
      name: Support
      dockerfile: sandbox/Dockerfile
      cpu: 2
      memory: 4

policy:
  default_mode: risk
policies:
  - match: helpdesk.close_ticket
    action: require_approval

# ─── Registries: what exists in this project ────────────────────────────────

skills:
  pdf: skills/pdf
  triage-rules: support/skills/triage-rules

tools:
  lookup_order: tools/lookup_order.ts

commands:
  summarize:
    description: Summarize a text in five bullets.
    prompt: Summarize $ARGUMENTS in five bullets.
  weekly-report:
    description: Write the weekly support report.
    prompt_file: support/commands/weekly-report.md

extensions:
  audit:
    opencode: extensions/audit.opencode.ts
    pi: extensions/audit.pi.ts
  web-access:
    pi: npm:pi-web-access@0.30.0

connectors:
  - slug: helpdesk
    name: Help desk
    provider: openapi
    spec: https://helpdesk.example.com/openapi.json
    auth:
      type: bearer

apps:
  dashboard:
    path: apps/dashboard/dist
    type: static
    spa: true

# ─── Agents: each one decides what it uses ──────────────────────────────────

agents:
  assistant:
    description: The project's main agent. Answers tickets and delegates research.
    mode: primary
    model: kortix/glm-5.3-flash
    prompt_file: agents/assistant.md
    permission:
      bash:
        "*": allow
        "git push *": ask
      external_directory: deny
    tools: all
    skills: all
    subagents: [researcher]
    commands: [summarize, weekly-report]
    extensions: [audit]
    connectors: [helpdesk]
    secrets: [HELPDESK_TOKEN]
    apps: [dashboard]
    kortix_permissions: [project.session.read, project.review.submit]

  researcher:
    description: Looks up an account's order history. Never edits files.
    mode: subagent
    prompt: |
      You research one account. Read its orders with lookup_order and
      report what you found. Never edit files.
    permission:
      edit: deny
      bash: deny
    tools: [read, grep, lookup_order, web_search]
    skills: [triage-rules]
    secrets: [HELPDESK_TOKEN]

  reporter:
    description: Writes the weekly report on a schedule.
    mode: primary
    hidden: true
    prompt_file: support/agents/reporter.md
    commands: [weekly-report]
    extensions: [web-access]
    codemode: only
    connectors: [helpdesk]
    secrets: [SLACK_WEBHOOK_URL]
    workspace:
      project_repository: false

triggers:
  - slug: weekly-report
    type: cron
    agent: reporter
    cron: "0 0 15 * * 1"
    timezone: Europe/Berlin
    prompt: Write the weekly support report for the last 7 days.
```

What each agent gets:

| | `assistant` | `researcher` | `reporter` |
| --- | --- | --- | --- |
| Tools | every tool | `read`, `grep`, `lookup_order`, `web_search` | every tool |
| Tool policy | allow, but `git push` asks and paths outside `/workspace` are refused | file edits and the shell refused | allow |
| Skills | every registered and Kortix skill | `triage-rules` | none |
| Subagents | `researcher` | none | none |
| Commands | `/summarize`, `/weekly-report` | none | `/weekly-report` |
| Extensions | `audit` (OpenCode plugin or pi package) | none | `web-access` (pi only) |
| Connectors, secrets | `helpdesk`, `HELPDESK_TOKEN` | `HELPDESK_TOKEN` | `helpdesk`, `SLACK_WEBHOOK_URL` |

## Split the manifest by topic

`imports` splits one manifest across several YAML files. The root `kortix.yaml` keeps the project-global keys. Each topic gets a folder, and a feature can keep its agents, prompts, commands, skills and triggers together in one folder. Kortix merges every file into one manifest before it validates or compiles it, so the example above and this layout define the same project.

```yaml
# support/support.yaml
skills:
  triage-rules: support/skills/triage-rules

commands:
  weekly-report:
    description: Write the weekly support report.
    prompt_file: support/commands/weekly-report.md

agents:
  reporter:
    description: Writes the weekly report on a schedule.
    mode: primary
    hidden: true
    prompt_file: support/agents/reporter.md
    commands: [weekly-report]
    extensions: [web-access]
    codemode: only
    connectors: [helpdesk]
    secrets: [SLACK_WEBHOOK_URL]
    workspace:
      project_repository: false

    type: cron
    agent: reporter
    cron: "0 0 15 * * 1"
    timezone: Europe/Berlin
    prompt: Write the weekly support report for the last 7 days.
```

- **Paths stay repository-relative.** `prompt_file: support/agents/reporter.md` in `support/support.yaml` is relative to the repository root, not to the YAML file.
- **A name lives in one file.** `assistant` in `agents/assistant.yaml` enables `weekly-report`, which `support/support.yaml` registers. A reference crosses files. A declaration does not.
- **Import a file, not a folder, when the folder holds other YAML.** A directory import reads every `.yaml` and `.yml` file below it. An App's source or a skill's reference files can hold YAML that is not manifest YAML, for example `pnpm-workspace.yaml`. In v3 such a file fails the whole manifest. Import `apps/apps.yaml`, not `apps/`.

## Top-level keys

| Key | Type | Default | Rule |
| --- | --- | --- | --- |
| `kortix_version` | `3` | required | Selects the schema. |
| `project` | map | none | `name`, `description`. For people who read the repository. The project name in Kortix does not come from here. |
| `default_agent` | agent name | required | A declared agent that is enabled and has `mode` `primary` or `all`. A session or trigger that names no agent runs it. |
| `runtime` | `opencode` or `pi` | `opencode` | The harness. See [The harness](#the-harness). |
| `imports` | list of paths | none | Other YAML files that merge into this one. See [Imports](#imports). |
| `env` | map | none | `required` and `optional`: lists of secret names. See [env](#env). |
| `sandbox` | map | the platform image | `templates` and `default`. See [sandbox](#sandbox). |
| `skills` | map | none | Registry: skill name to the folder that holds its `SKILL.md`. |
| `tools` | map | none | Registry: tool name to a module path. |
| `commands` | map | none | Registry: command name to `{ description, prompt }` or `{ description, prompt_file }`. |
| `extensions` | map | none | Registry: extension name to `{ opencode, pi }`, one implementation per harness. |
| `connectors` | list | none | Apps, APIs and MCP servers an agent can call. See [Connectors](/docs/connect/connectors). |
| `apps` | map | none | App slug to App configuration. See [Apps](/docs/apps#configure-in-kortixyaml). |
| `triggers` | list | none | Schedules, webhooks, monitors and app events. See [Triggers](/docs/connect/triggers). |
| `policy`, `policies` | map, list | `allow_all` | Approval rules for connector calls. See [Connector approvals](#connector-approvals-policy-and-policies). |
| `agents` | map | required | Agent name to agent block. At least one agent. |

A v3 manifest has no other key. An unknown key is an error, and these keys from earlier versions are errors with a pointer to their replacement:

| Key | Replacement |
| --- | --- |
| `permission` | `agents.<name>.permission` |
| `harnesses` | `extensions`, enabled per agent; `codemode` on the agent |
| `opencode`, `pi` | v3 reads no harness folder. Agents, commands and permissions go in `kortix.yaml`, plugins and pi packages under `extensions`. |
| `channels` | Connect a channel in the dashboard. It writes a `channel` connector. |
| `sandboxes` | `sandbox.templates` |

## Registries

A registry entry names a thing. Agents enable it by that name. An agent grant that names something the registry does not hold is an error.

**Names.** A skill, command or extension name is lowercase letters and digits in words joined by `-`, at most 64 characters: `^[a-z0-9]+(-[a-z0-9]+)*$`. A tool name is snake case: `^[a-z][a-z0-9_]{0,63}$`.

**Paths.** Every path is relative to the repository root. A path does not start with `/` or `-`, and has no `.`, `..` or empty segment. Each segment uses letters, digits, `_`, `-`, `.` and spaces.

**Built-ins are always registered.** Every v3 project has the seven [Kortix tools](/docs/project/tools) and the 12 Kortix skills without a registry entry. An agent enables them by name like any other.

| Built-in | Names |
| --- | --- |
| Kortix tools | `web_search`, `image_search`, `scrape_webpage`, `memory`, `show`, `kortix-connectors_call`, `kortix-connectors_describe` |
| Kortix skills | `kortix-apps`, `kortix-computer`, `kortix-connectors`, `kortix-drives`, `kortix-genui`, `kortix-harness-refinement`, `kortix-marketplace`, `kortix-memory`, `kortix-onboarding`, `kortix-slack`, `kortix-system`, `kortix-teams` |
| Harness tools | `bash`, `read`, `write`, `edit`, `apply_patch`, `glob`, `grep`, `list`, `task`, `question`, `todowrite`, `webfetch`, `websearch`, `skill`, `lsp` |

### skills

```yaml
skills:
  pdf: skills/pdf                                # skills/pdf/SKILL.md
  triage-rules: support/skills/triage-rules      # support/skills/triage-rules/SKILL.md
```

- The value is the folder that holds `SKILL.md`. The folder's last segment is the skill name: `pdf: skills/pdf`, not `pdf: skills/pdf-tools`.
- The frontmatter `name` in `SKILL.md` is the same name.
- A name that starts with `kortix-` is an error. That prefix belongs to the Kortix skills.
- A session loads exactly the registered folders and the Kortix skills. A `SKILL.md` that no entry names is never visible.

### tools

```yaml
tools:
  lookup_order: tools/lookup_order.ts
  web_search: integrations/search/web_search.ts  # replaces the Kortix web_search
```

- The value is a module that ends in `.ts`, `.js`, `.mts`, `.mjs`, `.cts` or `.cjs`. The module contract is on [Tools](/docs/project/tools#write-a-project-tool).
- A harness tool name, or a name that starts with `pty_`, is an error.
- A project tool with a Kortix tool's name replaces that Kortix tool for every agent.
- The v2 value `kortix:<name>` is an error. Kortix tools need no entry.

### commands

```yaml
commands:
  summarize:
    description: Summarize a text in five bullets.
    prompt: Summarize $ARGUMENTS in five bullets.
  weekly-report:
    description: Write the weekly support report.
    prompt_file: support/commands/weekly-report.md
```

| Key | Rule |
| --- | --- |
| `description` | Optional string. The command picker shows it. |
| `prompt` | The prompt text. Set exactly one of `prompt` and `prompt_file`. |
| `prompt_file` | A repository `.md` file whose text is the prompt. |

- `$ARGUMENTS` takes everything after the command name. `$1`, `$2`, … take one word each, and the last one takes the rest.
- A command has no `agent` key. It runs on the agent that enables it.
- A command that no agent enables is not compiled.

### extensions

An extension is code that changes a harness: an OpenCode plugin, a pi package, or both under one name.

```yaml
extensions:
  audit:
    opencode: extensions/audit.opencode.ts       # an OpenCode plugin module
    pi: extensions/audit.pi.ts                   # a pi extension file in this repository
  web-access:
    pi: npm:pi-web-access@0.30.0                 # a pi package, exact version
  mcp-adapter:
    pi:
      source: npm:pi-mcp-adapter@2.36.0
      extensions: ["extensions/*.ts"]            # load only these files of the package
      skills: []                                 # load none of its skills
```

| Key | Value |
| --- | --- |
| `opencode` | A repository module (`.ts`, `.js`, `.mts`, `.mjs`, `.cts`, `.cjs`). It loads as an OpenCode plugin. |
| `pi` | `npm:<name>@<x.y.z>` (an exact version), a repository path to a file or folder, or `{ source, extensions, skills, prompts, themes }`. |

- Set at least one of `opencode` and `pi`. Any other key is an error.
- In the `{ source, … }` form, each filter is a list of glob patterns. An omitted filter loads everything. `[]` loads nothing.
- A version range, a missing version and a git source are errors.
- An extension with no implementation for the session's harness does nothing on that harness. `web-access` above loads only on pi.
- The change request merge builds npm pi packages. A session never runs `npm install`.

## Agents

`agents` maps an agent name to one block. An agent name matches `[a-z0-9][a-z0-9_-]{0,127}`. Each block holds the agent's behavior and the registered things it enables. Both harnesses run the same compiled agent: the "Compiles to" column holds on OpenCode and pi unless it names one.

Behavior and governance come from different branches. A session compiles each agent's behavior (prompt, model, `permission`, the registered things it enables) from its own branch. Which agents may run, and their `connectors`, `secrets`, `apps` and `kortix_permissions` grants, always come from the default branch, so a session cannot widen its own access by editing its branch. An agent you add on a branch runs after its change request merges.

### Behavior

| Key | Default | Compiles to |
| --- | --- | --- |
| `description` | none | The agent's description. Agent lists show it, and a parent agent reads it to pick a subagent. |
| `mode` | `all` | `primary`: a session runs it. `subagent`: another agent starts it. `all`: both. |
| `prompt` | none | The system prompt, as text. |
| `prompt_file` | none | The system prompt, read from a repository `.md` file. Set `prompt` or `prompt_file`, not both. |
| `model` | the [model chain](/docs/project/models#how-the-default-is-chosen) | The model id, for example `kortix/glm-5.3-flash`. |
| `variant` | the model's default | The model's thinking-effort variant. See [Thinking effort](/docs/project/models#thinking-effort). |
| `temperature`, `top_p` | the model's default | Sampling settings. |
| `steps` | the harness default | The most model steps one turn may take. A positive integer. |
| `options` | none | Provider options for the model request. pi ignores it. |
| `color` | none | `#RRGGBB`, or `primary`, `secondary`, `accent`, `success`, `warning`, `error`, `info`. OpenCode's terminal client shows it. pi ignores it. |
| `hidden` | `false` | `true` hides the agent from agent menus. A trigger or a parent agent still starts it. |
| `enabled` | `true` | `false` compiles to `disable: true`. No session can start the agent, and it cannot be `default_agent`. |
| `permission` | `allow` | The tool policy. See [Permissions](#permissions). |

Both harnesses also add the repository's root `AGENTS.md` to every agent's instructions. When the root has no `AGENTS.md`, they read `CLAUDE.md`.

### What the agent enables

| Key | Default | Values | Compiles to |
| --- | --- | --- | --- |
| `tools` | `all` | `all`, `none`, a list, or `{ exclude: [names] }` | The tools the model sees. A list shows only those tools. `exclude` shows every tool but those. Names are harness, Kortix or registered tools. |
| `skills` | none | grant set of registered and Kortix skills | `permission.skill`: each granted skill `allow`, then `"*": deny`. |
| `subagents` | none | grant set of declared agents | `permission.task`: each granted agent `allow`, then `"*": deny`. A name must be another declared agent with `mode` `subagent` or `all`. |
| `commands` | none | grant set of registered commands | The command lists this agent among the agents that may run it. |
| `extensions` | none | grant set of registered extensions | OpenCode: the plugins a session of this agent loads. pi: the packages it loads. |
| `codemode` | `on` | `on`, `only`, `off` | pi only: `on` adds the `codemode` tool, `only` makes it the only tool, `off` removes it. OpenCode ignores it. |

A grant set is one of:

- `all`, or `"*"`, or a list that contains `"*"`: every registered entry of that kind, plus the built-ins.
- `none`, `""` or `[]`: nothing.
- A list of names: only those.

An omitted grant means none, except `tools` (every tool) and `codemode` (`on`). An agent with no `skills` key loads no skill, not even a Kortix skill. Grant the Kortix skills an agent needs by name, or use `skills: all`.

### Kortix access

| Key | Default | Effect |
| --- | --- | --- |
| `connectors` | none | Grant set of connector slugs the agent may call. The built-in `kortix_slack`, `kortix_teams`, `kortix_email` and `computer` need no `connectors` entry. |
| `connectors_required` | none | Connector slugs the agent needs a connected account for. A subset of `connectors`. Parsed, not read at session start. |
| `secrets` | none | Grant set of secret names the agent receives in its sandbox. See [Secrets](/docs/project/secrets#which-agents-receive-it). |
| `apps` | none | Grant set of App slugs the agent may open when the App access is `restricted` or `private`. The agent also needs `project.app.read`. |
| `kortix_permissions` | none | Grant set of project permissions for the Kortix CLI, API and git. See [What an agent may do](/docs/project/agents#what-an-agent-may-do). |
| `workspace.project_repository` | `true` | `false`: new sessions of this agent get no checkout in `/workspace` and no repository access (`403`). Its project tools still load. See [Tools](/docs/project/tools#agents-without-the-project-repository). |
| `sandbox` | `sandbox.default` | A sandbox template slug, or `default` for the platform image. |
| `network_egress` | none | Declaration only. Accepts `{ version: 1, default: deny, rules: [] }` and warns that egress is not enforced. |

`workspace` has no other key. A running session keeps the `workspace` value it started with.

These agent keys from earlier versions are errors in v3, with a pointer to their replacement:

| Key | Replacement |
| --- | --- |
| `file` | `prompt` or `prompt_file`, and the behavior keys on the block |
| `disable` | `enabled: false` |
| `opencode`, `harnesses` | the behavior keys on the block; `extensions`; `codemode` |
| `env` | `secrets` |
| `kortix_cli` | `kortix_permissions` |
| `connectors_personal` | `connectors_required` |
| `repository_access` | `workspace.project_repository` |
| `tools: { bash: false }` | `tools: { exclude: [bash] }` |

### Only declared agents run

A v3 project runs only the agents in `agents`. OpenCode's own `build`, `plan`, `general` and `explore` agents are off unless the manifest declares that name, and pi offers no built-in `general` or `explore` subagent. To give an agent a subagent, declare the subagent and list it under `subagents`.

## Permissions

Three separate layers decide what an agent may do. Each one has its own key, and none replaces another.

| Layer | Key | Where | Decides |
| --- | --- | --- | --- |
| Tool policy | `permission` | each agent | Whether a harness tool call runs, waits for a person, or is refused. |
| Kortix permissions | `kortix_permissions` | each agent | Which Kortix project actions the agent's own token may take: start sessions, push, merge, read secrets. Capped by the agent's ceiling role. |
| Connector approvals | `policy`, `policies`, and a connector's own `policies` | the connector registry | Whether a connector call runs, needs approval, or is blocked. |

### Tool policy: permission

`permission` is an action for every tool, or a map of tool to action. An action is `allow`, `ask` or `deny`. File and shell tools also take a map of pattern to action:

```yaml
permission:
  edit: allow
  bash:
    "*": ask
    "git status": allow
    "git diff *": allow
    "rm -rf *": deny
  webfetch: ask
```

- **Omitted is `allow`.** A tool never waits for a person unless the agent says `ask`. Each session runs in its own sandbox on its own branch.
- **Per agent only.** There is no project-wide `permission`. A subagent has its own.
- **`skill` and `task` are errors.** Use `skills` and `subagents`. The compiler writes `permission.skill` and `permission.task` from them.
- **Denials cascade.** `bash: deny` also denies the terminal tools (`pty_*`), and `edit: deny` also denies `memory`, unless the agent sets a rule for those tools.

The pattern syntax and the list of keys are on [Ask, allow or deny](/docs/project/agents#ask-allow-or-deny).

### Kortix permissions: kortix_permissions

`kortix_permissions` lists the project actions the agent may take through the Kortix CLI, API and git. It is deny-by-default. The agent's effective permissions are its `kortix_permissions`, cut to its ceiling role, minus the human-only `project.credentials.issue`. `kortix validate --scopes` prints every grantable entry. The full model is on [What an agent may do](/docs/project/agents#what-an-agent-may-do).

### Connector approvals: policy and policies

`policy.default_mode` decides a connector call that no rule matches:

- `allow_all` (default): the call runs.
- `risk`: a read runs; a write or destructive call needs approval.

`policies` holds rules over connector calls. A rule matches a tool path, `<connector-slug>.<tool>`, with `*` globs. Kortix checks these rules first, then the connector's own `policies`. The first matching rule wins. `conditions` limits a rule to calls whose arguments match:

```yaml
policy:
  default_mode: risk
policies:
  - match: gmail.send_email
    action: require_approval
    conditions:
      - arg: to
        match: "*@example.com"     # a glob, or /regex/ in slashes
  - match: gmail.send_email
    action: block
```

All conditions of a rule must hold. `negate: true` inverts one condition. These rules belong to the connectors, so they hold for every agent that the connector grant reaches. How approvals reach a person is on [Policies and approvals](/docs/connect/connectors#policies-and-approvals).

`kortix validate` does not check `policy` or `policies`. When Kortix syncs connectors, it skips a malformed rule and reports it as a connector sync error.

## The harness

A session runs one of two harnesses, OpenCode or pi. Both run the same compiled agents. Kortix picks the harness when a session starts:

1. The project's `llm_gateway` feature flag is off: OpenCode.
2. The project's `pi_harness` feature flag is on: pi.
3. `runtime: pi`: pi.
4. Anything else: OpenCode.

A v3 session reads only the compiled manifest. It does not read `harnesses/`, `.kortix/`, `.opencode/`, `.pi/`, `opencode.json`, `opencode.jsonc` or a pi `settings.json` from the repository.

- **Extensions load per session agent.** The agent a session starts with picks the plugins (OpenCode) or packages (pi). A switch to another agent in a running session keeps them, because both harnesses load extensions once.
- **Commands are listed with their agents.** The command list returns each command with the agents that may run it, and a client shows the commands of the selected agent. Running a command on an agent that does not enable it answers `403` with `{ "error": "command_not_enabled", "command": "<name>", "agent": "<name>" }`.
- **pi gaps.** pi does not serve rewind, fork, harness MCP servers, the todo list, shell turns, part edits or `session.attach`. See [What each harness supports](/docs/project/agents#what-each-harness-supports).

## Imports

1. A path is relative to the repository root. `..`, absolute paths and globs are errors. A path that matches no `.yaml` or `.yml` file is an error.
2. A directory import takes every `.yaml` and `.yml` file below it, at any depth, sorted by path.
3. An imported file declares only `agents`, `skills`, `tools`, `commands`, `extensions`, `connectors`, `apps`, `triggers` and `imports`. Any other key in an imported file is an error.
4. `kortix_version`, `project`, `default_agent`, `runtime`, `env`, `sandbox`, `policy` and `policies` stay in the root file.
5. One name, one file. An agent, skill, tool, command, extension or App name, or a trigger or connector slug, declared in two files is an error that names both files.
6. Imports nest up to 8 levels and 200 files. A cycle is an error. A file reached twice merges once.
7. Entries merge in order: the importing file first, then its imports as listed.

A broken import fails the whole manifest:

```text
imports: triggers "weekly-report" is declared in both triggers/a.yaml and support/support.yaml — one name, one file
```

An edit from the dashboard, the API or the CLI rewrites only the file that declares the entry. A new entry goes to the root file.

## env

`env` declares the secret names the project expects. Values live in [Secrets](/docs/project/secrets), never in the manifest.

```yaml
env:
  required: [DATABASE_URL]
  optional: [STRIPE_API_KEY]
```

| Field | Effect |
| --- | --- |
| `required` | The dashboard and `kortix ship` prompt for a missing value. A missing value never blocks a session. |
| `optional` | Offered by the same prompts. |

A name matches `^[A-Z_][A-Z0-9_]*$`. Any other key under `env` warns. The Secrets store refuses a name longer than 64 characters or one that starts with `KORTIX_`.

## sandbox

`sandbox.templates` lists named sandbox images. With no template, every session boots the platform image. What Kortix adds on top of an image is on [Sandboxes & previews](/docs/work/runtime#the-image-and-templates).

| Field | Default | Rule |
| --- | --- | --- |
| `slug` | required | Unique. `default` is reserved. A slug over 64 characters warns: the runtime drops it. |
| `name` | slug | Label in the template picker. |
| `dockerfile` | none | Repository-relative path. Set exactly one of `dockerfile` and `image`. |
| `image` | none | Public image with a tag or a digest. No tag is an error. `:latest` warns. |
| `entrypoint` | the image's | Overrides the container entrypoint. |
| `cpu` | provider default | vCPU cores, 1–32. |
| `memory` | provider default | GiB, 1–128. |
| `disk` | provider default | GiB, 1–500. |
| `container_runtime` | `false` | `true` runs Docker in the sandbox. See [Hardware and Docker](/docs/work/runtime#hardware-and-docker). |

A value below the minimum is an error. A value above the maximum warns and is clamped. `gpu` warns and does nothing. Image keys set directly on `sandbox` (`image`, `dockerfile`, `cpu`, …) are errors: put them in a template.

`sandbox.default` names a template, or `default` for the platform image. A session picks its template in this order: the `sandbox_slug` of the session request, the agent's `sandbox`, `sandbox.default`, then the platform image. A template change applies to the next session.

## triggers, connectors, apps

A trigger or connector entry is identified by its `slug`, and an App by its key under `apps`. Each one matches `[a-z0-9][a-z0-9_-]{0,127}` and is unique in its collection. A trigger's `agent` names a declared agent, and defaults to `default_agent`.

| Collection | Full reference |
| --- | --- |
| `triggers` | [Triggers & reminders](/docs/connect/triggers) |
| `connectors` | [Connectors](/docs/connect/connectors). Credentials live in the platform, never in the manifest. |
| `apps` | [Configure in kortix.yaml](/docs/apps#configure-in-kortixyaml) |

## Validate

Add the schema line at the top of `kortix.yaml`. A YAML editor then validates and completes every key:

```yaml
# yaml-language-server: $schema=https://kortix.com/schema/kortix.v3.schema.json
```

| Schema | URL |
| --- | --- |
| v3 | `https://kortix.com/schema/kortix.v3.schema.json` |
| All versions (selects by `kortix_version`) | `https://kortix.com/schema/kortix.schema.json` |
| v2 (legacy) | `https://kortix.com/schema/kortix.v2.schema.json` |
| v1 (legacy) | `https://kortix.com/schema/kortix.v1.schema.json` |

`kortix schema --version 3` prints the v3 schema, and `--url` prints its URL instead of the body.

Validate before you push:

```bash
kortix validate                       # ./kortix.yaml and every file it imports
kortix validate --file config/kortix.yaml --json
kortix validate --scopes              # every grantable kortix_permissions entry
```

| Flag | Effect |
| --- | --- |
| `--file <path>` | Validate this file instead of the project manifest in the current directory. |
| `--json` | Print a JSON report: `valid`, `path`, `issues`. |
| `--scopes` | Print the grantable `kortix_permissions` entries and their aliases, then exit. |
| `--no-dockerfile-lint` | Skip the checks on sandbox template Dockerfiles. |

`kortix validate` exits `0` with no errors, `1` with one or more errors, and `2` when the file is missing or unreadable. The same check runs in `kortix ship` and in the change request merge check. An error blocks the push or the merge. A warning never does.

The v3 check reports as errors:

- an unknown key, at the top level, in an agent, in a command or in an extension;
- an agent grant that names an unregistered skill, tool, command or extension, or a subagent that is not declared;
- a `default_agent` that is not declared, is disabled, or has `mode: subagent`;
- a trigger `agent` that is not declared;
- a registry name or path that breaks the rules above.

A session compiles the manifest when it starts. A `prompt_file` that does not exist fails that compile.

The project's `manifest_path` (default `kortix.yaml`) sets where Kortix looks. Change it with `kortix projects set --manifest <path>` or in **Customize → Settings**.

## Versions 1 and 2

`kortix_version` 1 (`kortix.toml`) and 2 (`agents/<name>.md` files plus harness folders) read and run. New projects are created on version 2. Their keys and layout are on [Manifest versions 1 and 2](/docs/project/legacy-manifests).

To move a v2 project to v3, run the CLI from the project root:

```bash
kortix migrate            # print the v3 manifest, change nothing
kortix migrate --write    # write it
kortix validate
```

Commit the result and merge it with a change request. A version above `3` is an error, and a `kortix.toml` that declares version `2` or `3` is an error.
