title: Tools
description: The six Kortix tools, project tools you write in TypeScript or JavaScript, and which agent may call which.
---

A tool is a function the model calls during a turn. This page is for project authors who choose the tools a project loads, write their own, and limit them per agent. Tool selection and per-agent access live in [`kortix.yaml`](/docs/project/manifest).

## Three kinds of tools

| Kind | Names | Comes from |
| --- | --- | --- |
| Harness tools | `bash`, `read`, `write`, `edit`, `glob`, `grep`, `task`, `question`, `codemode` | pi, the harness of every new session. A session that still runs OpenCode (deprecated) also has `apply_patch`, `list`, `todowrite`, `webfetch`, `websearch`, `skill` and `lsp`. |
| Kortix tools | `web_search`, `image_search`, `image_gen`, `scrape_webpage`, `memory`, `show` | Kortix maintains them. You select them under `tools:`. |
| Project tools | Any name you declare | One module in your repo, declared under `tools:`. |

Kortix tools and project tools are one module each. The sandbox runs the same module on both [harnesses](/docs/project/agents#harnesses-opencode-and-pi), with the same name, arguments, and output.

| Kortix tool | What it does |
| --- | --- |
| `web_search` | Searches the web. Returns titles, URLs, snippets, and a short answer. |
| `image_search` | Searches for images. Returns image URLs, titles, source pages, and dimensions. |
| `image_gen` | Generates or edits 1 to 4 images with an image model the project can use, and saves them in the workspace. See [Generate images](#generate-images). |
| `scrape_webpage` | Fetches one or more pages and returns them as Markdown. |
| `memory` | Views, creates, edits, renames, and deletes files under `memory/`, the project memory. |
| `show` | Presents a file, image, URL, document, or text to the person in the session. Each shown item whose path is an image file (png, jpg, jpeg, webp, gif, avif, svg) of at most 32 MiB carries `sha256`, the lowercase hex SHA-256 of its bytes, when the file is read within 2 s. |

## Choose Kortix tools

A new project lists all six under the top-level `tools:` key:

```yaml
tools:
  web_search: kortix:web_search      # maintained by Kortix, updated automatically
  image_search: kortix:image_search
  image_gen: kortix:image_gen      # generates images with an image model the project can use
  scrape_webpage: kortix:scrape_webpage
  memory: kortix:memory
  show: kortix:show
  # lookup_order: tools/lookup_order.ts   # your own tool: a module in your repo
```

`<name>: kortix:<name>` keeps the tool Kortix maintains. A fix to it reaches the project with no change in the repo.

| `kortix.yaml` | Kortix tools a session gets |
| --- | --- |
| No `tools:` key, in the root file or in any [imported](/docs/project/manifest#imports) file | All six. |
| A `tools:` key in any file, even an empty one | The Kortix tools it lists, plus `image_gen`. |

Project tools load in both cases.

- **Remove a Kortix tool:** delete its line. Every agent of the project loses it. `image_gen` is the exception: it loads when its line is missing. See [Turn it off](#turn-it-off). To hide a tool from one agent only, use [`agents.<name>.tools`](#give-each-agent-its-tools).
- **A skill that names a removed tool still loads.** The model finds no such tool and uses other tools.
- **See what a session gets:** run `kortix tools ls` from the project root.

```text
$ kortix tools ls
NAME            KIND                 SOURCE
web_search      kortix (overridden)  tools/web_search.ts
image_gen       kortix               kortix:image_gen
scrape_webpage  kortix               kortix:scrape_webpage
memory          kortix               kortix:memory
show            kortix               kortix:show
lookup_order    project              tools/lookup_order.ts

Removed Kortix tools: image_search
Add `<name>: kortix:<name>` under `tools:` to get one back.
```

`KIND` is `kortix`, `kortix (overridden)` (a Kortix tool name with your module), or `project`. `kortix tools ls --json` prints `{ manifest, tools_key, tools: [{ name, kind, source }], removed }`.

Rules for every entry under `tools:`:

- A name matches `^[a-z][a-z0-9_]{0,63}$`: snake case, 64 characters at most.
- A harness tool name (the table above, plus the OpenCode internals `invalid`, `execute`, and `plan_exit`) or a name that starts with `pty_` is an error.
- A value is `kortix:<name>` with the same name as the key, or a repo-relative module path.
- A path ends in `.ts`, `.js`, `.mts`, `.mjs`, `.cts`, or `.cjs`. It does not start with `/` or `-` and has no `.` or `..` segment. The folder is your choice.
- An imported file may declare tools. A name declared in two files is an error.

## Generate images

`image_gen` generates one to four images from prompts, or edits images that are in the workspace. It uses an image model the project can reach: `gpt-image-2` on a connected ChatGPT plan, or an image model of an OpenAI, Google, xAI, or OpenRouter key. You can also name a model of your [custom endpoint](/docs/project/models#which-model-makes-the-image). Kortix-managed models do not generate images yet. It saves each image under `/workspace/output/images/`.

- **One call, one to four images.** Each prompt is one image. The tool sends one request per prompt, all at the same time.
- **It needs an image model.** Connect ChatGPT in **Models** (**Connect ChatGPT**) or with `kortix providers login openai`, or add an OpenAI, Google, xAI, or OpenRouter key. See [Models](/docs/project/models#generate-images). With none, the call fails with `image_model_unavailable`.
- **It loads by default.** A project gets `image_gen` when its `tools:` list does not name it. A project with no `tools:` key gets it too.
- **The output is paths, not images.** The model receives `{ action, model, provider, images: [{ path, size, prompt, sha256 }], failed: [{ prompt, error }] }`. `model` and `provider` name what made the first saved image. `size` is `WxH`, read from the saved file when its header is readable, else the size the provider reported. `sha256` is the lowercase hex SHA-256 of the saved file's bytes. `failed` is present only when a prompt failed. When every prompt fails, the call fails with the first error.

| Argument | Value |
| --- | --- |
| `action` | `generate` new images, or `edit` the reference images. Required. |
| `prompts` | 1 to 4 non-empty strings, one per image: what the image shows, or what to change. Required. |
| `model` | An image model id, for example `codex/gpt-image-2`, `openai/gpt-image-1`, `google/gemini-2.5-flash-image`, or `openrouter/google/gemini-2.5-flash-image`. Omit it to use `auto`. See [Which model makes the image](/docs/project/models#which-model-makes-the-image). |
| `aspect_ratio` | `auto` (the default), `1:1`, `3:2`, `2:3`, `16:9`, `9:16`, `4:3`, or `3:4`. |
| `quality` | `auto` (the default), `low`, `medium`, or `high`. |
| `transparent_background` | `true` for a transparent background. The default is `false`. |
| `reference_images` | For `edit` only, and required there: 1 to 5 workspace paths of png, jpg, jpeg, or webp files. Every prompt uses them. |

- `quality` and `transparent_background` reach ChatGPT and OpenAI models only. Other models do not receive them.
- ChatGPT and OpenAI models receive a size, not a ratio. `auto` is `auto`. `1:1` is `1024x1024`. `3:2`, `4:3`, and `16:9` are `1536x1024`. `2:3`, `3:4`, and `9:16` are `1024x1536`. xAI models receive no aspect ratio. Other models receive the ratio as it is, and no ratio for `auto`.
- The file name is a slug of the prompt plus a timestamp. The extension comes from the image bytes: `.png`, `.jpg`, or `.webp`. Any other answer, for example an SVG, is not written.

### In the chat

A call shows one card with one frame per prompt.

- While the call runs, the card shows a placeholder per image in the requested aspect ratio, with "Generating image" (or "Generating 3 images"; "Editing image" for an edit) and the elapsed time. The images replace the placeholders when the call ends.
- One image fills the width of the message. Two to four images fill one rectangle: 2 side by side, 3 as one large image and two small ones, 4 as a 2 × 2 grid. On web, the card is at most 60% of the window height.
- The card shows no prompt and no model name. Click an image to open it full screen, uncropped. The full-screen view shows its prompt and the model that made it.
- A frame whose prompt failed shows the error. When the cause is a missing or expired connection, the card shows one connect action. A shared or read-only view shows no action.

### Limits

The tool enforces these limits in code. A prompt, a file, or a web page that the agent reads cannot raise them.

| Limit | Value |
| --- | --- |
| Images per call | 4. |
| Images per turn | 10. A call that would pass 10 is refused whole, before any request: `Image limit for this turn reached (10 images; 8 used, 3 asked).` |
| Images per session | 50, counted within one sandbox run. A sandbox restart resets the count. |
| Reference images per edit | 5. |
| Size of one reference image | 20 MiB. |
| Size of all reference images in one edit | 50 MiB. |
| Time per call | 300 seconds. |

- Every call of one turn counts toward the same 10: direct calls, parallel calls, calls from a `codemode` script, retried calls, and calls from a subagent the turn started.
- A reference image must be inside `/workspace`, after symlinks are resolved. Its content must match its extension. Any other file is refused before a request leaves the sandbox.
- An image is always written under `/workspace/output/images/`. An existing file is never replaced: the tool adds `-2`, `-3`, and so on to the name.
- When the turn stops, the requests stop and no further file is written.

### Errors

When the gateway refuses a prompt, its error is `Image generation failed (<status>): <message> <suggestion> [<code>]`. A rate limit adds `Retry after <n> s.` before the code. When the gateway names the provider that failed, `[provider:<id>]` comes right before the code, for example `[provider:openai] [provider_reauth_required]`. `openai-codex` is ChatGPT. The tool reports three failures itself: `Image generation returned no image.`, an image that is not png, jpeg, or webp, and its own 300-second timeout. The tool's timeout starts before the gateway's, so a slow request usually ends with the tool's timeout, not `image_timeout`.

| Code | Cause |
| --- | --- |
| `image_model_unavailable` | The project reaches no image model. |
| `not_an_image_model` | `model` names a model that cannot generate images. The suggestion names up to 5 image models the project can use. |
| `image_model_unsupported` | Kortix cannot call this model's provider for images, for example Anthropic or Bedrock. |
| `provider_not_connected` | `model` names a provider the project has no key or ChatGPT account for. |
| `provider_reauth_required` | The ChatGPT login expired, or the provider refused the key. Reconnect ChatGPT or check the key. |
| `image_rate_limited` | The provider's image limit is reached. The error gives the seconds until it resets. |
| `image_upstream_error` | The provider failed or answered without an image, for example after a safety refusal. |
| `image_upstream_unreachable` | The provider could not be reached. |
| `image_response_too_large` | The provider answered with more than 48 MiB. |
| `image_timeout` | The gateway stopped the request after 300 seconds. |

### Turn it off

Turn `image_gen` off for one agent with its `tools` map, or deny it with a permission rule:

```yaml
agents:
  kortix:
    tools:
      image_gen: false        # the model does not see the tool
  researcher:
    permission:
      image_gen: deny         # the model sees it, every call is denied
```

- Set `image_gen: ask` to approve each call.
- `image_gen` writes a file, so `edit: deny` also denies it, unless the agent sets a rule for `image_gen`.
- Deleting the `image_gen` line under `tools:` does not remove it.

### Replace it

Map `image_gen` to your own module. The module replaces the Kortix tool on every harness:

```yaml
tools:
  image_gen: tools/image_gen.ts
```

`kortix tools eject image_gen` writes the Kortix source to `tools/image_gen.ts` and sets this line. Keep the output shape `{ action, model, provider, images: [{ path, size, prompt, sha256 }], failed }`, or the chat shows the raw output in place of the image card. `sha256` is optional: outputs from before it was added have none.

## Write a project tool

Project tools need `kortix.yaml` with `kortix_version: 2` or `3`.

<Steps>
<Step title="Store the secret the tool reads">

```bash
kortix secrets set WEATHER_API_KEY=-
```

The command reads the value from stdin. Grant the secret to each agent that calls the tool, in `kortix.yaml`: `agents.<name>.secrets: all`, or a list such as `[WEATHER_API_KEY]`. See [Secrets](/docs/project/secrets).

Declare the name under `env:` in `kortix.yaml` too. In a `kortix_version: 2` manifest, `kortix validate` and `kortix ship` report an undeclared grant as an error:

```yaml
env:
  optional: [WEATHER_API_KEY]
```

</Step>
<Step title="Write the module">

```ts
// tools/weather_now.ts
export default {
  description: 'Current weather for a city: temperature in °C and conditions.',
  parameters: {
    type: 'object',
    properties: { city: { type: 'string', description: 'City name, e.g. "Berlin"' } },
    required: ['city'],
  },
  async execute(args, context) {
    const key = context.env.WEATHER_API_KEY
    if (!key) throw new Error('WEATHER_API_KEY is not set. Run `kortix secrets set WEATHER_API_KEY=-` and grant it to this agent.')
    const url = `https://api.weather.example.com/v1/current?city=${encodeURIComponent(args.city)}`
    const response = await fetch(url, { headers: { authorization: `Bearer ${key}` }, signal: context.signal })
    if (!response.ok) throw new Error(`weather API answered ${response.status}: ${await response.text()}`)
    const data = await response.json()
    return { city: args.city, temperature_c: data.temp_c, conditions: data.conditions }
  },
}
```

</Step>
<Step title="Declare it in kortix.yaml">

```yaml
env:
  optional: [WEATHER_API_KEY]
tools:
  # … the Kortix tools you keep
  weather_now: tools/weather_now.ts
agents:
  my-agent:
    secrets: [WEATHER_API_KEY]
```

Then [test it](#test-a-tool).

</Step>
</Steps>

The default export is a plain object. It imports nothing from a harness.

| Field | Rule |
| --- | --- |
| `description` | A non-empty string. The model reads it to decide when to call the tool. |
| `parameters` | JSON Schema of the arguments, with `type: 'object'`. The model receives it as written, so list required arguments in `required`. pi checks the arguments against it before `execute` runs. Check required values in `execute` too. |
| `execute(args, context)` | May be `async`. Returns a string, or any JSON value, which the model receives as indented JSON. A thrown error is the tool result, and the model reads its message. |

`context` carries:

| Field | Value |
| --- | --- |
| `sessionId` | The Kortix session the call belongs to. |
| `agent` | The agent that made the call. |
| `directory` | The project checkout the session works in, `/workspace`. Resolve relative paths against it. |
| `env` | The sandbox environment plus the secrets this agent receives, with their current values. Read a secret as `context.env.NAME`. A secret changed after the sandbox started is in `context.env`, not in `process.env`. |
| `signal` | An `AbortSignal` that aborts when the turn stops. Pass it to `fetch`. |
| `turnId` | Optional. The turn the call belongs to, when the harness names it. pi sets it, and it is the same for every call of one turn, also for calls from a `codemode` script or a subagent. `signal` can differ per call. Key a per-turn limit on `turnId`. An OpenCode session does not set it. |

- **Output size.** An output over 49 KiB or 1,990 lines is saved whole to a file in the sandbox temp directory. The model receives the head, the size, and the file path. Return what the model needs, not a raw dump.
- **Errors.** Throw a message that says what to change. The model reads it and can act on it.
- **Imports.** A module may import `node:*` modules, Bun APIs, and relative files. TypeScript runs without a build step. A package resolves only from a `node_modules` next to the module or above it. The sandbox installs no package for a tool, so use `fetch` for HTTP APIs.
- **Load failures.** A module that does not load is skipped, and the other tools still load. Causes: a missing file, no default export, `parameters` that is not an object schema, an error at import, or a package that does not resolve. The sandbox logs `[tools] project tools that did not load` with the reason for each tool.

<Callout type="info">
To write `parameters` with zod, print the schema once and paste the JSON into the module. An `import { z } from 'zod'` fails with `Cannot find package 'zod'` where no `node_modules` holds zod.

```bash
bun -e "import { z } from 'zod'; console.log(JSON.stringify(z.toJSONSchema(z.object({ city: z.string() })), null, 2))"
```
</Callout>

## Give each agent its tools

`agents.<name>.tools` decides which tools an agent's model sees. It names harness, Kortix, and project tools alike.

```yaml
agents:
  kortix:
    tools: all                                    # every tool (the default)
  researcher:
    tools: [read, grep, web_search, weather_now]  # only these
  support:
    tools:
      exclude: [bash, write, edit]                # every tool but these
  greeter:
    tools: none                                   # no tool
```

| Value | The agent gets |
| --- | --- |
| Omitted, or `all` | Every tool. |
| `none` | No tool. |
| A list | Only the tools listed. A list that contains `*` is `all`. |
| `{ exclude: [...] }` | Every tool except the ones listed. |
| `{ bash: false, … }` | The map form: `false` removes a tool. |

- **Visibility, not permission.** A hidden tool is also denied if the model calls it. For a visible tool, the agent's `permission` rules decide allow, ask, or deny. See [Agents & permissions](/docs/project/agents#ask-allow-or-deny).
- **Kortix tools.** An agent list cannot add a Kortix tool the project does not load. List it under the top-level `tools:` first.
- **Connector tools** follow `agents.<name>.connectors`, not this list. See [Connectors](/docs/connect/connectors).
- **Subagents.** On pi, a subagent gets only the tools that both its own list and the parent agent's list allow. On OpenCode, a subagent gets the tools of its own list. To stop an agent from delegating, leave `task` out of its list.
- **OpenCode groups.** On OpenCode, `bash` also covers the `pty_*` terminal tools. `write`, `edit`, and `apply_patch` share one permission: listing one shows all three, and excluding one hides all three. pi has separate `write` and `edit` tools.
- **Typos.** `kortix validate` warns about a name that is not a harness, Kortix, or project tool, and about a Kortix tool the project does not load. A typo in an `exclude` list leaves the real tool on.

### Agents without the project repository

An agent with [`workspace: { project_repository: false }`](/docs/project/manifest#agent-workspace) has no checkout in `/workspace`. Its project tools still load. The sandbox receives only these files from the default branch:

- the module of each project tool the agent may call (`agents.<name>.tools`);
- every file those modules import by a relative path (`./lib/client`, `../data/regions.json`), followed transitively.

No other file of the repository reaches the sandbox. A tool the agent may not call ships no file. Lock an agent down with both settings:

```yaml
tools:
  lookup_order: tools/lookup_order.ts
agents:
  support:
    workspace:
      project_repository: false
    tools: [lookup_order, web_search]   # no bash, read, or write
```

- A package import (`import { z } from 'zod'`) does not resolve: no `node_modules` ships. Use `fetch` and `node:*` modules.
- `context.directory` is `/workspace`, which is empty for this agent.
- A change to a shipped file reaches running sessions as their config converges, like any tool change.

## Eject or override a Kortix tool

`kortix tools eject <name>` gives the project its own copy of a Kortix tool:

```text
$ kortix tools eject web_search
  ✓  Ejected web_search
  wrote   tools/web_search.ts (the Kortix source, now the project's to change)
  set     kortix.yaml: tools.web_search: tools/web_search.ts

Next:
  1. Edit tools/web_search.ts. Keep the default export: { description, parameters, execute(args, context) }.
  2. kortix validate
  3. git add tools/web_search.ts kortix.yaml && git commit -m "Own the web_search tool"
  4. Open a change request: git push origin HEAD && kortix cr open --title "Own the web_search tool"
Sessions load the copy after the change request merges.
```

In a local checkout, give `kortix cr open` the branch you pushed: `--head <branch>`. Inside a sandbox the CLI fills it in.

- It writes the source the sandbox runs to `tools/<name>.ts`. The copy imports only `node:*` modules, so it runs as it is. `web_search`, `image_search`, and `scrape_webpage` call the Kortix API with `KORTIX_API_URL` and `KORTIX_TOKEN` from `context.env`. `image_gen` calls the Kortix LLM gateway with `KORTIX_LLM_BASE_URL` and `KORTIX_TOKEN`. `memory` and `show` work on files in the project checkout.
- It sets `<name>: tools/<name>.ts` in the file that declares the entry, the root file or an imported file. The line ends with `# ejected from kortix:<name>`. Other lines and comments stay.
- With no `tools:` key, it creates one and also lists the other five Kortix tools as `kortix:<name>`, so the eject removes nothing.
- It refuses when `tools/<name>.ts` exists or when the tool already points at another module. `--force` overwrites.
- It refuses a name that is not a Kortix tool, and a project without `kortix.yaml` at `kortix_version` 2 or 3.

Kortix does not update an ejected copy. To override without a copy, point the Kortix tool name at any module of yours:

```yaml
tools:
  web_search: integrations/search/web_search.ts
```

The module replaces the Kortix tool on every harness. Keep the name, the arguments, and the output shape, so skills that name the tool and the web app's view of it still work.

To return to the maintained tool, set the line back to `<name>: kortix:<name>` and delete the module.

## Test a tool

A tool change reaches sessions when it reaches the default branch, usually through a [change request](/docs/git#change-requests). New sessions then load the change, and running sessions pick it up as their config converges. On pi, a change to a project tool or to the Kortix tool list restarts the runtime in place while no turn runs. The session keeps its messages. See [How a change takes effect](/docs/project#how-a-change-takes-effect).

<Steps>
<Step title="Validate">

`kortix validate` checks names, paths, missing module files, and `kortix:` values. It warns when a `tools:` key lists no Kortix tool.

</Step>
<Step title="Check the list">

`kortix tools ls` shows each tool a session gets and the Kortix tools the project removed.

</Step>
<Step title="Merge">

Push a branch and open a change request on it: `git push origin HEAD:add-weather-now`, then `kortix cr open --head add-weather-now --title "Add weather_now"`. Merge it with `kortix cr merge <cr>` or on the [Review page](/docs/git#the-review-page).

</Step>
<Step title="Call it once">

```bash
kortix sessions new --wait --prompt "Call the weather_now tool once with city Berlin and print its output."
```

</Step>
<Step title="Read the result">

`kortix sessions log <session_id>` prints the session's messages, with each tool call, its status, and its output. A tool that did not load is not offered to the model. A tool that throws answers with its error message.

</Step>
</Steps>

## Tools in `harnesses/opencode/tools`

OpenCode also loads tool files from the `tools/` folder of its config directory (`opencode.config_dir`, `harnesses/opencode` in a new project). pi does not read that folder.

- On OpenCode, a tool in that folder wins over a Kortix tool or project tool of the same name. Delete copies of Kortix tools from it, so the maintained tools run.
- To run an OpenCode tool on both harnesses, port it to a project tool:
  1. Move the file out of the folder, for example to `tools/<name>.ts`.
  2. Replace `tool({ description, args, execute })` with the plain default export object. Write `args` as JSON Schema under `parameters`.
  3. Read secrets from `context.env`.
  4. Declare it under `tools:` in `kortix.yaml`.
