title: Tools
description: The seven Kortix tools, project tools you write in TypeScript or JavaScript and register in kortix.yaml, and which agent may call which.
---

A tool is a function the model calls during a turn. This page is for project authors who choose the tools a project loads, write their own, and limit them per agent. The tool registry and per-agent access live in [`kortix.yaml`](/docs/project/manifest).

## Three kinds of tools

| Kind | Names | Comes from |
| --- | --- | --- |
| Harness tools | `bash`, `read`, `write`, `edit`, `apply_patch`, `glob`, `grep`, `list`, `task`, `question`, `todowrite`, `webfetch`, `websearch`, `skill`, `lsp` | The harness, OpenCode or pi. |
| Kortix tools | `web_search`, `image_search`, `scrape_webpage`, `memory`, `show`, `kortix-connectors_call`, `kortix-connectors_describe` | Kortix maintains them. Every project has them without an entry. |
| Project tools | Any name you register | One module in your repo, registered under `tools:`. |

Kortix tools and project tools are one module each. The sandbox runs the same module on both [harnesses](/docs/project/agents#harnesses-opencode-and-pi), with the same name, arguments, and output.

| Kortix tool | What it does |
| --- | --- |
| `web_search` | Searches the web. Returns titles, URLs, snippets, and a short answer. |
| `image_search` | Searches for images. Returns image URLs, titles, source pages, and dimensions. |
| `scrape_webpage` | Fetches one or more pages and returns them as Markdown. |
| `memory` | Views, creates, edits, renames, and deletes files under `memory/`, the project memory. |
| `show` | Presents a file, image, URL, document, or text to the person in the session. |
| `kortix-connectors_call` | Calls a session connector action (e.g. `gmail.list_messages`) through the gateway, under the agent's policy. |
| `kortix-connectors_describe` | Describes one connector action's arguments from the session's connector catalog. |

## Register project tools

The top-level `tools:` key is the tool registry. It maps a name to a module in your repository:

```yaml
tools:
  lookup_order: tools/lookup_order.ts            # your own tool
  web_search: integrations/search/web_search.ts  # replaces the Kortix web_search
```

- **Kortix tools need no entry.** Every agent can call all seven unless its [`tools`](#give-each-agent-its-tools) grant hides them. Kortix updates them with no change in the repository.
- **A Kortix tool's name replaces that tool.** The module runs instead of the Kortix tool, for every agent. See [Eject or override a Kortix tool](#eject-or-override-a-kortix-tool).
- **To hide a tool from an agent**, use that agent's `tools` grant. There is no project-wide removal.

Rules for every entry under `tools:`:

- A name matches `^[a-z][a-z0-9_]{0,63}$`: snake case, 64 characters at most. A Kortix tool name is also accepted, to replace that tool.
- A harness tool name (the table above, plus the OpenCode internals `invalid`, `execute`, and `plan_exit`) or a name that starts with `pty_` is an error.
- A value is a repository-relative module path that ends in `.ts`, `.js`, `.mts`, `.mjs`, `.cts`, or `.cjs`. It does not start with `/` or `-` and has no `.` or `..` segment. The folder is your choice.
- The value `kortix:<name>` belongs to `kortix_version` 2 and is an error in v3. See [Manifest versions 1 and 2](/docs/project/legacy-manifests#tools-in-v2).
- An imported file may register tools. A name registered in two files is an error.

## Write a project tool

Project tools need `kortix.yaml` with `kortix_version: 2` or `3`.

<Steps>
<Step title="Store the secret the tool reads">

```bash
kortix secrets set WEATHER_API_KEY=-
```

The command reads the value from stdin. Grant the secret to each agent that calls the tool, in `kortix.yaml`: `agents.<name>.secrets: all`, or a list such as `[WEATHER_API_KEY]`. See [Secrets](/docs/project/secrets).

Declare the name under `env:` in `kortix.yaml` too, so the dashboard and `kortix ship` prompt for a missing value:

```yaml
env:
  optional: [WEATHER_API_KEY]
```

</Step>
<Step title="Write the module">

```ts
// tools/weather_now.ts
export default {
  description: 'Current weather for a city: temperature in °C and conditions.',
  parameters: {
    type: 'object',
    properties: { city: { type: 'string', description: 'City name, e.g. "Berlin"' } },
    required: ['city'],
  },
  async execute(args, context) {
    const key = context.env.WEATHER_API_KEY
    if (!key) throw new Error('WEATHER_API_KEY is not set. Run `kortix secrets set WEATHER_API_KEY=-` and grant it to this agent.')
    const url = `https://api.weather.example.com/v1/current?city=${encodeURIComponent(args.city)}`
    const response = await fetch(url, { headers: { authorization: `Bearer ${key}` }, signal: context.signal })
    if (!response.ok) throw new Error(`weather API answered ${response.status}: ${await response.text()}`)
    const data = await response.json()
    return { city: args.city, temperature_c: data.temp_c, conditions: data.conditions }
  },
}
```

</Step>
<Step title="Register it in kortix.yaml">

```yaml
env:
  optional: [WEATHER_API_KEY]
tools:
  weather_now: tools/weather_now.ts
agents:
  my-agent:
    tools: all                 # the default: every tool, weather_now included
    secrets: [WEATHER_API_KEY]
```

Then [test it](#test-a-tool).

</Step>
</Steps>

The default export is a plain object. It imports nothing from a harness.

| Field | Rule |
| --- | --- |
| `description` | A non-empty string. The model reads it to decide when to call the tool. |
| `parameters` | JSON Schema of the arguments, with `type: 'object'`. The model receives it as written, so list required arguments in `required`. pi checks the arguments against it before `execute` runs. Check required values in `execute` too. |
| `execute(args, context)` | May be `async`. Returns a string, or any JSON value, which the model receives as indented JSON. A thrown error is the tool result, and the model reads its message. |

`context` carries:

| Field | Value |
| --- | --- |
| `sessionId` | The Kortix session the call belongs to. |
| `agent` | The agent that made the call. |
| `directory` | The project checkout the session works in, `/workspace`. Resolve relative paths against it. |
| `env` | The sandbox environment plus the secrets this agent receives, with their current values. Read a secret as `context.env.NAME`. A secret changed after the sandbox started is in `context.env`, not in `process.env`. |
| `signal` | An `AbortSignal` that aborts when the turn stops. Pass it to `fetch`. |

- **Output size.** An output over 49 KiB or 1,990 lines is saved whole to a file in the sandbox temp directory. The model receives the head, the size, and the file path. Return what the model needs, not a raw dump.
- **Errors.** Throw a message that says what to change. The model reads it and can act on it.
- **Imports.** A module may import `node:*` modules, Bun APIs, and relative files. TypeScript runs without a build step. A package resolves only from a `node_modules` next to the module or above it. The sandbox installs no package for a tool, so use `fetch` for HTTP APIs.
- **Load failures.** A module that does not load is skipped, and the other tools still load. Causes: a missing file, no default export, `parameters` that is not an object schema, an error at import, or a package that does not resolve. The sandbox logs `[tools] project tools that did not load` with the reason for each tool.

<Callout type="info">
To write `parameters` with zod, print the schema once and paste the JSON into the module. An `import { z } from 'zod'` fails with `Cannot find package 'zod'` where no `node_modules` holds zod.

```bash
bun -e "import { z } from 'zod'; console.log(JSON.stringify(z.toJSONSchema(z.object({ city: z.string() })), null, 2))"
```
</Callout>

## Give each agent its tools

`agents.<name>.tools` decides which tools an agent's model sees. It names harness, Kortix, and project tools alike.

```yaml
agents:
  kortix:
    tools: all                                    # every tool (the default)
  researcher:
    tools: [read, grep, web_search, weather_now]  # only these
  support:
    tools:
      exclude: [bash, write, edit]                # every tool but these
  greeter:
    tools: none                                   # no tool
```

| Value | The agent gets |
| --- | --- |
| Omitted, or `all` | Every tool. |
| `none` | No tool. |
| A list | Only the tools listed. A list that contains `*` is `all`. |
| `{ exclude: [...] }` | Every tool except the ones listed. |

- **Visibility, not permission.** A hidden tool is also denied if the model calls it. For a visible tool, the agent's `permission` rules decide allow, ask, or deny. See [Agents & permissions](/docs/project/agents#ask-allow-or-deny).
- **Names.** Each name is a harness tool, a Kortix tool, or a tool registered under `tools:`. Any other name is an error. The legacy map form `{ bash: false }` is an error: use `{ exclude: [bash] }`.
- **Connector tools** follow `agents.<name>.connectors`, not this list. See [Connectors](/docs/connect/connectors).
- **Subagents.** On pi, a subagent gets only the tools that both its own list and the parent agent's list allow. On OpenCode, a subagent gets the tools of its own list. To stop an agent from delegating, leave `task` out of its list.
- **OpenCode groups.** On OpenCode, `bash` also covers the `pty_*` terminal tools. `write`, `edit`, and `apply_patch` share one permission: listing one shows all three, and excluding one hides all three. pi has separate `write` and `edit` tools.

### Agents without the project repository

An agent with [`workspace: { project_repository: false }`](/docs/project/manifest#kortix-access) has no checkout in `/workspace`. Its project tools still load. The sandbox receives only these files from the default branch:

- the module of each project tool the agent may call (`agents.<name>.tools`);
- every file those modules import by a relative path (`./lib/client`, `../data/regions.json`), followed transitively.

No other file of the repository reaches the sandbox. A tool the agent may not call ships no file. Lock an agent down with both settings:

```yaml
tools:
  lookup_order: tools/lookup_order.ts
agents:
  support:
    workspace:
      project_repository: false
    tools: [lookup_order, web_search]   # no bash, read, or write
```

- A package import (`import { z } from 'zod'`) does not resolve: no `node_modules` ships. Use `fetch` and `node:*` modules.
- `context.directory` is `/workspace`, which is empty for this agent.
- A change to a shipped file reaches running sessions as their config converges, like any tool change.

## Eject or override a Kortix tool

`kortix tools eject <name>` gives the project its own copy of a Kortix tool:

```text
$ kortix tools eject web_search
  ✓  Ejected web_search
  wrote   tools/web_search.ts (the Kortix source, now the project's to change)
  set     kortix.yaml: tools.web_search: tools/web_search.ts

Next:
  1. Edit tools/web_search.ts. Keep the default export: { description, parameters, execute(args, context) }.
  2. kortix validate
  3. git add tools/web_search.ts kortix.yaml && git commit -m "Own the web_search tool"
  4. Open a change request: git push origin HEAD && kortix cr open --title "Own the web_search tool"
Sessions load the copy after the change request merges.
```

In a local checkout, give `kortix cr open` the branch you pushed: `--head <branch>`. Inside a sandbox the CLI fills it in.

- It writes the source the sandbox runs to `tools/<name>.ts`. The copy imports only `node:*` modules, so it runs as it is. `web_search`, `image_search`, and `scrape_webpage` call the Kortix API with `KORTIX_API_URL` and `KORTIX_TOKEN` from `context.env`. `memory` and `show` work on files in the project checkout.
- It sets `<name>: tools/<name>.ts` in the file that declares the entry, the root file or an imported file. The line ends with `# ejected from kortix:<name>`. Other lines and comments stay.
- It refuses when `tools/<name>.ts` exists or when the tool already points at another module. `--force` overwrites.
- It refuses a name that is not a Kortix tool, and a project without `kortix.yaml`.

Kortix does not update an ejected copy. To override without a copy, point the Kortix tool name at any module of yours:

```yaml
tools:
  web_search: integrations/search/web_search.ts
```

The module replaces the Kortix tool on every harness. Keep the name, the arguments, and the output shape, so skills that name the tool and the web app's view of it still work.

To return to the maintained tool, delete the line and the module.

## Test a tool

A tool change reaches sessions when it reaches the default branch, usually through a [change request](/docs/git#change-requests). New sessions then load the change, and running sessions pick it up as their config converges. On pi, a change to a project tool restarts the runtime in place while no turn runs. The session keeps its messages. See [How a change takes effect](/docs/project#how-a-change-takes-effect).

<Steps>
<Step title="Validate">

`kortix validate` checks tool names and paths, and each agent's `tools` grant against the harness, Kortix and registered tools.

</Step>
<Step title="Check the list">

`kortix tools ls` shows each tool the project registers and each Kortix tool it overrides.

</Step>
<Step title="Merge">

Push a branch and open a change request on it: `git push origin HEAD:add-weather-now`, then `kortix cr open --head add-weather-now --title "Add weather_now"`. Merge it with `kortix cr merge <cr>` or on the [Review page](/docs/git#the-review-page).

</Step>
<Step title="Call it once">

```bash
kortix sessions new --wait --prompt "Call the weather_now tool once with city Berlin and print its output."
```

</Step>
<Step title="Read the result">

`kortix sessions log <session_id>` prints the session's messages, with each tool call, its status, and its output. A tool that did not load is not offered to the model. A tool that throws answers with its error message.

</Step>
</Steps>

## Tools in harness folders

A `kortix_version: 3` session does not read the `tools/` folder of an OpenCode config directory (`harnesses/opencode/tools/`, `.kortix/opencode/tools/`). To keep such a tool, port it to a project tool:

1. Move the file out of the folder, for example to `tools/<name>.ts`.
2. Replace `tool({ description, args, execute })` with the plain default export object. Write `args` as JSON Schema under `parameters`.
3. Read secrets from `context.env`.
4. Register it under `tools:` in `kortix.yaml`.
