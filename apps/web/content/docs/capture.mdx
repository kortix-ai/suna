Kortix Capture records a member's own computer: the screen (app, window title,
URL, on-screen text), input actions with screenshots, and audio when the
account's policy allows it. Kortix indexes the recordings into one timeline per
person.

Capture belongs to the **Kortix account** (your organization), not to a
project. One account has one Capture workspace: one switch, one policy, one set
of Capture roles. Devices sign in to the account.

## Turn Capture on

An account owner or admin turns Capture on for the account. It is off by
default. While it is off:

- every Capture route answers `403` with `code: "capture_disabled"`;
- a device cannot sign in or get storage credentials;
- nothing new is indexed.

From the API: `PATCH /v1/accounts/<account_id>/capture` with `{"enabled": true}`.
From TypeScript: `kortix.capture.account(accountId).workspace.setEnabled(true)`.

## Who sees what

Each member has a Capture role. The default comes from their account role; a
Capture admin can set a different one per person.

| Capture role | Default for | Reads | Writes |
|---|---|---|---|
| `admin` | account owners and admins | every member's devices, timeline and episodes, **People**, **Overview**, **Workflows**, the data API over the account | the policy, device overrides, Capture roles, workflow review, skill export, bulk export, run now |
| `viewer` | nobody (set it per person) | every member's devices, timeline and episodes, **People**, **Overview**, **Workflows**, the data API over the account | nothing |
| `member` | account members | their own devices, timeline and episodes, also through the data API | their own ranges |
| an agent | — | only the timeline of the person its private session acts for | nothing |

Every read of another member's data writes a `capture.member_view` entry to the
account's audit log; an account-wide read (all devices, **People**) writes
`capture.account_view`; an agent's read writes `capture.agent_read`. Turning
Capture on or off writes `capture.enable` or `capture.disable`; a role change
writes `capture.member_role`.

## The policy

The policy is one per account, with an optional override per device:

- layers: screen, actions, audio (audio is off until someone turns it on);
- personal-data masking on the device;
- an account-wide pause;
- retention on the device and in Kortix (`remote_days`, default 90);
- the notice the device shows the person being recorded.

Kortix publishes it to `orgs/<account_id>/policy.json` in the capture store,
where every device reads it. Kortix also enforces the layers when it indexes:
a device never widens the policy.

## Connect a device

1. Install the Kortix desktop app, or the standalone Kortix Capture engine.
2. Choose **Sign in with Kortix**. The browser opens `/capture/authorize` with
   a code.
3. Check that the code matches the app, then choose the account (only accounts
   with Capture on are listed). The device records into that account as you.

The device receives a revocable device token and, from it, short-lived storage
credentials for its own folder (`orgs/<account_id>/<device_id>/`) and read
access to the policy. Signing in again on the same computer reuses the device.
Forgetting a time range on the device removes it from Kortix too.

## Capture Intelligence

Kortix turns the timeline into the work it shows, in four layers.

| Layer | What it is | When it runs |
|---|---|---|
| **Episodes** | One task by one person: a label, goal, outcome (`succeeded`, `failed`, `abandoned`) and its apps. | When a detected activity session goes quiet for 15 minutes. |
| **Steps** | The ordered steps of an episode: a verb (`Open`, `Search`, `Create`, `Send`, …), the app, what it acts on, and the names of the values that change from run to run (`order_id`, `refund_amount`), never the values. | With the episode, in the same model call. |
| **Workflows** | A procedure people repeat, mined across people and weeks: the standard path, its variants with the decision that leads to each, and its stats. | 10 minutes after new episodes, and nightly. |
| **Skills** | A `SKILL.md` drafted from a workflow, reviewed by a person and published into a project. | When an admin chooses **Export as skill**. |

A saved range is a pinned episode: you said "this was one task".

**Workflow stats.** Runs per week (over the last 4 weeks), typical (p50) and
slow (p90) duration, people, success rate, and **determinism**: the share of
finished runs that follow a named path. The **automation score** is
`runs per week × p50 duration × determinism`, in hours a week. Workflows sort
by it.

**Review and export.** A workflow is `detected` until an admin reviews it
(edits its name, goal and steps) and `exported` once its skill is published.
The draft reads the stored workflow: its steps, its variants with their
conditions, the apps it needs, and its run count. Checks run before publishing:
every variant covered and named, no literal customer values. Publishing commits
`skills/<name>/SKILL.md` to the project's default branch. This is the only
place Capture touches a project.

**Use the data anywhere.** Capture has no chat of its own. Its data is an API:
see [Kortix Capture API](#kortix-capture-api). A script, a notebook or an agent
with a Kortix API key reads it and does the analysis.

**Bulk export.** Admins export episodes, steps and workflows as JSONL (any
tables in one file) or Parquet (one table per file). The export runs in the
background; the download is a signed URL valid for 1 hour.

**Run now.** Admins can queue the pipelines at once
(`POST /v1/accounts/<account_id>/capture/intelligence/run`) instead of waiting
for the next quiet session or the nightly run.

### Privacy and cost

- Only masked text reaches the model: emails, phone numbers, IBANs and long
  digit runs are replaced before the call, and labels, goals, outcomes and
  steps are cleaned of ids and numbers after it.
- The model is Kortix's managed open-weight model through the Kortix LLM
  gateway, billed to the account. Every episode and workflow stores the model
  and its cost. Spend is capped per account per UTC day
  (`KORTIX_CAPTURE_DAILY_COST_CAP_USD`, default 5 USD). Work over the cap waits
  for the next day.
- **Forget reaches everything derived.** When a person forgets a time span on
  the device, Kortix deletes the episodes and steps over it, rebuilds the
  workflows they fed from their remaining runs, expires every finished export
  of the account, and traces the span again without the forgotten item. A
  skill already published into a project is a commit in that project's history
  and stays there; it holds variable names, never values.
- Raw recordings expire with the policy's `remote_days`. Episodes, steps,
  workflows and skills stay.

### How well it works

Measured on a synthetic dataset with ground truth: 6 people, 15 workdays, 7
recurring workflows with 1 or 2 variants each, interruptions and abandoned
runs, 657 runs, ingested through the real device path and processed with the
real gateway (`apps/api/scripts/capture-intelligence/`):

| Measure | Result |
|---|---|
| Runs found as episodes | 99.5% (mean overlap 0.96) |
| Workflows recovered | 7 of 7, no extra workflows |
| Runs put in the right workflow (pairwise F1) | 0.98 |
| Variants recovered | 92% |
| Step sequence vs. truth (verb@app) | 0.89 |
| Model cost | 0.0015 USD per person-day |

## Kortix Capture API

Everything Capture records and learns is readable with a Kortix API key, from a
script, a notebook, a BI tool or an agent.

**Auth.** Create a key in Kortix (Settings → API keys) or with
`POST /v1/accounts/tokens`. Send it as `Authorization: Bearer kortix_pat_…`.
The key acts as you: the same Capture role, the same scoping, the same audit.

**Base URL.** `https://<your Kortix API>/v1/accounts/<account_id>/capture`.
`GET /v1/accounts` lists your accounts; `GET …/capture` answers
`{ "enabled": true, "role": "member" | "viewer" | "admin", "can_manage": false }`.

**Scoping.** A member reads only their own recordings. A Capture admin or viewer
may pass `user_id=<member>` (audited as `capture.member_view`) or, where the
route takes it, `scope=account` for every member (audited as
`capture.account_view`). A read outside your role answers `403`
`capture_forbidden`; while Capture is off, every route answers `403`
`capture_disabled`.

| Endpoint | Returns |
|---|---|
| `GET search?q=refund or invoice&kinds=screen,actions,audio&app=&from=&to=&limit=20&scope=account` | hits, newest first: `{ kind, id, ts, user_id, device_id, chunk_id, app, title, url, snippet }` (one screen hit per chunk and window; `limit` up to 100) |
| `GET timeline/items?from=&to=&user_id=&device_id=` | `{ frames, actions, audio }` in a window of at most 31 days, oldest first, at most 500 of each |
| `GET frames/<frame_id>` | `{ frame, video: { url, expires_at, offset_ms }, screenshot: { name, ts, url, expires_at } }`: the full on-screen text, the 1 fps chunk video to seek, the nearest action screenshot (signed URLs, 5 minutes) |
| `GET chunks/<chunk_id>/media` | signed URLs of an item's video or audio |
| `GET episodes?scope=account&workflow_id=&from=&to=&limit=50&before=` | `{ episodes, next_before }`: tasks with label, goal, outcome, apps, duration, `workflow_id`, `variant_key`; pass `next_before` back as `before` |
| `GET episodes/<episode_id>` | one episode with its ordered `steps` (`verb`, `app`, `object`, `params`, `variables`) |
| `GET workflows?status=&q=&app=&sort=hours&limit=20&offset=` | admins and viewers: workflows with runs/week, p50/p90 duration, people, success rate, determinism, `automation_hours_per_week` |
| `GET workflows/<workflow_id>` | the standard steps, variants (`name`, `share`, `differs`, `question`), and `people` (`user_id`, runs, typical duration) |
| `GET overview?from=&to=` | admins and viewers: hours recorded, people, devices, automatable hours a week, top and new workflows, 12-week trend |
| `POST exports` `{ "format": "jsonl" \| "parquet", "include": ["episodes","steps","workflows"], "from", "to" }` · `GET exports/<export_id>` | admins: a background export (Parquet holds one table); when `status` is `done`, `download.url` is valid for 1 hour |

People: `user_id` resolves to a name and email through `GET /v1/accounts/<account_id>/members`, which every member of the account may read.

Example:

```bash
curl -s -H "Authorization: Bearer $KORTIX_API_KEY" \
  "https://<your Kortix API>/v1/accounts/$ACCOUNT/capture/workflows?sort=hours&limit=5"
```

```json
{ "workflows": [ { "workflow_id": "…", "name": "Refund a damaged-order claim", "runs_per_week": 46.1,
  "duration_p50_s": 198, "people_count": 3, "automation_hours_per_week": 2.45, "status": "detected" } ],
  "counts": { "all": 7, "detected": 7, "reviewed": 0, "exported": 0 } }
```

The TypeScript SDK wraps the same routes: `kortix.capture.account(accountId)`
(see [SDK → reference](/docs/sdk/reference)).

## Agents in a session

An agent in a member's private session can search that member's timeline with
`kortix capture search`, `timeline` and `frame`. It reads only that person, in
the session's account. A trigger run or a shared session acts for no person and
gets `403 capture_no_human`.
