title: Capture
description: Record each member's screen, input actions and audio 24/7 into a searchable timeline that belongs to the Kortix account.
---

Kortix Capture records a member's own computer 24/7:

- the screen: video, the app, the window title, the URL and the on-screen text;
- input actions (clicks, typing) with a screenshot of each;
- audio, with a transcript, when the account's policy turns it on.

Kortix indexes the recordings into one timeline per person. You can rewatch
any moment and search all of it. Capture v1 is raw capture: it records,
uploads and indexes. It does no further processing.

Capture belongs to the **Kortix account** (your organization), not to a
project. One account has one Capture workspace: one switch and one policy.
Devices sign in to the account.

## Turn Capture on

A person with the `capture.manage` permission turns Capture on for the
account. Account owners and admins have it. Capture is off by default. While
it is off:

- every Capture route answers `403` with `code: "capture_disabled"`;
- a device cannot sign in or get storage credentials;
- Kortix indexes nothing new.

From the API: `PATCH /v1/accounts/<account_id>/capture` with `{"enabled": true}`.
From TypeScript: `kortix.capture.account(accountId).workspace.setEnabled(true)`.

## Record on your computer

Each member turns recording on for their own computer. Capture never starts on
a computer by itself.

1. Install the Kortix desktop app, or the standalone `kortix-capture` engine.
2. In the desktop app, open **Capture → This computer** and turn recording on.
   With the engine alone, run
   `kortix-capture sync setup --provider kortix --issuer <your Kortix API>`.
3. Approve the sign-in. The browser opens `/capture/authorize` with a code.
   Check that the code matches, then choose the account. Only accounts with
   Capture on are listed.
4. Grant the macOS permissions when asked: Screen Recording for the screen,
   Accessibility and Input Monitoring for actions, Microphone for audio.

The device records into that account as you, 24/7, and uploads every finished
item. It gets a revocable device token and, from it, short-lived storage
credentials for its own folder (`orgs/<account_id>/<device_id>/`) and read
access to the policy. Signing in again on the same computer reuses the device.
Forgetting a time range on the device removes it from Kortix too.

## Who sees what

Access is Kortix IAM. Capture has no roles of its own.

| Who | Reads | Writes |
|---|---|---|
| Every member | their own devices and timeline | revokes their own devices |
| `capture.read_all` | every member's devices and timeline, and account-wide search | nothing |
| `capture.manage` | the workspace and the policy | the switch, the policy, revokes any device |
| An agent | only the timeline of the person its private session acts for | nothing |

Account owners and admins have `capture.read_all` and `capture.manage` by
default. To give either one to someone else, add it to a custom role
(**Account → Roles**, area **Capture**). A Kortix API key acts as the person
who made it, with the same permissions.

Every read of another member's data writes `capture.member_view` to the
account's audit log. An account-wide read (all devices, account search) writes
`capture.account_view`. An agent's read writes `capture.agent_read`. Turning
Capture on or off writes `capture.enable` or `capture.disable`.

## The policy

One policy applies to every device of the account:

- layers: screen, actions, audio (audio is off until someone turns it on);
- personal-data masking on the device;
- mandatory exclusions: apps, websites, the categories password managers,
  messaging and banking, and private browsing. Password managers and private
  browsing are excluded by default. A device adds them to the member's own
  exclusions, which stay on that computer; the member cannot remove the
  account's;
- an account-wide pause;
- retention on the device and in Kortix (`remote_days`);
- the notice the device shows the person it records.

Kortix publishes the policy to `orgs/<account_id>/policy.json` in the capture
store, where every device reads it. A device cannot write a policy of its
own. Kortix also enforces the layers when it indexes: a device never widens
the policy.

A device records every connected display, the active one (the display with
the focused window) first. Each display is its own recorded item; the
timeline names the display of every item and frame.

## Kortix Capture API

Everything Capture records is readable with a Kortix API key, from a script, a
notebook, a BI tool or an agent.

**Auth.** Create a key in Kortix (Settings → API keys) or with
`POST /v1/accounts/tokens`. Send it as `Authorization: Bearer kortix_pat_…`.

**Base URL.** `https://<your Kortix API>/v1/accounts/<account_id>/capture`.
`GET /v1/accounts` lists your accounts.

**Scoping.** Every route reads your own data by default. With
`capture.read_all`, pass `user_id=<member>` (audited as `capture.member_view`)
or, where the route takes it, `scope=account` for every member (audited as
`capture.account_view`). A read outside your permissions answers `403`
`capture_forbidden`. While Capture is off, every route answers `403`
`capture_disabled`.

| Endpoint | Returns |
|---|---|
| `GET /` | `{ account_id, enabled, can_read_all, can_manage, updated_at }` |
| `PATCH /` `{ "enabled": true }` | the same; needs `capture.manage` |
| `GET devices?user_id=&scope=account` | devices with their live state: what the device last reported (for example `recording`, `paused`), or `offline` after 2 minutes of silence |
| `DELETE devices/<device_id>` | revokes the device: its token stops working at once |
| `GET devices/<device_id>/assets/<name>` | a signed URL of one action screenshot (5 minutes) |
| `GET policy` · `PUT policy` `{ "policy": { … } }` | the account policy; writing needs `capture.manage` |
| `GET days?tz=Europe/Berlin&user_id=&device_id=` | the days with recordings, newest first, in a time zone |
| `GET timeline?day=&from=&to=&user_id=&device_id=&display_id=` | `{ displays, focus, runs, chunks }`: the displays seen, which display held the focus when, app and window runs (of the focused display, or of `display_id`), and the indexed items, in a window of at most 31 days |
| `GET timeline/items?from=&to=&user_id=&device_id=&display_id=` | `{ frames, actions, audio }`, oldest first, at most 500 of each; `display_id=all` for every display |
| `GET search?q=refund or invoice&kinds=screen,actions,audio&app=&from=&to=&limit=20&scope=account` | hits, newest first: `{ kind, id, ts, user_id, device_id, chunk_id, display_id, display_name, app, title, url, snippet }` (one screen hit per chunk and window; `limit` up to 100) |
| `GET frames/<frame_id>` | `{ frame, video: { url, expires_at, offset_ms }, screenshot }`: the full on-screen text, the 1 fps chunk video to seek, the nearest action screenshot (signed URLs, 5 minutes) |
| `GET chunks/<chunk_id>/media` | signed URLs of an item's video or audio |

`user_id` resolves to a name and email through
`GET /v1/accounts/<account_id>/members`, which every member of the account may
read.

Example:

```bash
curl -s -H "Authorization: Bearer $KORTIX_API_KEY" \
  "https://<your Kortix API>/v1/accounts/$ACCOUNT/capture/search?q=invoice&limit=5"
```

The TypeScript SDK wraps the same routes: `kortix.capture.account(accountId)`
(see [SDK → reference](/docs/sdk/reference)).

## Agents in a session

An agent in a member's private session reads that member's timeline through
`/v1/capture/me/search`, `/v1/capture/me/timeline` and
`/v1/capture/me/frames/<frame_id>`, or with `kortix capture search`,
`timeline` and `frame`. It reads only that person, in the session's account. A
trigger run or a shared session acts for no person and gets `403`
`capture_no_human`.
