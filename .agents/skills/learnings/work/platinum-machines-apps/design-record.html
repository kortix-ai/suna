Summary

Build the machine platform in Platinum, name its core object Machine, and keep Kortix Apps as a thin product layer on top. Nothing is built yet. 7 decisions are open (section "Open decisions").

  1. Kortix Apps (apps/api/src/apps/, 12,765 non-test lines) already has most of Fly's App model: releases, machines, process groups, deploy strategies, volumes. It runs the machine layer itself, two proxy hops in front of the VM.
  2. Platinum Apps (/v1/apps, about 1,180 lines) is an experimental prototype: one VM per App, HTTP only, flag off by default.
  3. Fly is the right model for the App layer and for speed. It is the wrong model for the machine. A Fly Machine's root filesystem resets on restart, and its volumes are pinned to one host.
  4. The machine contract = a regular cloud VM (EC2 class), plus what only Platinum has: stop that keeps memory, fork, live resize, point-in-time volume restore, credentials kept outside the VM.
  5. One VM object, named Machine. "Sandbox" becomes a preset of a Machine and a compatibility name for the API.
  6. Storage separate from compute. A Machine is the durable identity. An Instance is the disposable VM on one host. Two storage modes: local and volume.
  7. The split. Platinum owns machines, proxy, network, volumes, regions and domains. Kortix owns kortix.yaml, access, App events, display and templates. About 4,855 lines of Kortix machine-layer code move to Platinum or are deleted.

Kortix Apps today

Kortix Apps is the working implementation: 12,765 non-test lines in apps/api/src/apps/, 68 commits since 2026-09-01. It runs on Platinum sandboxes but runs its own machine layer in the Kortix API. The App model is written for agents in packages/starter/templates/managed/skills/kortix-apps/references/apps-model.md.

How it runs on Platinum

  1. Build: the deployment worker builds a Platinum template. Images are shared per set of build inputs (kortix-appimg-<env>-<key>). A quota guard handles Platinum's per-org template cap (10, 50 or 500 by tier).
  2. Create: one Platinum sandbox per instance. It publishes the appd control port and ingress port, gets KORTIX_APPD_TOKEN, and mounts its volumes. An always-on App sets autoStopInterval: 0.
  3. Request path: client → Cloudflare → Kortix API public proxy (public-proxy-handler.ts: access gate, wake through ensureAppRuntimeRunning, activity record) → Platinum preview ingress → host edge → appd ingress → the app.
  4. Lifecycle loops in the Kortix API: the idle reaper stops machines past idle_deadline_at. The keep-alive pass runs every 5 minutes for always-on groups. A failed upstream fetch triggers a provider recovery and a retry.

Known problems

  1. Wake under load. On 2026-10-15, 212 parallel GETs to a running App returned 142×200, 56×202 app_starting and 14×503. The App's Next.js page rendered blank until a reload. The issue is still open.
  2. Latency. On 2026-10-11, dev added about 300 ms per request between edge and origin (dev 380–460 ms, prod 80–180 ms for a 1 ms /health).
  3. No real suspend. suspend acts as stop, and Kortix documents a stop as losing memory.
  4. No TCP. protocol: tcp is refused. A database that speaks raw TCP is reachable only from inside its own machine.
  5. No private networking between Apps.
  6. Volumes. Fixed at 100 GB with no grow. A group with a mount runs one machine (409 volume_single_machine).
  7. Missing: regions, custom domains, load balancing by concurrency, autoscaling.

Data model

  • apps: slug (unique per org, becomes <slug>.apps.<domain>), source (jsonb), build_env, runtime_env (secret values encrypted), port, health_path, cpu, ram_mb, disk_gb, region, current_deployment_id, current_sandbox_id, state (created|deploying|running|degraded|stopped|failed).
  • app_deployments: seq, template_id, sandbox_id, env_snapshot, status (building|booting|healthy|live|superseded|failed).
  • git_connections: kind pat or github_app_installation.
  • The module adds no column to sandboxes or templates. An App's real state is a template row (the build) and a sandbox row (the VM). Billing, backup, host-loss failover and audit come with them.

Sources

  • image: pinned references only. Floating tags such as latest are refused.
  • source: a build context in S3 plus a Dockerfile.
  • git: clone, then a Dockerfile if one exists, else nixpacks framework detection. Private repos work through an encrypted token or a git_connections row. POST /v1/apps/:id/git-push also exists.

Routes

POST /v1/apps, GET /v1/apps, GET|PATCH|DELETE /v1/apps/:id, POST /:id/deploy, GET /:id/deployments, GET /:id/deployments/:d, POST /:id/rollback, POST /:id/stop|start|restart, GET /:id/logs, and the connection routes (/connections, /github/install, /github/callback).

Rollout (rollout.ts)

  1. Build a template through an in-process call to the templates route. Wait up to 15 minutes for ready.
  2. Boot a persistent sandbox: auto_stop_minutes: 0, PORT set to the App port, the port exposed publicly, warm pool skipped. Wait for running.
  3. Probe the health path from inside the guest with curl, wget or a raw /dev/tcp GET. Any status from 200 to 499 passes. Timeout: 120 s.
  4. Flip current_deployment_id and current_sandbox_id in one UPDATE.
  5. Delete the old VM.

On failure the live release keeps serving, and the template built for the failed attempt is deleted. Traffic reaches the VM through platinum/apps/api/src/sandboxProxy.ts:183, which joins the slug to current_sandbox_id.

Limits

  • One VM per App: no machines, no process groups, no scale.
  • HTTP only. No volumes. No auto stop/start.
  • Deploys are not durable. POST /:id/deploy calls void deploy(...) inside the API process. An API restart in the middle of a deploy leaves the deployment in building.

Is Fly the right reference

Fly is the right reference for two things: the App layer (releases, process groups, proxy, auto stop/start) and speed. It is the wrong reference for the machine itself. For the machine, the reference is a regular cloud VM (EC2, GCE, Hetzner Cloud). Platinum already beats both on stop/start with memory, fork, live resize and secrets. It loses on the networking basics and on volume size.

The Fly facts below are from Fly's public docs as known on 2026-10-29, not re-checked that day. The Platinum facts are from platinum origin/main.

The target contract: a regular VM, and more

A regular VM gives you:

  • a persistent root disk;
  • a stable private IP and DNS name inside the org;
  • an optional dedicated public IP with every port, TCP and UDP;
  • inbound firewall rules;
  • SSH;
  • user-data at boot;
  • volumes you can attach and grow;
  • images and snapshots;
  • a choice of region.

"And more" is what Platinum already has and neither EC2 nor Fly has:

  • stop/start that keeps memory and processes, in under 1 s;
  • fork of a running VM;
  • live CPU/RAM resize;
  • point-in-time volume restore from commits;
  • credentials injected outside the VM;
  • an exec, files and managed-processes API that agents can drive.

Design rule: an App is only Machines plus proxy config. Anything an App does must also work through the raw Machine API. This is Fly's best idea, and it keeps the App layer thin.

Naming and object model

Name the core object Machine. Keep one VM object. "Sandbox" becomes a preset of a Machine and stays as a compatibility API name. An App is a named group of Machines, the same split Fly makes between Fly Machines and Fly Apps.

Names considered

Name Verdict Reason
Machine Use The standard term: Fly Machines, GCE machine types, Kortix Apps machines. It describes what the object is, not how it is built.
VM No It names how the object is built. Platinum also has a second runtime (cell, /v1/workers) that is not a VM.
Compute unit No Vague, and it sounds like a billing unit.
Sandbox Keep as a preset and a compatibility name The word agent buyers search for. platinum/docs/POSITIONING.md sells "existing sandbox SDKs work with a base-URL + key swap".

Terms in use today for one concept

Where Term
Platinum API sandbox (sbx_ ids, /v1/sandboxes)
PTXP box
Kortix Apps machine, plus instance (the app_runtimes table)
Kortix sessions session (session_id == sandbox_id)

One term removes this split.

One VM object, no new type

A sandbox and a 24/7 Postgres differ only in their defaults: auto-stop, auto-delete, backups, restart policy and storage mode. A second VM type would mean two schedulers, two billing paths and two lifecycle state machines for one hypervisor. The Platinum Apps prototype already builds on sandbox rows, which is correct.

Presets of one Machine

A sandbox and a persistent Machine are one object with two sets of defaults. Sandbox: local storage, auto-stop and auto-delete on, agent tools (exec, files, processes). Persistent: volume storage, no auto-delete.

The preset names and their exact fields are not decided.

Machines vs Apps

Fly has both. A Fly Machine is the VM API. A Fly App is a named group of Machines that share releases, config, secrets, IPs, certificates and proxy routing. A Fly App runs no compute of its own. Platinum should copy this split.

A Kortix App then becomes a Platinum App, plus what only Kortix has: the access gate and sign-in, App events, uses bindings, display, templates and IAM.

Storage separate from compute

Separate storage from compute inside the one Machine object. Platinum already runs most of this model: PTXP boxes boot from a root volume, and their compute is disposable. The one real gap is that a Machine booted from a volume never keeps memory across a stop.

The model

  • Machine = the durable identity and config: id, name, private IP and DNS name, image, size, volumes (root and data), network rules, secrets.
  • Instance = the disposable compute: one VM on one host. It is created on start. It is replaced on host loss, migration or a move to another region.
  • Memory snapshot = a cache that speeds up a start. It is not where state lives.

Kortix Apps already has this split: a stable machine_id, and one app_runtimes row per instance.

Evidence that Platinum has most of it

  • root_volume: a sandbox can boot from a volume (platinum/docs/sandboxes.md:382). PTXP boxes run this way.
  • Work volumes are committed to S3 about every 5 s and can be restored on any host (measured 2026-10-14 on dev).
  • Cross-host migration and host-loss failover exist (platinum/docs/FEATURES.md §3, §6).

What it buys

  • A host failure becomes a restart on another host with no data loss. Fly is weak here: its volumes are pinned to one host.
  • A move between regions becomes a restart somewhere else.
  • Scale to zero leaves nothing on a host.

The gap

A Machine that boots from a volume never saves memory on stop: "Sandboxes that boot from a volume (root_volume) never save memory, so their stops are always false" (platinum/docs/sandboxes.md:382). The fix: a stop that saves the root volume commit and the memory image together, consistently. With it, the durable mode starts as fast as the sandbox mode.

Two storage modes of one object

Mode Root disk Use Today
local Fast local disk on the host Disposable sandboxes, agent runs Today's sandbox
volume A volume, detachable, restorable anywhere Servers, databases, dev boxes Today's root_volume and PTXP

The cost of volume mode is disk I/O over the network. Ephemeral sandboxes keep local so they lose no speed.

Out of scope

  • Stateless compute in the Lambda sense (request-scoped, no state). platinum/docs/POSITIONING.md already says Platinum is not the answer for stateless function compute. The cell runtime (/v1/workers, behind flags.cell_runtime_enabled, default false, platinum/apps/api/src/config.ts:753) covers that case.
  • An App that scales to zero covers most of the same need.

Split of work and build order

Platinum owns everything on the byte path and everything that touches a VM. Kortix owns the product layer. The reason: wake-on-request, load balancing, private networking and TCP must sit at the host edge. Kortix runs wake in its API, two hops before the VM, which causes the 202 app_starting bug and about 300 ms of extra latency on dev.

Today a request crosses Cloudflare and the Kortix API before it reaches Platinum. In the target, the host edge does the gate, the wake and the balancing, one hop before the VM.

Kortix code that moves to Platinum or is deleted

11 files, 4,855 lines in apps/api/src/apps/: machines.ts, fleet.ts, fleet-routes.ts, idle-reaper.ts, public-proxy-runtime.ts, public-proxy-handler.ts, volumes.ts, volume-store.ts, images.ts, hosting.ts, deployment-worker.ts. Parts of these files stay in Kortix: the access gate inside the proxy handler, and the kortix.yaml translation inside the deployment worker.

Build order

  1. Proxy at the host edge: wake, load balancing, concurrency limits, idle stop. This fixes the app_starting bug.
  2. Private network and .internal DNS between Machines, across hosts.
  3. TCP services in Apps. Platinum already has TCP expose; this connects it to App services.
  4. Real suspend: connect App stop to memory_saved. Also fix the memory save for volume mode.
  5. Real public IPs: a dedicated IPv4/IPv6 per Machine or per App, every port, TCP and UDP. Today a game server needs an SRV record that points to a random port.
  6. Inbound firewall rules per Machine.
  7. Volumes: a chosen size, growth, and attach/detach while running. Platinum gives every volume a fixed 100 GB today.
  8. Custom domains and certificates.
  9. Regions: Machines placed in several regions, and a move between regions through a snapshot.
  10. Autoscaling by load.

Items 1–4 were the first proposed batch: one Platinum branch plus one Kortix branch. Whether to build all 10 is open decision 4.

Rename cost, migration path and risks

The safe path: /v1/machines becomes the main API, and /v1/sandboxes stays as an alias served by the same handlers. No client breaks.

Surfaces the rename touches

  • /v1/sandboxes and the sbx_ ids;
  • the TS and Python SDK Sandbox classes (83 files in Platinum's SDK, CLI and MCP packages mention "sandbox");
  • the pt sandbox CLI;
  • the MCP tool names (sandbox_create, sandbox_delete, …);
  • the sandbox.* webhooks and the sandbox.uptime billing events;
  • the DB tables;
  • Kortix's Platinum provider code and session_id == sandbox_id;
  • the Daytona-compatible surface (x-daytona-preview-token, "base-URL + key swap").

Parked idea: layered primitives and a bare-metal marketplace

Status: unproven, long-term idea from 2026-10-29. Not a plan. Nothing is decided, researched or built. Marko asked to keep it for later: decouple everything into base primitives, put Apps and similar products on top, and let users buy bare-metal CPU and GPU servers from many providers in one click through Platinum.

Four layers

Each layer uses only the public API of the layer under it. Kortix is an ordinary customer of L2, which proves the primitives are complete.

Image A bootable root filesystem from a Dockerfile, OCI image, git repo or spec /v1/templates
Snapshot Memory plus disk at one point in time; a source for restore and fork Sandbox snapshots
Network A private network per org, plus DNS (<name>.internal) None
Endpoint Ingress: HTTP host, TCP/UDP port, IP, domain plus certificate, access rule. Targets Machines by label. Does wake-on-request, balancing and idle stop. expose per sandbox (HTTP + TCP)
Secret A credential injected on egress, never stored in the VM /v1/secrets

The key move: the host-edge proxy is the Endpoint primitive, so an App needs no proxy of its own. These are not primitives: App, Database and Cron (compositions), GPU (a Machine field), Sandbox (a Machine preset), Workspace (a Machine plus volumes). Contracts that apply to every primitive: identity and scoped keys, durable operations, events, metering, audit, quotas, placement.

Composites (L2)

Composite Turns into Use
App Machines per process group, Endpoints, release history, deploy strategy Web apps, APIs, bots
Job One Machine that runs to exit, with retries Migrations, batch, agent tasks
Schedule A cron or interval that starts a Job or calls an Endpoint Nightly reports, polling
Function The cell runtime (/v1/workers, behind a flag) Request-scoped handlers
Workspace A Machine with a root volume, a home volume and a Network PTXP dev boxes
Template A parameterized bundle of specs Postgres, Redis, Convex, GPU apps

A composite labels every child it creates (owner: app/web). The user can see, exec into and detach each child.

DX principles

  1. One resource model for the API, TS/Python SDK, pt CLI, MCP and dashboard, generated from one OpenAPI.
  2. Declarative and imperative on one API: pt apply shows a plan and applies it; pt machine run acts now. Both upsert by name.
  3. Names, not IDs, in specs: volume: pg-data, db.internal.
  4. An escape hatch at every level: App → Machines → exec or SSH.
  5. Durable operations with an id that can be waited on, streamed and cancelled.
  6. Every state change is an event (webhook and stream). Composites react to events.
  7. Templates are data and can be shared.
  8. Agent-first: MCP tools map 1:1 to primitives; every write has a dry-run plan; every error has a code and a fix.

Bare-metal marketplace

Marko's framing: "u can easy 1 click buy through us all aggregated baremetal from all the various providers, so u can easy buy CPU". It covers CPU and GPU servers from providers such as OVHcloud, Scaleway and Latitude.sh.

The one-click flow:

  1. Catalog: one list of offers from all providers in one shape: CPU model and family, cores, RAM, disk, GPU model and count, region, delivery time, minimum term, price.
  2. Buy: pick an offer and a target pool, then pay.
  3. Order: Platinum orders the server through the provider's API and waits for delivery.
  4. Install: Platinum installs its host image (pinned guest kernel) and registers the host into the org's pool with a bootstrap token.
  5. Burn-in: a check of CPU, RAM, disk and GPU passthrough before the host is ready.
  6. Use: Machines land on it with pool: <name>, or the pool becomes the org's default.
  7. End of life: Platinum drains the host, then cancels or renews the server.

Whose account places the order:

On Platinum's account (Platinum sells) On the user's connected account
UX True one click, one bill One click after the user connects each provider account
Who pays the provider Platinum, which bills the user from credits The user; Platinum charges a platform fee
Platinum's risk The server term, abuse (mining), payment default None on hardware
Needs Reseller terms per provider, ID checks on users Only the API integration

Hard constraints:

  • Memory snapshots do not cross CPU families. A family is vendor plus CPU class plus region, and the control plane refuses a cross-family migration. Fork, suspend and migrate with memory stay inside one family; volume mode moves anywhere. Offers must show their family.
  • A template boots only on a host with the same guest kernel (templates.guest_kernel). The install must pin the host image.
  • Bare metal arrives in minutes to days, so "create a Machine now" must use existing capacity.
  • Most dedicated servers bill monthly while Machines bill per second. Someone carries the unused hours.
  • A private network across providers needs an encrypted overlay and costs egress per provider.
  • GPU offers need boards that support passthrough. Check this per SKU.

Not verified: which providers have an ordering API, bill by the hour, deliver fast, sell GPUs, allow resale, or verify identity on signup. Everything above about providers is from memory.
